排障、验证与软件工程

T104 原理问答

CPU 很高、内存增长、延迟变大分别怎么定位？

性能排障先判断系统在计算、等待 CPU、等待锁还是等待 I/O，再针对瓶颈收集证据。CPU、内存和延迟不是孤立指标，队列积压可能把三者同时推高。

原理与成立条件

先把“慢”变成明确指标

区分吞吐、响应平均值、p99、最大延迟和超时率，再标明输入负载与统计区间。端到端延迟可拆为排队、运行、I/O 等待及协议往返；CPU 利用率低只说明总体忙碌比例低，不排除某个线程长时间等待锁或某一次回调阻塞全部事件。

CPU 高时如何缩小范围

按进程、线程找到热点，再用采样看函数和调用链。热点可能是有意义计算，也可能是 EAGAIN 忙轮询、可写空转、重试风暴或日志格式化。将采样结果与每轮处理量关联；仅看到某函数采样多，不能断言它每次调用都慢，调用次数也可能很多。

内存增长如何分类

区分不可达对象泄漏、仍可达的队列积压、缓存策略和分配器保留。观察入出速率、对象数量与容量高水位，关闭负载后是否回落，再结合内存工具。RSS 不等于所有活对象字节总和，虚拟内存大小更不能直接当真实占用；不同平台要选适用统计。

优化实验怎么有说服力

固定固件/程序版本、编译参数、输入种子与环境，一次只改变关键因素，记录失败、尾延迟和资源成本。主机 Sanitizer 用于正确性，不能直接作为生产性能测量环境。MCU 通过 GPIO、DWT 或跟踪观察，注意探针与 printf 自身改变时序。

推演与反例

高 CPU 和慢响应怎样分开

用线程级 CPU、调用栈采样和系统调用观察，区分计算热点、EAGAIN 忙循环、锁竞争和频繁唤醒。CPU 不高仍慢时，检查阻塞调用耗时、调度等待、磁盘与网络队列。不要先把所有锁换无锁：若根因是数据库每行提交或串口带宽，改锁可能无益还增加复杂度。

内存增长先看对象生命周期

区分真正泄漏、队列增长、缓存保留、分配器未归还 OS 和碎片。结合活对象数量、队列深度、峰值输入及 RSS 曲线，判断是否随压力回落。记录吞吐与延迟分位数、最大值和超时率，比单个平均值更能反映突发问题；观测代码自身也应有开销预算。

继续追问

从 20% CPU 降到 10% 可以说性能翻倍吗？

不能。它只说明该条件下 CPU 占用变化，还需看吞吐、延迟、能耗和资源约束；业务响应可能完全没变，甚至因更大批量而变慢。

优化前后只看一组平均值够吗？

不够。需要相同输入、配置、环境和测量口径，并看尾延迟、资源峰值及错误率是否恶化。代码级推测不能直接写成已取得的性能提升。

依据与核对范围

Linux Kernel：Perf events — 性能事件采样与权限；性能诊断方案由本文组织。

proc(5) — 进程、内存与运行期诊断入口。

strace 官方文档入口 — 系统调用、信号与进程跟踪。

T105 原理问答

一个请求超时，如何分层定位并判断远端是否已执行？

请求超时的排查应沿同一请求身份逐段找最后一个确定进展点：接纳、入队、本地写出、对端接收、执行、结果返回、上层交付。每一层都要区分明确失败与结果未知。

原理与成立条件

从关联标识开始

一条命令应能在入口、接纳、发送、远端接收、执行、结果和上报各阶段被关联。记录业务 ID 与会话/序号、阶段时间和失败原因；缺少关联时，日志里看见一个“ACK”也可能是另一条或上一代命令，排障容易沿错误路径推测。

按最后确定的事实推进

若 MQTT 回调未收到，查连接、订阅和主题；收到但未接纳，查队列与窗口；已写但无节点接收，查波形、UART 错误、DMA 与解析；已接收无结果，查执行顺序、传感器等待及缓存；已收到结果但云端没有，查结果发布及其确认。每层都问“哪一步有证据”。

区分期限来源

超时可能是本地排队寿命、接收重传耗尽、业务结果期限、设备 HAL 超时或 MQTT 连接超时，含义不同。增加一个总 timeout 只会推迟所有错误暴露。先画实际事件时间线，核对每个计时起点及是否被重试重置，再决定阈值是否合理。

复现必须控制故障位置

有选择地丢命令、ACK 或结果，制造传感器卡线、数据库变慢和旧回调延迟，比较状态迁移是否符合预期。故障注入要限定环境并记录恢复，不能靠随机拔线后只看最终恢复就宣称所有中间结局正确。重试期间还要检查是否重复产生业务效果。

推演与反例

为什么统一请求身份很重要

串口序号、会话、云端业务 ID 与一次发送尝试不是同一个编号。若日志只写“超时 seq=3”，重连后另一个 seq=3 可能混进分析。记录身份、单调时间戳与状态变化，才能看出是排队超时、重传计时过早、节点慢业务还是结果 ACK 丢失。墙上时间用于跨系统对齐时还要考虑时钟同步误差。

定位最后一段已证实的事实

若线路上看见完整命令而节点 RX 计数不增长，优先查硬件/驱动；若解析成功但执行未开始，查窗口缺口和锁；若动作已完成而网关没结果，查结果队列、缓存和返回链。证据应逐层收窄，不要每轮同时改波特率、超时和优先级，否则即使恢复也无法知道原因。

继续追问

用户看到 timeout 后设备状态却已改变，是不是协议一定错了？

可能是执行成功而结果丢失，属于分布式不确定结局。协议应清楚报告这类边界并提供查询/幂等策略，不能仅凭超时保证撤销。

超时日志里最该避免哪种措辞？

把“没有收到结果”写成“设备没有执行”。前者是观察事实，后者需要额外证据；它会直接影响上层是否安全重试。

依据与核对范围

strace 官方文档入口 — 系统调用、信号与进程跟踪。

Eclipse Mosquitto：C API — publish 返回值、网络线程、回调与重连。

T106 原理问答

逻辑分析仪、示波器、GDB 各适合查什么？

逻辑分析仪看数字协议与时序，示波器看电压、边沿和模拟质量，GDB 看软件状态、调用栈和内存。要先确定问题发生在哪个层次，再选择能看到该现象的工具。

原理与成立条件

逻辑分析仪看协议，示波器看电气

逻辑分析仪适合长时间数字边沿和 UART/I2C/SPI 解码，前提是采样率、阈值与解码参数正确；示波器看上升沿、过冲、噪声、电压和时钟质量。解码乱码不必然是软件错，电气边沿不满足输入阈值也会导致同样现象。

用 GPIO 标记建立时间证据

在 ISR、临界区或任务关键阶段翻转闲置引脚，可直接观察占用和相对顺序。尽量使用低开销固定操作，并估计标记本身成本。长时间趋势可配 RAM 事件记录，不宜在微秒路径 printf；打印串口可能与业务串口冲突并显著改变调度。

调试器能看什么，也会改变什么

GDB/SWD 可读寄存器、栈与内存，硬件断点/观察点有数量限制。暂停 CPU 时外设、DMA 和 watchdog 是否继续运行取决于芯片与调试冻结配置；恢复后出现的超时不一定是自然运行故障。抓故障现场时记录二进制版本、优化选项和暂停条件。

Linux 工具如何配合

strace 看系统调用返回和等待，perf 看运行时热点，线程栈看等待对象，网络抓包看线上协议。它们分别观察不同层，不能用 strace 没有报错证明远端执行成功。工具开销与权限也影响实验，先用小范围捕获再扩大，避免采集本身造成新的超时。

推演与反例

同一 I2C 失败怎样交叉验证

逻辑分析仪可检查地址、ACK、START/STOP 和时序顺序；示波器判断上升沿是否过慢、低电平是否达标、是否有毛刺；调试器查看 HAL 状态和超时返回。数字解码器可能把边沿很差但勉强过阈值的波形解释成正确数据，因此解码成功不能证明模拟裕量充足。

调试会改变被测系统

断点暂停 CPU 时，DMA、外设和看门狗是否暂停取决于配置；原本没有的缓冲覆盖可能因断点出现，原本应复位的问题又可能被调试冻结掩盖。微秒路径适合 GPIO 打点、捕获和轻量计数，复杂日志放到事后输出。硬件观察点可定位哪条指令改坏某地址，但数量与访问能力有限。

继续追问

如何分清 UART 波特率错误和软件丢字节？

示波器先核实际位宽与电平，再比较线上完整字节序列、DMA 进度和应用接收记录；线上正确而软件缺失才把重点转向中断、缓冲与解析。

量到一次最短中断响应就能宣称最大延迟吗？

不能。要构造竞争、中断嵌套、临界区和总线负载等最坏条件，测量结果还应与分析边界结合。

依据与核对范围

GNU GDB 官方手册 — 断点、栈、寄存器、远程调试与目标现场。

ST RM0008：STM32F1 参考手册 — RCC、GPIO、DMA、TIM、USART、I2C、IWDG/WWDG 等章节；配置同时核对本地 HAL。

T107 原理问答

测试应该分哪些层，怎样覆盖时序与并发边界？

单元测试验证局部逻辑，集成测试验证组件接口，端到端测试验证真实链路，板级测量验证硬件和时序。覆盖层次越清楚，面试时越不容易把一种证据夸大成另一种。

原理与成立条件

测试层级按隔离对象划分

单元测试验证纯函数和状态机；集成测试覆盖模块间交接及真实 I/O API；目标端测试覆盖移植、驱动和硬件时序；系统测试验证业务链与恢复。某层通过只覆盖该层使用的假设，不能从协议核心测试推出 DMA、供电和 Flash 都可靠。

好用例来自边界和不变量

对解析器测最短/最长长度、任意分块、坏校验、噪声；对状态机测重复、乱序、超时边沿、回绕和新旧会话；对队列测满、关闭与生产者并发。用例预期应描述业务现象，如“不重复执行且补发结果 ACK”，不能只断言某内部函数刚好被调用一次。

测试替身要暴露不确定性

假 HAL 若永远立即成功，会隐藏超时、短写和回调重入。替身应允许控制成功/失败、进度与事件顺序，可控时钟可避免 sleep 导致不稳定。硬件替身也要声明模拟不了的内容，例如 DMA 总线仲裁和真实中断 pending，防止测试越界背书。

报告怎样不夸大

记录构建类型、用例数、输入与环境，以及未执行板卡/耐久/性能测试。通过率不代表覆盖率，覆盖率也不证明语义正确。已有仓库测试是项目证据，个人贡献需另核实；将验证资产全写成个人设计反而会在追问时暴露责任不清。

推演与反例

怎么把测试从函数覆盖变成语义覆盖

协议应断言同一请求的执行次数、结果是否匹配、超时后资源是否释放，而不只断言某个函数被调用。并发应覆盖关闭时生产者仍在提交、回调删除自身、条件变量超时与入队竞争。错误注入应包括短写、EINTR、队列满和数据库失败，检查系统能否给出明确终态并继续处理后续工作。

确定性与真实环境怎样互补

用虚拟时间和可控 I/O 缩短边界测试并复现失败；用 PTY、真实 Broker 或真实板验证系统调用、库回调及电气接口。模拟环境不会自动体现 DMA 覆盖、LSI 误差或 DHT 波形，真机测试也不容易穷举所有状态排列。分别记录做过什么、观察到什么和未验证什么，才有可评估的工程结论。

继续追问

为什么不只做完整端到端测试？

它覆盖真实链路却定位困难、运行成本高，稀有事件顺序也难控制；小范围确定性测试与真实系统验证互补，不能互相取代。

仓库里有一套测试，能算个人贡献吗？

不能仅据存在就这样表述。应区分自己编写、维护或实际运行验证的内容，并明确其他成员或已有资产的来源。

依据与核对范围

GCC：Instrumentation Options — ASan/UBSan/TSan 的用途与限制。

CMake：cmake-buildsystem — 构建目标、依赖与使用要求。

T108 原理问答

systemd 部署、日志与自动重启怎样配合？

systemd 负责进程生命周期、启动依赖、权限与失败重启；应用仍负责识别故障、释放资源和保存必要状态。自动重启可以恢复部分服务，却不能替代正确的业务恢复协议。

原理与成立条件

服务管理器提供什么

systemd 根据 unit 描述启动命令、身份、环境和依赖，跟踪进程退出并按策略重启。Type=simple 的“已启动”不等于应用所有资源已就绪；若要精确就绪通知需相应协议。重启机制恢复进程活性，不会自动恢复内存中的未完成业务。

退出与重启策略

Restart 的选项决定哪些退出原因触发重启，RestartSec 控制间隔，启动频率限制避免快速崩溃循环。正常 stop 通常发终止信号并给停止期限，超时可能被强制杀死。应用应响应信号并有限排空，不能假设有无限时间写库或等待外设。

启动顺序不是资源可用证明

After 描述相对顺序，不自动建立全部依赖或验证远端 broker 可访问；网络就绪也不证明 DNS 与业务服务可用。应用仍需要错误分类、退避重试和状态上报。WorkingDirectory、配置路径、设备权限及运行用户也是“手动能跑、服务不能跑”的常见差别。

最小权限和运维证据

给服务必要的设备与数据目录权限，避免为了一个串口直接长期用 root；资源限制与沙箱选项需与设备访问兼容。journal、退出码、重启次数和应用阶段日志一起反映健康。不要把 systemd WatchdogSec 当作 MCU IWDG，它依赖应用协议和用户态服务管理语义。

推演与反例

启动顺序不等于外部服务已经可用

After 约束启动顺序，Wants/Requires 表达不同依赖关系，network-online 也不保证某个 Broker 已可连接。应用应对连接失败有明确启动或重试策略。Type=simple 通常以进程启动作为服务开始，不表示数据库和网络都已准备好；需要精确就绪通知时应选择相应协议和配置。

最小权限如何影响部署正确性

串口访问需要合适设备权限，数据库与日志需要可写目录；ProtectSystem、DynamicUser 等限制必须与实际路径匹配。ExecReload 发送 SIGHUP 只是请求重载，是否成功生效仍需应用反馈。Restart=on-failure 加退避能避免快速重启风暴，但若每次重启都丢失未完成业务，服务“又起来了”不等于命令已可靠恢复。

继续追问

服务显示 active，能否说明数据正在正常采集？

只能说明服务管理器所观察的生命周期状态；采样、串口、数据库和云端仍需业务健康指标。

进程一直重启，第一步是什么？

先查退出码、服务日志、权限和配置路径，保留现场；不要把重启间隔调得更短来掩盖启动失败或资源依赖问题。

依据与核对范围

systemd 官方 systemd.service 手册源码 — 重启、停止超时与服务状态；官网手册访问受限时采用官方源码。

systemd 官方 systemd.exec 手册源码 — 运行身份、目录权限和沙箱配置。

T109 原理问答

怎样设计一个可移植、可测试的驱动或协议模块？

可移植模块把纯逻辑与时间、I/O、存储等环境依赖分开，接口明确数据所有权、调用上下文与错误语义。可测试性来自可控制这些输入，而不仅仅是把代码拆成多个文件。

原理与成立条件

可移植核心应该排除什么

把编码、解析和可靠协议状态机写成不依赖硬件寄存器、线程 API 和真实时钟的核心，通过参数或回调传入时间与发送/交付事件。这样同一逻辑可在 MCU 与 Linux 使用，也便于确定性测试。接口必须明确发送返回到底是接纳、提交还是线路完成。

状态与平台资源怎样分层

核心拥有协议状态和固定容量，适配层拥有 fd、DMA、RTOS 对象与缓冲交接。核心不能隐式阻塞等待平台完成，否则跨平台语义容易失真；适配层也不应偷偷改协议内部序号。用清晰的事件/状态接口保留单一所有者。

可移植不等于行为自动一致

整数宽度、端序、结构布局、编译选项和时间回绕都可能不同。使用明确宽度、显式序列化和受约束时间类型，两个平台仍需验证所有调用前提。共享源码可以减少漂移，不能替代不同 I/O 模型下的生命周期与并发检查。

版本与同步如何管理

共享库单一来源、子模块或自动同步检查各有维护成本；至少应记录版本、协议常量和固定向量。协议兼容变更与实现内部重构分开处理，跨端部署还需考虑升级次序，不能只在开发机把两个文件改得一样就认为线上节点全已更新。

推演与反例

协议内核如何脱离某个操作系统

把当前时间、发送帧和执行业务设计为回调或接口，状态机只处理有界字节与显式状态，不直接睡眠、访问 UART 或创建线程。主机测试可注入虚拟时间与记录发送结果，MCU 适配层则调用真实队列和驱动。接口需说明回调是同步还是异步、参数是否只在调用期间有效，否则移植后仍可能出现寿命错误。

分层不能把责任一起丢掉

驱动层报告搬运或硬件错误，协议层处理定界、确认与重试，业务层决定参数合法性和执行结果。每层都应保留足够的错误信息，并明确谁负责恢复；若底层只返回 void、上层假定成功，分层反而隐藏失败。不要为每个小函数都造抽象，而应在真实变化点和测试控制点建立边界。

继续追问

把 HAL 类型放进公共协议头有何代价？

核心会依赖节点工具链和头文件，网关测试与其他平台复用变难；可把硬件句柄留适配层，以普通数据和回调定义核心边界。

mock 全部通过就证明真驱动正确吗？

不能。mock 只能验证其建模的契约，真实中断次序、时钟、DMA 和电气行为仍需集成或板级验证；接口模型本身也可能错误。

T110 原理问答

手写单生产者单消费者环形队列，关键不变量是什么？

SPSC 环形队列的优势来自只有一个生产者推进写位置、一个消费者推进读位置。正确性不仅是下标取模，还包括空满判定、数据发布顺序、回收顺序和计数回绕约束。

原理与成立条件

SPSC 为什么能简化同步

单生产者只推进 head，单消费者只推进 tail，避免多个写者同时竞争同一索引。常见 N 槽环保留一个空槽，head==tail 表示空，next(head)==tail 表示满，实际容量 N−1；也可用单调计数和代数表达满空，但需处理位宽回绕与比较范围。

发布顺序是核心

生产者先写元素，再 release 发布新 head；消费者 acquire 看到这个 head 后才读元素，防止读到尚未完成的数据。消费者读完再 release 发布 tail，生产者 acquire 观察后才复用对应槽，防止消费者未结束就被覆盖。只让索引 volatile 不建立这两条 C++ 同步关系。

为什么多生产者不能直接套用

两个生产者可能同时看到同一 head 并写同一槽，单纯原子递增也可能出现某个槽尚未填好就被消费者看见。MPMC 常需 CAS、每槽序号和更复杂的发布/回收协议。所谓 lock-free 也不保证每个线程固定步数内完成，wait-free 是更强性质。

DMA 环与 CPU 环的差异

DMA 没有自动执行你的 C++ release/acquire 协议，硬件会按配置覆盖槽，消费者需要完成计数、缓存维护、借用期限或流控。索引都正确也不能恢复已被覆盖的数据。真正零拷贝还要定义块何时归还、错误取消和部分消息跨块处理。

推演与反例

发布与回收各需要一条同步链

生产者先确认有空间，再写槽内容，最后 release 发布新写位置；消费者 acquire 观察该位置后才能读对应槽。消费者读完再 release 发布读位置，生产者 acquire 观察后才可复用该槽。若先公布索引再写内容，消费者可能读取未准备好的数据；若先公布槽已空再读完，生产者可能覆盖仍在使用的数据。

容量与算法模型要说清

一种设计留一个空槽区分空满，N 个槽只能存 N−1 项；另一种用单调计数及差值表示占用，可利用全部槽，但要证明计数回绕不会产生歧义。多生产者直接改成 CAS 增写位置还不够：预留顺序和实际写完顺序可能不同，需要额外发布协议。普通 volatile 下标不自动提供 C++ 跨线程同步。

继续追问

head 和 tail 都是原子，数据区是否就一定安全？

只有写数据→发布 head→读取，以及读取完→发布 tail→复用两条关系正确且符合 SPSC 假设时才可推导；原子变量的存在本身不是证明。

为什么不把 CPU 队列证明直接套在 DMA 环上？

DMA 不通过同一个 C++ 原子协议发布，也可能独立覆盖内存；若有非一致缓存还需维护。必须重新定义硬件生产进度、覆盖代数与 CPU 消费完成的交接机制。
