P001 项目问答

请用两分钟介绍这个网关与节点项目。

面试时这样回答

这是一个由 Linux 网关和 STM32 节点组成的采集与控制系统。节点用 FreeRTOS 管理传感器采集、命令处理和串口发送；网关接收节点数据，转换后上传 MQTT 并写入 SQLite，同时提供 HTTP 查询。反方向，云端命令通过网关下发到节点，节点执行后把结果返回。

网关采用多个 I/O 事件循环加一个共享业务线程：串口 epoll、MQTT 网络循环和 Boost.Beast/Asio HTTP 分别管理通信，GatewayCore 顺序处理设备业务。独立管理 Reactor 接收退出和重载信号，专门管理工作线程准备资源，SQLite 查询和写入交给各自线程。控制链使用带会话号的 SR 协议，区分“已接收”和“已执行”，处理丢帧、重复和超时。

这个项目最主要解决什么工程问题？

让网络、串口和磁盘等异步来源在有限资源内协作：事件循环不做数据库查询或业务格式化，同一设备的业务逻辑有明确执行线程，链路重试不等于重新执行业务。仍需分别说明过载、断电和跨会话恢复边界。

P002 项目问答

一条温湿度数据从节点到云端和数据库，具体怎么走？

面试时这样回答

采样任务先通过传感器服务读取数据，并拿到温湿度是否有效的标志。有效值转换成协议规定的整数单位，编码成一条完整帧，再按值复制进发送队列，由发送任务统一写串口。这样采样任务不直接和其他任务抢发送口。

网关串口 Reactor 增量拼帧并检查 CRC，将完整遥测帧和接收时间交给 GatewayCore。业务线程解码温湿度、生成 MQTT 消息并提交数据库写入；HTTP 的历史查询另交读执行线程，SQL 不在串口、HTTP 或业务线程直接执行。

上报成功是否代表数据库已经写成功？

不能。节点入队、网关收帧、业务接纳、MQTT 库接受发布、写库入队和事务提交是不同阶段；线程解耦不自动增加端到端可靠确认。

P003 项目问答

一条云端查询命令怎样形成完整闭环？

面试时这样回答

MQTT 网络回调复制并投递 topic/payload，GatewayCore 在业务线程调用 translateCommand，再向串口命令队列提交内部命令并用 eventfd 唤醒。串口 Reactor 在会话就绪、窗口有空间时分配链路序号、组帧并发送。节点先保存命令并确认接收，再按序执行业务。

节点把结果存入缓存后尝试发回。串口 Reactor 处理 SR 状态与结果确认，把已完成命令事件交给 GatewayCore 映射数据、返回码和云端应答。网络循环负责实际 MQTT 收发；各线程都不为等待节点回应而阻塞。

继续追问

这里哪一个 ACK 表示执行成功？

SR_RECEIVED 只表示节点保存请求。业务结果的返回码与数据才描述执行结局；SR_RESULT_ACK 主要用于节点释放结果缓存。收到重复结果仍须确认，但不能重复完成上层请求。

当前实现边界

云端命令目前没有跨重连、跨进程重启的持久业务 ID；链路闭环不能直接外推成整个云端业务恰好一次。

P004 项目问答

这种架构属于哪种 Reactor 模式，为什么共用业务线程？

面试时这样回答

整个网关仍在一个进程内，串口、MQTT、HTTP 分别有通信事件循环，管理面还有独立 ManagementReactor 处理信号，因此属于多事件循环、多线程架构。三个通信入口共用 GatewayCore；管理 Reactor 只分派管理事件，耗时重载交给专门工作线程。

共用业务线程是因为这些入口经常涉及同一设备、同一命令。业务处理顺序集中在一个线程，链路窗口由串口 Reactor 独占，SQL 由独立读写线程负责，资源准备和 MQTT 发布/替换由管理工作线程串行管理。这样按状态归属和阻塞资源划分，比仅按 MQTT、HTTP、串口入口各建业务池更容易解释一致性。

实现依据与展开

三类常见模式的区别

单 Reactor 单线程让 I/O 和业务串行执行；单 Reactor 多线程把业务交给工作线程；多 Reactor 多线程让多个循环管理不同连接或通道，业务线程可共享。进程数量是另一个维度。Asio 对应用暴露异步完成接口，Linux 默认后端通常为 epoll，描述时须区分接口与实现层。

默认线程数量

稳定运行时通常为 9 条线程：串口主线程、MQTT 网络、HTTP 网络、gateway-admin 管理 Reactor、gateway-manage管理工作线程、GatewayCore、SQLite 查询、SQLite 写入和异步日志。库内部临时线程或重建期间的新旧 MQTT 循环可能改变瞬时数量；线程数不是吞吐结论。

节点侧的对应关系

Cmd、Trans、Sample 优先级分别为 3、2、1，分别等待 StreamBuffer、发送队列或采样周期。它们共享 SRAM，节点 SR 状态由 Cmd 任务独占；此轮网关线程改造没有把节点改成 Reactor。

继续追问

为什么不先建多个业务线程提高并行度？

会增加设备状态、命令关联和顺序协调。先测业务排队与处理耗时；若确有瓶颈，可按设备分组，让同一设备各入口事件始终到同一业务线程。该扩展是后续方案，当前没有实现。

当前实现边界

多循环隔离了直接回调占用，但仍共享 CPU、内存与磁盘；线程更多不是性能一定更好的证据。当前选择同时考虑协议库已有事件循环及实现成本。

P005 项目问答

哪些资源由谁拥有，怎样避免多处同时操作？

面试时这样回答

串口 fd、输出缓冲和 CommandTracker/SR 状态由串口 Reactor 操作；MQTT 网络回调只交接消息，GatewayCore 做应用转换；HTTP 连接由 Asio 循环管理，业务线程通过完成函数返回响应。SQLite 写连接和读查询分别由专用执行线程串行使用；普通 MQTT 发布与客户端替换统一交管理工作线程管理。signalfd 与管理 epoll 归 gateway-admin，管理线程不能直接改串口窗口或注册。

我会把“谁能访问”和“谁负责释放”分别说明。Channel 借用串口 fd，真正关闭 fd 的是串口所有者；HTTP 响应须活到异步写结束，连接关闭后迟到业务结果不能写到新连接。跨线程消息持有自身数据，避免把局部帧、topic 或 payload 的引用留给后续消费者。

P006 项目问答

你怎样评价项目现在的可靠性？

面试时这样回答

我会把可靠性分层回答。串口控制链有校验、有限重试、会话隔离、按序执行和结果缓存，能处理规定范围内的丢帧与重复。传感器读取带有效性判断和部分错误恢复，看门狗用于发现关键任务长期没有签到。

但它还不是掉电后也能完整恢复的业务系统。节点的协议记录在 RAM，云端命令缺少持久业务 ID，遥测也没有统一的端到端确认。队列满、发布失败和数据库错误都有需要明确处理的路径，所以不能只说“用了 QoS 1 和重传，数据就不会丢”。
