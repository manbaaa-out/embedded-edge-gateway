TCP、MQTT、HTTP 与网络边界

T046 原理问答

TCP 为什么还需要应用层分帧？

TCP 可靠传输的是有序字节流，不保存应用每次 send 的消息边界。接收端必须根据应用协议的长度、分隔符或其他明确规则恢复消息，即使每次发送都恰好是一条完整命令。

原理与成立条件

TCP 保证的单位是字节

TCP 为连接提供有序字节流，通过序号、确认与重传恢复部分传输丢失。一次 send 的边界不会成为对端 recv 的边界：协议分段、路径 MTU、缓冲与读取大小都会改变交付块。因此所谓“粘包/拆包”通常是应用没有正确实现消息定界，而不是 TCP 把协议消息弄坏了。

应用层如何分帧

固定长度简单但浪费且不灵活；长度前缀需校验最大长度及整数溢出；分隔符需转义；文本协议也必须严格定义正文长度。读取时把新字节追加到受限缓冲，循环解析已完整的消息，保留残片，不能只处理一条就丢掉尾部，也不能为恶意长度直接分配任意大小内存。

TCP 的“可靠”不覆盖业务提交

send 返回通常表示本地内核接纳，TCP ACK 表示对端 TCP 接收相应字节，并不意味着对端进程已解析或数据库提交。连接断开时，本地可能不知道最后一个请求是否已执行。因此请求响应协议仍需业务 ID、结果与恢复规则；换成 TCP 不会消除分布式结局不确定。

EOF 和半关闭

recv 返回 0 对流 socket 表示对端发送方向有序结束，已缓冲数据通常先被读出；它不直接表示本端发送方向也不能再发送。shutdown 可关闭某个方向，close 释放本地描述符引用。收到 EOF 时，若解析器仍持有半条消息，应按截断错误处理，而非把残片当成功请求。

推演与反例

合并与拆分为什么都是正常现象

应用连续 send 两条 20 字节消息，接收方可能一次读到 40 字节，也可能先读 7 字节再读 33 字节；网卡、TCP 分段、接收缓冲和线程调度都可影响读取分块。这里通常称为“粘包/半包”的现象并不是 TCP 把数据顺序弄错，而是应用错误地把接口调用边界当成消息边界。

定界方法各有什么代价

固定长度解析简单但可能浪费空间；长度前缀能承载任意二进制数据，但必须验证上限并处理头部不完整；分隔符需要转义或保证正文不包含分隔符；关闭连接定界限制了复用和双向交互。无论哪种方法，接收缓冲都要保留未完成消息及多余后缀，不能每次 read 后清空。

继续追问

TCP_NODELAY 能解决粘包吗？

不能。它影响 Nagle 小包合并策略与延迟，不提供消息边界。无论开关如何，接收方都必须正确按应用协议解析字节流。

开 TCP_NODELAY 能解决粘包吗？

不能。它影响 Nagle 算法相关的小包发送行为，不改变 TCP 字节流语义。应用仍必须自行分帧。

T047 原理问答

TCP 三次握手、四次挥手和 TIME_WAIT 如何联系实际故障？

握手用于建立双方的序号与连接状态，关闭则分别结束两个方向的数据发送。TIME_WAIT 让主动关闭方在一段时间内处理迟到报文及最终 ACK 的重传问题，不是单纯的资源浪费。

原理与成立条件

三次握手交换了什么

客户端 SYN 带初始序号 x，服务端 SYN+ACK 确认 x+1 并给出 y，客户端 ACK 确认 y+1。SYN 各消耗一个序号。双方建立本次连接的序号空间并确认彼此发送接收路径；第三次确认还帮助避免服务端把历史重复 SYN 直接当成已建立的新连接。不能只背“三次是最低次数”而不解释状态与旧报文。

为什么关闭常见四次却不固定四包

TCP 双向独立，每一方发送 FIN 表示本方向不再有新数据，另一方可以先 ACK，等剩余数据发完再 FIN。ACK 与 FIN 可能合并，也有同时关闭，所以实际报文数不必固定四个。FIN 同样占一个序号；收到 FIN 后的 CLOSE_WAIT 表示本地应用仍需完成关闭。

TIME_WAIT 的作用与归属

通常发送最后 ACK、主动关闭一侧进入 TIME_WAIT，保留足够时间让对方重传 FIN 时可再次确认，并降低旧连接延迟报文污染相同四元组新连接的风险。经典等待为 2MSL，具体系统取值及复用策略以实现为准；同时关闭也可能双方进入，不能绝对说“只有客户端”。

状态异常怎样推理

大量 CLOSE_WAIT 常提示应用未及时关闭收到 FIN 的连接；大量 TIME_WAIT 可能只是短连接负载特征，应结合连接频率与资源耗尽判断。重用端口、减少等待等调优牵涉正确性和系统版本，先考虑连接复用与正常关闭，不应凭状态多就直接改内核参数。

推演与反例

三次握手中分别确认了什么

A 发送 SYN 和初始序号 x；B 返回 SYN、自己的初始序号 y，并确认 x+1；A 再确认 y+1，双方才完成相互序号认知。SYN 占用序号空间，第三次确认使 B 知道自己的同步信息已被 A 收到。还必须结合旧重复报文和具体状态机解释，不能简化为“验证网络能不能双向通”就认为两次足够。

四次挥手为什么也可能看到三段

一方 FIN 只表示它不再发送数据，对方仍可继续发送自己的剩余数据，因此 ACK 与另一个方向的 FIN 在逻辑上分开；若条件合适可合并到一个报文段。收到对端 FIN 后应用迟迟不关闭，可能停在 CLOSE_WAIT；主动关闭方完成最终确认后通常进入 TIME_WAIT。两种堆积的排查方向不同。

继续追问

第三次 ACK 丢了会怎样？

服务端可能重传 SYN+ACK，客户端再次确认；携带有效确认的后续数据也可推进状态。关键是双方状态机和重传处理，不能说连接立刻永久失败。

TIME_WAIT 能一律调短或删除吗？

不应先从参数下手。先看连接创建频率、主动关闭方、连接复用和资源是否真的耗尽；缩短保护时间可能改变迟到报文隔离与重传处理条件。

依据与核对范围

T048 原理问答

TCP 流量控制与拥塞控制有何不同？

流量控制防止接收端缓冲被压垮，拥塞控制防止网络路径被压垮。发送方能在途的数据同时受接收窗口 rwnd 和拥塞窗口 cwnd 约束，还要扣除已经在途的未确认字节。

原理与成立条件

流量控制与拥塞控制保护谁

流量控制用接收窗口 rwnd 保护接收方缓冲，拥塞控制用发送端估计的 cwnd 控制向网络注入的数据量。可发送的新数据通常受两者较小值减去当前在途字节限制。接收方很快不代表网络没有拥塞，链路空闲也不代表慢应用有足够接收空间。

经典慢启动与拥塞避免

Reno 类经典算法在慢启动阶段随新 ACK 扩大 cwnd，理想条件下每 RTT 近似翻倍；达到 ssthresh 后转入较慢的增长，典型拥塞避免约每 RTT 增一个 MSS。丢包或超时触发减少窗口与恢复。现代系统可采用 CUBIC 等其他算法，不能把某个经典算法的每个数值当成所有 TCP 的固定行为。

快速重传与 RTO

重复 ACK 可能表明后续数据到达而中间有缺口，经典三次重复 ACK 可触发快速重传，不必等 RTO。乱序也可能产生重复 ACK，因此推断并非完美。RTO 根据 RTT 及波动估计并退避，重传样本有歧义；不能把应用请求超时与 TCP 重传定时器混成一个参数。

接收窗口为零时如何恢复

发送方暂停正常发送新数据，并通过零窗口探测等机制获取窗口恢复信息，避免窗口更新丢失后双方永等。应用停止读取可逐步传导为 TCP 背压，但若应用先把数据搬进无限队列，内核窗口仍可能持续打开，压力只转移到用户态内存。

推演与反例

为什么接收缓冲很大仍可能很慢

即使 rwnd 很大，连接刚开始时 cwnd 可能较小，需要根据 ACK 逐步增长；发生丢包或拥塞信号后又可能收缩。反过来，路径空闲但接收应用读得慢，rwnd 可能变小甚至为零。慢启动不是“线性慢慢增大”，经典过程按 RTT 可近似指数增长；具体算法和实现版本会改变细节。

带宽时延积与缓冲膨胀

若路径带宽为 B、往返时间为 R，要持续利用链路通常需要量级为 B×R 的在途数据；缓冲过小限制吞吐，过大且缺少控制又可能把排队时延推高。吞吐、时延和丢包需要一起看，不能只把 socket 缓冲调到最大。串口虽然不运行 TCP，同样要面对生产消费速率与排队增长，只是控制机制不同。

继续追问

扩大 socket 发送缓冲一定降低延迟吗？

可能提高高带宽长 RTT 场景吞吐，却也允许更多数据排队，增加延迟和过期数据。要结合带宽时延积、业务新鲜度和实际瓶颈。

超时重传说明一定发生拥塞了吗？

不一定，可能有链路错误、接收端停顿或 ACK 丢失；TCP 仍按其算法对信号做保守处理。应用排障应结合具体路径证据，不能把协议动作当成唯一根因。

依据与核对范围

RFC 9293：TCP — 握手、序号、字节流和关闭；§3.4–3.8。

T049 原理问答

MQTT QoS 0、1、2 到底保证什么？

MQTT QoS 0 不确认，QoS 1 用确认实现至少一次交付并允许重复，QoS 2 用分阶段状态避免同一次协议消息被重复交付。它们首先约束相邻 MQTT 通信端点之间的协议交付，不自动把外部业务动作纳入事务。

原理与成立条件

QoS 的保证限定在哪一段

MQTT QoS 描述发送方与接收方之间一次协议传递的交付语义，发布者到 broker、broker 到订阅者是各自的一跳，订阅获准的 QoS 也限制下行级别。QoS0 没有 MQTT 层确认；QoS1 用 PUBLISH/PUBACK，重发可能产生重复；QoS2 用四步交换与报文状态避免同次协议消息重复交付。

QoS2 四步为什么能去重

PUBLISH→PUBREC 表示接收方保存处理该报文所需状态，PUBREL→PUBCOMP 推进并结束这次交付。Packet Identifier 与双方状态机使重复报文能被识别，而不是再次作为新消息。状态必须按会话契约保存；发布者以新标识再次提交同一业务内容，仍是新的协议消息。

三类确认不能混用

publish API 返回成功常仅表示客户端库接纳；PUBACK/PUBCOMP 表示协议阶段完成；业务响应表示订阅应用或更下游设备的执行结果。即使 QoS2 已交付一次，业务回调执行一半后进程崩溃，数据库或执行器效果仍需应用自己的事务与恢复方案。

选择 QoS 要连同资源讨论

更高 QoS 增加报文、缓存与状态维护，低带宽节点或断续网络尤其需要容量预算。周期遥测可按业务容忍损失选 QoS0，重要命令常结合 QoS1 与应用幂等。不能仅靠 QoS 数字决定端到端可靠性，持久会话、客户端本地持久状态和上层补偿同样重要。

推演与反例

QoS 2 的四步在防什么重复

PUBLISH、PUBREC、PUBREL、PUBCOMP 使双方在不同阶段保留消息标识与处理状态。某一步丢失时可以重传对应控制报文，接收方依状态避免重复向后交付同一协议消息。它依赖会话状态及标识的正确保存；发布应用自己用一个新标识重新提交相同业务，仍可能成为另一条合法消息。

Broker 确认与设备执行隔了几层

发布方收到 PUBACK，说明当前 MQTT 交互完成了规定确认，不代表某个订阅应用已经处理，更不代表订阅应用控制的电机已经动作。Broker 到订阅者是另一段交付，订阅最大 QoS 也影响实际等级。需要业务闭环时，应让最终执行者返回稳定业务 ID 对应的结果，并定义掉线、重复与重启恢复。

继续追问

DUP=0 是否证明业务从未收到过这条内容？

不能。它只涉及这次控制报文的重发标记；同一业务内容可以以新报文 ID 再发布，应用仍需自己的稳定请求标识。

QoS 1 重复时 DUP 必然为 1 吗？

不能把 DUP 当业务去重键。规范允许同一业务内容以不同 Packet Identifier 再次发送；业务重复与某次 PUBLISH 的重发是不同层次。

T050 原理问答

Clean Session、Retain、Keep Alive 和遗嘱分别是什么？

Clean Session 决定会话状态是否保留，Retain 保存主题最近一条保留消息供新订阅者获取，Keep Alive 检测连接活动，遗嘱用于异常断开后的通知。这四者不能互相替代。

原理与成立条件

Clean Session 保存的是会话状态

MQTT 3.1.1 中 Clean Session=true 请求使用新的会话状态，断开后不保留该会话；false 配合稳定 ClientId，可让 broker 保留订阅及相应未完成 QoS 状态。客户端也需要正确保存它负责的状态。它不是任意长时间的无限消息仓库，更不替应用持久化尚未交给 MQTT 的命令。

Retain 是主题最后值语义

带 RETAIN 发布让 broker 保存某主题的最后保留消息，之后匹配的新订阅者可先取得该值。它适合配置、状态快照，却不是历史队列。对“执行一次动作”使用 retain 可能导致新订阅或重连时再次收到旧动作，必须慎重区分目标状态与一次性指令。

Keep Alive 与遗嘱

Keep Alive 限制控制报文间隔，空闲时 PINGREQ/PINGRESP 帮助确认 MQTT 通信仍在推进；broker 对超时有规范规定。遗嘱是连接异常结束等条件下由 broker 代发的消息，正常 DISCONNECT 通常抑制遗嘱。它们判断 MQTT 连接状态，不验证传感器、数据库和命令业务是否健康。

ClientId 冲突与在线判定

同一 ClientId 的新连接可能导致已有连接被断开，多个设备错误共用标识会表现为反复上线掉线。在线状态还存在网络分区、延迟和遗嘱发布时差，不能当成绝对实时事实。需要业务健康时再增加状态时间戳与有效期，避免旧 retain 在线值被长期误解。

推演与反例

持久会话需要什么前提

MQTT 3.1.1 中要使用稳定 Client ID 并按 Clean Session 设置恢复会话，Broker 和客户端还要具备相应状态保存能力。订阅、未完成 QoS 交换及离线消息的处理受协议与服务端资源约束。只把 Clean Session 改成 false，并不会自动为应用生成跨重连业务 ID，更不会让未入库的本地命令在进程重启后恢复。

为什么控制命令慎用 Retain

新订阅者建立订阅时会收到主题的保留值，适合“设备当前目标配置”这类状态表达；若内容是“再开一次阀门”这样的事件，重连订阅可能触发过期动作。命令应带有效期、身份和明确的状态/事件语义。Keep Alive 表示协议连接活动，遗嘱出现也不一定表示硬件损坏，可能只是网络分区。

继续追问

Clean Session=false 加 QoS1 就能自动补齐掉电期间所有遥测吗？

不能补尚未发布或客户端已丢失的数据；broker 的会话持久性、限制和客户端恢复能力也要核实。应用持久补传需另设计。

心跳业务消息与 MQTT PING 能互相替代吗？

PING 主要验证 MQTT 连接路径，业务心跳可带传感器状态、任务进展和数据新鲜度。两者观察层次不同，应按故障定位需求设计。

T051 原理问答

断网、重连、消息重复时怎样保证业务可追踪？

断网恢复要解决两件事：消息有没有被持久保存，以及重复到达时能否识别为同一个业务。重连只是恢复传输通道，不能填补已经丢失的业务记录。

原理与成立条件

连接恢复与业务恢复的区别

重新建立 TCP/MQTT 连接，只恢复通信通道；断开期间哪些请求已执行、哪些结果尚未提交，仍需业务记录。瞬断可能发生在任意阶段，发送方看到失败并不证明对端未处理。恢复逻辑首先区分可直接重试、需查询结果和必须人工/补偿处理的请求。

outbox 与 inbox 分别解决什么

outbox 在本地事务中保存待发送业务记录，让进程崩溃后仍能找到未确认工作；inbox 用业务 ID 标记接收与处理结果，识别重复。发送成功后删除 outbox 与远端效果仍通常不是同一事务，所以可重复发送加接收去重是常见组合，而非声称网络跨端天然原子。

重试必须有身份与节奏

同一业务重试使用相同 ID，附带类型、参数摘要和过期时间；新动作使用新 ID。指数退避加抖动可以减少大批客户端同时恢复时的冲击，仍需最大次数/时长与可观察失败。对明显的参数错误反复重试没有意义，错误分类决定恢复策略。

重连后的顺序和有效期

离线期间积累的命令可能已经过时，恢复时应检查有效期与当前设备状态。配置可合并为最新目标，动作命令不可随意折叠或重排。去重记录保留期至少与允许业务重试的范围协调，删除记录后仍允许旧请求重发会重新打开重复执行窗口。

推演与反例

outbox 怎样关闭本地提交空隙

若先改数据库再发消息，进程可能在两步之间崩溃；若先发消息再改数据库，也可能产生相反不一致。可在同一数据库事务里写业务变化与待发送 outbox 记录，再由后台反复发送，确认后标记完成。发送与标记之间仍可能重复，所以接收方还需要稳定 ID 和 inbox/幂等处理；这是一组配合机制，不是单个发送队列。

有限资源如何决定恢复策略

断网无限久而数据持续产生，有限磁盘不可能保证永久保存所有数据。应定义保留期、空间上限、优先级、合并或拒绝策略，并区分遥测与控制命令。恢复时也要限速，避免把全部积压瞬间灌入节点导致新一轮超时。可靠性承诺必须包含这些资源与故障持续时间条件。

继续追问

云端没有收到成功，是否应该换一个 ID 再发？

如果是在重试同一次业务，换 ID 会绕开去重，可能再次执行。应保留 ID 并查询或重发；只有明确的新业务才分配新 ID。

数据持久化成功后能立即告诉用户动作成功吗？

只能报告已可靠接纳或已记录，执行成功仍需要执行方结果。接纳、传输、执行和结果持久化是四个不同里程碑。

T052 原理问答

心跳、健康检查与有效进展分别能证明什么？

心跳证明某条路径在某个时刻还能产生活动，不证明所有功能健康。健康检查应把任务存活、业务进展、外设有效性、数据新鲜度和通信双向能力分开观测。

原理与成立条件

心跳只能证明观察到的层

链路心跳表明某个通信路径最近可达；进程心跳表明某段代码还能运行；业务心跳需证明关键工作有进展。一个线程持续回应 ping，其他线程可能已经死锁；因此健康定义应围绕关键服务，而不是仅看 TCP 连接存在或 CPU 未复位。

超时判定是怀疑，不是证明

网络延迟、调度暂停和拥塞都可能让健康节点晚回心跳。缩短间隔提高发现速度，也增加流量和误报；通常需要连续失败阈值、恢复去抖和单调时钟。网络分区下双方都可能活着却互不可达，不能仅凭一次超时断言远端已死。

健康信息应该包含什么

分别报告最近通信、最近成功采样、各传感器有效性、队列积压和错误计数，让上层区分节点离线、局部传感器失败及处理变慢。状态位是瞬时快照，计数能表达长期趋势，时间戳说明新鲜度；用单一布尔 online 会丢失很多诊断信息。

心跳与负载控制

业务忙时若心跳被排在同一拥塞队列尾部，会把过载误判为断线。可为控制消息保留预算，但不能让心跳独立畅通后掩盖业务完全停滞。设计要同时考虑探活优先级和“已处理多少有效工作”的进度指标。

推演与反例

“有心跳、命令没响应”如何成立

发送任务和采样任务仍运行，能周期性发心跳，但接收 DMA 已因错误停止；或者接收仍有数据，命令任务却卡在传感器锁上。此时连接看起来活着，控制链实际已失效。要区分这两类问题，需观察 RX 字节/错误计数、解析成功数、命令开始/结束、TX 进度，而不是仅增加心跳频率。

有效进展要和任务职责绑定

周期采样任务可上报上次采样完成时间，命令任务可上报状态机推进或有界空闲循环，写库任务可上报队列消费位置与错误状态。空闲任务不应因为没有业务而被误判故障；持续积压时又不能仅凭循环转了一圈就视为健康。阈值要覆盖正常最长工作及调度延迟。

继续追问

心跳一直正常，数据库却没有新数据，从哪里查？

按采样有效性、串口解析、业务分流、写库入队和提交逐层检查；心跳只缩小部分故障范围，不能跳过数据链验证。

节点在线时为什么仍要发送传感器无效标志？

在线只说明节点或部分任务存活。独立有效性可防止把上次成功读数当作当前新数据，也帮助区分设备离线与单个传感器故障。

T053 原理问答

设备接入网络需要哪些认证与输入边界？

网络安全首先明确通信对象是谁、消息有没有被改、调用者允许做什么，以及外部输入最多消耗多少资源。TLS、权限控制、输入验证与业务去重各自解决不同问题。

原理与成立条件

安全需求拆成三件事

认证回答对方是谁，授权回答其能做什么，完整性/保密性保护传输内容。TLS 经正确证书与主机名验证可建立受保护通道，但应用仍需对设备、主题和命令权限进行授权。只加密而不验证身份，可能仍连接到攻击者控制的端点。

为什么 CRC 不能防攻击

CRC 无密钥且线性，攻击者能修改数据并重算；MAC 或认证加密借助秘密密钥验证来源与内容。即便有 MAC，也要用请求 ID、计数或 nonce 及接收窗口防重放；一个过去合法的开阀命令被原样重播，校验仍可能完全正确。

输入验证怎样形成边界

在分配与复制前校验长度，解析数值时检查完整消费、溢出和范围，对设备标识与命令类型建立白名单/权限。传感器周期等参数还应符合资源预算，不能仅满足整数类型范围。限制连接数、队列量与重试速率，防止合法格式的洪水耗尽资源。

密钥与部署也影响保证

私钥不硬编码进公共仓库，配置文件权限与进程身份应最小化；证书轮换、设备撤销、可信时间及固件完整性需要生命周期方案。日志要保留足够审计信息又避免输出凭据。安全机制必须沿实际命令路径验证，不能因为网络库支持 TLS 就宣称应用已启用。

推演与反例

TLS 完成了哪些验证才有意义

加密通道如果没有正确验证证书链、主机名或预共享密钥身份，仍可能连接到错误对端。服务端认证与客户端认证也不同；Broker 确认设备身份后，还要按主题或业务权限限制发布订阅。CRC 只能发现某些传输差错，不提供密钥身份鉴别，不能替代 TLS 或消息认证。

合法连接也可能提交危险输入

已认证客户端仍可能发超长 JSON、越界周期、未知设备或无限命令。应在分配大块内存、排队和执行前验证大小、类型、范围、速率与权限，必要时给业务设置有效期和防重放标识。安全策略必须与有界队列和错误响应连接起来，否则“有认证”仍可能被合法流量拖垮。

继续追问

TLS 已防篡改，还要业务幂等吗？

需要。合法重试、进程崩溃和重复发布并不是攻击，TLS 不知道动作是否已执行，也不替应用保存业务结果。

串口在本地，是否完全不需要输入校验？

不需要默认把它当公网攻击面，但物理噪声、驱动错误、测试工具和被替换节点都可能产生异常输入。长度、状态与范围校验本身就是基本正确性要求。
