P015 项目问答

串口帧怎样设计，为什么还要增量解析和 CRC？

面试时这样回答

帧包含同步头、长度、类型、业务负载和 CRC。同步头帮助寻找候选起点，长度限定正文边界，CRC 检查内容是否损坏。接收端按字节推进解析状态，不依赖一次 read 或一次 DMA 回调恰好得到一条帧。

当前同步头是 AA55，LEN 包含 TYPE，允许 1 到 64，因此完整帧为 6 到 69 字节。CRC 使用 CRC16/MODBUS 参数，覆盖 LEN、TYPE 和 payload，结果低字节先传；业务多字节整数则按协议大端编码。CRC 端序与业务端序是分别约定的。

P016 项目问答

为什么用 SR，窗口为什么设成 8？

面试时这样回答

SR 允许多条命令在途，并对缺失项单独重传，比每发一条都等完结果更能利用链路。节点可以先保存乱序到达的后续命令，但只按序号顺序执行业务，避免控制顺序被乱序传输打乱。

窗口 8 是当前资源和状态复杂度下的配置选择，不是由 8 位序号强制算出来的最佳值。节点有 16 个槽共同保存待执行命令和已完成结果，结果还要等确认或到期释放，所以窗口不能只按序号位数放大。

P017 项目问答

接收确认、执行结果和结果确认为什么要分开？

面试时这样回答

接收确认告诉网关“这条请求已保存，可以停止接收阶段的重传”；执行结果告诉网关“业务已经结束，结果是什么”；结果确认告诉节点“网关已经拿到结果，可以释放缓存”。三个消息对应三种责任，不能合成一个含糊的 ACK。

节点执行完先保存结果、推进执行序号，再尝试发送结果。这样 TX 队列暂时满了，也不会因为同一请求重来就再执行一次。结果确认影响缓存回收，不决定下一条业务是否可以执行。

P018 项目问答

会话号怎样防止旧命令污染新连接？

面试时这样回答

请求身份由 64 位 session 和 8 位 seq 共同组成。session 区分不同一轮链路，seq 区分本轮请求；双方先通过 OPEN 握手建立会话，再接纳该会话的命令。旧会话的确认、结果和写完成回调不能直接修改新会话状态。

节点在本次启动期间保留会话高水位，更高 session 才能开启新一轮并清理旧状态。同一会话内 seq 不复用，序号用完且在途清空后再建立新会话，减少迟到短序号被误认成新请求的机会。

P019 项目问答

500 ms、4 s、10 s 三个时间分别控制什么？

面试时这样回答

500 ms 是一轮命令整帧写入内核后等待接收确认的重试间隔，最多额外重试 3 次。4 s 限制未取得接收确认的请求总寿命，避免在本地排队或持续重试中无限占资源；10 s 是从请求被状态机接纳排队起等待业务结果的总期限。

收到接收确认后不再按“命令没到”重复发送，但仍保留业务对象等待结果。网关每 200 ms 扫描一次，再加主循环延迟，所以实际报告超时会晚于名义阈值；这些值是判定条件，不是精确的完成时间承诺。

P020 项目问答

一条命令重试耗尽，为何中止整轮会话？

面试时这样回答

节点要求按序执行。如果缺失的是 5，后面的 6、7 即使已经收到，也不能跳过 5 执行。网关只删除 5 的本地记录，节点仍会等这个缺口，所以需要双方重建一致的顺序起点。

当前做法是结束旧会话，让相关请求得到失败或会话中止结果，再用更高 session 建立新会话。旧命令不会自动复制到新会话重发，因为其中一些可能已经执行，只是结果没回来。

P021 项目问答

结果缓存满了、过期了、结果确认丢了，分别会怎样？

面试时这样回答

节点的 16 个槽同时存待执行请求和已完成结果。没有空槽时不确认未保存的新命令，让发送方继续按协议重试或终止；执行后结果从完成时刻起保留 5 s，收到结果确认可以提前释放，重复请求不会无限续期。

结果确认丢失时，节点在规定次数内重发结果，网关对重复合法结果再次确认。缓存过期后，旧序号仍在执行基序号左侧，所以不会重新执行，但可能已经无法返回原来的具体结果。

P022 项目问答

MQTT 使用什么 QoS，发布与重建由谁管理？

面试时这样回答

命令订阅与命令结果使用 QoS 1，遥测使用 QoS 0。libmosquitto 网络线程处理 MQTT 收发和回调，消息回调只提交原始数据给 GatewayCore，业务解析和结果格式化都在业务线程。CONNACK 成功后重新订阅，连接 API 返回、收到 CONNACK 与订阅成功是不同阶段。

GatewayCore 生成的发布任务交给单一 gateway-manage 线程；MQTT 客户端替换也在该线程执行，避免业务线程借用正在销毁的客户端。网络入口过载时直接通过回调所属客户端发送 gateway_busy，这是固定接纳失败处理；实际网络收发仍由库推进。

拆线程后网络重建就不会影响任何消息了吗？

P023 项目问答

云端重复发送同一命令，会不会重复执行？

面试时这样回答

如果是同一条串口请求因 ACK 丢失而重传，session/seq 保持不变，节点按协议识别重复，不再执行业务。但如果云端重新发来同样文本，网关可能把它当作新的业务提交，分配新的链路身份，节点就会把它视为新命令。

所以链路去重和业务去重必须分开。要处理云端重发，需要让云端携带稳定业务 ID，网关或最终执行者持久记录它与参数及结果的关系；同 ID 不同参数应拒绝，而不是按新命令执行。

P024 项目问答

项目各处队列满时怎么办，完成事件怎样预留空间？

面试时这样回答

GatewayCore 普通邮箱上限 1024，命令准入最多 512，查询最多 32；完成事件另可使用 552 个预留位置。命令占据准入额度直到管理工作线程执行拒绝或终态消息的 publish 调用，再释放额度，避免已接收命令结果被新的遥测挤掉。串口下行队列容量 512，一轮最多消费 32，SR 在途仍最多 8。

普通邮箱满时遥测拒绝并记日志，HTTP 返回 503；MQTT 未接纳命令回 gateway_busy。查询过多也返回 503。管理工作线程普通队列和写库队列各为 1024；管理工作线程另预留 528 个位置，其中 512 对应未发布终态额度，16 是控制余量。遥测不能挤占这些位置，但库拒绝或网络中断仍不保证结果已上传。

容量证明的前提

预留为 512+32+8，分别覆盖已准入命令的单次终态、查询完成及生命周期控制余量。Core 的 pending 请求 ID 去重与 Reactor 每请求只交付一次终态是该估算的前提。TaskExecutor 关闭后拒绝新任务、按 FIFO 排空已有项，生产者不等待空位；当前并非无锁容器。

节点与网关单位不同

节点 TX 为 8 个 TxFrame，RX DMA 和 StreamBuffer 各 64 字节，SR 请求/结果槽为 16。节点 TX 满可能丢新帧，StreamBuffer 短写仍须检查调用点；条目数不等于字节容量，网关队列限制不能自动保护节点所有缓冲。
