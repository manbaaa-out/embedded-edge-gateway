T111 原理问答

有界队列、背压与丢弃策略如何从负载推导？

队列把生产与消费在时间上解耦，却不会增加消费者的长期处理能力。设计应先估算到达、服务与最长停顿，再决定容量、接纳条件以及满时对上游反馈什么。

原理与成立条件

长期速率与短期突发

若长期到达率 λ 大于服务率 μ，积压会持续增长，任何有限队列最终都会满；λ 小于 μ 只说明长期有排空机会，仍可能被短时突发压满。一个停顿 T 内最多到达 B 字节、此前已经积压 Q 字节，则这段至少需要容纳 Q+B，后续还需保证恢复消费能追上。平均速率不能给出最坏容量。

延迟与内存来自同一份积压

积压越多，排在后面的任务越晚开始；容量增大可少拒绝一些瞬时请求，同时扩大最坏等待与对象寿命。在稳定系统中，Little 定律把平均在系统内数量、有效到达率和平均停留时间联系为 L=λW，但它不是用平均值直接证明最坏期限的公式。实时控制应同时限制队列深度和最老任务年龄。

选择丢弃需要业务语义

周期遥测可考虑保留最新值、合并或丢新数据并计数；有顺序的命令、不可重建的事件和已确认接纳的操作不能套同一策略。背压可以表现为暂停读取、返回忙、发放信用或限制在途请求。停止读取也会把压力转移到底层缓冲，必须确认该链路能否把压力传回真正生产者。

推演与反例

窗口为什么不等于字节信用

允许 8 条命令在途，只约束数量；若每条长 69 字节，它们仍可在很短时间内形成数百字节突发。接收端 64 字节 DMA 环与 64 字节软件流缓冲，不能由“窗口只有 8”直接推出安全。应计算帧长、发送节奏、ISR 延迟、执行停顿与结果占用，必要时按可用字节或块数发信用。

继续追问

不丢、不阻塞、内存有限能否对任意输入同时保证？

不能。只要输入可持续超过消费能力，就必须拒绝/减速、丢弃或增加持久存储等资源。接口应明确接受范围及失败表现，不能把无限队列当可靠性方案。

T112 原理问答

零拷贝为什么首先是缓冲所有权问题？

零拷贝的目标是减少数据搬运，但前提是消费者使用期间底层存储保持有效且内容稳定。只把数组换成指针队列，只减少了指针传递时的复制，并没有证明数据不会被复用或覆盖。

原理与成立条件

建立一块缓冲的完整生命周期

以块池为例，块从 FREE 变成 FILLING，生产者写完后变成 READY，消费者取得后进入 PROCESSING，最后回到 FREE。各状态只能有明确拥有者；入队失败、超时取消、错误恢复和退出都要规定谁归还块。引用计数可以表达多个消费者共同拥有，但要避免释放时仍有 DMA 或回调借用。

DMA 环为什么难以直接借用

循环 DMA 按硬件进度不断回写，没有等待应用归还某段内存的机制。CPU 取得一个环内指针后，耗时解析、传感器读取或写库都可能使 DMA 追上并覆盖。可改为停交接的分块设计、双缓冲配合消费预算，或让解析器及时拷贝必要数据；每一种都有吞吐、延迟和 RAM 代价。

重传进一步延长寿命

发送请求可能第一次失败后再发送，同一编码帧要活到最后一次可能访问结束；一份业务数据同时去数据库与 MQTT，也要等两条支路均不再借用才能复用。超时上报不等于底层 I/O 已停止，取消与完成必须有确定的最终归属。所谓零拷贝应明确节省的是哪一段，而不是宣称全链路没有复制。

推演与反例

块池耗尽时如何保持闭环

若所有块都被慢消费者占用，DMA 或生产者需要停接纳、启用流控、丢弃并重同步，或使用有界备用路径。没有满池策略的所有权图仍是不完整的。测收益时同时看节省的 CPU、增大的驻留内存和新增控制复杂度。

继续追问

小帧一定值得零拷贝吗？

不一定。几十字节的复制通常换来简单而稳定的寿命边界，管理复杂度可能比复制开销更大。先测瓶颈，再选择值得优化的交接点。

T113 原理问答

状态机怎样把事件、超时和错误恢复组织清楚？

状态机用“当前状态、输入事件、保护条件、动作、下一状态”表达流程。价值在于把非法事件和异步先后关系显式化，而不只是把一组 if 换成枚举。

原理与成立条件

状态与事实要避免互相矛盾

一个请求可用排队、发送中、等接收、等结果、完成/失败来描述主要阶段，同时记录会话、尝试次数和截止时间。派生事实尽量从权威状态计算，避免多个布尔值出现“已完成但仍在等待发送”等无意义组合。每个转换应维护窗口、缓冲及回调次数等不变量。

所有事件都要有处理规则

正常 ACK、重复 ACK、结果先到、错误会话、取消、发送失败、定时到期都应明确是推进、忽略、补确认还是恢复。事件处理最好在一个所有者线程/任务中串行进行，跨线程输入先排队；如果同一状态由多个上下文改写，状态机图本身并不能消除数据竞争。

超时也是普通事件但不是远端事实

超时转换只说明本地决定不再等，它可能与完成事件同时到达。应以一次终态提交保证回调至多一次，并隔离晚到事件。若底层仍可能执行，终态可以表达“结果未知”，由业务恢复流程处理，不应伪造成“已取消远端操作”。

推演与反例

从转换表得到测试

为每个状态列出允许输入与拒绝输入，再覆盖所有边界转换；使用假时钟生成到期前、到期时和到期后的事件。检查每次转换后占用资源是否有界、终态是否单向、旧代是否能污染新代。这样测试跟随语义，而不是机械重复内部函数实现。

继续追问

状态越少越好吗？

过少会把不同责任混在一个状态里，过多又增加非法组合。应按等待的外部事实和资源责任划分，能解释每个状态存在的必要性。

T114 原理问答

定点编码、单位、有效性与采样时间如何设计？

一个传感值至少包含数值、单位、缩放、有效性和采样时间语义。线上使用整数可简化跨平台表示，但必须先定义范围、符号和舍入规则，不能只写“乘十传过去”。

原理与成立条件

定标怎样影响范围与分辨率

用有符号 16 位整数表示 0.1 °C，量化步长为 0.1，理论编码范围约为 −3276.8 到 3276.7 °C；真实传感器范围通常更窄。若改成无符号，负温无法直接表达，不能强转后让它变成很大的正数。扩大编码小数位也不会提高传感器本身精度，它只改变数字表示粒度。

舍入必须先验证数值

对已知非负且处于范围内的值，加 0.5 再截断可实现常见四舍五入；负数、NaN、无穷大和超范围值需独立处理。两端必须约定饱和、拒绝还是报告错误，不应一端截断另一端解释为有效大数。整数字段相乘也要在足够宽的类型中完成，再检查缩窄。

无效数据不应伪装成正常零值

读取失败时返回 0 会混淆“零照度”与“传感器掉线”。可以通过独立 valid/status 和错误码表示，缓存旧值则应附时间或年龄。采样时刻、节点发送时刻、网关接收时刻及入库时刻不同；若只能记录接收时间，应明确它不是精确采样时间。

推演与反例

如何做一条端到端数值核对

从传感器原始字节开始，写出符号与小数解析、业务值、定点整数、线上字节序、网关还原和数据库单位。选正常小数、零、边界、负值与无效数据逐项追踪，能发现小数被截掉、单位重复缩放或状态被忽略的问题。

继续追问

温度字段多加一个小数字节就能提高测量精度吗？

不能。编码分辨率、器件分辨率和测量准确度是三件事，必须引用器件条件并对误差作合理解释。

T115 原理问答

错误码、异常安全与恢复重试怎样形成一致契约？

错误处理不仅是记录日志，还要告诉上层哪些动作已经发生、哪些资源仍有效，以及能否安全重试。返回值、异常与状态转移应共同表达这一契约。

原理与成立条件

先区分未开始、部分完成和结局未知

打开候选串口失败时旧端口可以完全未变；写了半帧后失败已经产生部分外部效果；数据库提交返回异常时还要确定事务状态。把这些都压成 false 会让上层无法决定重试或回滚。接口应尽量保留阶段、错误原因和已完成进度，避免把失败路径中的实际效果隐藏掉。

异常安全的层次

基本保证要求失败后不泄漏且对象仍保持有效不变量；强保证希望失败后观察状态不变；不抛异常保证用于特定清理路径。构造新资源再交换可实现许多局部强保证，但外部网络发送和物理动作无法靠交换指针撤销。析构通常不能抛异常穿过另一个异常展开，应采用可诊断的受控失败方式。

重试必须有分类和期限

临时不可用可重试，非法参数或永久权限错误通常不应原样无限重试。还需退避、最大次数、总截止时间和重复副作用处理；重试本身占用队列与资源，可能放大过载。恢复成功应以实际可用状态确认，不只是某个重初始化函数被调用过。

推演与反例

日志与返回值应一致

如果底层写失败只打日志仍返回成功，上层就可能删除唯一待重试副本。相反，底层已成功而上层无证据地重做，会产生重复。对重要操作，应使成功返回对应明确的完成里程碑，并为部分成功或结果未知提供独立表示。

继续追问

捕获所有异常然后继续运行更稳健吗？

只有能恢复对象不变量并给请求明确结局时才是恢复。吞掉错误后继续使用半初始化资源，往往把清晰失败变成更难定位的后续损坏。

T116 原理问答

固定优先级任务怎样做最坏响应时间分析？

平均 CPU 利用率不能证明实时性。对一个任务，需要把自身执行、低优先级资源阻塞和更高优先级任务/中断的干扰合起来，判断最坏响应是否小于截止时间。

原理与成立条件

一个常见分析模型

在单核、固定优先级、可抢占、独立周期/间歇任务、截止期不大于周期、无释放抖动且阻塞已被正确界定时，可迭代估计 Ri=Ci+Bi+Σceil(Ri/Tj)Cj，求和针对高优先级任务。Ci 是本任务最坏执行时间，Bi 是受控阻塞上界，Tj/Cj 是高优先级任务周期与执行预算。中断、释放抖动和额外不可抢占区需要按相应模型加入；不是任何实际程序都可直接代入这个简式。

CPU 执行与等待外设必须区别

任务持锁等待 180 ms 转换时，CPU 可能在运行其他任务，但高优先级查询仍会因资源阻塞等待很久。若直接把全部等待算成纯 CPU 执行，利用率估计又会失真。需要按自挂起、服务任务或资源协议建立正确模型，再分别报告 CPU 利用和端到端完成期限。

推演与反例

用数字说明为何需要迭代

低优先级任务自身需 2 ms，阻塞上界 1 ms；高优先级任务每 5 ms 到达一次、每次执行 1 ms。从 R=3 开始，代入得到 R=3+ceil(3/5)×1=4 ms，再代入仍为 4，得到该模型下的上界。如果截止时间是 3 ms，即使平均利用率看起来不高，也无法满足。增加一个中断源还需重新分析。

继续追问

哪些证据才能支持“实时响应优化了”？

同等负载下的最大中断屏蔽、任务唤醒、排队与业务完成测量，加上最坏到达和资源阻塞分析。只减少平均函数耗时或提高任务优先级不足以形成这个结论。
