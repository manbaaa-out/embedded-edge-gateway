T054 原理问答

SQLite 的连接、读写并发与线程模式怎么理解？

SQLite 可以有多个连接，但同一数据库文件的写入需要协调；WAL 改善读写并发，通常仍只有一个写者。让写连接归一个线程、读连接归相应读线程，可以把事务状态与线程所有权说清楚。

原理与成立条件

单写者为何适合 SQLite

SQLite 是嵌入式数据库，连接在进程中执行 SQL；多个线程各开连接并不意味着同一库可以任意并发写。串行写者集中管理事务和顺序，减少应用层连接竞争。它不能让慢存储消失，而是把写入延迟隔离到专门队列，并使接纳、提交和失败回报边界可管理。

WAL 的读写路径

修改页先追加到 WAL，读事务记录一个可见提交边界，读取时组合数据库文件与该边界前的 WAL 页，从而获得一致快照。写者可继续追加，不必让读者看见中途变化。WAL 允许读写并行，但仍只有一个写者能在同一时刻推进写事务，并不是“所有操作无锁”。

checkpoint 与长读事务

checkpoint 把已提交 WAL 内容迁回主数据库；若仍有读者依赖较旧快照，回收或推进会受限制。长期不结束的查询可能导致 WAL 增长、I/O 和恢复压力。读连接独立很有用，但仍要限制长事务与查询范围，并观测 checkpoint 和 SQLITE_BUSY。

线程安全模式不等于业务安全

SQLite 编译和运行期线程模式决定内部互斥行为；即使 serialized 模式保护连接，也不能让多个线程随意交错 BEGIN、INSERT、COMMIT 还保持各自业务事务边界。连接归属、语句寿命和事务所有权应由应用明确规定，而不是寄希望于库内部锁自动猜测意图。

推演与反例

serialized 模式为什么不等于业务事务安全

SQLite 的 serialized 模式可在接口层对共享连接调用做串行化，但线程 A 的 BEGIN、线程 B 的 INSERT、线程 A 的 COMMIT 仍可能在业务上混用一个事务上下文。数据库内部互斥不理解“这些语句属于哪个请求”。因此连接使用权、预编译语句复用和事务范围仍需应用层管理，不能看到线程安全编译选项就随意共享连接。

WAL 的读快照怎么成立

写者把新页面版本追加到 WAL，读事务基于开始时可见的提交位置读取一致快照。读者不必因为每次追加而停止，但长读事务可能阻止检查点回收其仍需看到的历史版本，导致 WAL 增长。独立读连接缓解互相干扰，却不消除文件级锁、检查点和磁盘容量约束。

继续追问

WAL 开启后为什么仍会遇到忙？

写者间仍需串行，checkpoint、锁升级和其他操作也可能竞争。应按错误类型与事务状态设计有限等待/重试，不可无限循环 SQLITE_BUSY。

多开几个写线程就能线性提升 SQLite 吞吐吗？

通常不能，文件级写者竞争仍存在，反而增加锁等待。先减少每行提交开销、复用语句并缩短事务，再用测量判断是否需要换存储架构。

T055 原理问答

批量写入为什么能提速，怎样控制额外延迟？

批量写入的收益主要来自把多条记录合进较少的事务，摊薄事务与同步开销。是否额外等待攒批，是另一个策略选择，直接影响低负载延迟。

原理与成立条件

批量为什么能加速

每条记录各开一次事务，会重复承担事务管理与同步成本。多行共用一次事务可摊薄这些固定开销，复用预编译语句还可减少解析与编译 SQL 的工作。收益取决于存储与事务配置，不是“插入次数除以批大小”就能得到性能倍数。

三种批量边界

按行数限制内存，按时间限制低负载等待，按字节数限制大记录；实际可组合使用。等待凑满批会增加首条记录延迟，机会式批处理则只合并已经排队的数据，不主动等新数据。两者需要明确区分，尤其不要把一个行数阈值描述为定时刷新机制。

失败时批次怎样定义

批量事务必须检查 BEGIN、每次绑定/step 和 COMMIT，失败时按事务状态回滚并回报。若 BEGIN 失败仍继续执行，语句可能落入不同事务语义；若中间某条失败却继续提交，可能形成部分成功。接口需要返回提交结局或明确允许逐项成功，不能仅因使用了 BEGIN 字符串就宣称原子批次。

排队与确认的业务边界

入队成功说明任务被内存队列接纳，数据库提交才说明到达数据库层的持久边界。进程在二者之间退出会丢队列内容。控制任务如换库或停止不能被跨越合并，否则先后关系被改变；批处理优化应服从业务顺序，不应把控制标记当普通行忽略。

推演与反例

两种批处理的延迟不同

固定每 100 ms 刷一次，即使只有一条数据也可能多等近 100 ms；机会式批处理先阻塞等第一项，再立即取走此刻已有项，到数量上限或暂时无数据就提交。前者主动攒批提高合并机会，后者利用已有积压，空闲时延迟更低。两者都必须限制单次批量，避免大事务长期占写锁或拖住资源切换。

上限单位必须一致

队列容量可能按任务数计，一个任务又包含多行记录；事务阈值可能按行数计，加入最后一个任务后实际行数可略超阈值。算内存和延迟时不能把“1024 项”直接当“1024 条传感数据”。还要考虑字符串、vector 容量与队列节点开销，不能只乘 payload 长度。

继续追问

批次越大越好吗？

更大批次占用更多内存、延长锁持有和失败恢复时间，也可能恶化查询及尾延迟。需在吞吐、最大等待和恢复成本间选择。

合批时遇到“切换数据库”任务怎么办？

它应作为顺序屏障：先把屏障前的行写入旧连接，再切换，屏障后数据使用新连接。跨过控制任务继续合批会破坏提交顺序。

T056 原理问答

ACID、WAL 和断电安全有什么关系？

ACID 分别描述原子性、一致性、隔离性和持久性，WAL 是实现事务与并发的一种机制，不是“绝不丢数据”的开关。持久性还依赖同步配置、文件系统和存储设备兑现写入承诺。

原理与成立条件

ACID 应分别解释

原子性要求事务效果整体成立或撤销；一致性要求事务维护已定义的约束，数据库不能自动理解全部业务规则；隔离性约束并发事务互相可见的方式；持久性描述成功提交后在规定故障条件下保留。隔离级别与错误处理仍需单独讨论，不能把四个词合成“绝不丢数据”。

WAL 为什么有助于恢复

先把可恢复的修改和提交信息写入日志，再在适当时机迁入主文件；恢复时依据日志识别完整提交，避免把未完成事务误当成功。数据库文件和 WAL 共同构成当前状态，运行时随意只复制主文件可能丢掉最新数据，备份应使用一致的数据库备份方式。

返回值是事务证明的一部分

提交可能失败，I/O 错误、空间不足和锁竞争都要检查。某些错误会改变事务是否仍活跃，不能盲目重试同一语句或报告成功。业务 API 若完全不向上游暴露提交结局，上层最多知道已尝试写入，无法构建严格的端到端提交确认。

推演与反例

COMMIT 与 checkpoint 各做什么

WAL 模式提交记录让这一批变化成为已提交事务，checkpoint 再把合适的 WAL 页面合并到主数据库。提交不要求每次都把全部变化写回主文件，所以能减少随机写与等待；恢复时依据 WAL 中的提交边界判断哪些变化有效。长读事务可能限制检查点推进，因此需要监测 WAL 大小与读事务时间。

NORMAL 与 FULL 的具体差别

WAL 配合 synchronous=NORMAL 在正常条件下保持事务原子性与一致性，但系统掉电或操作系统崩溃可能让已经返回成功的最近事务回退；FULL 在每次提交增加必要同步以提高该层持久保证。进程自身崩溃与整机断电不同，页缓存仍在时恢复条件更好。无论何种设置，硬件若谎报同步完成，软件也无法单独证明物理介质已保存。

继续追问

fsync 成功就能保证任何硬件故障都不丢吗？

它建立操作系统和设备承诺下的持久边界，不涵盖失效介质、虚假缓存刷新实现或物理毁坏。面试中需说明故障模型，而非给无限保证。

一个事务里单条 INSERT 失败，会自动整批回滚吗？

取决于错误类别、冲突策略和应用如何处理。应用若记录错误后继续执行并提交，可能形成部分业务成功；必须明确检查返回值并给出批次失败策略。

T057 原理问答

索引、预编译语句和查询上限为什么重要？

索引减少定位和排序的工作，预编译语句减少重复解析并支持安全参数绑定，查询上限限制结果生成与传输成本。它们解决的瓶颈不同，应按真实查询模式组合。

原理与成立条件

B-tree 索引怎样减少扫描

索引按键有序组织，先通过树定位范围，再扫描匹配项，避免逐行检查整表。组合索引按多个字段的字典序排序，查询条件对前导字段的约束决定能缩小多少范围；不能把“最左前缀”简化为后面的列绝对毫无价值，优化器还会考虑排序、覆盖、统计和其他访问策略。

用实际查询推导索引

例如按 device_id 等值、ts 范围查历史并按 ts 排序，可考虑 (device_id, ts)。若只按 ts 跨设备查询，该索引未必最合适。索引包含查询所需全部列时可能覆盖查询、减少回表；代价是额外空间和每次写入的维护成本，不能给每列都建索引后再谈写入性能。

预编译与绑定分别解决什么

prepare 把 SQL 编译成可执行语句，重复执行时 bind 参数、step、reset 并按需清理绑定，减少重复编译。绑定值还避免把用户输入拼进 SQL 语法，但表名/列名等标识符通常不能当普通值参数绑定，需要白名单构造。绑定内存的复制与寿命策略也要遵守接口契约。

怎样判断优化是否生效

看 EXPLAIN QUERY PLAN 与代表性数据上的延迟，区分全表扫描、索引查找、排序临时结构和结果返回成本。LIMIT 不能消除大 OFFSET 的跳过成本，大量历史翻页可考虑按稳定键进行游标翻页。测量要带数据量、分布、缓存冷热和并发负载。

推演与反例

联合索引为什么看字段顺序

查询 WHERE device_id=? ORDER BY ts DESC LIMIT n 时，以 device_id、ts 排序的索引可先定位某设备范围，再按时间方向扫描少量记录。若只建相反顺序，可能需要遍历更多候选项。等值过滤、范围过滤、排序方向和覆盖列都会影响计划，最终用 EXPLAIN QUERY PLAN 核对，不能只凭“建了索引”判断有效。

绑定值不等于拼 SQL 文本

预编译后用 bind 传递参数，使用户输入作为值解释，避免把引号或运算符拼进 SQL 结构。表名、列名等结构通常不能靠普通值参数代替，需要白名单。语句复用还要正确 reset、处理绑定数据寿命和错误码；数据库行指针一般只能在接口规定期间使用，返回给业务前应取得必要副本。

继续追问

查询只有十行，为什么仍慢？

可能先扫描或排序了大量候选数据，最后才 LIMIT；返回行数少不代表访问行数少，要查执行计划和条件的可用索引。

索引越多越好吗？

每次写入还要维护索引，占用磁盘和缓存。应围绕高频查询建立必要索引，并衡量写放大与实际扫描量。

T058 原理问答

为什么异步日志要在锁外写盘，队列满怎么办？

异步日志把磁盘 I/O 从调用线程移到消费者线程，但生产者仍承担格式化、同步和排队开销。锁应只保护缓冲交接，慢写盘放在锁外；队列满时的策略必须显式定义。

原理与成立条件

异步日志改变了哪段成本

业务线程把记录写入内存缓冲或队列，后台线程集中写文件，将磁盘等待从业务路径移开。格式化、复制、锁与入队仍发生在前台，严重过载时还有满队列问题。所谓异步只描述交接模型，不代表日志开销为零或日志已经落盘。

双缓冲的交接规则

生产者写当前缓冲，满时把它交给后台并换到空缓冲；后台独占待写缓冲直到 I/O 完成。交换应在短锁内完成，实际文件写出尽量在锁外。没有空缓冲时要选择阻塞、丢弃或降级，不能同时让两方写同一块内存，也不能后台未完成就复用。

顺序与持久化边界

同一队列可保留入队顺序，但多线程日志的打印时间不等于事件真实发生顺序；时间戳应尽量在事件发生处记录。write 成功、用户缓冲刷新和 fsync 也属于不同持久边界。发生崩溃时异步日志可能丢尾部，关键审计记录需要更强策略和成本预算。

日志系统也要能失败

磁盘满、路径权限、写入 EINTR/短写、零进度与后台线程退出都要处理；错误报告不可递归调用同一个失败日志通道。要限制记录长度、速率和队列高水位，避免故障时每次重试都打印大量日志，把原始故障放大为 I/O 与内存雪崩。

推演与反例

双缓冲怎么减少临界区时间

生产者向当前缓冲追加，缓冲满或需要刷新时，在短锁内把整块缓冲转交待写队列并换上空缓冲；消费者取得待写块后释放锁，再循环处理短写与错误。若消费者一直拿着同一把锁写文件，其他线程仍会被磁盘延迟阻塞，名义上的后台线程就失去主要价值。

有限缓冲必然需要取舍

磁盘暂停期间到达日志总量超过队列容量，有限内存无法同时做到永不阻塞、永不丢失和无限接纳。可按级别丢弃、采样、阻塞关键日志或降级到另一通道，并累计丢失数。日志若用于业务审计，通常需要比调试日志更强的持久化与失败契约，不能只共用一个“尽力写”的接口。

继续追问

把 flush 调得越频繁是否越安全？

先确认 flush 指向用户缓冲、内核写入还是设备同步；频繁同步会增加时延，只能在明确故障模型下讨论更强持久性。

write 成功后日志就能抗掉电吗？

通常只能说明数据被相应内核路径接纳；还要看 fsync/fdatasync、文件系统和介质。线程排空、内核接纳、介质持久化是不同完成层级。

T059 原理问答

配置快照、资源切换与事务原子性是什么关系？

原子替换配置指针可以让读者看到完整的新快照，却不能让数据库、串口和网络客户端一起原子切换。内存发布与外部资源变更属于不同事务边界。

原理与成立条件

不可变快照怎样发布配置

读取方一次取得完整配置对象，此后只读；更新方先解析并校验新对象，再原子替换共享指针。读者可以继续持旧版本，不必在每个字段访问时加锁，也不会读到新旧字段混合。发布顺序和对象保活分别由原子同步与共享所有权承担。

指针替换不是资源事务

配置中的串口名、数据库路径或网络参数会触发外部资源变更。新配置对象合法，不代表新串口能打开、新数据库能写或 broker 可连接。如果先公布配置再逐一重建失败，就可能出现“显示新配置，部分资源还按旧配置运行”的混合状态。

两阶段更新的思路

先解析、做字段间一致性校验，并尽可能准备候选资源；条件满足后在拥有资源的线程提交切换，最后公布生效版本。无法提前准备或无法回滚的外设，需要显式部分失败状态与恢复动作。整个过程的失败语义应设计出来，不能仅靠 try/catch 恢复全部外部效果。

并发更新与版本观测

多次重载可能交错，候选异步完成时需要版本或代数检查，避免旧准备结果覆盖新配置。向用户区分期望版本与实际生效版本，日志记录失败资源及保留策略。配置对象每次都相等也不代表上次资源重建成功，重试逻辑不能仅比较字段后跳过修复。

推演与反例

一次重载为什么会出现混合版本

先发布新配置，再依次重建数据库和串口，如果数据库成功、串口失败，读取配置的线程看到新串口路径，实际 I/O 仍可能走旧端口。若允许这种降级，应暴露期望版本与实际生效状态；若要求全有或全无，就要预构造候选资源、验证后在受控点提交，并处理无法回滚的外部动作。

不可变快照怎样减少读侧锁

加载新配置时先构造完整对象并校验；发布后不再原地修改，读者一次取得一份共享所有权，整次操作都用这份快照。这样避免读一半旧字段、一半新字段，旧读者也不会因替换而悬空。但同一操作若反复重新加载指针，仍可能跨越版本，应让快照范围与业务操作范围一致。

继续追问

atomic shared_ptr 就是无锁配置系统吗？

不保证原子共享指针实现 lock-free，资源重建也可能阻塞；它主要保证一致发布和生命周期，不是对所有路径的性能承诺。

为什么配置语法正确仍不能保证重载成功？

路径可能打不开、端口可能被占用、Broker 可能拒绝连接。语法校验与资源可用性验证是两步，生效结果必须按实际执行反馈。

T060 原理问答

如何有序切换后台资源而不破坏读写一致性？

切换一个被后台消费的资源，最好让“切换”与普通数据经过同一条有序通道。这样顺序本身确定哪批数据属于旧资源、哪批属于新资源，避免读写侧各自切换而短暂错配。

原理与成立条件

热切换要先定义分界点

“换数据库”必须说明旧数据写到哪、新数据从何时写到新库。按墙上时间切分可能受线程排队影响；在单写者 FIFO 中插入切换控制项，可以令其之前任务先处理、之后任务使用新连接，建立可观察的顺序边界。

读者为什么需要保留旧连接

切换时已有请求可能正在查询旧库。立即 close 旧连接会让它们悬空或失败；读请求取得共享连接快照，切换只改变后来请求取得的指针，最后一个旧请求结束再释放旧连接。这个机制解决寿命，不会把跨库查询变成一致事务。

候选连接如何失败

可先打开和校验候选库，再排入切换控制项；若准备失败，旧库继续提供服务。若切换完成通知晚到，又发生新一轮切换，需要防止旧完成覆盖当前读连接。候选资源的拥有者也必须覆盖队列等待和回调寿命，失败时明确释放。

切换不是数据迁移

新库可为空，旧历史仍留在旧文件；要合并历史需单独迁移与查询策略。批处理不能把切换前后记录合成一个跨边界批次，也不能在旧任务没执行完时提前关闭写连接。停止与切换同时出现时同样需要统一控制项顺序。

推演与反例

把控制任务放进数据队列的效果

队列为数据 A、数据 B、Swap、新数据 C。消费者先完成 A、B 对旧连接的写入，再替换连接，之后 C 使用新连接。切换完成时发布读侧新连接，才可保证读侧不会先看到一个还未被写侧接管的新库。Swap 入队成功只表示将来会执行，不等于切换已经完成。

旧资源何时可以销毁

正在处理查询的读线程可能还持有旧连接，切换后新查询用新连接，旧查询允许完成并释放自己的引用。写连接的替换也必须等此前批次结束。共享所有权解决“何时最后一个使用者离开”，有序控制任务解决“什么时候逻辑切换”，两种机制各有职责。

继续追问

指针已换到新库，为什么页面还看到旧记录？

已有请求可能持旧快照，这是允许的请求级一致性；如果要求全系统同一瞬间切换，就需要暂停入口、等待旧请求排空等更强协调。

切换任务进不了满队列怎么办？

应返回明确失败或在有限期限内等待，保留旧资源继续运行；不能先把配置标成已生效，再默默丢掉切换任务。是否允许这种暂时不一致应由接口定义。

T061 原理问答

优雅退出为什么要先停止生产者，再排空消费者？

优雅退出按照依赖顺序结束工作：先停止产生新任务，再关闭队列入口、唤醒消费者，按契约排空或取消，等待线程退出，最后释放被借用资源。这个顺序与构造顺序相反但并不总能只靠默认析构自动完成。

原理与成立条件

停机首先停止谁

先停止新的生产和接纳，才可能让存量工作稳定减少；之后通知消费者按约定排空或取消，等待线程结束，再关闭被使用资源。若消费者先退出而生产者继续入队，会留下永远无人处理的任务；若先释放回调依赖，停止过程中可能出现释放后使用。

排空必须与最终提交区分

队列为空只说明任务已被取走，后台可能仍在写数据库。需要消费者处理完当前任务并报告退出，才能确认内存处理阶段结束；最终是否提交成功还取决于错误回报。join 保证线程终止，不自动证明其所有业务成功。

退出等待也需要唤醒路径

stop 标志不能叫醒条件变量、epoll 或阻塞设备调用。为每个等待点设计 close/notify、eventfd 或有限超时；等待者醒来后用状态谓词判断退出。线程不应持有另一个退出线程所需的锁再 join，否则关闭流程本身形成死锁。

有限退出和故障策略

系统服务管理器通常有停止期限，到期可能强制终止。应用应让关键数据优先提交、次要日志有界排空，并记录未完成数量。无限 I/O 会使“优雅退出”没有完成上界；一开始就选择有限等待与可取消接口，通常比析构时补救更可靠。

推演与反例

为什么先销毁队列会产生悬空访问

网络回调可能还在运行并准备入队，如果主线程已经释放队列或 eventfd，回调会访问无效资源。先停网络生产者并等待其线程结束，再关闭队列，消费者才能在“不会再有新项”的前提下安全排空。对相互依赖线程还需避免一边持锁一边 join，防止被等待线程正需要同一把锁退出。

排空也必须有业务边界

写数据库能否一直等、远端离线时是否继续重试、日志失败是否阻止进程退出，都需要明确。有限退出期限可能意味着最终取消部分任务，此时应给请求终态并保存必要恢复记录。队列空只说明这一层消费完，后面若还有内核缓冲、网络发送或持久化步骤，不能据此宣称业务全部完成。

继续追问

进程正常退出时 OS 会回收资源，为何还要自己关闭？

OS 不能替业务完成队列提交、发送结果或维护设备状态；正常资源回收也有助于发现泄漏和保证嵌入其他程序时的正确性。

为什么 detached 线程不适合随意使用？

对象析构后无法自然 join 它，后台线程可能继续借用已经释放的成员。除非生命周期独立且清楚管理完成协议，否则显式所有者和可等待退出更易证明正确。
