P007 项目问答

串口 Reactor 与业务线程的职责怎样严格区分？

面试时这样回答

串口 Reactor 管非阻塞读写、增量拆帧、CRC，以及会话、序号、窗口、确认和重传这些链路状态。GatewayCore 管命令解释、遥测单位转换、MQTT topic/payload、业务结果映射和 HTTP 路由；SQLite 查询与写入再提交专用执行线程。

链路处理留在 Reactor，是因为它紧贴部分写完成、收到 ACK 和超时扫描，需要单一状态所有者。收到遥测帧或完成事件后只交接消息，不在串口回调中格式化业务结果。业务提交命令后继续消费其他事件，不阻塞等节点响应。

实现依据与展开

两类状态与两个时间点

CommandTracker 独占的是链路请求状态，串口整帧被内核接受后才更新本次发送时间。GatewayCore 消费的是已拥有存储的应用事件；帧完成不等于业务处理完成，业务完成也不等于 MQTT 对端已确认。

事件源依据

串口主 epoll 等待串口读写、eventfd 跨线程提交与停机通知、timerfd 单调时钟扫描，不再监听 signalfd。独立 gateway-admin 用自己的 epoll/signalfd 接收管理信号，并用自己的 eventfd 唤醒退出。MQTT/HTTP 各有网络循环，GatewayCore 和管理工作线程等待任务队列，不另算 I/O Reactor。

继续追问

Reactor 是否必须完全不解析任何协议？

不需要。消息定界、CRC、HTTP/MQTT 解析和轻量链路状态属于通信层；业务字段解释、传感器单位、路由与 SQL 属于应用层。边界按责任和耗时界定，不以函数里有没有 if 或状态机来区分。

串口 ET 排空和局部资源操作仍需单独分析耗时；采用多循环不证明所有高负载尾延迟已经验证。

P008 项目问答

MQTT 到业务线程再到串口，为什么需要两次消息交接？

面试时这样回答

MQTT 网络回调先把拥有独立存储的原始消息交给 GatewayCore；业务线程被任务队列的条件变量唤醒，解释命令后才提交串口下行队列并写 eventfd。第一段隔离 MQTT 收发与业务解析，第二段保证串口和链路状态只由串口 Reactor 修改。

串口 Reactor 被唤醒后以实际队列与链路许可为准消费命令，不把 eventfd 计数当作命令数量。一次只处理有限批次，仍有可处理任务就重新安排；会话未就绪或 SR 窗口满则等链路状态推进，避免没有发送能力时忙循环。

继续追问

为什么不按 eventfd 读出的数值恰好处理同样多命令？

多个通知可合并，消费者也可能主动续发通知；计数和业务条目不是一一对应。队列保存消息，eventfd 仅让事件循环知道可能有工作，不能替代容器同步和接纳策略。

当前实现边界

有界队列和有限批次不自动建立全链路背压。已经被 MQTT 协议接收但业务队列拒绝的消息，仍须按应用失败契约解释，不能声称 QoS 自动保证设备执行。

P009 项目问答

串口为什么用 ET，读到 EAGAIN 有什么意义？

面试时这样回答

串口使用非阻塞 fd，收到可读事件后循环读取，把每次实际读到的字节送进增量解析器，直到 EAGAIN 才返回。ET 不保证对已经留在内核里的剩余数据再提醒一次，所以不能只读固定一帧就退出等待。

这里一次 read 与一条协议帧没有对应关系。解析器保留半帧状态，能处理一次读到半帧或多帧。EINTR 会重试，EAGAIN 表示当前没有更多进展，其他错误则记录并结束这次读取。

P010 项目问答

短写和 EAGAIN 时，怎样保证帧不会交错或重复前缀？

面试时这样回答

网关发送队列保存完整编码帧和当前偏移。一次 write 只接受部分字节，就只推进相应偏移；遇到 EAGAIN 保留剩余部分，等可写事件继续。队首帧没写完之前不发送后面的帧，所以不会把两条帧的字节交错。

整帧被内核接受后才通知命令状态机启动这一轮等待确认的计时。尚未开始的旧请求可以通过身份检查取消；已经写出一部分的帧不能随意扔掉后缀，否则会破坏对端字节流。

为什么只在有待发数据时监听 EPOLLOUT？

P011 项目问答

回调里关闭连接，怎样避免访问已经释放的对象？

面试时这样回答

epoll_wait 一次可能返回多个 Channel 指针。处理前面的回调时，如果删除了后面某个 Channel，事件数组里仍保留它的旧指针。因此注销后先标记失效，并暂存一份所有权，等整批事件处理完再释放。

派发时跳过失效对象；一个读回调也可能删除自己，所以再调用写回调前还要检查一次。这里同时处理了逻辑失效和内存寿命，单纯从 map 删除或从 epoll 注销都不够。

P012 项目问答

退出与重载怎样通过 signalfd 和跨线程屏障协作？

面试时这样回答

main 在线程启动前统一屏蔽 SIGHUP、SIGTERM、SIGINT，屏蔽失败立即退出。独立 gateway-admin 线程运行 ManagementReactor，以 epoll/signalfd 接收信号；SIGHUP 只投递任务给 gateway-manage，TERM/INT 则直接设置停机状态并通过主 eventfd 唤醒串口 Reactor，不排在慢重载任务后面。

析构先设置入口停止状态并停止、等待管理 Reactor 退出，防止继续产生重载和停机回调；再 shutdown 下行与候选队列并等待 HTTP 循环，把已排队或在途命令交给业务线程形成 shutdown 终态。随后 Core 屏障确认任务提交，query 排空，Core 排空完成事件，管理工作线程排空，最后 MQTT join 和写库排空。

实现依据与展开

管理事件与耗时任务分开

ManagementReactor 的 signalfd 回调只发出重载/退出通知，不读配置文件、不连接 Broker、不 join 工作线程。它自身 stop 设置停止状态并写管理 eventfd，叫醒 epoll_wait；TERM/INT 到串口的通知使用主 eventfd，是另一条资源与唤醒路径。

启动和异常边界

初始 MQTT 创建任务先进入管理工作队列，再创建 ManagementReactor，最后由启动主线程等待初始化 future。因此初次同步连接期间管理线程已能接收信号，但主线程仍须结束初始化等待才能处理事件；不能据此承诺立即退出。管理 fd 全部成功创建/注册后才启动线程，事件循环异常通过失败回调通知主线程停止。

为什么查询需要独立屏障

如果 core 先关闭，尚未完成的 SQL 就无法把结果投回；如果 query 先关闭，尚未运行的 HTTP 业务又可能继续提交 SQL。屏障确认此前 HTTP 已完成任务提交，再关闭 query，最后关 core，保证生产者与消费者的依赖顺序。等待仅由退出所有者执行，正常 Reactor/业务任务不等待。

继续追问

MQTT 为什么最后才 join，是否还会投递到已经关闭的业务对象？

stopping 先让网络入口返回，已进入回调的尝试由 Core accepting 和邮箱关闭协议拒绝；Core 对象一直保留到 MQTT 停止之后。HTTP 迟到回复则由失效的 ReplyBridge 丢弃，不能向已销毁的 io_context post。

管理工作线程卡在 connect 时，还能接收 TERM 吗？

可以，独立管理 Reactor 不等待该工作线程，能先通知串口停止；但进程最终析构仍要 join管理工作线程，慢 DNS/connect/loop_stop 可能拖长完成时间。快速发出停机请求与全部线程已退出是两个边界。

当前实现边界

排空邮箱只证明任务已处理或交给下一层，不保证 MQTT PUBACK、远端业务执行或数据库提交全都成功。独立管理 Reactor 没有提供阻塞系统调用取消能力，当前不承诺网络故障下的完整退出时间上界。

P013 项目问答

C++ 的 RAII、移动语义和共享快照在项目中分别起什么作用？

面试时这样回答

RAII 负责让串口、线程和连接等资源跟着所有者生命周期释放；移动语义把完整帧或连接交给后续消费者，避免不必要复制；共享快照则用于让正在运行的读者继续持有旧版本。三者分别解决资源释放、交接成本和并发读寿命。

例如串口发送队列持有完整 vector，不借用临时组帧数组；写库线程持有自己的数据库连接；配置更新时发布新快照，已经取得旧快照的操作可以继续完成。只靠一个裸指针或把变量声明为 volatile，做不到这些保证。

P014 项目问答

为什么换成 Boost.Beast，HTTP 与业务线程怎样配合？

面试时这样回答

HTTP 协议解析和异步收发改用 Boost.Beast/Asio。独立线程运行 io_context，连接用 async_read 跨读取拼出完整请求，再把拥有自身存储的请求投递 GatewayCore。路由与参数校验在业务线程执行，历史数据查询提交独立读执行线程。

查询完成后生成响应，通过完成函数投递回连接所属 io_context，最终 async_write 发送。连接对象和响应对象保持到相应回调结束，慢查询不占住 HTTP 事件循环，业务线程也不通过 future.get 等待查询。第三方库减少自行维护 HTTP 定界、错误解析与短写的负担。

每个 HTTP 请求是否都建立一个新线程？

不是。多个连接共享 HTTP I/O 线程；GatewayCore 共享业务线程，SQL 共享有界读执行器。每个连接保存自己的解析、等待和响应状态，当前请求完成后才推进后续响应顺序。
