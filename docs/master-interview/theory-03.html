Linux I/O 与事件驱动

T026 原理问答

select、poll、epoll 的区别，epoll 真的是 O(1) 吗？

select、poll 每次提交要检查的描述符集合；epoll 把关注集合长期保存在内核中，由事件把相关描述符加入就绪集合。它主要减少大量空闲连接下反复传递和扫描集合的工作，不代表整个服务器所有操作都是 O(1)。

原理与成立条件

select 与 poll 在做什么

它们接收本次关注的描述符集合，内核检查这些对象的状态，返回后应用再识别哪些可读写。select 使用位图及 nfds 范围，常见 glibc fd_set 有 FD_SETSIZE 限制；poll 使用结构数组，没有同样的位图上限，但仍受系统 fd 与资源限制。集合很大而活跃项很少时，反复传递和扫描有成本。

epoll 的区别在哪里

epoll 把关注关系长期注册在内核中，通过 epoll_ctl 增删改；epoll_wait 返回本次就绪项，避免应用每次重新提交所有关注对象。内核通过被监视对象的通知机制维护就绪状态。因此它对大量空闲连接很合适，但注册、注销、事件复制和回调执行仍然有成本。

为什么不能背“epoll 永远 O(1)”

一次返回 k 个事件至少要处理 k 项，连接频繁变化还会增加控制操作，全部连接持续活跃时也要执行全部业务。不同实现的数据结构复杂度不能替代端到端成本模型。连接少时，poll 的简单数组和局部性也可能足够好，不能仅凭 API 名称宣称性能提升倍数。

就绪集合并非完整业务结果

读就绪可能代表有字节、EOF 或错误；写就绪只表示可能写入部分内容。事件也会合并，不能按事件次数计算消息数。应用必须继续检查实际 I/O 返回值、保存部分状态，并处理错误、挂断和资源关闭。事件驱动的正确性来自这些状态规则，而不只是调用 epoll_wait。

推演与反例

用 N 个连接、K 个就绪连接看成本

select/poll 的一次等待通常需要处理规模为 N 的集合，返回后用户也要找到哪些项就绪；epoll_wait 主要交付就绪项，应用仍至少处理 K 个结果。注册变更、内核回调、锁、复制和业务处理都有成本。若 N 很小或几乎所有连接都持续就绪，epoll 的优势未必明显；“10 万连接”也不代表 10 万个连接都能同时执行复杂业务。

描述符数量之外还有什么限制

select 的常见 fd_set 有固定表示上限；poll 没有同样的位图接口限制，但集合仍需传递和扫描。epoll 关注表同样占内核内存，并受到资源限制。连接规模还受 socket 缓冲、用户对象、HTTP 输入上限、fd 限额和每连接处理成本影响，不能只调高 ulimit 就认为系统具备相同容量。

继续追问

epoll 比 select 快，是否因为它完全没有用户态与内核态复制？

不是。就绪事件仍需要交付给用户态，实际读写也可能复制数据。主要区别在关注集合的维护和就绪分发方式，不能称为自动零拷贝。

epoll 是零拷贝接口吗？

不是。它改变就绪事件的管理方式，事件数组仍要交付用户态，实际 read/write 也可能复制数据。I/O 多路复用与数据零拷贝是不同问题。

T027 原理问答

ET 和 LT 的区别，为什么 ET 要读到 EAGAIN？

LT 在就绪条件持续满足时仍可报告，ET 主要报告就绪状态的变化。ET 要求应用记住尚未处理完的工作，通常以非阻塞 I/O 读写到 EAGAIN 才重新等待，否则可能把已经存在的数据留在内核里。

原理与成立条件

为什么要用非阻塞并读到 EAGAIN

循环 read，正数就消费，EINTR 按语义重试，EAGAIN 表示暂时无法继续，此时才能可靠回到事件等待。如果 fd 是阻塞的，读完已有数据后的下一次 read 可能把整个事件循环挂住。EOF、设备错误与串口特殊 read 语义还需要分别处理，不能统一作为 EAGAIN。

写事件应该怎样管理

业务先把待发数据放入输出缓冲并尝试写；写不完时保留偏移并关注可写事件，继续直至缓冲排空或 EAGAIN。LT 下无数据仍一直监听 EPOLLOUT，容易不断醒来形成空转。输出缓冲也要有上限，慢对端可能让内存增长远快于内核缓冲消耗。

一直读到空会不会饿死其他连接

会。高吞吐连接可能持续补入数据，让一次回调占用过久。可设置字节或时间预算，但 ET 下提前退出时必须把该连接留在应用就绪队列，主动轮转继续处理；直接再次等内核新边沿会丢失继续推进的机会。公平与 ET 完整消费必须一起设计。

推演与反例

半读为何可能永久等不到下一次通知

管道已有 2 KB，收到一次可读事件后只读走 1 KB。剩余 1 KB 仍可立即读取，但状态没有经历新的“从不可读到可读”的转换；如果对端等你的应答而不再写，你再 epoll_wait 就可能卡住。读到 EAGAIN 表示这一轮可取得的进展已耗尽，再等待才有依据。就绪只是提示，最终仍要按 read 的返回值判断。

读到 EAGAIN 与公平性怎样兼容

持续高流量可能让一个连接长时间都读不到 EAGAIN，饿死其他连接。可为每轮处理设置预算，同时把该连接保存在用户态待处理集合，轮转后继续读；只有真正耗尽时才移除。不能达到预算就丢掉待处理标记、直接等下一条 ET 通知，否则又回到漏处理问题。写方向也应只在有待发数据时关心 EPOLLOUT。

继续追问

EPOLLONESHOT 能代替并发保护吗？

它可在一次报告后暂停该关注项，便于把连接交给一个工作者，处理后需重新 MOD 激活；对象生命周期、其他入口访问和重新激活的竞态仍要管理。

EPOLLONESHOT 能自动解决并发安全吗？

它能让一次事件交付后暂停该项通知，便于由一个工作者处理后重新激活，但对象寿命、缓冲同步和 rearm 时机仍由应用负责。

依据与核对范围

epoll(7) — 就绪集合、ET/LT、EAGAIN 与事件生命周期。

T028 原理问答

串口短写、EINTR、EAGAIN 分别怎样处理？

短写表示这次调用只接受了前一部分数据，EAGAIN 表示目前无法继续，EINTR 表示被信号中断。正确发送器保存未发送后缀及偏移，只在能够继续时推进，不能把它们统一当作整帧失败后从头重发。

原理与成立条件

三类结果要分别处理

EINTR 通常表示在没有返回有效进度前被信号打断，应结合接口语义重试；EAGAIN/EWOULDBLOCK 表示非阻塞条件暂不满足，要等就绪。其他错误按连接或设备故障处理。对非零请求意外返回 0 的写操作，应防止无限零进度循环，而不是无条件重试到 CPU 满载。

本地提交、线路完成和对端接收

串口 write 成功常表示数据进入驱动/内核缓冲，硬件可能还在发送。tcdrain 等待终端输出传输完成，但仍不能证明对端正确接收和执行。应用层 ACK 才能增加对远端状态的认知，因此命名发送回调时应精确描述它确认的是哪一步。

取消发送为何需要状态

帧尚未写出任何字节时，可从输出队列直接删除；已有前缀发出后，通常需要继续发送完整帧，或使用双方约定的链路复位/重新同步机制。取消业务等待和停止线路传输是两个动作。缓存必须一直活到驱动不再访问，不能超时就释放仍被异步发送使用的内存。

推演与反例

用 100 字节演示状态推进

初始 offset=0，write 返回 40，就把 offset 改为 40；下一次从 data+40 发送剩余 60。返回 EAGAIN 时偏移不变，保留数据并等待可写；返回正数即消费那部分进展。若所有 100 字节都被内核接受，才完成本地提交。若此时业务期限到了，已写出的前 40 字节不能从线路撤回，随意丢掉后缀再写新帧可能破坏对端分帧。

错误处理为什么必须保留错误类别

真正的设备断开、无进展返回 0、暂时不可写和 EINTR 需要不同策略。回调还可能修改发送队列，所以完成当前项时应先取得回调、移除当前项，再调用外部代码，避免回调使正在引用的队首失效。fd 的发送完成只代表该接口约定的完成层级，不代表对端已经收到或执行。

继续追问

为什么单写者有助于正确处理短写？

它让偏移和帧 FIFO 只有一个修改者，避免多个线程把两帧余下部分交叉写入同一字节流。单写者并不免除容量限制和错误处理。

一个 write 返回整帧长度，RTO 就能忽略本地发送时间了吗？

不能，驱动或 UART 仍可能排队。RTO 起点可以选择“内核接纳完成”，但预算必须包含此后的本地发送、对端处理和返回延迟。

T029 原理问答

eventfd 为什么配一个队列，计数是否等于命令条数？

eventfd 是可纳入 epoll 的计数型唤醒通道，队列才保存命令或任务内容。通知可以合并，消费者以队列为真实状态，不能把读出的计数机械当作必须处理的命令数。

原理与成立条件

为什么要另配队列

队列保存数据与顺序，eventfd 告诉消费者“可能有新工作”。生产者先在同步保护下入队，再发通知；消费者醒来消费队列状态，而不是只按某一次事件次数推断队列内容。内核 fd 通知不能替代 C++ 对队列的互斥或原子同步，容器的数据竞争仍要单独解决。

有限批处理的继续条件

如果一次只消费 32 项，队列可能还有剩余，而 eventfd 累计值已被读空。此时必须让程序主动安排下一轮处理或再次通知；否则没有新生产者时，旧工作可能永远留在队列中。空队列与写入之间的竞态也要推演，但先入队后通知让多余唤醒通常只造成一次空检查。

计数器满和关闭如何处理

非阻塞写在计数器无法继续增加时可返回 EAGAIN；这往往意味着已有未消费通知，但仍需明确协议。关闭时先禁止生产者继续入队/写通知，再等待它们结束，最后关闭 fd；否则 fd 数值被复用后，旧生产者可能写到无关对象。EINTR 和写失败也不应被当作业务已消费。

推演与反例

两个生产者如何安全唤醒一个消费者

生产者先在同步保护下入队，再写 eventfd。消费者读取计数以清除通知状态，然后检查并消费队列；即使多个写被合并，队列中任务仍在。若先通知后入队，消费者可能醒来发现空队列并再次睡眠，生产者随后入队却没有新通知。入队顺序与唤醒协议必须成套考虑，eventfd 不会自动使一个不安全的容器变安全。

限额消费后还有数据怎么办

一次只消费 32 项可以降低对其他事件的干扰，但队列还没空时必须保留“还有工作”的事实，例如自行再通知或进入本地待运行列表。若只是把 eventfd 读到零然后提前返回，剩余数据可能要等下一位生产者碰巧唤醒。计数满时非阻塞写 EAGAIN 一般说明已有唤醒待消费，但其他写错误仍应处理。

继续追问

每入队一次就 write 1，读取数值是否等于当前队列长度？

不保证。消费者可并行取走数据，通知可以多余，其他生产者也可正好入队；队列自身才是工作数量的权威来源。

EFD_SEMAPHORE 改变什么？

普通读通常取走累计值并清零；信号量模式每次读返回 1 并递减计数。两者都不保存业务载荷，也不替代任务队列的容量与退出设计。

T030 原理问答

timerfd 怎样报告超时，时钟和定时精度如何选择？

timerfd 把定时到期变成可读事件，便于与其他 fd 在同一事件循环处理。定时器决定何时到期，线程何时获得 CPU、何时运行回调是另一件事，因此超时回调可能晚于配置期限。

原理与成立条件

定时器只报告到期

timerfd 把定时器到期变成可读事件，读取的 64 位数表示自上次读取后累计的到期次数。线程晚运行时可一次读到多个到期，不表示曾及时执行过多次回调。定时器分辨率、调度延迟和业务处理时间共同决定实际反应时间。

时钟选错会产生什么问题

CLOCK_REALTIME 表示日历时间，可能被设置而跳变；CLOCK_MONOTONIC 适合通常的经过时间，不含系统挂起时间；若期限需要把系统挂起也算进去，Linux 可考虑 CLOCK_BOOTTIME。超时逻辑应在同一时钟域比较，不能拿墙上时间戳减单调时间，也不能假设定时源不受平台配置影响。

三个时间点不能混淆

业务排队起点决定总寿命，真正提交发送决定一轮响应等待起点，获得接收确认后可能进入另一结果等待期限。若把发送重试时刻不断重置成总期限起点，持续重试可能使请求永不过期；若在长队列等待时就起短 RTT 定时，又会导致未发送先重试。

扫描精度怎样估算

每 Δ 毫秒扫描截止时间，理想情况下到期发现额外延迟小于一个扫描间隔；实际还要加调度与回调阻塞。因此“超时 500 ms”通常表示判断阈值，不能承诺恰在第 500 ms 回调。可改成按最近截止时间设单次定时，但仍不能免除执行者被阻塞的延迟。

推演与反例

相对期限为什么用单调时钟

墙上时间可能被校时向前或向后调整，用它计算“等待 500 ms”会产生误判；CLOCK_MONOTONIC 避免这类跳变，但不包含系统挂起时间，若业务要求把 suspend 算入期限，需考虑 CLOCK_BOOTTIME。绝对业务时间戳和相对超时应分别选时钟，不能用一个毫秒值隐去时钟域。

扫描周期怎样带来额外延迟

若每 200 ms 扫一次请求表，某请求在 t=501 ms 到期而上一轮在 500 ms 扫过，通常要到 700 ms 左右才被发现，再叠加回调排队和调度延迟。读取 timerfd 得到累计到期次数，可以知道错过了多个周期，但业务应按当前单调时间判断 deadline，不应简单把超时判定次数当真实经过时间。

继续追问

到期次数为 5，要把所有业务处理重复调用 5 遍吗？

不必然。计数告诉你错过了节拍，业务可按当前单调时间检查真实截止时间；周期控制是否补做、跳过或合并由业务决定。

把扫描周期改小一定更好吗？

它减少离散扫描误差，却增加唤醒和遍历成本。请求多时可用按截止时间排序的结构、时间轮或重设最近到期的一次性定时器；选型要结合数量和允许误差。

T031 原理问答

为什么用 signalfd，为什么要在创建线程前屏蔽信号？

signalfd 把选定信号转换成普通读取事件，使退出和重载逻辑在正常线程上下文执行。前提是相关线程正确屏蔽这些信号，避免信号走传统处理路径。

原理与成立条件

传统信号处理的限制

异步信号可能打断线程正在执行的库函数，因此处理器中不能随意调用非 async-signal-safe 的分配、日志或带锁函数。例如主线程持日志锁时被信号打断，处理器再取同一锁可能死锁。处理器应极简，或把信号转入普通执行上下文处理。

signalfd 怎样转换模型

先把目标信号加入信号掩码阻塞，再创建 signalfd 并纳入事件循环。信号产生后成为可读取的记录，程序在正常回调上下文执行停止或重载逻辑。signalfd 不是让信号失去语义，而是改变接收方式；哪些线程屏蔽该信号仍直接影响它会被谁处理。

为什么要在创建线程之前屏蔽

新线程继承创建者的信号掩码。主线程先屏蔽再启动工作线程，可以避免进程定向信号跑到某个未屏蔽线程触发默认处理。若线程已经存在，需要确保所有相关线程的掩码配置一致；只改主线程并不足以完成这个约束。

信号不能当可靠任务队列

普通信号待处理期间多次出现可能合并；实时信号有排队语义但也有资源限制。线程定向信号与进程定向信号还影响谁能接收。业务命令需要参数、顺序和可靠接纳时应使用专门队列或 IPC，而不是给每个业务动作随意分配一个普通信号。

推演与反例

为什么必须在线程创建前准备

线程有自己的信号掩码，新线程通常继承创建者当时的掩码。若部分工作线程已经运行且没有屏蔽进程定向信号，内核可能把信号交给它们，而不是让主线程通过 signalfd 消费。先设置掩码再创建线程，可以让继承关系成为设计的一部分；之后再创建 signalfd 仍不等同于自动修改所有线程掩码。

普通信号处理函数的限制来自哪里

信号可打断任意执行位置，例如线程正持有 malloc 或日志内部锁。处理函数再调用非异步信号安全函数，可能重入受损状态或死锁。signalfd 回调则在事件循环中的普通调用路径，可安排资源重建与退出；但回调依旧不能无界阻塞主循环。标准信号还可能合并，不能把它当可靠消息队列。

继续追问

收到退出信号后在 signalfd 回调里直接销毁所有对象可行吗？

仍要遵循生产者停止、线程 join、队列排空和资源释放顺序。普通上下文解除的是信号安全限制，不是生命周期约束。

SIGKILL 能通过 signalfd 优雅处理吗？

不能，SIGKILL 和 SIGSTOP 不能被捕获、忽略或这样接管。强制终止后的恢复必须依赖外部持久状态与启动恢复机制。

signal(7) — 信号上下文与屏蔽。

T032 原理问答

回调删除连接时，如何避免 use-after-free？

回调对象必须活到所有可能引用它的已排队操作结束。把 fd 从 epoll 注销只阻止后续注册产生事件，并不会抹掉已经返回到用户态事件数组中的指针。

原理与成立条件

为什么注销后仍可能访问对象

epoll_wait 已经把事件数组复制给应用，数组中的用户指针不会因稍后 DEL 自动被清除。处理事件 A 的回调可能销毁 B，而本批稍后仍有指向 B 的事件；同一个 Channel 的读回调也可能关闭自身，分派器随后若继续调写回调，就发生释放后使用。

把逻辑死亡和物理回收分开

先标记对象不可再处理，注销关注关系并关闭或接管 fd；但让对象至少活到当前事件批次不再引用它。批次分派时检查死亡标记，跳过后续回调。可用延迟销毁列表、稳定句柄或代数编号实现，关键是明确“最后一个潜在访问者”何时退出。

fd 复用为什么又是一层问题

操作系统可把刚关闭的 fd 数值交给新连接。延迟回调只比较数值，可能把旧结果应用到新连接。用连接代数或唯一 token 区分每一代生命周期；对象仍存活也不等于它代表的业务实例仍有效。地址复用造成的 ABA 同样需要身份规则。

多线程场景还需要什么

延迟一个 Reactor 批次只保护该线程的旧事件，无法保护其他线程正持有的裸指针。跨线程访问需要共享所有权、引用/读侧保护，或把请求送回对象所属线程处理。关闭过程还要定义晚到结果是否丢弃、如何释放其附带资源，不能只在开头判断一次 closed。

推演与反例

同一批事件如何触发释放后使用

epoll_wait 返回 A、B 两个指针，先处理 A 时关闭并删除 B；随后循环读到 B 的指针，它已经悬空。常见办法是把 B 标成失效，从活动集合移走，但暂存一份所有权，直到本轮事件批次处理完再释放。B 的条目被访问时先看失效标记；若读回调还能删除自身，写回调前也要再次确认。

更广义的代数与取消规则

定时器、线程池和网络库队列可能比一个 epoll 批次活得更久，单轮延迟回收不够。可使用 shared_ptr/weak_ptr、连接代数或显式取消完成确认。取消请求只是提出意图，只有保证回调不再运行或运行时能安全识别失效，才允许释放被借用对象；否则“取消了”仍可能与已取出的回调竞争。

继续追问

回调里拿到 shared_ptr 就绝对安全了吗？

它保护对象不析构，但对象可能已逻辑关闭，fd 也可能无效；仍需检查状态、身份和回调是否允许继续执行。

用 shared_ptr 能否彻底避免所有错误？

它可以保活对象，但回调可能在逻辑关闭后继续修改新状态，也可能形成引用环。物理寿命和逻辑有效性都需要管理。

依据与核对范围

epoll(7) — 就绪集合、ET/LT、EAGAIN 与事件生命周期。

T033 原理问答

串口 termios 配置为什么重要？

串口配置同时决定物理帧格式和终端驱动怎样解释字节。二进制协议通常需要原始模式，关闭行编辑、回显及软件流控，并明确波特率、数据位、校验位和停止位。

原理与成立条件

原始模式要关闭哪些加工

终端默认可能有规范行输入、回显、特殊控制字符、换行转换和软件流控。这些适合人机终端，却可能把二进制协议中的字节当作控制字符。串口原始模式应明确关闭不需要的加工，并设置数据位、校验、停止位、波特率以及本地/接收标志。

VMIN 与 VTIME 的四种情况

非规范阻塞读取中，VMIN=0/VTIME=0 可立即返回；VMIN>0/VTIME=0 等最少字节；VMIN=0/VTIME>0 提供从调用开始的超时；两者都非零时，通常等待首字节后使用字节间计时。VTIME 单位为十分之一秒。它们描述 read 完成条件，不是协议帧超时或字节边界。

与 O_NONBLOCK 怎样配合

O_NONBLOCK 会改变暂时没有数据时的返回行为，不能把阻塞模式 VMIN/VTIME 四种规则不加条件地套到非阻塞读取。应按目标系统手册处理 EAGAIN，必要时也接受无数据返回 0 的终端语义。socket 的 read=0 表示有序关闭，不能机械推广到所有终端配置。

刷新和排空不是同一操作

tcflush 丢弃相应队列中的未处理数据，可能破坏协议；tcdrain 等待已排队输出发送结束，可能阻塞很久。修改串口配置时要明确是立即生效、输出排空后生效，还是连输入也丢弃。热切换波特率尤其需要双方协调，避免半帧跨越两种线路配置。

推演与反例

一个合法二进制字节为什么会被吃掉

终端行规程可能把换行转换、等待整行或把 XON/XOFF 控制字节用于软件流控。协议中的 0x11/0x13 如果被驱动解释成控制字符，上层看到的字节流就变了，CRC 会失败，却并非物理链路随机出错。调试应先确认 termios 与两端格式一致，再看解析器。

VMIN、VTIME 与非阻塞不能混讲

非规范模式中的 VMIN/VTIME 控制读等待条件，不同组合可表示等最少字节、首字节后超时等语义；O_NONBLOCK 又使调用在无进展时返回。跨系统细节需查实现，不能把“VMIN=帧长”当通用分帧方法。tcdrain 关心已提交输出的发送完成，而 write 返回更接近本地接纳，两者不能替代对端 ACK。

继续追问

波特率一样为什么仍全是乱码？

继续检查时钟误差、数据位/校验/停止位、电平标准与接地、引脚映射、终端加工及方向控制。波特率只是链路约定的一部分。

改波特率之前要处理哪些旧状态？

需要考虑输出中残余帧、输入半帧、解析器状态和对端切换协议。只改寄存器或 termios 可能把一条帧的前后两段按不同速率发送。

依据与核对范围

termios(3) — 串口原始模式、VMIN/VTIME 和 tcdrain。

T034 原理问答

HTTP 如何处理半包、连续请求和慢客户端？

HTTP/1.1 在 TCP 字节流上定义消息结构，解析器要跨多次读取保存状态，并按规范确定正文长度。一次 recv 可能半条请求，也可能包含多条，不能用读取次数划消息边界。

原理与成立条件

HTTP 解析必须增量进行

TCP 给出字节流，头部结束标记、字段甚至正文都可能拆在任意两次读取间；一次读取也可能包含多个请求。解析器保存已消费位置与阶段，先得到完整头部，再根据消息定界规则取得正文；处理一条请求后保留剩余字节，不能清空整块输入缓冲。

正文长度为什么是安全边界

HTTP/1.1 有 Content-Length、分块传输及无正文等不同规则。重复长度字段、冲突长度、非法数字与 Transfer-Encoding 组合必须依规范处理。前后两层解析器若对请求边界理解不同，可造成请求走私；不能靠“找到一个 Content-Length 就读这么多”称为完整 HTTP 实现。

输入和输出都可能失控

请求头应有长度和时间限制，正文有容量限制，连接数有上限；否则慢速持续发送可占用资源。发送响应时同样可能短写，输出缓冲应保存偏移并限制积压。只限制请求体不保护慢客户端造成的输出增长，也不保护无限 keep-alive 空闲连接。

生命周期与顺序如何保证

流水线请求可连续到达，响应顺序和每个请求的状态不能混乱；若业务异步处理，必须维持连接身份与响应排队。EOF 时还要区分完整请求已到与半个请求被截断，错误退出应及时注销事件和释放资源。成熟 HTTP 库通常比自行补齐全部边界更经济。

第三方 HTTP 库与业务边界

HTTP 库可承担增量解析、消息定界与异步收发，但路由、参数校验、授权和数据库查询仍是应用责任。网络完成回调只交接拥有独立存储的请求，业务完成后再向连接所属执行器投递响应。响应对象必须活到异步写完成；连接已关闭时，迟到结果只能取消或丢弃，不能凭复用后的 fd 数值寻找新连接。

推演与反例

正文长度为什么涉及安全

请求行与头部必须有大小上限；正文按有效的 Content-Length 或 Transfer-Encoding 等规则处理。冲突长度、非法重复头和不支持的分块编码不能各层自行猜测，否则前后代理对同一字节流的边界理解不一致，可造成请求走私。实现一个受限子集时应明确拒绝不支持的形式，不能悄悄忽略后继续复用连接。

慢客户端如何耗尽资源

客户端每隔很久发一个字节，若每次收到字节就把整个超时重新计满，可能永久占用连接和缓冲。应区分头部总期限、正文期限、空闲期限与输出上限，并限制连接数量。处理完一条请求要保留剩余字节供下一条解析，出错或关闭时再一致清理连接状态。

继续追问

recv 一次返回了完整 JSON，是否就能直接处理请求？

还不够。先确认 HTTP 头部和规定的正文长度已完整到达，并处理尾随请求；JSON 有效不证明 HTTP 消息边界正确。

返回 200 是否意味着后台动作完成？

取决于接口契约。若只完成排队，响应应清楚表达接纳或提供结果查询；HTTP 状态码本身不能替底层业务建立完成保证。

T035 原理问答

事件循环如何同时保证就绪处理、公平性与退出？

事件循环的可扩展性不仅来自多路复用，还来自每次回调的工作量可控。任何长计算、同步写盘或无界排空，都可能推迟其他连接、定时器和退出请求。

原理与成立条件

公平性从哪几个维度考虑

事件循环要限制单个连接、单类事件和单轮批处理的占用。大量小消息、长解析和持续可写都可能让其他事件饥饿。预算可以按字节、条数或执行时间，但达到预算后应保存足够状态并主动安排后续处理，不能因追求公平把工作遗忘。

队头阻塞为什么难被平均值发现

若一次同步配置重载耗时 300 ms，串口、超时和停止信号都可能等它结束。平时回调很快，平均 CPU 仍很低，p99 或最大响应却显著变坏。应记录每类回调的占用分布、两次循环之间最大间隔与队列等待，而非只看每秒处理数量。

正确停止是一个协议

先禁止新任务进入，再让生产者停止，叫醒阻塞消费者，按约定排空或取消队列，等待线程退出，最后销毁依赖资源。若先 join 一个仍在等永远不会到来的通知的线程，退出本身就死锁。若先销毁被回调捕获的对象，停止阶段会出现正常运行中没有的悬空访问。

停止也要有期限和结果

关键持久工作可能需要排空，过期遥测可能允许丢弃；必须按业务选择。有限停止期限到达后要有明确降级与记录，强制退出不能伪装成全部提交成功。控制平面停止命令应避免排在无界业务洪水后面，否则系统可能连退出都无法及时响应。

推演与反例

用处理预算建立公平性

每轮限制读字节数、处理任务数或实际执行时间，把未完成工作记在本地待处理集合，然后轮转处理。预算不能破坏 ET 的继续处理责任；后台线程也要有有界队列，否则只是把拥塞移到看不见的地方。稳定运行要求长期消费能力覆盖到达率，短时预算解决公平性，容量和背压解决过载。

停止标志为什么需要唤醒

一个线程把 running=false，主循环却正在无限期 epoll_wait；若没有新事件，它可能永远不再检查标志。正确退出通常既改变持久停止状态，也通过 eventfd、信号等唤醒等待点，然后停止接纳新任务、处理已有任务并退出。修改原子标志只保证可见性，不会凭空制造调度事件。

继续追问

只设置 atomic<bool> stop=true 为什么线程还不退？

标志只改变状态，不会自动唤醒阻塞在队列、epoll 或 I/O 的线程；还要触发它所等待的机制，并让循环在醒来后检查退出条件。

回调中写一条日志也可能阻塞吗？

可能。即使平时很快，文件系统、锁或日志队列满时都可能改变行为。需要了解日志接口的最坏路径和满队列策略，而不是只看函数名称含 async。
