帧协议、可靠传输与幂等

T036 原理问答

如何设计一条能抗分包和噪声的串口帧？

字节流没有天然帧边界。接收器要靠同步标志、长度、类型和完整性校验逐步识别消息，并在任意分包、连续多帧和损坏输入后恢复到可继续解析的状态。

原理与成立条件

字节流如何恢复消息边界

串口和 TCP 都可能把应用消息拆开或合并。常见定界方法有固定长度、分隔符加转义、长度前缀和同步头加长度。分隔符需要处理负载中相同字节；长度字段一旦损坏可能让解析器错误等待很久，因此常配合法范围、校验与重新同步规则。一次中断或 read 的边界不是消息边界。

增量解析器怎样工作

用状态保存当前在找帧头、收长度、收正文还是收校验；每输入一字节更新已收计数，只在足够数据到达后读字段。帧可以跨任意输入块，状态不能在每次回调结束时清空。容量上限应在接受长度时立即检查，不能先复制到数组再判断长度非法。

噪声与同步头重叠

发现非法长度或 CRC 后需要重新寻找候选帧头；例如 AA AA 55 中第二个 AA 仍可能是新帧起点，简单清空后丢弃当前字节可能错过它。是否回扫已收缓存取决于协议设计和内存预算；重要的是保证持续噪声下时间、空间有界，并能最终识别后续合法帧。

校验通过后仍需业务验证

类型对应的最小/精确长度、字段取值、版本和状态都要继续检查。CRC 只过滤一类字节错误；它不能防止合法校验但语义非法的输入。测试应把每个合法帧从所有可能位置切分，再加入连帧、坏长度、坏校验和噪声前缀，验证消费和恢复行为。

推演与反例

一个增量解析器需要记住什么

设帧为同步头、长度、正文、CRC。它必须记住目前在找头、收长度、收正文还是收校验，以及已收字节数。一次输入只有半个头时不能丢掉合法前缀；一次输入多帧时每完成一帧后还要继续处理余下字节。若正文也可能包含同步头，正常收正文阶段不能见头就重启，必须由当前长度和校验决定边界。

恢复策略怎样避免越界和锁死

长度必须在写入正文缓冲前检查。校验失败后可重新搜索候选同步位置，但要考虑重叠前缀，例如 AA AA 55 中后一个 AA 仍可能是新头。错误长度可能吞掉后续帧，因此还应有最大帧长、必要的组帧超时和重同步策略。解析器接受外部字节时任何路径都必须有界，不能通过无限等待更多字节掩盖非法状态。

继续追问

为什么 IDLE 后就把当前缓冲当整帧会失败？

发送方可在一帧中停顿，也可连续发多帧而没有足够空闲；物理空闲只表示接收进度，帧界仍应由协议决定。

用 IDLE 或 read 返回短数据来划帧可以吗？

只有协议明确把静默间隔作为定界条件且满足时序约束时才行。一般自定义长度协议应把这些当传输分块，最终边界由协议自身决定。

T037 原理问答

CRC16 与累加和有什么区别，能保证不出错吗？

累加和把字节作加法，CRC 把消息看作二进制多项式做模二除法。CRC 对特定差错模式有可证明的检测能力，但仍有漏检模式，也不提供防恶意篡改的认证。

原理与成立条件

为什么比简单累加更适合突发错误

累加和可能漏掉相互抵消的字节变化，甚至交换字节后不变。适当生成多项式可保证检测某些长度内突发及特定比特错误模式；r 位 CRC 对长度不超过 r 位的突发有相应保证，但超过长度并非全部可检。随机残余错误率常近似 2^-r，不能当作对任意输入或攻击者的保证。

反射多项式和线上端序

0x8005 与反射算法使用的 0xA001 可描述同一生成多项式的不同位处理方向；仅给出多项式仍不足以复现校验。CRC16/MODBUS 常用初值 0xFFFF、反射处理、最终不异或。结果哪一个字节先在线上传输又是独立协议约定，不由 CPU 字节序自动决定。

怎样验证实现

用公开 check 向量及自建边界向量分别核对参数、覆盖范围和输出顺序。例如 ASCII “123456789” 的 CRC16/MODBUS 数值为 0x4B37，低字节先发时是 37 4B。CRC 不带秘密，攻击者能修改负载并重算；需要防篡改与身份鉴别时应考虑 MAC 或认证加密。

推演与反例

为什么调换字节可能骗过累加和

两字节 01、02 与 02、01 的加法和相同，但字节位置在 CRC 的多项式中对应不同次数，因此通常得到不同余数。生成多项式决定哪些错误模式是其倍数而无法检出；合适的 r 位 CRC 可检测长度不超过 r 的突发错误，但其他性质还要看多项式和消息长度。随机错误下常说的约 2^-r 漏检概率依赖分布假设，不是对所有输入的绝对保证。

一套 CRC 参数必须完整给出

除了宽度和多项式，还要约定初值、输入/输出反射、最终异或、参与计算的字节及结果线上顺序。0x8005 与反射实现的 0xA001 是位方向相关的表示；看到同名 CRC16 仍不能确定双方兼容。用固定 check 向量确认基础算法，再用真实帧验证覆盖范围，才能把算法错误和协议拼帧错误区分开。

继续追问

帧头也必须算 CRC 吗？

由协议约定，不能凭经验猜。同步头常用于寻找边界，长度和正文通常需要保护；接收端必须与发送端对完全相同的字节序列计算。

攻击者改了数据后能重算 CRC 吗？

能。CRC 没有秘密密钥，不能证明来源或阻止重放。需要身份鉴别和防篡改时使用合适的 MAC、认证加密及新鲜度机制。

T038 原理问答

停止等待、GBN 与 SR 怎样工作，窗口上限如何推导？

停等用最少状态换取较低链路利用率；GBN 批量在途但通常从缺口起重传；SR 分别确认并缓存乱序数据。窗口大小受带宽时延积、缓存以及序号歧义共同限制，不能只追求更大。

原理与成立条件

窗口为什么影响吞吐

若发送一帧耗时 Ttx，往返等待远大于 Ttx，窗口 W 太小就不能持续填满链路。可按带宽时延积估计在途需求，再考虑接收 RAM 与执行能力。窗口大并不自动更快：链路已满、业务执行串行或接收缓存不足时，增大窗口只会增加积压和结果等待。

SR 半序号空间规则的由来

经典循环序号 SR 中，接收方必须区分上一轮延迟的旧帧和新一轮同序号帧。若发送/接收窗口可重叠太多，就可能把重传旧帧当新帧；常见对称窗口要求 W≤2^(m-1)。这是特定模型下的必要约束，仍需最大报文寿命等假设，不能凭此消除任意长延迟造成的歧义。

接收顺序与执行顺序可以分开

SR 可提前接纳后续帧而暂不交付业务，等缺口补齐再按序交付。这样改善线路利用率，但永久缺口仍会阻塞后续执行。设计必须规定重试耗尽后如何跳过、重置或中止；默默丢掉缺口继续执行，可能违反控制命令的顺序语义。

推演与反例

利用率可以怎样近似计算

设一帧发送耗时 T，最后一位发完到确认返回还需 D，忽略处理和 ACK 发送开销，停等利用率约为 T/(T+D)。允许 W 帧在途后，理想利用率上界可近似写成 min(1, W×T/(T+D))。这里 D 的定义已经排除本帧发送时间，避免把 RTT 和 T 重复相加；有丢包、半双工、有限接收处理能力时还会更低。

半序号空间限制来自“旧帧像新帧”

对称 SR 窗口为 W、序号空间为 M，接收方交付一整窗后，新窗口不能与发送方仍可能重传的旧窗口发生无法区分的重叠，因此典型约束是 M≥2W。这个结论依赖循环序号模型及报文寿命等前提；若协议在序号用完前换会话，则还需证明新会话与旧迟到报文能被区分，不能仅引用公式就结束设计。

继续追问

使用 8 位序号为什么不直接开 128 帧窗口？

理论最大值不是资源建议。要结合帧大小、接收缓存、结果保留、链路 RTT 和业务时延；还要遵守具体协议的会话与寿命规则。

SR 为什么还会产生队头阻塞？

链路可先接收后续帧，但要求按序交付的业务仍要等前面的缺口。SR 减少无效重传，不自动取消业务顺序约束。

T039 原理问答

传输确认、按序交付与业务完成为什么不是同一状态？

接收确认表示对方已承担保存责任，按序交付表示数据可以进入业务，执行结果表示业务已经完成。这三个事件可能相隔很久，必须用不同状态与资源计数描述。

原理与成立条件

为什么需要两种在途计数

接收窗口保护传输顺序与接收缓冲，业务在途表保护尚无最终结果的请求。一个命令已被接收但仍在执行，可能不再需要接收重传，却仍占业务资源。只维护一个计数，会在 ACK 后过早删除请求，或把执行等待误当丢包不断重发。

确认可以改变哪些状态

接收 ACK 可以标记已接纳、停止接收阶段重传，但不能产生业务成功结果。结果消息通常隐含命令已到达，可在接收 ACK 丢失时补足接收认知；若结果先到，状态机应允许直接完成。重复结果应补确认，但不能再次通知上层执行完成。

发送许可要满足多个约束

是否能发下一条，可能同时取决于最早未确认序号限定的窗口范围、未完成业务数量、接收端信用和本地输出容量。即使后续项已确认，前面的缺口未补上，窗口也未必能前移。简单用“ACK 数量减一”替代范围判断，会在乱序确认时突破接收窗口。

结果缓存与接纳责任

节点执行前应预留足以记录命令与结果的资源，否则动作已经发生却无法保存结果，将难以响应重试。接收确认时承诺的资源边界应包含这个需求。窗口小于缓存容量，可以给已完成未确认结果留空间，但仍要分析最坏结果滞留与新命令竞争。

推演与反例

ACK 乱序时窗口为什么不能随便前移

发送 0、1、2，先收到 1 和 2 的接收确认，0 仍未确认。虽然已确认数量是 2，窗口左边界仍被 0 挡住；若简单按 ACK 数减在途数就继续无限发送，会超出接收端可接受范围。另一方面，0 已确认但执行仍很慢时，它可不再需要链路重传，却仍占业务结果表中的一个位置。

结果先到的合法顺序

接收 ACK 可能丢失，而结果消息已经返回。只要结果身份、类型和长度有效，结果本身可证明该请求至少被接收并执行，状态机应允许直接进入完成。之后迟到的接收 ACK 不能把状态倒退，重复结果可以补发结果确认，但不能再次调用完成回调。这要求把状态转移设计成单向、幂等的规则。

继续追问

接收 ACK 都齐了，为什么还不能释放全部业务对象？

结果可能还没到，调用者回调、结果期限和去重身份仍需保留。传输结束不等于请求生命周期结束。

哪一刻可以复用请求对象内存？

只有相关输出、定时器、回调和重试引用都已结束或被安全隔离后。业务完成是必要条件之一，不代表所有异步借用立即消失。

T040 原理问答

会话号与序号为什么缺一不可？

序号回答“本轮哪一条”，会话号回答“属于哪一轮”。组合键防止上一轮迟到的请求或确认命中新一轮相同序号，但仍需明确会话生成、接受规则与重启后的保存范围。

原理与成立条件

序号解决重复，会话解决哪一代

短序号用来关联当前协议实例中的消息，会话或 epoch 区分重连/重建后的实例。若只使用 seq=3，延迟到达的旧确认可能命中新发送的 seq=3。把 session 与 seq 一起作为键，可以隔离旧消息，但前提是会话标识不会在相关消息寿命内再次碰撞或被错误接受。

随机与单调标识的区别

随机足够宽标识依概率降低碰撞，不天然表达新旧顺序；单调标识允许接收方拒绝旧代，但需要解决分配与重启持久化。用当前时间生成要考虑时钟回拨、分辨率和多个发送者。若没有认证，攻击者还可能伪造更大代数，所以新旧判定与身份鉴别不能混为一谈。

序号耗尽要有明确流程

可以限制最大在途及报文寿命后安全回绕，也可在回绕前排空并换会话。换会话通常先停止旧代提交、处理旧在途，再通过握手建立新代。只有本地变量加一而对端仍接受旧代，会留下过渡期歧义；迟到的旧回调也必须带会话校验。

重启是最容易漏掉的边界

接收端只在 RAM 保存会话高水位，掉电后就忘记过去；随机启动标识或持久计数可改善区分，但仍需对双方恢复做完整设计。业务 ID 的寿命通常长于一次链路 session，不能把链路键当作跨所有重连的永久去重键。

推演与反例

随机标识与有序标识不能直接互换

随机足够宽的标识主要降低碰撞概率，不天然支持数值越大越新；单调递增会话可让接收方维护高水位，但要处理持久化、分配冲突和重启回退。基于墙上时间生成还要考虑时钟回拨。若接收方用“大于旧值”决定切换，发送方也必须遵守同一全序契约，而不是随便生成一个随机数。

旧回调必须带哪一代身份

旧会话的写完成、定时器或网络结果可能在新会话建立后才执行。若回调只带 seq，它可能修改同号新请求；因此校验至少包含会话与请求身份，必要时再带发送尝试代数。会话重建不仅是清空哈希表，还要让外部队列中残留操作无法污染新状态。

继续追问

64 位 session 是否意味着永不重复执行？

不意味着。标识宽度只缓解冲突，是否重复还取决于接收策略、保存期限、掉电恢复，以及业务效果与记录是否一致提交。

64 位会话为什么仍不能保证跨掉电不重复？

如果接收方丢失已执行记录，同一个业务可能以新会话身份再次到达。链路会话区分与长期业务去重是不同层次，后者需要稳定业务 ID 和相应持久状态。

T041 原理问答

怎样设计 RTO、总截止时间与有限重试？

RTO 控制一轮发送后多久重试，总截止时间限制请求整个生命期，重试预算限制额外尝试次数。三者分别解决暂时丢包、无限等待和资源占用，起点不能混用。

原理与成立条件

一轮重试和总体截止时间

单轮 RTO 判断“这次发送后等多久再尝试”，总体 deadline 判断“这个请求还能活多久”。每次重试可以更新本轮起点，却不能无条件延长总寿命。还要区分发送前排队、等待接收、等待执行结果，否则排队拥塞会触发无效重发，慢业务也会被误认作线路丢包。

RTO 应覆盖哪些延迟

一次往返包含线路发送、驱动缓冲、对端处理和返回调度。设置过短会产生重复与拥塞，过长则恢复慢；可依据有界模型或 RTT 估计选择。重传报文的 ACK 很难区分对应哪一次尝试，直接用于 RTT 估计会有歧义。TCP 的估计和退避机制可作背景，但自定义协议不必照搬全部机制。

重试次数为什么要明确初次是否计入

“重试 3 次”常指初次发送之外再发 3 次，总尝试 4 次。失败日志、计时和测试必须统一口径；输出队列一直未真正发送时，也不应凭空消耗真实发包轮次。对非幂等业务，还需明确哪些阶段允许重传同一请求，哪些阶段只能查询结果。

超时处理不能删除一切痕迹

晚到结果可能证明业务已发生，旧发送回调也可能仍排在事件队列里。状态机需要完成只回调一次、旧轮次不能改新状态、部分发送缓冲继续收尾等规则。超时是本地决策，不能倒推远端动作被撤销；上层需要知道失败与结局不确定的区别。

推演与反例

RTT 估计为何不能直接取最近一次测量

正常 RTT 会抖动，通常要结合平滑值和变化幅度留出裕量；TCP 的经典形式是 SRTT 加上与 RTTVAR 相关的裕量，并在超时后退避。重传后到达的 ACK 可能对应第一次发送，也可能对应重发，直接从最近发送时刻算样本会低估 RTT，因此需要处理重传歧义。自定义协议可采用固定有界 RTO，但也应解释选值覆盖哪些延迟。

排队与发送期限要分开

假设请求在本地队列等了 300 ms、线上往返正常只需 50 ms。如果从入队立即启动 100 ms 单轮重传计时，就可能尚未发出便排入多份重试。可把排队纳入总期限，而在约定的本地发送完成点启动单轮计时。该完成点如果只是内核接纳，后续驱动排队也仍要计入 RTO 预算。

继续追问

把 RTO 从 500 ms 改到 50 ms，响应就一定更快吗？

正常响应不会因此提前，反而可能在合法处理延迟内重复发送。应先测延迟组成与丢失原因，再选择能覆盖正常波动的阈值。

超时后能向上层报告“没有执行”吗？

通常不能。请求可能已执行而结果丢失。应区分发送前拒绝、明确业务失败和结果未知，重试非幂等操作前先解决这种不确定性。

T042 原理问答

有序协议缺口无法补齐时，怎样恢复会话？

有序协议遇到永久缺口时，必须让双方就“跳过还是重建”达成一致。发送方只删本地超时项，不会改变接收方等待的序号，也不能恢复后续业务的顺序执行。

原理与成立条件

有序交付为何会被一个缺口卡住

接收端已缓存 6、7，但执行基序号是缺失的 5。若命令有依赖，不能跳过 5 直接执行后面的动作。重传可以补临时缺口，有限重试耗尽后必须有协议规定的恢复动作，否则队列保持有数据却永远不能前进，形成协议级队头阻塞。

跳过与重建的取舍

显式跳过要求双方一致记录该序号已放弃，并说明后续命令仍合法；重建会话则丢弃旧代推进关系，让双方在新起点同步。重建更容易隔离混乱状态，但旧会话中有些操作可能已执行，只是结果未到，因此不能把所有旧命令当成“未执行”自动复制到新代。

恢复过程要避免双重控制

暂停新提交，给旧请求一个明确终态或不确定结局，处理尚未完成的线路输出，建立更高代数的会话，再开放入口。所有旧回调、结果和确认都通过代数校验隔离。若新 OPEN 还未确认就发送新命令，可能再次在双方会话认知不同的状态下工作。

业务补偿与传输恢复分工

传输恢复的目标是让链路继续接纳新请求，不负责自动撤销已发生的物理效果。业务层若需要恢复目标状态，可以读取现状后发送绝对目标，或使用持久业务 ID 重试。对于“再走一步”这类动作，不做结局核实的自动重放可能扩大故障。

推演与反例

为什么整体重建有时更简单

接收端等 5，却缓存了 6、7。若要跳过 5，需一个本身可靠、可去重的跳过协议，并说明 6、7 在缺少 5 时是否仍有意义；重建会话可以直接结束旧顺序关系，让双方从新起点开始。但旧 5 可能已经执行、仅结果丢失，因此重建只是恢复传输能力，不是把现实世界回滚到未执行。

恢复期间最容易漏掉的发送残留

本地可能已经写出半条旧帧，或者旧重试还排在发送队列。切换时要区分尚未开始的旧项与已经部分写出的帧：前者可因身份失效而取消，后者需按流完整性策略收尾或关闭流。新会话握手成功后再放行新命令，旧回调继续按代数过滤，不能仅清一个 active 标志。

继续追问

为何不把丢失序号对应请求删除就继续？

删除本地表项不会改变接收端等待的执行基序号；双方必须通过明确协议事件对跳过或新起点达成一致。

能否在新会话自动重发所有失败命令？

只有业务明确允许这种语义才行。绝对设置值可相对容易重建目标状态；增量动作需要稳定业务去重或查询实际结果，不能把链路重连当成重放授权。

T043 原理问答

去重缓存满了、过期了或结果 ACK 丢了会怎样？

去重表不是普通缓存，它记录接收方已经承担的执行与结果责任。容量、TTL 起点、重复是否续期、确认后释放以及过期后的拒绝规则共同决定可靠性范围。

原理与成立条件

结果缓存保存的是协议责任

接收方执行后保存请求键、参数身份和结果，使同一请求重传时返回原结果，而不是再执行一次。未执行的待处理项也占资源；因此缓存不能只按“已完成数量”估算。结果发出去并不等于对端收到，只有结果确认或明确到期策略才能结束保存责任。

TTL 的起点影响保证

从接收起计时可能让长业务刚执行完就过期；从完成起计时则给回传保留固定时间。重复请求是否续期也要明示：无限续期可能让恶意或故障发送者永久占槽，不续期则必须保证重试策略与有效窗口协调。TTL 应与最大网络延迟、总请求期限和容量一起分析。

满缓存时不能先承诺后丢弃

若无槽位仍回复“已接收”，发送端可能停止重传，而接收端无法保存命令或最终结果。合理选择是拒绝/不确认、实施信用流控，或提供明确忙响应。对已经接纳的非幂等请求，随意淘汰记录会重新打开重复执行窗口，不能只用普通 LRU 思路处理。

缓存过期不一定允许重新执行

若协议还记得该序号已在执行基序号左侧，可拒绝再次执行业务，但可能再也无法重放结果。于是“防重复执行”和“始终可返回原结果”有不同寿命。要向调用者解释这一区别，否则有限缓存会被误称为永久 exactly-once 服务。

推演与反例

满缓存时为什么不能先 ACK

若收到非幂等命令后先确认，再发现没有空间保存请求与结果，发送方可能停止重试，接收方却无法履约。应先预留记录，再接纳并确认；没有资源时不接纳、返回忙或用信用流控。随意 LRU 淘汰已接纳但未结束的项，会把重复执行风险重新引入系统。

“不再执行”与“还能回原结果”寿命不同

一个协议可能通过单调执行基序号记住 0..20 已经执行，而只保存最近若干条具体结果。21 之前的旧请求不会重做，但缓存被释放后也无法回答旧 3 的结果。相反，只保留短 TTL 哈希表而没有序号历史，过期后可能把同一请求当新请求执行。必须说明使用的是哪一套状态，而不是笼统说“做了去重”。

继续追问

RESULT_ACK 丢失会怎样？

接收方继续保存或重发结果，发送方对重复合法结果再次 ACK；应避免重复业务回调，缓存最终还需有限释放规则。

TTL 比发送方总期限短就一定错误吗？

需要连同完成时刻、结果重传、窗口推进和过期拒绝规则一起判断。短 TTL 会缩短结果可恢复期，但不必然破坏“旧请求不重执行”；保证的是哪一种性质必须分别写出。

T044 原理问答

幂等、去重与恰好一次有什么区别？

幂等是重复操作的效果属性，去重是识别重复请求的机制，恰好一次则涉及定义好的观察范围与失败模型。稳定请求 ID、结果记录和业务效果之间的原子关系决定保证能做到哪一层。

原理与成立条件

幂等是效果属性，去重是识别机制

一个操作重复执行多次与执行一次效果相同，称为幂等，例如设置目标值；去重则识别同一请求已处理，从而跳过或返回原结果。即使设置值本身幂等，重复日志、通知或继电器脉冲等附带效果也未必幂等；必须说明观察哪些业务效果。

请求键必须稳定且防错配

重试保留同一个业务 ID，新业务使用新 ID；接收方将 ID 与规范化参数或摘要关联。同 ID 不同参数应拒绝，而不是返回旧结果或覆盖记录。连接序号通常只在一次会话内稳定，跨重连由发送者重新生成的序号不能承担长期业务去重。

数据库事务能解决的部分

业务效果若完全在同一数据库，可在事务中以唯一键插入请求记录、修改业务数据并保存结果；重复命中后读取已记录结果。并发请求还需让“检查与写入”由唯一约束和事务保证，而不是先查不存在再无保护执行。外部物理动作不能自动纳入数据库原子提交。

物理动作怎样降低不确定性

优先使用设置绝对状态，结合动作 ID、设备侧持久状态和恢复查询；必要时做可补偿流程。必须承认断电落在物理效果与持久记录之间的风险，某些业务需要硬件反馈或操作规程处理。不能通过加一个布尔 done 就证明任意物理动作恰好一次。

推演与反例

数据库内的效果为什么较容易合并

如果业务只是更新同一数据库，可在事务中插入唯一请求键、修改业务数据并保存结果。并发重复请求由唯一约束仲裁，提交成功后可返回已保存结果；不能先在事务外查重再执行，因为两个线程可能都查到不存在。失败后要看事务是否真正提交，提交结果不确定时仍需按同一键查询，而非生成新键盲目重做。

物理动作为什么留下空隙

先写“已完成”再让电机转，断电可能留下记录成功但动作未发生；先转电机再写记录，断电后又可能无法知道已转过。普通数据库事务不能自动覆盖电机。可改成设置绝对目标、记录动作 ID、读取位置反馈、设计恢复流程，但必须给出硬件可观察性与持久化假设，不能靠一个 done 位宣称任意动作恰好一次。

继续追问

HTTP PUT 被称为幂等，是否每次响应都必须相同？

幂等主要约束重复请求的预期服务端效果，不要求状态码、时间戳或所有响应字节完全相同；具体接口仍需定义副作用。

设置同一个值就必然幂等吗？

只对选定业务效果可能幂等。若每次设置还触发计费、通知、脉冲或重置定时器，重复调用的总效果可能不同，应把这些副作用纳入定义。

T045 原理问答

如何验证协议状态机，而不只测试正常收发？

协议验证要检查状态与不变量，正常收发只是其中一条路径。应控制消息丢失、重复、乱序、迟到和时间推进，证明每次输入后资源与完成语义仍正确。

原理与成立条件

状态机测试先写不变量

先规定永远应成立的性质：不会执行窗口外请求、一次请求最多完成回调一次、缓存满不伪确认、旧代不能改新代。再枚举状态和事件，而不是只覆盖函数行数。相同输入事件序列应能复现结果，可控时钟比真实 sleep 更适合边界与回绕测试。

单独丢包不足以覆盖故障

分别丢命令、接收 ACK、结果、结果 ACK，行为不同；再加入重复、乱序、发送短写、延迟回调和新旧会话交错。错误往往来自组合，例如超时刚处理完收到旧结果，或重载后旧发送回调抵达。测试需要覆盖事件顺序而不只是数据值。

用模型检查迁移是否合法

可以写较简单的参考状态模型，输入生成的事件序列，对比接纳、交付顺序和终态；记录随机种子以复现。模糊测试擅长字节解析健壮性，却不自动理解协议语义，需要额外的不变量判定。越界无崩溃也不等于消息没有被错误执行。

证据层级要分别报告

纯 C 核心测试验证协议计算，伪终端可覆盖网关 read/write 集成，节点主机替身无法精确模拟中断和 DMA，真实板卡再观察波形、覆盖与复位。每层失败都能定位更小范围，但上层通过不能代证下层时序。

推演与反例

怎样从不变量推导测试

先写出“同一请求最多执行业务一次”“窗口不越界”“完成回调至多一次”“总期限不被重试延长”等规则，再生成破坏条件的序列：结果先于接收 ACK、旧会话 ACK 到新会话、缓存刚过期、发送半帧时取消。测试不仅看返回值，还统计执行次数、保留槽数、发送内容与最终状态。

虚拟时间为什么比等待真实超时好

把单调时钟作为依赖注入，可以直接检查 deadline 前一单位、等于和后一单位，不必每次睡几秒，也避免调度抖动让测试偶然通过。解析层再用任意切分点与噪声输入测试，与协议层的状态测试分开；最后用真实串口或 PTY 验证接口衔接。各层证据解决不同问题，不能彼此替代。

继续追问

最有价值的边界用例是什么？

选择最容易跨越生命周期的事件：最后一轮超时与合法结果同时到达、序号耗尽换会话、缓存到期后一份旧命令再次到达，并明确预期只有一个业务终态。

随机压测很久没错，是否比边界测试更充分？

随机测试能发现未想到的组合，但不保证命中关键边界。应保存种子与失败序列，结合针对不变量的确定性测试和真实链路验证。
