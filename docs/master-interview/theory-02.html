操作系统：执行、同步与内存

T013 原理问答

进程、线程和 FreeRTOS 任务有什么区别？

进程主要提供资源与地址空间的隔离，线程和 RTOS 任务主要描述可调度的执行流。判断差别要看共享哪些资源、切换保存哪些状态以及故障能否被隔离，不能只记“进程重、线程轻”。

原理与成立条件

进程隔离什么，线程共享什么

进程是资源与保护边界的抽象，线程是执行流的抽象。在常见 Linux 多线程进程中，线程共享地址空间、代码、堆、全局变量和文件描述符表，各自有寄存器现场、栈、线程局部存储和调度状态。线程栈虽按用途分开，却仍在共同地址空间内；一个线程持有另一线程栈地址时，硬件不会替它阻止越界访问。

切换成本为什么不同

线程切换要保存和恢复寄存器及调度状态；跨地址空间的进程切换还涉及页表上下文，并可能增加 TLB 与缓存失效成本。现代 CPU 有地址空间标识等优化，不能简单说“进程切换必然清空全部缓存”。真正成本受工作集、缓存命中和调度频率影响，不宜背固定微秒数。

RTOS 任务是不是进程

RTOS 任务同样有任务控制块、独立栈和寄存器上下文，但许多小型单片机应用让所有任务共享物理地址空间，没有 Linux 式进程隔离。MPU 可以提供区域权限保护，但 MPU 不等于支持地址翻译的 MMU。任务越界可能直接破坏其他任务、内核链表或外设状态。

选型怎样推导

需要强隔离、独立升级和故障遏制时，考虑多进程；频繁共享状态、资源紧张时，多线程或 RTOS 多任务较方便，但必须额外保证同步与生命周期。并发表示多个工作在时间上交错推进；并行要求有多个执行资源同时运行。单核抢占式多任务主要提供并发，并不把 CPU 算力变成多份。

推演与反例

从一次切换看到真实成本

同一进程的两个线程切换时，需要换寄存器、栈指针和调度状态，但通常不用换地址空间；跨进程还要改变地址翻译上下文。缓存和 TLB 是否保留取决于架构与标识机制，工作集改变仍可能导致大量未命中。因此大量细碎任务即使各只计算几微秒，也可能把时间花在调度与缓存重新变热上；成本必须结合平台和负载测量。

隔离为什么不是线程库能补出来的

同进程线程可访问彼此堆和栈地址，一个越界写可能破坏任意共享对象；互斥量只协调合法访问，无法拦住非法地址。常见无 MPU 隔离的 MCU 任务也如此。需要容错边界时，可考虑独立进程或 MPU 区域，代价是通信、资源复制和权限管理；把任务拆得更多并不会自动增加可靠性。

继续追问

一个线程崩溃是否只影响自己？

普通线程的非法内存访问可能让整个进程终止；即使没有立即终止，共享数据也可能已损坏。“各有自己的栈”不等于故障隔离。

一个任务阻塞会不会让整个单核停住？

若由调度器把它置为 Blocked，其他 Ready 任务可运行；若它关中断忙等、持有全局关键锁或阻塞的是唯一事件循环，则可能拖住更多工作。关键是阻塞发生在哪个调度层。

T014 原理问答

用户态、内核态、系统调用、中断和上下文切换是什么关系？

用户态与内核态是权限边界，上下文切换是执行流切换。系统调用、异常和中断提供进入处理代码的路径，但每次进入内核并不一定更换线程。

原理与成立条件

为什么区分用户态和内核态

权限级别使普通程序不能随意修改页表、处理中断或访问任意设备。用户程序通过系统调用请求内核服务，内核检查参数与权限，再操作受保护资源。C 库函数并不必然对应系统调用，例如字符串长度计算通常全部在用户态完成，缓冲式文件 I/O 也可能暂时不进入内核。

三类入口的区别

系统调用是程序主动发出的同步请求；缺页、非法指令等异常由当前指令触发；外部中断由设备等异步事件触发。进入处理程序时处理器保存必要返回状态，切换到相应入口与权限环境，软件再补充保存寄存器。异常与中断的命名在不同架构中略有差别，应先说明讨论平台。

模式切换不等于线程切换

read 进入内核后，如果数据已经可取，可以复制数据并返回原线程，只发生权限环境切换。若线程需要等待，内核将其置为睡眠状态并调度另一个线程，才发生执行流切换。中断返回也可能继续原线程，或因更高优先级工作就绪而触发调度；不能把每次中断都计成任务切换。

性能成本从哪里来

成本不仅是几条入口指令，还包括参数检查、用户地址访问、缓冲复制、锁竞争和缓存扰动。减少无效系统调用、批量处理和降低唤醒频率可能有效，但批量过大会增加尾延迟。对耗时先区分线程在运行、可运行但等 CPU，还是在等待 I/O，才能选对优化方向。

推演与反例

对比三条 read 路径

数据已经在内核缓冲时，read 检查参数、复制并返回原线程；阻塞 fd 暂时无数据时，线程进入等待，调度器运行其他线程；非阻塞 fd 无数据时，返回 EAGAIN，让用户决定何时重试。三者都可能进入内核，只有需要等待且另选执行流的路径必然涉及调度。一次系统调用耗时包含等待和抢占，不能全部归因于复制。

用户指针为何不能直接相信

系统调用收到的是用户提供的地址和长度，内核要处理地址是否可访问、范围是否越界以及访问过程中可能发生的缺页。权限切换并不使用户指针天然可信。类似地，设备协议的外部长度也必须先验证，再访问数组；底层代码和上层协议都需要在信任边界检查输入。

继续追问

read 很慢就能断定内核复制慢吗？

不能。耗时可能主要来自等数据或调度；应结合系统调用耗时、线程状态和 CPU 采样，分离等待时间与实际执行时间。

中断时保存了寄存器，是否就叫一次线程切换？

可以称为异常上下文保存，但不等同调度到另一个线程。面试中应把异常进入/退出与调度切换分开描述，避免把中断数直接当任务切换数。

依据与核对范围

syscalls(2) — 系统调用接口与内核边界。

read(2) — 读取返回值、EINTR、EAGAIN。

T015 原理问答

虚拟内存、页表、TLB 和缺页分别解决什么问题？

虚拟内存让程序使用独立、受保护的地址空间；页表给出映射，TLB 缓存翻译结果，缺页异常处理当前映射无法直接完成的访问。TLB 未命中不等于缺页，缺页也不一定读磁盘。

原理与成立条件

虚拟地址怎样变成物理地址

程序使用虚拟地址；MMU 按当前地址空间的页表，把虚拟页号映射到物理页框，页内偏移保持不变，同时检查读写、执行和特权权限。多级页表只为实际使用的地址范围分配下级结构，减少稀疏地址空间的管理开销。连续虚拟地址不要求对应连续物理内存。

TLB 未命中与缺页不是一回事

TLB 缓存地址翻译结果。未命中时需要查页表，若页表已有有效映射，填充 TLB 后继续执行，不必从磁盘读取。缺页异常表示这次访问无法按现有映射直接完成：可能是首次按需分配、写时复制、文件页尚未驻留，也可能是权限错误或非法地址。后两类不能一概通过“调入一页”解决。

分配成功为何不等于物理内存已到位

malloc 主要向分配器申请虚拟内存范围；按需分页下，某些物理页直到首次访问才实际建立。匿名页首次写入可能需要分配并清零；文件映射缺页可能涉及存储 I/O。Linux 的内存承诺策略还会影响分配与后续访问失败的时机，所以“malloc 返回非空”不是实时访问时延的保证。

保护、共享与实时性的联系

独立页表可将不同进程相同虚拟地址映射到不同物理页，也可显式映射同一物理页实现共享。共享映射仍需同步。实时路径可预分配、预触页并在适当权限和资源预算下锁页，但锁页不消除锁竞争、调度和所有硬件延迟。必须分清虚拟容量、驻留内存与峰值工作集。

推演与反例

一次写入匿名页可能经过什么

程序先申请一段虚拟地址，第一次写某页时发现尚无可写物理映射，触发异常；内核检查该地址属于合法区域，分配或准备物理页、清零并更新页表，随后重新执行该条指令。若地址不合法或权限不允许，则走错误路径。页表已有有效映射而 TLB 没记录时，只需重新建立翻译缓存，这一过程通常不涉及存储 I/O。

写时复制与实际内存占用

fork 后父子进程最初可以共享物理页并把相关映射设为只读；一方首次写入触发写保护异常，内核为它复制该页，使两边后续修改独立。复制单位是页，不是被修改的一个字节。大量随机写会扩大驻留内存及缺页成本；RSS、虚拟地址空间大小和程序申请总量因此不能互相替代。

继续追问

有 MPU 的单片机就支持 Linux 式虚拟内存吗？

不一定。MPU 主要检查区域权限，MMU 提供页表翻译；二者能力不同，不能由“有保护单元”推出按需分页或进程地址空间。

mlock 后是否就能保证访问延迟？

锁页可减少被换出导致的等待，但仍需预触页、控制工作集及权限资源；缓存未命中、调度、中断和锁竞争依然存在，它不是完整硬实时保证。

依据与核对范围

mmap(2) — 虚拟内存与文件映射。

proc(5) — 进程、内存与运行期诊断入口。

T016 原理问答

阻塞、非阻塞、同步、异步如何区分？

阻塞描述调用是否等待，异步描述完成如何交付，两者不是同一坐标。非阻塞 I/O 通常仍由调用者在就绪后继续推进；异步接口则提交操作并在之后报告完成。

原理与成立条件

两组概念分别回答什么

阻塞与非阻塞描述调用在暂时不能取得进展时是否等待；同步与异步描述操作的完成如何交付、由谁等待并推进。讨论前必须限定接口语境：POSIX I/O 的同步定义，与把“后台线程执行”口头称为异步不是同一层概念。非阻塞 read 立即返回 EAGAIN，仍由调用者稍后重试并取得数据。

就绪通知和完成通知

select/poll/epoll 通知某个方向可能取得进展，应用仍要执行读写；这是典型 Reactor。异步提交接口则先接受操作描述，之后报告完成及结果，常称 Proactor 风格。完成前缓冲必须保持有效，取消也需要确认它不再被使用。异步并不等于没有复制，更不等于零延迟。

为什么非阻塞仍然可能占满 CPU

若不断 read 并在 EAGAIN 后立即重试，线程没有阻塞却在忙轮询。正确做法通常是暂存状态，通过事件机制等待条件变化；对小而明确的硬件等待，也可有意采用有限忙等。采用哪种方式，要比较等待长度、允许抖动、上下文切换成本与功耗。

看一个发送例子

要发送 100 字节，write 返回 40，只完成本次调用的 40 字节提交，余下 60 字节仍归应用管理。可写事件只表示再次尝试有意义，不能推断全部 100 字节已发送。即使接口报告本地发送操作完成，也要看它定义的是缓冲复制、DMA 结束、线路结束，还是对端确认。

事件循环数量与业务线程是两个维度

单 Reactor 单线程通常由同一线程处理 I/O 与业务；单 Reactor 多线程把业务交给其他线程；多 Reactor 多线程让多个循环分别管理一部分 I/O。多个循环可以共用业务执行器，并不要求每个循环固定配一套业务线程。单进程可以包含上述任一种布局，进程数不能替代线程数。主从 Reactor 按连接分配，按协议或设备分工也是一种多循环布局。

库的接口风格与底层实现

Boost.Asio 的 async_read/async_write 通过完成回调交付结果，属于 Proactor 风格接口；Linux 上可由 epoll 就绪机制推进底层读写。io_context::run 的调用线程执行处理函数，异步 API 不会自动另开业务线程。描述架构时既要说明库对应用的完成接口，也要说明事件循环由哪些线程运行，不能只凭 async 或 Reactor 一个词判断执行上下文。

推演与反例

读一个完整消息为什么需要状态

一次非阻塞 read 得到头部的前 3 字节，应用必须保留这 3 字节及解析位置，等待后续就绪。若把“返回了数据”当“消息已经完成”，协议会在合法分包时失败。完成式接口也未必替你完成业务消息定界，它可能只完成一次指定长度的底层读操作。接口完成单位与协议消息单位要分别确认。

缓冲生命周期怎样变化

同步写接口若已把数据复制进内核，调用返回后通常可复用用户缓冲；DMA 或异步接口可能继续读取提交的内存，直到其明确完成。取消请求同样可能与完成竞态，不能一发出 cancel 就释放缓冲。使用异步接口时，所有权问题通常比函数返回快不快更关键。

继续追问

把阻塞函数丢进工作线程就成真正异步 I/O 了吗？

对调用者可以形成异步接口，但工作线程内部仍是阻塞 I/O。应分别说明外部接口和内部执行机制，避免把线程池成本隐藏掉。

Reactor 是同步还是异步？

通常采用非阻塞同步 I/O 加就绪通知，应用负责实际读写；从业务调用者看又可能提供异步服务。必须说明讨论接口层，不能单靠 Reactor 这个名字判断所有层的语义。

依据与核对范围

read(2) — 读取返回值、EINTR、EAGAIN。

epoll(7) — 就绪集合、ET/LT、EAGAIN 与事件生命周期。

Boost.Asio：平台实现与事件分派 — Linux 的 epoll 后端与可选 io_uring；仅说明上游机制，具体配置以本地编译为准。

Boost.Asio：io_context::run — 只有执行 run/poll 系列接口的线程分派处理函数；多个 run 调用者构成线程池。

T017 原理问答

互斥量、信号量、条件变量和自旋锁怎么选？

互斥量保护共享状态，信号量记录可用数量，条件变量等待共享谓词变化，自旋锁用持续运行换取免睡眠的短等待。选型先看语义和上下文，再比较开销。

原理与成立条件

条件变量为何要搭配锁

条件变量不保存业务事实，只提供等待状态变化的机制。真实条件是队列非空、停止标志等共享谓词，需要在同一同步协议下检查和修改。wait 原子地释放互斥量并进入等待，返回前重新取得锁；收到通知后仍要重新检查谓词。具体无丢失唤醒推导见 T018。

自旋锁什么时候合适

自旋锁等待时持续检查锁，避免睡眠和唤醒开销，适合持锁时间极短、持有者能及时运行的场景。在单核上，如果高优先级任务一直自旋，低优先级持有者可能没有机会解锁；在不可睡眠的中断上下文，更必须保证不会等待一个被自己打断的持有者。自旋锁不是“性能更好的互斥量”。

选择先看不变量和上下文

保护多个字段的一致更新，用互斥或短临界区；计数可用信号量；等待复杂状态可用互斥量加条件变量；传数据优先考虑队列。然后检查是否在 ISR、能否阻塞、锁最长占用以及取消退出。把通知工具用于保护数据，或把保护锁当成事件队列，都会造成丢事件或竞态。

Linux 互斥量为什么不一定每次进内核

常见 pthread 互斥实现先在用户态用原子操作尝试取得锁，无竞争时走快速路径；竞争时通过 futex 等机制等待内核唤醒。futex 的等待会检查期望值，避免在锁状态已改变后错误睡下。解锁与唤醒不表示等待者立即运行，它还要竞争锁并接受调度；自旋、睡眠和优先级协议受实现与属性影响。

推演与反例

用生产者消费者区分工具

队列内容和关闭标志是一组共享状态，用锁保证入队、出队及关闭之间的一致性；消费者等待“非空或关闭”，适合条件变量；若用计数信号量，计数必须与可消费项目严格对应，还要额外解决容器互斥与关闭唤醒。把二值通知当计数使用，会把两次到达合成一次；把计数工具当对象寿命保护，也解决不了释放后访问。

自旋什么时候会把短等待变成死锁

在单核中，高优先级代码抢占持锁的低优先级任务后若持续自旋，持锁者得不到 CPU，锁便永远不会释放。中断若等待被自己打断的临界区，也存在类似问题。自旋适合明确不可睡眠、持锁极短且有正确抢占/中断约束的上下文；用户态长临界区通常应使用会睡眠的锁或改变所有权结构。

继续追问

一个原子变量能否替代所有锁？

仅当整个不变量能由该原子协议表达时才可能。多个字段各自原子，并不使它们的组合成为同一时刻的一致快照。

futex 为什么能避免每次加锁都系统调用？

无竞争时可在用户态以原子状态转换取得锁；发生竞争才通过内核等待。等待前比较期望状态与入队的原子衔接，可防止状态已变化却错误睡下；futex 本身仍需要用户态协议构成完整互斥量。

T018 原理问答

条件变量为什么要配谓词，如何避免丢失唤醒？

条件变量等待的是“受锁保护的条件为真”，通知只提示重新检查。正确性来自检查谓词、原子解锁等待、重新加锁检查这一整套协议，while 循环和同一把锁缺一不可。

原理与成立条件

为什么一定循环检查

允许虚假唤醒，而且被唤醒不等于立即取得锁。假设两个消费者同时被通知，消费者 A 先拿锁并取走唯一元素，B 拿到锁时队列已空。因此写 while(!predicate) wait，或使用带谓词的 wait；用 if 只检查一次会把“曾有人通知”错当成“现在有数据”。

停止和超时也属于协议

退出时先设置 stopping，再唤醒所有可能等待的线程，让它们选择排空后退出或立即取消。若超时循环每次重新等完整的相对时长，虚假唤醒会把总等待拖长；应计算一次绝对截止时间，并选适合相对期限的单调时钟。通知放在锁内或锁外都可能正确，关键是状态修改与等待判断受一致同步保护。

推演与反例

把丢唤醒的竞态写成时间线

错误路径为 C 看见 empty→C 解锁→P 入队并 notify→C 开始睡眠，此后如果没有新通知，队列虽有数据 C 仍可一直睡。正确 wait 把解锁与注册等待连接起来：生产者一旦能拿到同一把锁并更新状态，它发出的通知就不能落在“已解锁但尚未成为等待者”的缝隙中。通知可在解锁后发，但谓词更新仍需遵守这个保护协议。

while 同时解决两个不同问题

虚假唤醒使线程在条件没变时返回；即使没有虚假唤醒，另一个消费者也可能先拿到锁并取走数据。两种情况下返回后谓词都可为假。退出还要使用 closed 这样的持久状态：消费者在 closed 且队列空时退出，在 closed 但仍有数据时继续排空。仅 notify_all 不修改谓词，不能让线程按预期停止。

继续追问

为什么修改谓词为 atomic 后仍可能丢通知？

原子只解决该变量访问的竞态；若“检查假值→注册等待”之间没有与生产者同步，通知仍可能落在缝隙里。状态原子性与等待协议原子性是两个问题。

超时返回时能否断定队列仍然为空？

不能，超时与生产者入队可能竞争。重新取得锁后仍需检查谓词，并按接口明确截止时间与事件同时发生时的取舍；多轮等待应复用同一绝对截止时间。

T019 原理问答

volatile、原子操作和内存屏障有什么区别？

volatile 保留实现规定的可观察访问，原子操作解决并发访问的不可分割与语言同步关系，内存屏障约束指定层次的排序。三者解决不同问题，不能把 volatile 当作多线程同步。

原理与成立条件

volatile 保证的范围

在 C/C++ 中，volatile 用于要求编译器按实现约定保留对该对象的可观察访问，常用于内存映射外设。它不自动提供多线程原子性、互斥或 happens-before，也不保证普通数据对另一执行者的发布顺序。volatile int 的自增仍包含读、计算、写，两个执行者可以互相覆盖更新。

原子操作和数据竞争

原子类型的单次 load/store 或 read-modify-write 按其语义不可被拆成对其他线程可见的中间状态。C++ 中两个线程无同步地冲突访问同一普通对象，至少一个为写，就可能形成数据竞争并导致未定义行为。“我的 CPU 读 32 位只要一条指令”不能替代语言级同步关系，也不涵盖 ++ 这样的复合操作。

三层屏障不能混用

编译器屏障约束编译重排；CPU 内存屏障约束处理器访问顺序；缓存维护处理 CPU 与非一致性 DMA 之间的数据副本。DMB 主要建立访问顺序，DSB 还等待相关操作完成，ISB 刷新后续指令执行环境。它们不自动实现线程锁或缓存清理。C++ 线程优先用标准原子和锁，设备通信按架构及驱动契约处理。

推演与反例

release/acquire 的证明链

生产者先写 payload=42，再 ready.store(true, release)；消费者的 acquire load 若读取了这次 release 发布的值，就有“payload 写入先于发布、发布与读取同步、读取先于使用”的 happens-before 链，随后读 payload 才安全。若消费者只用 relaxed，或根本没读到对应发布，链条不成立。这个例子还要求生产者不会在消费者读取期间再次无同步修改 payload；重复使用同一槽需要新的握手。

为什么多核一致缓存仍然不够

缓存一致性主要约束同一位置副本之间的关系，不自动给多个普通对象建立 C++ 的线程同步。CPU 可能重排，编译器也可以在语言规则允许范围内重排；语言数据竞争还可能直接带来未定义行为。DMA 若不参与缓存一致性，另需 cache clean/invalidate 和所有权移交；单独执行 DMB 不是把脏缓存写回内存。

继续追问

shared_ptr 的引用计数原子，就能普通读写同一个 shared_ptr 变量吗？

不能。不同 shared_ptr 实例可共享控制块；同一个实例被并发修改仍需锁或对应原子访问接口，被指向对象也要独立同步。

relaxed 什么时候足够？

只需要该原子变量自身的独立统计或标志值、且不依赖它发布其他普通数据时可能足够。必须先说明它保护的不变量，不能以“单核”或“测试没出错”替代证明。

T020 原理问答

死锁、活锁、饥饿和优先级反转怎么区分？

死锁是互相等待导致无法前进，活锁是一直动作但没有业务进展，饥饿是某个参与者长期得不到资源，优先级反转是高优先级被低优先级持有的资源拖住。四者的解决办法不同。

原理与成立条件

死锁的形成条件

经典资源死锁涉及互斥使用、持有资源同时等待、不能强行剥夺、形成循环等待。两个线程各持 A/B，再等 B/A，二者都不会主动推进。工程上常用统一锁顺序打破循环等待，或一次性申请、try-lock 失败后释放并重试；超时只能提供退出机会，若不回滚已持资源，仍可能继续占用并扩大故障。

活锁与饥饿的区别

活锁中线程一直在执行和响应，却相互让步或重试而没有完成有效工作；随机退避、限制重试、引入确定仲裁可改善。饥饿是某个工作长期拿不到 CPU 或资源，其他工作仍可能正常前进；公平排队、缩短占用和设置预算可缓解。CPU 很高不排除活锁，CPU 很低也不排除死锁。

优先级反转为什么多出一个中优先级任务

低优先级 L 持锁，高优先级 H 等锁，本就有必要的资源阻塞；若中优先级 M 不断抢占 L，H 就间接受 M 延迟，出现难以控制的额外反转。优先级继承把 L 临时提升，使其更快运行到解锁点；它不能让硬件转换提前完成，也不会消除循环等待。

如何系统性排查

先收集所有线程栈和资源等待图，识别谁持有、谁等待、持有者是否还能运行。再检查嵌套锁顺序、锁内 I/O、回调重入和等待另一个线程退出的 join。只在某条卡住路径加超时可能隐藏真正错误；必须同时规定超时后的资源归还、状态回滚和调用者结果。

推演与反例

死锁条件如何用于设计

互斥、持有并等待、不可抢占、循环等待同时成立时可能死锁。规定所有线程按同一顺序拿 A、B 两把锁，可以破坏循环等待；把慢 I/O 移到锁外、先取得所需资源再进入临界区，也可减少持有并等待。超时只能让一次等待退出，如果退出后没归还已持资源或继续无休止重试，仍可能形成泄漏、活锁或严重抖动。

经典三任务优先级反转

低优先级 L 持锁，高优先级 H 等锁，中优先级 M 不断抢占 L，H 就间接被不相关的 M 延迟。优先级继承使 L 暂时获得 H 的优先级，以便尽快释放锁；它不能让设备转换立即完成，也不自动解决多锁死锁。要得到时限，仍要约束最长持锁时间和更高紧急度中断。

继续追问

“每次加锁都只等 1 秒”能保证没有死锁吗？

若超时后正确释放并回滚，可避免永久等待；若仍持其他锁循环重试，系统可能转成活锁，甚至一直无法恢复一致状态。

不用锁是否就没有死锁？

没有。两个线程可能互相 join，两个有界队列可能互相等待对方消费，协议双方也可能都等一个永远不会到来的消息。需要分析的是等待依赖图。

T021 原理问答

Linux 调度与 FreeRTOS 调度有什么不同？

通用 Linux 调度追求多任务响应与公平，实时调度强调优先级或期限约束；常见单核抢占式 FreeRTOS 选择最高优先级就绪任务。无论哪种调度器，“高优先级”都不等于已经证明最坏响应时间。

原理与成立条件

RTOS 调度强调什么

典型单核抢占式 FreeRTOS 选择最高优先级就绪任务；高优先级任务阻塞后才让较低优先级运行。同优先级是否轮转受时间片等配置影响。优先级是选择执行者的顺序，不是 CPU 份额；一个始终就绪的高优先级循环可以让低优先级永久得不到运行机会。

Linux 策略不能混成一类

普通调度追求公平和交互表现，nice 影响相对权重；其具体算法与内核版本相关，例如 EEVDF。SCHED_FIFO、SCHED_RR 是固定实时优先级策略，RR 对同优先级加入时间片；SCHED_DEADLINE 使用运行预算、截止时间和周期等参数。策略名称并不证明整机满足硬实时，驱动、锁和中断也会干扰截止时间。

如何解释最坏响应时间

对有界、周期或偶发任务，在限定调度模型下，可迭代估算 Rᵢ=Cᵢ+Bᵢ+Σceil(Rᵢ/Tⱼ)Cⱼ：自身最坏执行 C、低优先级资源阻塞 B，以及更高优先级任务的干扰。实际还要纳入中断、调度开销和释放抖动；若任务自挂起或执行时间无界，不能直接照搬简化公式。

从公式反推设计

降低平均 CPU 不一定改善最坏响应；缩短最长关中断区、限制锁内耗时和为长操作设置有限超时，往往更直接。周期越短的任务常需要较高优先级，但不是盲目按周期排序；必须结合截止时间、依赖和共享资源。实时性是“在约束内完成”，不是“越快越好”。

推演与反例

固定优先级的干扰怎样计算

高优先级任务即使只执行 1 ms，若每 2 ms 就释放一次，也会消耗约一半 CPU。低优先级任务除自身执行时间外，还要承受所有高优先级任务和中断的干扰，以及资源阻塞。一个任务 taskYIELD 后只要自己仍是最高优先级就绪任务，就不保证低优先级运行；等待实际事件而阻塞才会从就绪竞争中退出。

调度策略与系统前提

Linux 的 SCHED_FIFO、SCHED_RR 与普通策略不同，但仍受权限、实时带宽限制、内核可抢占性和驱动长临界区影响；目标内核使用 CFS 还是 EEVDF 应按版本确认。FreeRTOS 也要核对抢占、时间片、Tick 频率与移植层配置。同名优先级在 NVIC 和任务调度中的数值方向甚至可能相反。

继续追问

CPU 只有 20% 为什么还超时？

平均利用率掩盖了突发、长临界区和资源阻塞。一次 30 ms 的不可抢占区就可能让 10 ms 截止时间失败，即使其余时间 CPU 都空闲。

CPU 平均利用率低，能证明任务不超时吗？

不能。短时间内的突发、长临界区、优先级反转和 I/O 等待都可能错过期限。实时性应看最坏响应和到达模式，而不只看一分钟平均值。

T022 原理问答

中断上半部、下半部与任务化处理为什么重要？

中断前段负责必须及时处理的硬件状态，后续任务负责可以调度的解析和慢工作。拆分的目的是限制不可调度时间，并明确数据怎样从硬件上下文安全交给任务。

原理与成立条件

中断处理为什么分前后两段

中断前段直接响应硬件：读状态、清应清的标志、保存必须及时取得的数据，并安排后续工作。复杂解析、存储、协议重试放到可调度上下文，避免一个设备延迟所有同级或更低紧急度工作。分段的本质是限制不可调度时间，不是机械规定中断中只能写几行代码。

延后执行也有不同上下文

Linux 硬中断与通常的 softirq/tasklet 不能按普通进程上下文随意睡眠；工作队列的工作函数在内核线程上下文运行，通常可睡眠，线程化中断也有自己的约束。RTOS 常由 ISR 通知专用任务执行后半段。不能因为都叫“下半部”，就认为每种机制都能拿阻塞锁。

怎样保证交接不丢数据

ISR 与任务间需要数据容器以及唤醒协议。先保存数据，再通知消费者，避免消费者先醒来却看不到任务。缓冲容量至少覆盖消费者最长不能服务期间的输入，并明确满时策略；只发一个二值事件可能合并多次输入，所以消费时应排空数据或读取生产进度，而不是把事件数等同于字节数。

延迟预算应怎样拆

从设备产生事件，到 ISR 获得执行机会，再到任务就绪、获得 CPU、完成业务，是四段不同延迟。缩短 ISR 可能降低前两段，却增加排队或复制成本；应测最大中断屏蔽时间、缓冲高水位和任务唤醒延迟。DMA 可减少逐字节搬运，但不替你完成协议解析和流量控制。

推演与反例

延后处理为什么仍需要容量证明

ISR 只把数据放入缓冲然后唤醒任务，看似很短，但如果任务长时间拿不到 CPU，缓冲仍会满。必须计算中断到达速率、最长屏蔽时间、任务最坏调度延迟和消费速率；复制或 DMA 都只是改变搬运方式。一次 ISR 放入数据后立即退出，是把后续工作转移出去，而不是把工作消灭。

不同平台的“下半部”不能混用

Linux 的 softirq、tasklet、工作队列和线程化中断有不同上下文限制，尤其能否睡眠不能统一回答。MCU 上常用 ISR 加任务通知/队列形成类似分工，但不是运行 Linux 的 softirq。描述机制时应先说平台，再说谁运行、何时可抢占、共享数据如何同步以及满缓冲怎么办。

继续追问

中断中 printf 为什么危险？

格式化、锁、发送等待和潜在分配都可能耗时或不可重入。可在 ISR 写入固定大小事件记录，由任务格式化输出，并处理记录区满的情况。

把所有工作都放入最高优先级任务会怎样？

它可迅速接手中断，却可能长期饿死其他任务；若任务内仍做无界等待，响应链依旧无界。需要短工作段、适当优先级和可阻塞的等待点。

T023 原理问答

fork、exec、写时复制与进程间通信怎么理解？

fork 创建一个新的进程执行流，exec 用新程序替换当前进程映像，两者不是同一个操作。父子可通过继承的文件描述符通信，而普通私有内存修改不会自动同步。

原理与成立条件

fork 创建了什么

fork 创建子进程，子进程拥有独立的虚拟地址空间视图，继承许多资源引用。Linux 常用写时复制让父子初始共享物理页，只在某方需要写时分离；页表和进程管理仍有成本，所以不能说 fork 完全零拷贝或父子变量永久共享。

exec 与 fork 的区别

exec 用新程序映像替换当前进程的代码、数据和初始执行环境，成功后不返回旧调用点，进程身份并不是简单另起一个子进程。exec 本身不负责先 fork；shell 常组合二者完成新命令。文件描述符是否保留取决于 close-on-exec 等状态，泄漏 fd 会让管道和服务退出异常。

多线程 fork 的特殊风险

子进程通常只保留调用 fork 的线程，其他线程消失，但它们持有的锁状态可能留下。子进程在 exec 前若调用 malloc、日志等可能拿到无人释放的锁；应遵守 POSIX 对此阶段可调用函数的限制，必要时使用合适的 spawn 接口或严格的 atfork 协调，而非随意复制多线程运行态。

IPC 选择依据

管道适合相关进程的顺序字节流，Unix socket 适合双向与本机消息/凭证等能力，共享内存避免部分数据复制但需要独立同步和布局协议，消息队列提供消息边界但有容量限制。共享内存不是“自动线程安全”，信号也不适合搬运大量可靠业务数据。

推演与反例

从返回值理解两条执行流

fork 成功后，父进程得到子 PID，子进程得到 0，两边从调用之后分别继续；exec 成功时不返回原程序，而从新映像入口执行。现代 Linux 的写时复制减少了 fork 立即复制全部内存的成本，但页表、任务状态和后续首次写页仍有开销。把 fork 称为“复制一个线程”会漏掉地址空间和资源语义。

多线程 fork 的锁为什么危险

子进程只保留调用 fork 的线程，但地址空间中可能留下另一个已不存在于子进程的线程所持有的锁。子进程再调用依赖该锁的库函数可能卡住。POSIX 对多线程 fork 后、exec 前可调用的函数有严格限制；优先使用合适的 spawn/exec 流程，不把普通线程库操作任意塞进子分支。

继续追问

fork 后两个进程写同一个继承 fd，偏移是否独立？

它们常引用同一 open file description，文件偏移共享；进程地址空间独立不代表所有内核资源对象都独立。

共享内存是不是最快就一定最好？

它可减少数据复制，但必须自己解决通知、同步、数据布局和崩溃恢复；管道/socket 自带消息传递所需的一部分生命周期边界。选择应结合数据量与故障隔离要求。

T024 原理问答

fd、open file description、dup 与 close 有什么区别？

fd 是进程中的整数索引，open file description 是内核维护的一次打开状态。dup 或 fork 继承的 fd 可以共享该状态，因此“两个 fd”不必然对应两份独立文件偏移或状态标志。

原理与成立条件

fd、打开文件描述与文件对象

fd 是进程描述符表里的整数索引；它指向内核的 open file description，其中保存文件偏移和部分状态标志，后者再关联具体文件/设备。对同一路径调用两次 open 通常得到两个独立打开描述；dup 得到新 fd，却共享原打开描述。

dup 共享与不共享的状态

共享偏移和 O_NONBLOCK 等文件状态标志，意味着通过一个副本读写或改变状态会影响另一个；FD_CLOEXEC 属于每个描述符的标志，不是共享打开描述属性。把某个 fd 复制一份不等于创建独立通信连接，也不自动建立新的读写顺序隔离。

close 只释放一个引用

只有相关引用都释放后，内核对象才最终关闭；对 socket 还可用 shutdown 表达方向结束。epoll 注册与打开描述的关联使 dup/fork 后关闭一个数值不一定立即消除所有事件，应用需明确注销。整数被复用后，旧异步操作若仅凭 fd 数值识别对象就可能误操作新连接。

close 错误不能机械重试

Linux 在某些 close 错误报告之前已释放 fd 数值，重试可能关闭其他线程刚打开并复用该数字的对象；EINTR 的跨平台语义也需要按系统核实。资源封装应使自身进入不拥有状态，并通过合适通道记录错误，而非无限重复 close。

推演与反例

dup 后谁的偏移会变

fd1 与 dup 得到的 fd2 通常指向同一 open file description，一边 read 推进的偏移会影响另一边；另一次独立 open 则通常有自己的打开状态。O_NONBLOCK 属于文件状态标志，相关描述符可共享；FD_CLOEXEC 是描述符标志。区分两层，才能解释子进程继承、关闭和 epoll 注册的行为。

fd 重用怎样制造误操作

连接 A 的 fd=7 被关闭后，新连接 B 可能立即拿到 7。一个迟到任务若只记着整数 7，再调用 write 或 close，可能操作 B。因此异步身份应带连接对象/代数并校验寿命；关闭一次失败后盲目再 close 同一数字，在 Linux 的某些失败情形下可能关闭已复用描述符，应按具体接口语义处理。

继续追问

为什么多线程程序创建 fd 时优先原子设置 CLOEXEC？

若先 open 再 fcntl，另一线程可能在中间 fork/exec，让 fd 泄漏进新程序。使用支持的 O_CLOEXEC 等原子接口缩小该竞态。

RAII 已经保证 close，为什么还要取消回调？

RAII 解决资源最终释放，无法自动删除外部队列里尚未执行的借用操作。回调的有效期必须早于资源释放，或能检测对象已失效。

T025 原理问答

Cache、伪共享和内存序为什么会影响多核并发？

Cache 改变访问成本，缓存一致性协调同一地址的多份缓存，内存序约束并发访问的先后关系。三者相关但不等价；“硬件缓存一致”不能替代语言同步。

原理与成立条件

缓存一致性按缓存行工作

多核 CPU 缓存通常以固定大小缓存行为传输和一致性管理单位。两个线程分别更新不同变量，语言层面没有共享同一对象，却可能因变量位于同一缓存行而互相使缓存副本失效，产生不必要的一致性流量，这叫伪共享。

为什么原子变量也会很慢

原子性保证更新语义，不消除缓存行取得写权限的成本。两个核频繁写同一行中各自的原子计数器，缓存行仍可能来回迁移。把内存序从 seq_cst 改为 relaxed 只能去掉不必要排序约束，无法自动消除同一缓存行的争用。

怎样验证再优化

先定位热点及核间访问，结合 perf c2c、数据布局与平台支持查看高争用缓存行，再用控制实验把热写字段分开或分线程计数后聚合。单纯看到多线程就给所有字段填充，会增加内存、缓存和 TLB 压力，可能得不偿失；缓存行大小也不是所有 CPU 都固定 64 B。

与真正共享及 DMA 区分

如果多个线程本就更新同一业务计数，这是实际共享，需要改变算法或分片，不只是加 padding。DMA 一致性又涉及设备与 CPU 缓存副本，应按平台维护。无 D-cache 的小型单核 MCU 不存在相同的多核缓存行争用问题，不能把 Linux 服务器经验照搬过去。

推演与反例

伪共享为什么没有逻辑共享仍会变慢

两个线程分别修改不同计数器，数据没有竞争，却恰好位于同一缓存行。每次写可能使该行的所有权在核心间转移，产生额外一致性流量。把热点写字段分散到不同缓存行可改善，但具体行大小需按目标确认；盲目填充所有结构体会增加工作集和内存占用。

DMA 与缓存是另一种所有权问题

非一致性 DMA 从内存读，CPU 最新数据可能仍在脏缓存中；DMA 写完内存，CPU 又可能读到旧缓存。需要按方向在规定时机 clean 或 invalidate，并遵守缓存行对齐和共享行边界。Cortex-M3 的 STM32F103 不应直接套用带 D-cache 的 M7 操作，但移植到后者时必须重新审计这条链。

继续追问

两个只读线程读同一缓存行算伪共享吗？

一般不会触发这种写失效抖动；关键是至少有频繁写入，使其他核需要重新取得该行。共享读取常能有效利用缓存。

加 memory fence 能修复伪共享吗？

不能。屏障可能增加开销，它不改变两个字段处于同一缓存行的事实。伪共享是布局与访问模式问题；缺少同步则是另一个正确性问题。
