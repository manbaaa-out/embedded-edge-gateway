Cortex-M3 与 STM32 系统基础

T062 原理问答

STM32 上电后如何走到 main，再启动 FreeRTOS？

Cortex-M 复位后先从向量表取得初始主栈地址和复位入口，再由启动代码建立 C/C++ 运行环境，才进入 main。RTOS 调度器又在此之后建立任务运行环境，二者是不同阶段。

原理与成立条件

复位后 CPU 从哪里开始

Cortex-M 的启动向量表首项给初始主栈指针 MSP，第二项给复位处理程序入口；处理器依据启动映射取这些值。STM32 的启动引脚/选项与芯片系列决定映射主 Flash、系统存储器或其他区域。地址 0 的启动别名与实际 Flash 基址是两个概念，不能一概说程序永远从 main 地址开始执行。

C 运行环境由谁准备

复位处理程序通常调用早期系统初始化，把 .data 的初值从非易失存储复制到 RAM，清零 .bss，执行必要运行库和全局构造初始化，再进入 main。具体先后看启动文件。此阶段还不能任意假定全局变量和 C++ 对象都已就绪，早期 SystemInit 的代码必须遵守初始化时序。

main 到调度器之间

通常先初始化 HAL、系统时钟和外设，再创建队列、互斥量、任务等对象。使能中断和启动 DMA 前，应保证 ISR 将访问的句柄与缓冲已有效。调度器启动时选择首个就绪任务并恢复其上下文；任务函数通常无限循环，若要结束，应通过内核接口删除自己而不是普通 return。

为什么启动时序是正确性问题

外设先来一个中断而队列还没创建，会在“看似正常初始化”过程中访问空句柄；时钟修改后未更新延时参数，会让微秒时序错误。调度器前不能直接使用依赖任务阻塞的延时接口。排查未到 main 或未进任务时，要按向量、栈、段初始化、时钟、对象创建和调度器逐层定位。

推演与反例

为什么 main 前必须搬运和清零

有初值的可写全局变量，初始内容通常存在 Flash，启动时要复制到其 SRAM 运行地址；未显式初始化的静态存储对象所处 BSS 要清零。否则全局变量不满足语言规定的初始值。随后还可能调用 C++ 静态对象构造，再调用 main。SystemInit 与运行库初始化的具体次序以启动文件为准，早期代码不能假定后续才初始化的数据已经可用。

任务怎样从一块栈开始运行

创建任务时内核为它构造初始上下文，栈中预先放入入口、参数、状态等内容；启动调度器后移植层通过异常返回机制开始第一个任务。任务函数不能像普通 main 子函数一样自然返回，结束时应显式删除或进入受控路径。调度器启动失败往往涉及内核任务创建、堆容量或中断配置，不能只看任务入口是否有断点。

继续追问

下载成功却进 HardFault，先看什么？

检查向量表初始 MSP 是否位于有效 RAM、Reset_Handler 地址及 Thumb 状态、链接地址与下载地址是否匹配，再看故障现场；下载校验成功只证明写入字节一致。

Bootloader 跳应用为什么不能只调用一个函数指针？

还要处理向量表、MSP、残留中断、SysTick、外设和特权/栈选择状态，并校验入口地址。否则应用遇到第一次中断时可能仍跳到旧表或使用错误栈。

T063 原理问答

Flash、SRAM、DATA、BSS、堆和任务栈如何分布？

链接脚本描述段在 Flash/SRAM 中的放置，启动代码把这种布局变成运行时状态。text、rodata、data、bss、C 库堆、RTOS 堆和各类栈有不同来源，不能只看某个数组大小估算 RAM。

原理与成立条件

.text、.rodata、.data、.bss

代码通常进 .text，常量可能进只读段；带非零初值的静态对象通常在 .data，零初始化静态对象通常在 .bss。段名和放置是工具链约定与链接策略，不能把 const、static 这些语言属性直接等同于某个绝对物理地址。优化还可能完全消除未使用对象。

装载地址与运行地址

.data 需要掉电后仍保留初值，所以镜像可在 Flash 保存一份，运行时复制到 SRAM。它因此同时消耗镜像和 RAM；.bss 只需记录大小并清零，通常不在镜像保存同样长度的零字节。看 size/map 时需区分文件占用与运行期占用。

任务栈和主栈

每个任务需要保存局部变量、调用现场和部分异常上下文，RTOS 常从堆分配任务栈；异常处理使用 MSP，任务一般使用 PSP。任务栈总预算之外，还要给 ISR 嵌套、启动代码和主栈留空间。链接脚本里的栈预留不会自动限制所有运行期任务栈。

const 与 Flash 写入的误区

const 限定通过相应类型访问的修改规则，不保证对象必在 Flash；局部 const 可能放栈或寄存器。Flash 擦写又有页/半字等硬件粒度、执行时延和寿命限制，不能当普通 RAM 随意写。大查找表、格式化库和全局数组分别要从 map 中核对，而不是只凭源码估算。

推演与反例

LMA 与 VMA 为什么需要两个地址

带初值变量运行时可写，放在 SRAM 的 VMA；复位后 SRAM 内容不可靠，初值又要从 Flash 的 LMA 装载。链接器提供边界符号，启动代码按它们复制。BSS 通常不需要在 Flash 为每个零存一份镜像，而由启动循环清零。noinit 区若要跨复位保留，必须明确启动流程不覆盖它，并用校验/版本判断内容是否可信。

一份 RAM 预算要把哪些项相加

静态变量占 data/bss，动态创建的 FreeRTOS 任务栈、TCB、队列通常来自内核堆，主栈/MSP 则还要承受异常处理与嵌套。C 库 malloc 可能又使用另一块堆。把内核堆数组算在 BSS 后再把其中任务栈重复加入总 RAM 会双计；反过来只统计应用任务又会漏掉 Idle 和 timer 任务。map 文件与运行期高水位应对应解释。

继续追问

固件 40 KiB、SRAM 20 KiB，为什么仍可能内存不够？

Flash 文件大小不表示 RAM 余量，动态堆、多个任务栈和中断主栈有独立开销；.data 还同时占两边资源。

Flash 还剩很多空间，为什么创建任务失败？

创建任务主要需要 RAM 中的栈和控制块，Flash 富余不能直接替代可写 RAM。还要分清总剩余堆与最大连续可分配块。

T064 原理问答

STM32 时钟树、APB 定时器倍频与 PWM 怎样计算？

外设频率应沿时钟源、PLL、AHB、APB 和外设分频逐级推导。STM32F1 的定时器输入时钟在 APB 分频不为 1 时通常为对应 PCLK 的两倍，不能直接拿 CPU 主频代入所有公式。

原理与成立条件

时钟树为何不止一个频率

内部/外部振荡源经 PLL 和分频形成系统时钟，再分给 AHB、APB 与各外设。CPU 主频、总线频率、定时器输入时钟和外设采样时钟可能不同；修改 PLL 后若仅更新一个全局数字，不代表全部外设分频都仍合法，还需满足电压、Flash 等待周期和总线最高频率限制。

STM32F1 的定时器倍频规则

该系列在 APB 预分频为 1 时，相应定时器时钟通常等于 PCLK；预分频不为 1 时，相应定时器内核时钟为 2×PCLK。这个规则属于具体时钟树，不能推广成所有 STM32、所有外设都自动倍频。USART、I2C 等也不能照套定时器规则。

时钟误差如何传到系统

UART 位宽、PWM、I2C 速率和 DWT 延时都依赖实际输入时钟，振荡器误差与温漂会影响时序。切换时钟应等待稳定与切换状态，按芯片要求配置 Flash 延迟和分频；故障路径需要有限等待。测量可用 MCO、定时器输出或已知 GPIO 脉宽校验。

PWM 频率与占空比

对向上计数、边沿对齐的常见 PWM 模式，周期仍由 PSC/ARR 决定，比较寄存器 CCR 决定在周期中切换的计数点。例如有效高且 CNT<CCR 时输出有效，占空比约 CCR/(ARR+1)。极性、PWM 模式和中心对齐会改变解释；更新预装载可让新参数在更新事件生效，避免周期中途改值产生毛刺。

推演与反例

一个定时器周期怎样算

假设系统 72 MHz，APB1 分频为 2，则 PCLK1=36 MHz，相关定时器时钟为 72 MHz。向上计数模式下，更新频率通常为 fTIM/((PSC+1)(ARR+1))；PSC=71、ARR=999 时得到 1 kHz。公式中的加一来自计数包含零。高级定时器重复计数器、中心对齐模式等会改变事件频率，应注明模式再计算。

PWM 频率和分辨率如何权衡

边沿对齐 PWM 中，周期由 ARR 决定，占空比由 CCR 与计数周期关系决定；ARR 越大，可分的占空比步数越多，但在给定计数时钟下频率越低。更新 ARR/CCR 还要考虑预装载，避免在周期中途改变导致毛刺。系统提高主频时同时要满足电压、Flash 等待周期及 APB 最高频率等限制。

继续追问

APB1 36 MHz，TIM4 为什么还能按 72 MHz 算？

因为当前 APB1 分频不是 1，F1 时钟树给该定时器内核使用 2×PCLK1；先确认分频配置才能使用这个结论。

改系统时钟后哪些软件常数会失效？

UART 波特率、I2C 时序、TIM 周期、SysTick 重装值以及按 CPU 周期计算的 DWT 延时都可能需要重新配置；不能只更新 SystemCoreClock 变量。

T065 原理问答

NVIC 优先级为什么数值越小越高？抢占与子优先级怎样区分？

NVIC 中断优先级通常是数值越小紧急度越高，FreeRTOS 任务优先级则通常数值越大越高。抢占优先级决定能否打断当前异常，子优先级只在相应候选异常之间影响选择次序。

原理与成立条件

数字优先级与紧急度相反

Cortex-M 可配置异常优先级数值越小越紧急；FreeRTOS 任务通常数值越大越优先，两套排序不可混用。NVIC 寄存器字段可能有 8 位，但芯片只实现其中高若干位，STM32F103 实现 4 位，因此库常用逻辑值 0..15，再移位写入寄存器。

抢占优先级与子优先级

分组把有效位划分为抢占和子优先级。抢占部分决定能否打断正在执行的异常；同一抢占等级的子优先级只在多个待处理异常间决定先后，不能造成同级嵌套。没有更紧急者时，异常在满足屏蔽条件后进入；pending、active 与 enable 是不同状态。

为什么 FreeRTOS 限制 ISR 调用范围

内核更新就绪链表等共享结构时，用 BASEPRI 屏蔽一部分中断。如果更紧急且不被屏蔽的 ISR 也修改这些结构，就可能在临界区中打断内核，造成破坏。因此只有落在允许范围的 ISR 才能调用 FromISR；更紧急 ISR 应仅处理独立硬件或通过安全延后路径交接。

怎样核对配置

先确认 __NVIC_PRIO_BITS，再确认分组，区分库逻辑优先级与左对齐硬件值。例如逻辑阈值 5、有效位 4，对应 BASEPRI 0x50；逻辑 5..15 的可配置 ISR 才在该阈值保护范围。0 是最高紧急度且不能用非零 BASEPRI 阈值屏蔽，不能让调用 RTOS 的 ISR 留在默认 0。

推演与反例

逻辑优先级与寄存器编码怎样换算

若实现 4 个优先级位，逻辑值 0..15 存在 8 位优先级字段的高 4 位，逻辑 5 对应寄存器值 0x50。CMSIS/HAL 接口可能接收未移位逻辑值，底层 BASEPRI 配置则可能需要已移位编码。把 5 当成 0x05 直接写寄存器会丢失有效位，造成与预期完全不同的屏蔽范围。

分组为什么会影响 RTOS 合法性

PRIGROUP 划分已实现的位为抢占位和子优先级位。依赖 BASEPRI 的内核希望中断屏蔽与调用 API 的范围可按其端口规则判断；某些不合适分组会使开发者给出的数字无法表达预期紧急度。调用 FromISR 的 IRQ 必须位于可被内核临界区屏蔽的范围，更紧急的 IRQ 可用于短硬实时处理，但不能直接进入内核对象操作。

继续追问

把串口中断从 6 改成 3，响应更快就一定更好吗？

若它调用 FromISR 而阈值仍为 5，会越过内核保护范围；先满足正确性，再讨论延迟。中断越紧急也会增加其他工作延迟。

两个 IRQ 数值一样会相互嵌套吗？

同一抢占优先级通常不能彼此抢占；挂起后的执行次序还受子优先级和异常号等规则影响。不能仅凭“先到的中断”解释所有情况。

T066 原理问答

中断入栈保存哪些寄存器，MSP 和 PSP 各做什么？

Cortex-M3 异常入口由硬件保存基础返回现场，软件或 RTOS 移植层保存其余任务现场。线程可使用 MSP 或 PSP，Handler 模式使用 MSP；进入异常前的那份基础帧可能保存在被打断线程的 PSP 上。

原理与成立条件

MSP、PSP 和 EXC_RETURN

MSP 是主栈，PSP 常供任务使用；Thread 模式可按 CONTROL 选择，Handler 模式用 MSP。异常期间 LR 中保存特殊 EXC_RETURN 编码，异常返回时据此决定返回模式、使用哪个栈及相关帧类型。它不是普通 C 函数返回地址，调试时要把异常 LR 与堆栈中原 LR 分开。

RTOS 为什么还要软件保存

硬件基本帧没有自动保存所有通用寄存器。任务切换时移植层再保存 R4–R11 等需要跨上下文维持的状态，将栈顶记入 TCB；选择新任务后反向恢复。嵌套中断未必发生任务切换，内核常把切换延后到最低紧急度 PendSV，避免在高紧急度处理器中穿插复杂调度。

尾链与延迟到达有什么意义

处理一个异常结束时，若另一个合适异常已等待，处理器可通过尾链减少完整退栈再入栈；更高紧急度异常在入口阶段到达也可改变先服务对象。这些优化减少固定开销，但总响应仍受屏蔽、总线和更高紧急度工作影响，不能把手册理想周期数当整机最坏延迟。

推演与反例

一次任务被中断的栈变化

任务在 PSP 上运行，异常入口把 R0–R3、R12、LR、PC、xPSR 等基础帧压入该任务栈，然后处理函数在 MSP 上运行；若 Handler 再被嵌套，相关现场压入 MSP。基础帧常为 8 个字，必要时还有对齐填充。不能因为“中断函数用 MSP”就漏算任务栈上的异常入栈空间。

EXC_RETURN 为什么不是普通返回地址

异常处理期间 LR 中的特定 EXC_RETURN 值描述返回到 Thread/Handler、使用哪一个栈等信息。异常返回据此恢复栈中现场。FreeRTOS 的 PendSV 还保存 R4–R11、更新 TCB 栈顶，并加载下一任务栈，让异常返回继续另一个任务。把该值当普通函数地址跳转会破坏返回过程。

继续追问

任务 PSP 足够大，为什么中断仍可能栈溢出？

ISR 嵌套和 ISR 内调用主要消耗 MSP，需独立预算；任务栈与异常主栈是两套容量，不能只测任务高水位。

切换上下文为什么不是硬件全包了？

硬件只保存定义好的基础帧，不知道哪个任务应运行，也不维护 TCB、延时队列和所有软件寄存器现场。调度选择与剩余保存由内核移植层完成。

T067 原理问答

PRIMASK、BASEPRI 与临界区有什么区别？

PRIMASK 广泛屏蔽可配置优先级异常，BASEPRI 按阈值屏蔽一段紧急度范围；它们都不是把芯片所有硬件停止。临界区要说明防的是谁、屏蔽多久以及退出时如何恢复原状态。

原理与成立条件

临界区必须保护同一组访问者

如果共享变量还被更紧急、未屏蔽的 ISR 修改，使用 BASEPRI 的任务临界区就不能独占它；需要重新设计交接或使用适当更强的短保护。单核关中断也不能阻止 DMA 写 RAM，更不能推广为多核系统的全局互斥。保护机制的范围必须覆盖实际写者。

嵌套与恢复旧状态

临界区退出要恢复进入前的屏蔽状态，而非无条件开中断；否则内部函数可能提前打开外层要求关闭的中断。RTOS 提供嵌套计数和 ISR 专用保存/恢复接口，不宜混用手写寄存器修改破坏它们。ISR 使用哪个宏也受移植层契约限制。

代价在最坏延迟而非平均占用

长临界区推迟 SysTick、串口回调和任务切换，可能造成 DMA 缓冲被覆盖、多个 Tick 只留下一个待处理状态。区内不应等待队列、互斥量或依赖被屏蔽中断更新的超时。保护几十条指令合理，并不意味着可以把几毫秒传感器事务整体包起来而无需分析。

推演与反例

为什么内核保留更紧急中断

以 BASEPRI 建立临界区时，可调用内核 API 的中断被屏蔽，因而任务与这些 ISR 不会同时修改内核链表；更紧急中断仍能响应硬件，但必须不访问受保护内核结构。这是一份双方契约：若高紧急度 ISR 违规调用 FromISR，它就可能在内核数据结构更新到一半时进入，问题不一定立刻暴露。

嵌套临界区为何要保存状态

外层已屏蔽中断，内层若退出时无条件全开，会提前破坏外层保护。任务临界区通常维护嵌套计数，ISR 专用屏蔽接口可能返回旧掩码供恢复；具体用法由端口规定。普通用户代码不要混用不配对的 enable/disable 与 RTOS 临界区，尤其不能在临界区里等待依赖被屏蔽中断的完成事件。

继续追问

进入临界区后 DMA 还收不收？

若 DMA 和外设时钟仍工作，硬件传输可继续；延迟的是 CPU 处理相关中断。缓冲因此可能被继续写满甚至覆盖，临界区不是 DMA 暂停按钮。

DMA 在关中断时会停吗？

通常不会。DMA 控制器仍可搬数据，只是 CPU 处理其完成或半满通知被延后；因此长临界区仍可能导致循环缓冲覆盖，甚至使多次硬件事件合并。

T068 原理问答

HardFault 应当怎样定位，为什么不能只在里面死循环？

HardFault 首先是现场采集问题，再是根因分析问题。应保存异常栈帧和故障状态寄存器，区分非法地址、指令状态、除零、栈破坏或被升级的其他异常，而不是只停在死循环里猜测。

原理与成立条件

HardFault 是入口，不一定是根因

Cortex-M3 的非法访问、执行状态等故障可由 MemManage、BusFault、UsageFault 描述；未使能相应处理或处理失败时可能升级为 HardFault。HFSR 的 FORCED 等信息指示升级，再结合 CFSR 子状态判断；只看“停在 HardFault_Handler”无法定位哪条业务语句有错。

首先保住现场

在极简异常入口根据 EXC_RETURN 选择 MSP/PSP，保存硬件栈帧中的 PC、LR、xPSR 及必要状态寄存器。读取 BFAR/MMFAR 前检查有效标志。故障可能发生在压栈阶段或栈已损坏，此时栈帧地址与内容也需要校验，不能盲目再次深度调用格式化库。

从状态到故障代码

精确总线故障时堆栈 PC 常能帮助定位访问指令；缓冲写引起的不精确故障可能不能直接指向真正起点。结合反汇编看地址来源、对齐和访问宽度，再追溯越界、空指针、栈破坏和错误函数指针。使用与故障固件完全对应的 ELF/map，地址才能映射正确。

复位后还要能读取证据

可把最小故障记录写到适当保留区域或在重启时输出，配上固件版本、复位原因和校验；不应在故障态进行无限 I/O。栈水位、哨兵与可选 MPU 可提前发现破坏，watchdog 仅负责最终复位，不会自动解释为什么出错。

推演与反例

现场如何指向出错指令

根据异常返回信息确认故障时使用 MSP 还是 PSP，定位堆栈中的 PC、LR 与参数寄存器；结合 CFSR、HFSR 及地址有效标志判断 MMFAR/BFAR 是否可解释。用对应 ELF 反汇编和源码映射检查指令，例如一次访问指针加偏移后的地址。若错误是非精确总线故障，堆栈 PC 未必就是最早出错指令，不能过度解读。

为什么故障处理程序本身要克制

栈可能已经损坏，日志堆锁和外设状态也可能不可靠。在 Handler 中执行复杂 printf、动态分配或无限等待串口，可能再次故障或掩盖原现场。更稳妥的是用最小代码保存有限寄存器到预留区，附带校验和复位原因，下次启动再输出；同时确认看门狗是否允许保留足够取证时间。

继续追问

PC 指向一个正常函数，是否能排除内存越界？

不能，栈或函数指针可能更早被破坏，真正错误与最终异常有时间距离；需结合寄存器、调用链和周边内存找首次破坏点。

开栈溢出 Hook 就能抓住所有栈越界吗？

不能，它只在特定检测点与条件下发现部分问题；越界可能已经破坏调度结构，或发生在 MSP。还需静态栈预算、高水位、保护区与故障现场结合。

T069 原理问答

寄存器读改写、BSRR 和位操作有什么并发问题？

寄存器不是普通内存变量，读写可能有硬件副作用。读改写会经过多个操作，既可能与中断竞争，也可能误处理写一清零、读清除等特殊位；应按寄存器契约使用专用置位/复位接口。

原理与成立条件

内存映射寄存器如何访问

外设寄存器映射在处理器地址空间，读写相应地址通过总线触发硬件操作。volatile 让编译器按实现约定保留访问，但寄存器可能具有读清零、写 1 清除、只写、保留位等特殊语义，不能把所有寄存器都当普通变量做任意 |= 或 &=。

读改写的竞态

REG |= mask 通常先读整个寄存器、改本地副本再写回；若两次访问间 ISR 或硬件改变其他位，旧副本可能覆盖新状态。例如两个执行者分别更新同一输出寄存器不同引脚，仍可能丢更新。解决方法包括专用置位/清零寄存器或覆盖所有写者的适当临界区。

BSRR 为什么适合 GPIO

STM32F1 的 GPIO BSRR 用不同位段表达置位与复位，一次写入让硬件修改指定引脚，避免软件先读 ODR 再写回的窗口。它保护的是这次位更新，不自动保护更复杂的“判断引脚后执行多步”事务；多个引脚有严格同步要求时也要查看单次写及电气时序。

位带与原子指令不是万能替代

位带属于特定地址范围的架构映射能力，不是所有 MCU/寄存器都支持；LDREX/STREX 的适用内存类型和成功条件也有限。设备寄存器最好遵循手册提供的访问方式。更一般地，单次总线原子更新不等于多个对象间的 C++ happens-before。

GPIO 模式与速度容易混淆

推挽能主动驱高和驱低，开漏只主动拉低、释放时需上拉；浮空输入无确定空闲电平，上拉/下拉输入给出默认偏置，模拟模式通常关闭数字输入路径以减少干扰和功耗。GPIO speed 描述输出驱动/边沿能力，不是软件翻转频率；过高边沿速度会增加振铃和 EMI，应按负载与时序选择。

推演与反例

GPIO 的丢更新怎样发生

任务读 ODR 得到旧值，准备置位 bit0；中断先置位 bit1，任务随后把旧值加 bit0 写回，就可能把 bit1 清掉。使用 BSRR 可在单次写中表达某些位的置位或复位，避免为这些操作读取整个 ODR。它不自动使“先判断输入再切换输出”的多步业务原子化，复杂状态仍需协调。

GPIO 模式背后的电气行为

推挽可以主动驱动高低，开漏只主动拉低，释放后的高电平靠上拉；输入浮空可能被噪声影响，模拟模式可关闭部分数字输入路径以适应模拟信号。复用功能把引脚控制权交给外设，但仍需配置正确的电气模式、速度和上下拉。F1 的 MODE/CNF 与后续系列寄存器结构不同，不能跨系列照抄位域。

T070 原理问答

HAL、LL 和裸寄存器怎么取舍？

HAL 提供状态机、超时和较统一接口，LL 更贴近单次外设操作，裸寄存器让控制最直接。选择应依据时序约束、代码体积、可维护性与对硬件的掌握，而不是预先把某层判为一定慢或一定可靠。

原理与成立条件

三个层次分别封装什么

直接寄存器代码最接近硬件，开发者负责所有状态与时序；LL 提供较薄的寄存器操作封装；HAL 进一步封装句柄、状态机、超时与回调。抽象程度越高通常越容易初始化和移植应用，但可能带额外检查及不显眼的阻塞点，必须读到真正影响时序的路径。

选择看约束而非阵营

普通初始化和非关键路径用成熟 HAL 可减少配置错误；严格微秒时序可用定时器/DMA、LL 或局部寄存器实现。不能仅以源代码行数判断性能，也不能认定 HAL 天然线程安全。句柄状态、锁和回调上下文需要对照当前驱动版本核实。

混用的风险来自状态不一致

应用直接改外设寄存器后，HAL 句柄仍可能以为在原模式运行；直接停止 DMA、改中断或清标志，也可能破坏 HAL 的完成状态机。可混用，但应划清某个外设何时归哪层管理，切换时同步状态，不能让两套驱动同时独立拥有硬件。

超时接口也要读实现

某些 HAL timeout 靠 HAL_GetTick，若当前上下文屏蔽其 Tick，就可能永远不到期；HAL_MAX_DELAY 又可能绕过超时。DMA 启动返回 HAL_OK 只表明启动成功，最终结局在回调或错误路径。把 API 名字和返回码直接当完成证明，是驱动集成常见问题。

推演与反例

高层驱动隐藏了哪些状态

一次 HAL 接收启动不仅设置地址和长度，还可能检查句柄状态、锁、DMA 回调和错误标志。如果应用直接改寄存器而不更新句柄状态，硬件与软件认知会分离，下一次 HAL 调用可能返回 BUSY 或执行错误清理。混用不同层时要明确哪个模块拥有外设，以及如何保持两层状态同步。

优化要从具体路径开始

在微秒采样循环中，函数封装和 GPIO 读取路径可能影响判位；在等待 180 ms 传感器转换时，省几条配置指令却几乎没有收益。可把严格时序段写成经过测量的短操作，其余初始化和错误恢复保留可维护接口，并用逻辑分析仪验证真实波形。整体替换 HAL 前必须考虑版本、勘误和恢复路径。

继续追问

面试官要求不用 HAL 重写驱动，应先讲什么？

按时钟/引脚、寄存器配置、启动条件、数据传输、完成/错误及恢复顺序解释，先展示硬件状态理解，再讨论函数封装。

HAL 返回 OK 是否代表业务正确？

只代表该接口定义的操作成功，不代表传感器数值合理、数据新鲜或上层命令已完成。驱动结果还要经过格式、范围与业务检查。

T071 原理问答

如果增加 Bootloader/OTA，怎样设计启动与回滚？

Bootloader/OTA 的核心是任何允许的掉电点之后仍有可运行、可验证的启动路径。下载完成、完整性检查、真实性验证、试运行确认和回滚应形成明确状态机。

原理与成立条件

Bootloader 与应用的职责

Bootloader 在启动时选择并验证可运行镜像，应用负责正常业务或下载候选镜像；芯片出厂系统 Bootloader 又是另一套固化能力。自定义升级需规划启动区、应用区、下载区与元数据，并限制擦写对当前执行、向量和中断的影响，不能仅用一个 memcpy 到 Flash 代替完整升级流程。

掉电安全依赖状态提交顺序

先接收候选镜像并校验完整性与真实性，写入可恢复元数据，再标记为待试运行；试运行通过自检才确认生效，否则回退旧镜像。A/B、外部暂存或交换方案各有 Flash 容量与擦写代价。升级任何一步掉电，重启后都应能确定仍有一个完整可启动版本。

CRC、签名和版本分别解决什么

CRC/哈希帮助检测损坏，签名结合可信公钥验证发布者及内容，版本/单调计数用于限制回滚到已撤销旧固件。只验证哈希而哈希值也来自同一不可信下载源，不能证明镜像可信。密钥、元数据原子更新与防回滚存储同样属于设计。

跳转应用前要清理环境

核对初始栈和入口地址，停止不应继承的 DMA、SysTick 和中断，按要求调整向量表与栈，再进入应用复位入口。应用不能意外继承下载期间的外设状态。具体跳转序列受内核、启动模型和编译约束影响；很多系统采用复位后由 Bootloader 选择镜像更易界定状态。

推演与反例

双镜像为何仍需提交标记

新固件写入备用区后，先校验长度、哈希及签名，再把它标为可试运行；首次启动若不能在限定条件下确认，Bootloader 回到旧镜像。状态标记本身也可能写到一半，需要原子写粒度、冗余或日志式更新。只保留两份二进制而没有可恢复元数据，仍可能不知道哪份完整、哪份已确认。

安全与可用性是两组验证

CRC/哈希发现损坏，签名验证发布者身份；防回滚还需要受保护的版本策略。应用即便签名正确，也可能启动后卡死，因此需试运行与恢复入口。Flash 页擦除、写入对齐、同 Bank 执行限制、向量表和外设状态都要纳入平台设计；空间不足时应明确外部暂存或独立恢复协议，不能承诺凭空双备份。

继续追问

只有一份应用存储空间，怎样保证升级掉电能恢复？

必须保留独立可运行的恢复入口，并有外部暂存、分块恢复协议或重新下载能力；若擦掉唯一应用又没有恢复通道，就无法仅靠软件标志承诺回滚。

为什么升级不能沿用普通 RAM 队列的可靠性说法？

升级跨复位和掉电，RAM 中的进度会丢失，必须依赖可恢复的持久状态及受保护启动代码；传输成功只是其中一步。
