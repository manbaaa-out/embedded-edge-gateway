C 与 C++：对象、内存与语言规则

T001 原理问答

RAII 为什么比到处手动 close 更可靠？

RAII 把资源的释放时机绑定到对象生命周期。关键不是“用了析构函数”，而是任何时刻都有明确所有者，取得资源后立即交给它；这样正常返回、提前返回和异常展开都走同一套释放规则。

原理与成立条件

RAII 的核心不变量

资源获取即初始化，把资源有效期绑定到对象有效期。成功构造的对象拥有资源，析构时负责释放；离开作用域、提前 return 或异常栈展开都走同一释放路径。资源不仅是堆内存，还包括 fd、互斥锁和连接。与 goto cleanup 相比，责任随类型封装，调用者不必逐条记住释放动作。

RAII 不能替代业务关闭协议

析构能释放内存，却不保证后台线程已退出、队列已排空或数据库提交成功。成员按声明顺序的逆序销毁，也要符合依赖关系。线程仍使用某成员时就析构该成员，即使每个成员都用了智能指针，整体设计仍可能错误。先建立停止顺序，再让 RAII 承担最后的资源回收。

推演与反例

为什么只靠成对调用仍会泄漏

假设函数先 open 文件，再分配缓冲，最后启动线程。第二步失败时，第三步从未发生，但第一步已经需要清理。逐条 goto 或 catch 可以做对，却会随路径增加而变复杂。用 fd 包装器、vector 和线程管理对象分别接管资源，已构造完成的成员在失败时逆序析构；尚未构造完成的对象自身不会调用析构，因此构造中的裸资源尤其应先交给已完整构造的子对象。

独占所有权怎样影响接口

资源包装器通常禁用复制，允许移动：移动后原对象进入“不持有资源”的状态，最终只关闭一次。借用者可使用 fd 或指针，但不能擅自释放，也不能活得比所有者长。线程资源还多一步：析构前先提出停止、唤醒阻塞点并 join，只有释放句柄不足以保证后台代码已经停止访问成员。

继续追问

为什么不能依赖析构函数自动提交数据库事务？

析构缺乏清晰的失败返回通道，而且异常退出时往往应回滚。一般让提交显式发生，析构负责在未提交时安全撤销或关闭。

RAII 能保证断电时也执行清理吗？

不能。进程被强制终止、断电或异常终止路径不保证正常栈展开。RAII 解决进程内资源生命周期；持久状态仍靠事务、日志及恢复协议。

T002 原理问答

unique_ptr、shared_ptr、weak_ptr 如何选择？

先决定谁拥有对象，再选智能指针。唯一拥有者用 unique_ptr；确实有多个独立生命周期共同拥有时用 shared_ptr；只想观察共享对象而不延长寿命，用 weak_ptr。裸指针也可表达借用，重点是接口是否说清释放责任。

原理与成立条件

循环引用与析构线程

A 强持 B、B 强持 A 会让计数无法归零，可将非拥有方向改为 weak_ptr。回调按值捕获 shared_ptr 也可能形成隐蔽环。最后一个强引用在哪个线程释放，析构就可能在哪个线程执行；若析构耗时或必须在某个线程进行，需要额外的销毁调度设计。

推演与反例

控制块和对象是两个层次

shared_ptr 通过控制块管理强弱引用计数、删除器等。强引用归零时销毁对象；控制块还要供 weak_ptr 判断失效，通常到相关弱引用也释放后才能回收。weak_ptr::lock 把“是否还活着”和“取得一份强引用”组合为安全操作，不能先 expired 再使用一个原始指针，因为两步之间对象可能被销毁。

原子引用计数没有保护哪些东西

两个不同 shared_ptr 实例可共同管理一个对象并分别调整引用；但一个 shared_ptr 变量被一个线程赋值、另一个线程普通读取，仍涉及该变量自身的竞争。C++17 可以使用针对 shared_ptr 的原子自由函数或锁；atomic<shared_ptr<T>> 是 C++20 的接口。无论哪种方式，被指对象的业务字段仍需单独同步。

继续追问

weak_ptr.expired()==false 后直接用旧裸指针安全吗？

不安全，检查后对象仍可能销毁。应 lock 取得一个覆盖整个访问过程的强引用，再检查业务对象是否处于可用状态。

make_shared 总比分别 new 更好吗？

通常减少分配次数并简化异常安全；但大对象与控制块合并分配时，残留 weak_ptr 可能使整块分配迟迟不能归还。自定义删除器、外部资源或特殊分配要求也会影响选择。

T003 原理问答

std::move 做了什么，移动后对象还能用吗？

std::move 只是把表达式转换成可被移动重载接受的值类别，真正转移资源的是被选中的移动构造或移动赋值。它本身既不搬运字节，也不清空原对象。

原理与成立条件

转移所有权不等于端到端零拷贝

队列中移动 vector 可转移其缓冲，但编码时、内核 I/O 和硬件搬运仍可能复制。移动也不会让指向原对象子对象的任意引用自动有效，具体失效规则看类型。return 局部对象通常让编译器进行复制消除或隐式移动，随意加 std::move 可能妨碍 NRVO。

推演与反例

一次容器插入究竟发生什么

把一个 vector 移进另一个对象，在通常的分配器条件下可以转交数据区指针、大小和容量，避免逐个复制元素；但小对象、内嵌存储或不兼容分配器可能仍需逐项操作。对 const 对象 std::move 得到的仍带 const，常规 T&& 移动构造不能接收它，因此最终可能调用复制构造。判断是否发生移动必须看类型及重载，而不是看到 move 字样就下结论。

移动后如何写正确代码

标准库对象通常保证有效但未指定状态：可析构、赋新值，也能调用满足前置条件的成员；不能普遍假设字符串一定为空或容器一定保留旧内容。自定义类型应明确移动后的不变量。容器扩容还会考虑移动是否 noexcept；当移动可能抛异常且可复制时，vector 可能用复制维持异常保证。

继续追问

怎么验证某次操作究竟复制还是移动？

先看重载签名和值类别，再用可控示例或调试观察构造路径；不要仅凭源码出现 std::move 判断，也不要用打印改变时序后的单次测量宣称性能提升。

返回局部变量时都写 return std::move(x) 吗？

通常不需要，它可能阻碍命名返回值优化。应优先让返回值优化和隐式移动发挥作用，再在确需转移已有对象时显式 move。

T004 原理问答

vector 扩容、迭代器失效和字符串缓冲有什么坑？

容器操作首先要问“对象有没有搬家”和“元素位置有没有变化”。vector 连续存储，扩容会搬迁元素；即使没有扩容，中间插入或删除也可能使后面的元素移动，因此不同操作的引用失效范围不同。

原理与成立条件

view 与裸指针都不会保活

string_view、span 类视图以及 data() 返回地址都依赖原存储；容器扩容、销毁或修改相应区域后，视图可能悬空或含义改变。异步回调拿着一个 view 时，必须让拥有者在回调结束前保持稳定，而不是只保证局部 view 对象还存在。

消费缓冲怎样避免重复搬移

每处理一个字节就 erase(begin) 会反复搬动尾部，累计可能接近平方级成本。常用读写偏移标记已消费区域，空间不足时再集中压缩或扩容；但压缩后原地址同样失效。优化复杂度时还需设总容量上限，否则慢速消费者仍会拖垮内存。

推演与反例

用三个元素说明失效

vector 有 A、B、C，保存了指向 B 的指针。若 push_back 导致重新分配，旧数据区释放，所有元素指针都失效；若容量足够，既有元素指针仍有效，但旧 end 已改变。若 erase(A)，B、C 被前移，即使底层地址没换，原 B 位置也不能继续当作原来的 B。reserve 只减少扩容，不能解决擦除引起的身份变化。

字符串缓冲与异步发送

data 或 c_str 返回的是对象内部存储的借用地址，后续修改、扩容、移动和析构可能使地址或内容不再满足要求。把这个地址交给异步接口后马上复用字符串，错误可能在很久后才出现。应让发送任务持有整个字符串/独占缓冲，或在提交时复制，而不是仅延长一个裸指针变量的寿命。

继续追问

提前 reserve 足够大就永远不会有失效问题吗？

只能在不超容量且相应操作不移动目标元素的条件下减少失效。erase、中间插入、容器销毁与超出预估的增长仍需处理。

把 vector 改成 list 就没有生命周期问题了吗？

list 的节点地址通常更稳定，但擦除对应节点后仍失效，遍历缓存局部性和分配成本也不同。稳定地址不能代替所有权与删除时机设计。

依据与核对范围

C++ 工作草案：vector modifiers — 扩容、擦除和失效规则。 项目按 C++17，未引入新标准专属特性。

T005 原理问答

引用、指针、const 和回调捕获该怎样解释？

指针和引用描述访问关系，const 描述通过某个表达式允许做什么，它们都不自动延长普通被引用对象的生命周期。回调捕获尤其要区分“保存值”和“保存对原对象的借用”。

原理与成立条件

lambda 捕获的真实内容

[x] 复制 x，若 x 是裸指针，只复制地址；[&x] 借用局部变量，不能越过其寿命；[this] 捕获当前对象地址，不复制对象。C++17 的 [*this] 才是对象副本语义。异步保存的 lambda 应逐项分析捕获数据及其指向对象的寿命，而不是看到“按值捕获”就认为安全。

接口如何表明生命周期

短同步读取可借用 const 引用；接管资源可用独占拥有者或值参数移动；真正共享可用 shared_ptr；可选但不拥有可用指针并写清有效期。返回局部对象引用是立即悬空的典型错误，延长某些临时对象寿命的语言规则也不会普遍沿多层引用传递。

推演与反例

回调返回后为何容易悬空

函数中创建局部配置，用 [&] 把它交给后台线程，函数返回后局部配置销毁，回调再访问就是悬空。改成值捕获只复制被捕获的对象；若复制的是裸指针，底层对象仍没有被保活。捕获 this 通常也是保存指针，不会复制整个对象。可让回调持有必要数据副本，或捕获 weak_ptr，运行时 lock 取得访问期间的所有权。

const 的三种常见误读

const T* 限制通过该指针修改 T，T* const 限制指针本身改指向，两者可以同时存在。const 成员函数限制通过 this 修改普通成员，但 mutable 成员仍可变，也不意味着线程安全。对真正 const 对象强行去 const 后写入有未定义行为；不能把 const 当“优化器不会动它”的设备同步手段。

继续追问

回调按值捕获一个含指针的结构体安全吗？

结构体副本只复制成员值，不自动深拷贝指针目标。仍需看目标由谁拥有，以及回调何时结束。

引用一定不为空，因此就一定安全吗？

合法绑定时应引用有效对象，但对象之后仍可能销毁，引用同样会悬空。引用没有“自动检查仍然存活”的运行期能力。

T006 原理问答

结构体为什么不能直接当作串口协议发送？

结构体是编译器在内存中的对象布局，协议是双方约定的字节格式。二者不能混为一谈：协议必须明确字段宽度、符号、端序、单位、长度和校验范围，再逐字段编码解码。

原理与成立条件

显式编解码的顺序

先验证整帧最小长度和字段范围，再按字节构造数值。例如大端 32 位值逐字节先转为 uint32_t 再左移组合，避免 int 提升造成符号或移位问题。解析失败应返回明确错误且不读取后续越界区域；未知版本与未知类型要有清晰兼容策略。

协议必须约定的内容

除字段顺序，还需明确长度是否含头尾、校验覆盖范围、单位和比例、有符号性、保留字段以及合法值。CRC 自身字节序可以与业务字段不同，只要两端一致。跨平台测试应比较固定字节向量，而非仅用同一份错误编码再喂给同一份解码获得“互通”。

推演与反例

对齐怎样改变 sizeof

在一种常见 ABI 中，含 uint8_t、uint32_t、uint16_t 的结构体可能在第一字段后补 3 字节、尾部再补 2 字节，sizeof 为 12 而有效字段仅 7 字节；这是示例布局，不能作为所有平台的固定保证。直接发送整块对象会把填充字节也带出去，还可能泄露未初始化内容。packed 可减少填充，但会引入未对齐访问，依然没有解决端序、版本和数值表示问题。

解码应当先检查再组合

读取一个大端 u16 时，先证明至少还剩两个字节，再用无符号类型执行 (uint16_t(p[0]) << 8) | p[1]。不要把任意 uint8_t* 强转成 uint16_t* 解引用：地址可能未对齐，访问还可能不满足语言对象/别名规则，且仍依赖主机字节序。编码过程应与解码互逆，并用固定向量跨平台核对。

继续追问

memcpy 到本地整数就能解决端序吗？

memcpy 可避免部分对齐和别名问题，但取得的是本机表示，仍需按协议端序转换，也仍要先保证源长度足够。

memcpy 到结构体能解决所有问题吗？

它可避免某些未对齐解引用问题，但只有布局、字节序、对象表示等契约都匹配时才可能正确。外部格式仍应显式解析。

T007 原理问答

整数溢出、符号转换和时间回绕有哪些隐蔽问题？

整数问题常发生在表达式计算时，而不是赋值时。先确定每个操作数经过整数提升后的类型，再判断溢出、移位和符号转换；最后才看目标变量是否放得下结果。

原理与成立条件

长度计算如何防溢出

判断 offset+len<=capacity 前，加法可能已回绕；更稳妥是先保证 offset<=capacity，再判断 len<=capacity-offset。分配 n 个元素前检查 n<=SIZE_MAX/sizeof(T)。网络字段即使范围很小，也应在转换为本机大小类型前验证，不能把强制转换当作输入校验。

经过时间与先后顺序不同

同宽无符号 now-start 可以处理计数回绕，但要求真实经过时间未达到一个完整计数周期，否则无法知道绕了几圈。比较两个环形时间戳的先后，通常还需半周期以内的距离约束或明确代数；直接转有符号的实现习惯也要考虑语言和平台契约。

数值例子帮助建立边界

32 位毫秒计数约 49.7 天一圈；72 MHz 的 32 位周期计数约 59.65 秒一圈。要延时几十微秒可以用差值，但不能拿后者无扩展地计一天。秒乘 1000、微秒乘时钟频率还可能在乘法阶段溢出，因此应先选择足够宽类型，再校验最大允许输入。

推演与反例

为什么扩大目标类型仍会溢出

两个 32 位有符号数先相乘，再赋给 int64_t，乘法可能早已在 32 位中产生未定义溢出。应在运算前扩大一个操作数。无符号减法按 2^N 取模，可用 elapsed = now - start 处理计数器的一次回绕，但必须保证实际经过时间没有超过能唯一解释的范围；超过一整圈后，仅凭两个端点无法知道经过了几圈。

时间先后与经过时间不是同一问题

若采用 N 位序号的半空间比较，只能在差值严格小于 2^(N-1) 的约束下区分新旧；正好半圈存在歧义。elapsed 是否达到一个有限 duration，与任意比较两个远距离绝对时间点，是不同算法。毫秒转 Tick 还要检查乘法宽度和向零截断，短延时可能被换算为 0。

继续追问

序号 255 后变 0，为什么不能只判断 new>old？

普通数值顺序不表达环形序号顺序；必须限制可比较距离，或增加会话/代数明确区分新旧。半空间规则及寿命约束见 T038、T040。

有符号整数溢出会像硬件一样自然回绕吗？

标准 C/C++ 不能这样假设。无符号运算有明确模规则；需要饱和、范围拒绝或宽位计算时应明确实现，不能依赖优化前看到的现象。

T008 原理问答

malloc/free、new/delete、堆栈与碎片有什么区别？

存储取得、对象构造和对象销毁是三件事。malloc/free 管理原始存储；new 通常取得存储后构造对象，delete 先析构再释放。栈是自动生命周期的一种典型实现，堆适合运行期变化的生命周期，但需管理容量和碎片。

原理与成立条件

存储期与对象生命周期

栈常承载自动对象，函数返回时局部对象结束；堆允许存储跨作用域存在，但必须明确拥有者。malloc/free 管原始存储，new/delete 还执行构造与析构；placement new 可以在已有存储中构造，不再次分配。new[]/delete[] 与单对象形式也需配对，不能混用释放接口。

内存池如何改变问题

固定大小块池通过空闲链表等结构提供有界分配和回收，代价是最大并发数需要预估，块大小不匹配会浪费。不同大小对象可分池；池耗尽必须明确拒绝、等待或降级。静态分配消除一部分运行期失败，但不会阻止数组越界、栈溢出或错误地提前复用块。

嵌入式预算为何不能只看链接表

静态段占用只是部分 RAM；动态任务栈、内核对象、C 库堆、ISR 主栈和 DMA 缓冲都可能来自不同区域。递归、printf、大局部数组和最坏中断嵌套会放大栈需求。需要静态调用分析、运行水位与异常路径覆盖，不能以正常运行一次没有复位作为容量证明。

推演与反例

内部碎片与外部碎片怎么区分

分配器按对齐或大小类别给出比请求更大的块，未使用部分属于内部碎片；空闲空间被已分配块隔开，总量足够却没有足够大的连续块，是外部碎片。例如空闲 100、占用 100、空闲 100，总空闲 200 仍不能直接满足连续 150 的请求。合并相邻空闲块只消除相邻边界，不能跨过仍在使用的块。

实时系统关注最坏路径

一次分配可能包含链表遍历、锁竞争、页分配甚至缺页，因此平均很快不能保证截止时间。启动时预分配、固定大小块池和静态对象可以缩小运行期不确定性，但会固定容量。栈上大数组虽然不需要堆锁，却可能造成任务栈溢出；优化应同时算静态区、堆、每个任务栈和中断栈。

继续追问

还有 2 KiB 空闲堆，申请 1 KiB 为什么失败？

可能最大连续空闲块不足，或还需要块头、对齐开销；也可能查询的是另一分配器的堆。先确认分配器与最大块统计口径。

new[] 的结果为什么必须 delete[]？

数组释放需要按匹配的数组分配协议销毁元素并释放存储，混用 delete、free 等不匹配接口会产生未定义行为。

T009 原理问答

编译、链接、静态库、extern C 和交叉编译分别做什么？

编译把每个翻译单元变成目标文件，链接把符号引用和段布局组合成最终映像；交叉编译还要保证指令集、ABI、库和链接脚本都与目标一致。能在 PC 上通过编译，不代表固件能在 MCU 正确启动。

原理与成立条件

四个阶段各处理什么

预处理展开包含、宏和条件编译；编译进行语义检查并生成目标架构代码表示；汇编形成带符号和重定位信息的目标文件；链接解析跨目标文件符号并确定最终地址。找不到头文件通常属于前期，undefined reference 多发生在链接阶段，运行时找不到共享库则又是装载问题。

静态库与动态库

静态库是目标文件归档，链接器通常按未解析符号需求抽取成员，因此库顺序和循环依赖可能影响结果；共享库一般由装载器映射，并按平台机制解析符号。静态链接方便分发却可能增加镜像体积，动态链接方便共享与独立更新却引入版本和部署依赖。

extern C 与交叉编译

extern "C" 指定语言链接，解决 C++ 名称修饰等与 C 接口的匹配；不会把实现自动限制为 C，也不保证结构体 ABI 在任意平台一致。交叉编译必须匹配指令集、字节序、浮点调用约定、运行库及 sysroot，不能只换一个编译器可执行文件名。

链接脚本和启动代码如何配合

链接脚本给 .text、.data、.bss 等安排运行地址与装载地址。初始化数据常在 Flash 保存初值、在 RAM 运行；启动代码按符号复制 .data 并清零 .bss，再调用运行库初始化及 main。若脚本和启动符号不一致，可能构建成功却在首次使用全局变量时出错。

推演与反例

undefined reference 与重复定义的根因

头文件只声明外部函数而没有把实现目标文件加入链接，会出现未定义引用；把非 inline 外部变量的定义放在被多个源文件包含的头文件中，可能出现多重定义。静态库按需要抽取目标文件，传统链接器的库顺序还会影响是否找到依赖。先检查最终链接命令、符号表和 map，比盲目添加 include 更有效。

extern C 到底改变什么

它让 C++ 声明采用 C 语言链接规则，便于与 C 目标文件中的符号匹配；不会让 C++ 类、异常或 STL 容器变成 C ABI。跨边界更适合固定宽度数据、显式长度、错误码和不透明句柄。ARM 固件还要核对 Thumb、CPU 类型和浮点 ABI，目标相同名称不代表二进制调用约定相同。

继续追问

声明已经写进头文件，为什么仍 undefined reference？

声明只承诺存在定义；还要把包含定义的目标文件链接进来，并确认签名、命名空间、语言链接及条件编译一致。

静态库与动态库主要差在哪里？

静态库中的被选对象通常并入最终映像；动态库在装载/运行阶段建立共享对象依赖。动态库可独立更新，但增加部署和 ABI 兼容要求，不能只比较文件大小。

T010 原理问答

如何回答未定义行为、越界与优化后才出现的 bug？

未定义行为表示语言标准不再约束程序结果，编译器可据此前提优化。越界、悬空访问、数据竞争和某些整数运算错误都可能在低优化时偶尔正常，在高优化或不同布局下暴露。

原理与成立条件

UB 与其他不确定行为

未定义行为意味着标准不再约束程序结果；实现定义行为要求实现说明其选择，未指定行为则允许若干结果而不要求固定选择。三者不能混为“随机”。越界、悬空访问、部分非法移位、有符号溢出和 C++ 数据竞争都是需要优先排查的来源。

典型内存错误怎样识别

数组形参会调整为指针，函数内部 sizeof(param) 通常不是原数组长度；memcpy 的源和目的区间不能重叠，重叠搬移使用 memmove；二进制数据不保证以零终止，strlen 可能越界。先验证长度再读字段，并同时证明源可读范围、目的可写范围和对象寿命。

推演与反例

优化为什么会放大已有错误

如果程序用有符号溢出是否变小来判断溢出，编译器可基于“合法执行不会发生有符号溢出”删去该判断。越界写也可能原先碰巧落在未用空间，换一版编译器后就覆盖对象的长度或返回地址。应修复语言规则和边界证明，而不是把关闭优化当作最终方案。

检测工具覆盖不同错误

ASan 更适合越界和释放后使用，UBSan 检测一部分未定义运算，TSan 发现被执行路径上的数据竞争；它们改变时序且不覆盖所有问题。MCU 上可结合 MPU、栈检查、填充哨兵、硬件观察点和错误现场。一次工具无报错只说明此次执行没有命中其可检测条件。

继续追问

Sanitizer 都过了，能断言没有 UB 吗？

不能，只能说明已执行路径上未发现所启用检测能识别的错误；未覆盖路径、外设语义和工具盲区仍需分析。

memcpy 与 memmove 什么时候不能互换？

memcpy 的源与目的区域不得重叠；存在重叠时应使用 memmove 或证明安全的专用算法。不能依据某个 libc 版本恰好复制成功推导通用合法性。

T011 原理问答

static、extern、const、inline 和宏最容易错在哪里？

这些关键字分别控制链接、存储期、访问限制或多重定义规则，不能混成“性能优化关键字”。先区分作用域、链接性和存储期，再讨论编译器会不会内联或常量折叠。

原理与成立条件

static 的含义取决于位置

C 文件作用域 static 通常提供内部链接，让名字仅在该翻译单元可见；函数内 static 则让对象跨调用保持存储期，而作用域仍局限函数。C++ 类 static 成员属于类层面，不是每个实例各一份。存储期、作用域和链接性是三个不同问题。

局部静态初始化与线程安全

C++11 起局部 static 的初始化具有并发保护，但初始化之后对象的普通修改并不自动同步。嵌入式 C 的同名 static 不提供相同的 C++ 运行库初始化承诺。工具链关闭相关运行库能力或使用特别编译选项时，还需核实目标构建契约。

推演与反例

头文件中的定义为什么危险

文件作用域 static 通常给予内部链接，每个包含它的翻译单元可能有自己的对象；extern 声明通常指向别处定义。C 与 C++ 对文件作用域 const 的默认链接规则不同，应按语言判断。C++ inline 函数允许满足规则的同一定义出现在多个翻译单元中，不要求机器码一定展开；C++17 inline 变量也有明确的 ODR 用途。

宏展开与函数调用的本质差异

宏是预处理文本替换，例如 MIN(i++, j++) 可能重复求值，运算符优先级和语句上下文也可能改变含义。内联函数或模板有类型检查、作用域和一次求值语义，通常更适合普通运算。宏仍用于条件编译、字符串化等预处理任务，不能简单宣称应全部消灭。

继续追问

const 指针变量所在内存能否被别名改写？

要区分指针自身 const、指向对象 const，以及对象真实是否为 const；通过强转修改真实 const 对象可能 UB，不能把 const_cast 当成通用取消保护。

函数内 static 初始化线程安全吗？

C++11 起局部静态对象的初始化具有线程安全保证，但对象初始化后的所有业务访问不会自动加锁；C 语言和禁用相应实现机制的环境也不能直接套用这一结论。

T012 原理问答

虚函数、多态、函数指针和模板如何取舍？

虚函数把实现选择放到运行期，模板通常在编译期确定类型与实现，函数指针提供显式运行期回调。选择取决于变化发生在哪一层，以及是否需要跨语言、二进制接口和运行期替换。

原理与成立条件

虚函数提供运行期分派

通过基类指针/引用调用虚函数，根据对象动态类型选择最终覆盖函数。常见实现使用虚表与隐藏指针，但精确布局属于 ABI，不是语言强制每个对象固定增加某个字节数。构造/析构期间的动态分派受当前构造阶段限制，不能期待调用尚未构造完成的派生行为。

析构与对象切片

经普通基类指针 delete 派生对象时，基类通常需要虚析构以正确销毁完整对象；若禁止经基类删除，可采用受保护非虚析构等明确契约。把派生对象按值复制到基类会发生切片，只保留基类部分，不能再期待原来的多态效果。

函数指针与上下文参数

C 常用函数指针加 void* context 实现回调；函数指针负责行为，上下文指向状态。生命周期、类型匹配和重入安全由接口设计保证。C++ std::function 可包装多种可调用对象，方便但可能涉及类型擦除和分配；不能在有严格实时预算时未经测量就忽略开销。

模板的静态多态

模板让编译时根据类型生成和选择实现，有利于内联及消除分派，但可能增加实例化代码体积与构建复杂度。运行期插件类型未知时虚函数或回调更自然；类型已知且资源紧时模板可能合适。选择要看扩展边界、代码尺寸、测试与 ABI，不是单纯“虚函数慢，模板快”。

推演与反例

动态分派会增加哪些约束

通过多态基类接口调用覆盖函数，常见 ABI 使用虚表等机制，但标准不规定必须怎样布局。若通过基类指针 delete 派生对象，基类一般需要虚析构；构造和析构期间的虚调用还有当前构造层次的限制。不能把“有虚表指针”当成所有 C++ 对象的共同结构，也不能直接序列化多态对象。

模板与回调的代价不同

模板可暴露实现给优化器、避免某些间接调用，但每组实例可能增加代码体积并扩大编译依赖。函数指针通常需要额外 context 指针表达状态，调用者必须保证 context 活到回调结束。嵌入式选择要同时衡量 Flash、执行时间、测试替换与接口稳定性，而不是只比较一条调用指令。

继续追问

有虚函数就一定无法内联吗？

编译器若能证明动态类型，可能去虚化并内联；反之模板中的大函数也不一定展开。标准语义与优化结果应分别说明。

用函数指针替换虚函数一定更快吗？

不一定，两者都可能是间接调用，优化器也可能去虚化。应结合生成代码和实际调用频率分析；布局、所有权与可维护性往往更重要。
