## 29
A: RAII 把资源的释放时机绑定到对象生命周期。关键不是“用了析构函数”，而是任何时刻都有明确所有者，取得资源后立即交给它；这样正常返回、提前返回和异常展开都走同一套释放规则。
E: 为什么只靠成对调用仍会泄漏|假设函数先 open 文件，再分配缓冲，最后启动线程。第二步失败时，第三步从未发生，但第一步已经需要清理。逐条 goto 或 catch 可以做对，却会随路径增加而变复杂。用 fd 包装器、vector 和线程管理对象分别接管资源，已构造完成的成员在失败时逆序析构；尚未构造完成的对象自身不会调用析构，因此构造中的裸资源尤其应先交给已完整构造的子对象。
E: 独占所有权怎样影响接口|资源包装器通常禁用复制，允许移动：移动后原对象进入“不持有资源”的状态，最终只关闭一次。借用者可使用 fd 或指针，但不能擅自释放，也不能活得比所有者长。线程资源还多一步：析构前先提出停止、唤醒阻塞点并 join，只有释放句柄不足以保证后台代码已经停止访问成员。
F: RAII 能保证断电时也执行清理吗？|不能。进程被强制终止、断电或异常终止路径不保证正常栈展开。RAII 解决进程内资源生命周期；持久状态仍靠事务、日志及恢复协议。
## 30
A: 先决定谁拥有对象，再选智能指针。唯一拥有者用 unique_ptr；确实有多个独立生命周期共同拥有时用 shared_ptr；只想观察共享对象而不延长寿命，用 weak_ptr。裸指针也可表达借用，重点是接口是否说清释放责任。
E: 控制块和对象是两个层次|shared_ptr 通过控制块管理强弱引用计数、删除器等。强引用归零时销毁对象；控制块还要供 weak_ptr 判断失效，通常到相关弱引用也释放后才能回收。weak_ptr::lock 把“是否还活着”和“取得一份强引用”组合为安全操作，不能先 expired 再使用一个原始指针，因为两步之间对象可能被销毁。
E: 原子引用计数没有保护哪些东西|两个不同 shared_ptr 实例可共同管理一个对象并分别调整引用；但一个 shared_ptr 变量被一个线程赋值、另一个线程普通读取，仍涉及该变量自身的竞争。C++17 可以使用针对 shared_ptr 的原子自由函数或锁；atomic<shared_ptr<T>> 是 C++20 的接口。无论哪种方式，被指对象的业务字段仍需单独同步。
F: make_shared 总比分别 new 更好吗？|通常减少分配次数并简化异常安全；但大对象与控制块合并分配时，残留 weak_ptr 可能使整块分配迟迟不能归还。自定义删除器、外部资源或特殊分配要求也会影响选择。
## 31
A: std::move 只是把表达式转换成可被移动重载接受的值类别，真正转移资源的是被选中的移动构造或移动赋值。它本身既不搬运字节，也不清空原对象。
E: 一次容器插入究竟发生什么|把一个 vector 移进另一个对象，在通常的分配器条件下可以转交数据区指针、大小和容量，避免逐个复制元素；但小对象、内嵌存储或不兼容分配器可能仍需逐项操作。对 const 对象 std::move 得到的仍带 const，常规 T&& 移动构造不能接收它，因此最终可能调用复制构造。判断是否发生移动必须看类型及重载，而不是看到 move 字样就下结论。
E: 移动后如何写正确代码|标准库对象通常保证有效但未指定状态：可析构、赋新值，也能调用满足前置条件的成员；不能普遍假设字符串一定为空或容器一定保留旧内容。自定义类型应明确移动后的不变量。容器扩容还会考虑移动是否 noexcept；当移动可能抛异常且可复制时，vector 可能用复制维持异常保证。
F: 返回局部变量时都写 return std::move(x) 吗？|通常不需要，它可能阻碍命名返回值优化。应优先让返回值优化和隐式移动发挥作用，再在确需转移已有对象时显式 move。
## 32
A: 容器操作首先要问“对象有没有搬家”和“元素位置有没有变化”。vector 连续存储，扩容会搬迁元素；即使没有扩容，中间插入或删除也可能使后面的元素移动，因此不同操作的引用失效范围不同。
E: 用三个元素说明失效|vector 有 A、B、C，保存了指向 B 的指针。若 push_back 导致重新分配，旧数据区释放，所有元素指针都失效；若容量足够，既有元素指针仍有效，但旧 end 已改变。若 erase(A)，B、C 被前移，即使底层地址没换，原 B 位置也不能继续当作原来的 B。reserve 只减少扩容，不能解决擦除引起的身份变化。
E: 字符串缓冲与异步发送|data 或 c_str 返回的是对象内部存储的借用地址，后续修改、扩容、移动和析构可能使地址或内容不再满足要求。把这个地址交给异步接口后马上复用字符串，错误可能在很久后才出现。应让发送任务持有整个字符串/独占缓冲，或在提交时复制，而不是仅延长一个裸指针变量的寿命。
F: 把 vector 改成 list 就没有生命周期问题了吗？|list 的节点地址通常更稳定，但擦除对应节点后仍失效，遍历缓存局部性和分配成本也不同。稳定地址不能代替所有权与删除时机设计。
## 33
A: 指针和引用描述访问关系，const 描述通过某个表达式允许做什么，它们都不自动延长普通被引用对象的生命周期。回调捕获尤其要区分“保存值”和“保存对原对象的借用”。
E: 回调返回后为何容易悬空|函数中创建局部配置，用 [&] 把它交给后台线程，函数返回后局部配置销毁，回调再访问就是悬空。改成值捕获只复制被捕获的对象；若复制的是裸指针，底层对象仍没有被保活。捕获 this 通常也是保存指针，不会复制整个对象。可让回调持有必要数据副本，或捕获 weak_ptr，运行时 lock 取得访问期间的所有权。
E: const 的三种常见误读|const T* 限制通过该指针修改 T，T* const 限制指针本身改指向，两者可以同时存在。const 成员函数限制通过 this 修改普通成员，但 mutable 成员仍可变，也不意味着线程安全。对真正 const 对象强行去 const 后写入有未定义行为；不能把 const 当“优化器不会动它”的设备同步手段。
F: 引用一定不为空，因此就一定安全吗？|合法绑定时应引用有效对象，但对象之后仍可能销毁，引用同样会悬空。引用没有“自动检查仍然存活”的运行期能力。
## 34
A: 结构体是编译器在内存中的对象布局，协议是双方约定的字节格式。二者不能混为一谈：协议必须明确字段宽度、符号、端序、单位、长度和校验范围，再逐字段编码解码。
E: 对齐怎样改变 sizeof|在一种常见 ABI 中，含 uint8_t、uint32_t、uint16_t 的结构体可能在第一字段后补 3 字节、尾部再补 2 字节，sizeof 为 12 而有效字段仅 7 字节；这是示例布局，不能作为所有平台的固定保证。直接发送整块对象会把填充字节也带出去，还可能泄露未初始化内容。packed 可减少填充，但会引入未对齐访问，依然没有解决端序、版本和数值表示问题。
E: 解码应当先检查再组合|读取一个大端 u16 时，先证明至少还剩两个字节，再用无符号类型执行 (uint16_t(p[0]) << 8) | p[1]。不要把任意 uint8_t* 强转成 uint16_t* 解引用：地址可能未对齐，访问还可能不满足语言对象/别名规则，且仍依赖主机字节序。编码过程应与解码互逆，并用固定向量跨平台核对。
F: memcpy 到结构体能解决所有问题吗？|它可避免某些未对齐解引用问题，但只有布局、字节序、对象表示等契约都匹配时才可能正确。外部格式仍应显式解析。
## 35
A: 整数问题常发生在表达式计算时，而不是赋值时。先确定每个操作数经过整数提升后的类型，再判断溢出、移位和符号转换；最后才看目标变量是否放得下结果。
E: 为什么扩大目标类型仍会溢出|两个 32 位有符号数先相乘，再赋给 int64_t，乘法可能早已在 32 位中产生未定义溢出。应在运算前扩大一个操作数。无符号减法按 2^N 取模，可用 elapsed = now - start 处理计数器的一次回绕，但必须保证实际经过时间没有超过能唯一解释的范围；超过一整圈后，仅凭两个端点无法知道经过了几圈。
E: 时间先后与经过时间不是同一问题|若采用 N 位序号的半空间比较，只能在差值严格小于 2^(N-1) 的约束下区分新旧；正好半圈存在歧义。elapsed 是否达到一个有限 duration，与任意比较两个远距离绝对时间点，是不同算法。毫秒转 Tick 还要检查乘法宽度和向零截断，短延时可能被换算为 0。
F: 有符号整数溢出会像硬件一样自然回绕吗？|标准 C/C++ 不能这样假设。无符号运算有明确模规则；需要饱和、范围拒绝或宽位计算时应明确实现，不能依赖优化前看到的现象。
## 36
A: 存储取得、对象构造和对象销毁是三件事。malloc/free 管理原始存储；new 通常取得存储后构造对象，delete 先析构再释放。栈是自动生命周期的一种典型实现，堆适合运行期变化的生命周期，但需管理容量和碎片。
E: 内部碎片与外部碎片怎么区分|分配器按对齐或大小类别给出比请求更大的块，未使用部分属于内部碎片；空闲空间被已分配块隔开，总量足够却没有足够大的连续块，是外部碎片。例如空闲 100、占用 100、空闲 100，总空闲 200 仍不能直接满足连续 150 的请求。合并相邻空闲块只消除相邻边界，不能跨过仍在使用的块。
E: 实时系统关注最坏路径|一次分配可能包含链表遍历、锁竞争、页分配甚至缺页，因此平均很快不能保证截止时间。启动时预分配、固定大小块池和静态对象可以缩小运行期不确定性，但会固定容量。栈上大数组虽然不需要堆锁，却可能造成任务栈溢出；优化应同时算静态区、堆、每个任务栈和中断栈。
F: new[] 的结果为什么必须 delete[]？|数组释放需要按匹配的数组分配协议销毁元素并释放存储，混用 delete、free 等不匹配接口会产生未定义行为。
## 37
A: 编译把每个翻译单元变成目标文件，链接把符号引用和段布局组合成最终映像；交叉编译还要保证指令集、ABI、库和链接脚本都与目标一致。能在 PC 上通过编译，不代表固件能在 MCU 正确启动。
E: undefined reference 与重复定义的根因|头文件只声明外部函数而没有把实现目标文件加入链接，会出现未定义引用；把非 inline 外部变量的定义放在被多个源文件包含的头文件中，可能出现多重定义。静态库按需要抽取目标文件，传统链接器的库顺序还会影响是否找到依赖。先检查最终链接命令、符号表和 map，比盲目添加 include 更有效。
E: extern C 到底改变什么|它让 C++ 声明采用 C 语言链接规则，便于与 C 目标文件中的符号匹配；不会让 C++ 类、异常或 STL 容器变成 C ABI。跨边界更适合固定宽度数据、显式长度、错误码和不透明句柄。ARM 固件还要核对 Thumb、CPU 类型和浮点 ABI，目标相同名称不代表二进制调用约定相同。
F: 静态库与动态库主要差在哪里？|静态库中的被选对象通常并入最终映像；动态库在装载/运行阶段建立共享对象依赖。动态库可独立更新，但增加部署和 ABI 兼容要求，不能只比较文件大小。
## 38
A: 未定义行为表示语言标准不再约束程序结果，编译器可据此前提优化。越界、悬空访问、数据竞争和某些整数运算错误都可能在低优化时偶尔正常，在高优化或不同布局下暴露。
E: 优化为什么会放大已有错误|如果程序用有符号溢出是否变小来判断溢出，编译器可基于“合法执行不会发生有符号溢出”删去该判断。越界写也可能原先碰巧落在未用空间，换一版编译器后就覆盖对象的长度或返回地址。应修复语言规则和边界证明，而不是把关闭优化当作最终方案。
E: 检测工具覆盖不同错误|ASan 更适合越界和释放后使用，UBSan 检测一部分未定义运算，TSan 发现被执行路径上的数据竞争；它们改变时序且不覆盖所有问题。MCU 上可结合 MPU、栈检查、填充哨兵、硬件观察点和错误现场。一次工具无报错只说明此次执行没有命中其可检测条件。
F: memcpy 与 memmove 什么时候不能互换？|memcpy 的源与目的区域不得重叠；存在重叠时应使用 memmove 或证明安全的专用算法。不能依据某个 libc 版本恰好复制成功推导通用合法性。
## 116
A: 这些关键字分别控制链接、存储期、访问限制或多重定义规则，不能混成“性能优化关键字”。先区分作用域、链接性和存储期，再讨论编译器会不会内联或常量折叠。
E: 头文件中的定义为什么危险|文件作用域 static 通常给予内部链接，每个包含它的翻译单元可能有自己的对象；extern 声明通常指向别处定义。C 与 C++ 对文件作用域 const 的默认链接规则不同，应按语言判断。C++ inline 函数允许满足规则的同一定义出现在多个翻译单元中，不要求机器码一定展开；C++17 inline 变量也有明确的 ODR 用途。
E: 宏展开与函数调用的本质差异|宏是预处理文本替换，例如 MIN(i++, j++) 可能重复求值，运算符优先级和语句上下文也可能改变含义。内联函数或模板有类型检查、作用域和一次求值语义，通常更适合普通运算。宏仍用于条件编译、字符串化等预处理任务，不能简单宣称应全部消灭。
F: 函数内 static 初始化线程安全吗？|C++11 起局部静态对象的初始化具有线程安全保证，但对象初始化后的所有业务访问不会自动加锁；C 语言和禁用相应实现机制的环境也不能直接套用这一结论。
## 117
A: 虚函数把实现选择放到运行期，模板通常在编译期确定类型与实现，函数指针提供显式运行期回调。选择取决于变化发生在哪一层，以及是否需要跨语言、二进制接口和运行期替换。
E: 动态分派会增加哪些约束|通过多态基类接口调用覆盖函数，常见 ABI 使用虚表等机制，但标准不规定必须怎样布局。若通过基类指针 delete 派生对象，基类一般需要虚析构；构造和析构期间的虚调用还有当前构造层次的限制。不能把“有虚表指针”当成所有 C++ 对象的共同结构，也不能直接序列化多态对象。
E: 模板与回调的代价不同|模板可暴露实现给优化器、避免某些间接调用，但每组实例可能增加代码体积并扩大编译依赖。函数指针通常需要额外 context 指针表达状态，调用者必须保证 context 活到回调结束。嵌入式选择要同时衡量 Flash、执行时间、测试替换与接口稳定性，而不是只比较一条调用指令。
F: 用函数指针替换虚函数一定更快吗？|不一定，两者都可能是间接调用，优化器也可能去虚化。应结合生成代码和实际调用频率分析；布局、所有权与可维护性往往更重要。
## 9
A: 进程主要提供资源与地址空间的隔离，线程和 RTOS 任务主要描述可调度的执行流。判断差别要看共享哪些资源、切换保存哪些状态以及故障能否被隔离，不能只记“进程重、线程轻”。
E: 从一次切换看到真实成本|同一进程的两个线程切换时，需要换寄存器、栈指针和调度状态，但通常不用换地址空间；跨进程还要改变地址翻译上下文。缓存和 TLB 是否保留取决于架构与标识机制，工作集改变仍可能导致大量未命中。因此大量细碎任务即使各只计算几微秒，也可能把时间花在调度与缓存重新变热上；成本必须结合平台和负载测量。
E: 隔离为什么不是线程库能补出来的|同进程线程可访问彼此堆和栈地址，一个越界写可能破坏任意共享对象；互斥量只协调合法访问，无法拦住非法地址。常见无 MPU 隔离的 MCU 任务也如此。需要容错边界时，可考虑独立进程或 MPU 区域，代价是通信、资源复制和权限管理；把任务拆得更多并不会自动增加可靠性。
F: 一个任务阻塞会不会让整个单核停住？|若由调度器把它置为 Blocked，其他 Ready 任务可运行；若它关中断忙等、持有全局关键锁或阻塞的是唯一事件循环，则可能拖住更多工作。关键是阻塞发生在哪个调度层。
## 10
A: 用户态与内核态是权限边界，上下文切换是执行流切换。系统调用、异常和中断提供进入处理代码的路径，但每次进入内核并不一定更换线程。
E: 对比三条 read 路径|数据已经在内核缓冲时，read 检查参数、复制并返回原线程；阻塞 fd 暂时无数据时，线程进入等待，调度器运行其他线程；非阻塞 fd 无数据时，返回 EAGAIN，让用户决定何时重试。三者都可能进入内核，只有需要等待且另选执行流的路径必然涉及调度。一次系统调用耗时包含等待和抢占，不能全部归因于复制。
E: 用户指针为何不能直接相信|系统调用收到的是用户提供的地址和长度，内核要处理地址是否可访问、范围是否越界以及访问过程中可能发生的缺页。权限切换并不使用户指针天然可信。类似地，设备协议的外部长度也必须先验证，再访问数组；底层代码和上层协议都需要在信任边界检查输入。
F: 中断时保存了寄存器，是否就叫一次线程切换？|可以称为异常上下文保存，但不等同调度到另一个线程。面试中应把异常进入/退出与调度切换分开描述，避免把中断数直接当任务切换数。
## 11
A: 虚拟内存让程序使用独立、受保护的地址空间；页表给出映射，TLB 缓存翻译结果，缺页异常处理当前映射无法直接完成的访问。TLB 未命中不等于缺页，缺页也不一定读磁盘。
E: 一次写入匿名页可能经过什么|程序先申请一段虚拟地址，第一次写某页时发现尚无可写物理映射，触发异常；内核检查该地址属于合法区域，分配或准备物理页、清零并更新页表，随后重新执行该条指令。若地址不合法或权限不允许，则走错误路径。页表已有有效映射而 TLB 没记录时，只需重新建立翻译缓存，这一过程通常不涉及存储 I/O。
E: 写时复制与实际内存占用|fork 后父子进程最初可以共享物理页并把相关映射设为只读；一方首次写入触发写保护异常，内核为它复制该页，使两边后续修改独立。复制单位是页，不是被修改的一个字节。大量随机写会扩大驻留内存及缺页成本；RSS、虚拟地址空间大小和程序申请总量因此不能互相替代。
F: mlock 后是否就能保证访问延迟？|锁页可减少被换出导致的等待，但仍需预触页、控制工作集及权限资源；缓存未命中、调度、中断和锁竞争依然存在，它不是完整硬实时保证。
## 12
A: 阻塞描述调用是否等待，异步描述完成如何交付，两者不是同一坐标。非阻塞 I/O 通常仍由调用者在就绪后继续推进；异步接口则提交操作并在之后报告完成。
E: 读一个完整消息为什么需要状态|一次非阻塞 read 得到头部的前 3 字节，应用必须保留这 3 字节及解析位置，等待后续就绪。若把“返回了数据”当“消息已经完成”，协议会在合法分包时失败。完成式接口也未必替你完成业务消息定界，它可能只完成一次指定长度的底层读操作。接口完成单位与协议消息单位要分别确认。
E: 缓冲生命周期怎样变化|同步写接口若已把数据复制进内核，调用返回后通常可复用用户缓冲；DMA 或异步接口可能继续读取提交的内存，直到其明确完成。取消请求同样可能与完成竞态，不能一发出 cancel 就释放缓冲。使用异步接口时，所有权问题通常比函数返回快不快更关键。
F: Reactor 是同步还是异步？|通常采用非阻塞同步 I/O 加就绪通知，应用负责实际读写；从业务调用者看又可能提供异步服务。必须说明讨论接口层，不能单靠 Reactor 这个名字判断所有层的语义。
## 13
A: 互斥量保护共享状态，信号量记录可用数量，条件变量等待共享谓词变化，自旋锁用持续运行换取免睡眠的短等待。选型先看语义和上下文，再比较开销。
E: 用生产者消费者区分工具|队列内容和关闭标志是一组共享状态，用锁保证入队、出队及关闭之间的一致性；消费者等待“非空或关闭”，适合条件变量；若用计数信号量，计数必须与可消费项目严格对应，还要额外解决容器互斥与关闭唤醒。把二值通知当计数使用，会把两次到达合成一次；把计数工具当对象寿命保护，也解决不了释放后访问。
E: 自旋什么时候会把短等待变成死锁|在单核中，高优先级代码抢占持锁的低优先级任务后若持续自旋，持锁者得不到 CPU，锁便永远不会释放。中断若等待被自己打断的临界区，也存在类似问题。自旋适合明确不可睡眠、持锁极短且有正确抢占/中断约束的上下文；用户态长临界区通常应使用会睡眠的锁或改变所有权结构。
F: futex 为什么能避免每次加锁都系统调用？|无竞争时可在用户态以原子状态转换取得锁；发生竞争才通过内核等待。等待前比较期望状态与入队的原子衔接，可防止状态已变化却错误睡下；futex 本身仍需要用户态协议构成完整互斥量。
## 14
A: 条件变量等待的是“受锁保护的条件为真”，通知只提示重新检查。正确性来自检查谓词、原子解锁等待、重新加锁检查这一整套协议，while 循环和同一把锁缺一不可。
E: 把丢唤醒的竞态写成时间线|错误路径为 C 看见 empty→C 解锁→P 入队并 notify→C 开始睡眠，此后如果没有新通知，队列虽有数据 C 仍可一直睡。正确 wait 把解锁与注册等待连接起来：生产者一旦能拿到同一把锁并更新状态，它发出的通知就不能落在“已解锁但尚未成为等待者”的缝隙中。通知可在解锁后发，但谓词更新仍需遵守这个保护协议。
E: while 同时解决两个不同问题|虚假唤醒使线程在条件没变时返回；即使没有虚假唤醒，另一个消费者也可能先拿到锁并取走数据。两种情况下返回后谓词都可为假。退出还要使用 closed 这样的持久状态：消费者在 closed 且队列空时退出，在 closed 但仍有数据时继续排空。仅 notify_all 不修改谓词，不能让线程按预期停止。
F: 超时返回时能否断定队列仍然为空？|不能，超时与生产者入队可能竞争。重新取得锁后仍需检查谓词，并按接口明确截止时间与事件同时发生时的取舍；多轮等待应复用同一绝对截止时间。
## 15
A: volatile 保留实现规定的可观察访问，原子操作解决并发访问的不可分割与语言同步关系，内存屏障约束指定层次的排序。三者解决不同问题，不能把 volatile 当作多线程同步。
E: release/acquire 的证明链|生产者先写 payload=42，再 ready.store(true, release)；消费者的 acquire load 若读取了这次 release 发布的值，就有“payload 写入先于发布、发布与读取同步、读取先于使用”的 happens-before 链，随后读 payload 才安全。若消费者只用 relaxed，或根本没读到对应发布，链条不成立。这个例子还要求生产者不会在消费者读取期间再次无同步修改 payload；重复使用同一槽需要新的握手。
E: 为什么多核一致缓存仍然不够|缓存一致性主要约束同一位置副本之间的关系，不自动给多个普通对象建立 C++ 的线程同步。CPU 可能重排，编译器也可以在语言规则允许范围内重排；语言数据竞争还可能直接带来未定义行为。DMA 若不参与缓存一致性，另需 cache clean/invalidate 和所有权移交；单独执行 DMB 不是把脏缓存写回内存。
F: relaxed 什么时候足够？|只需要该原子变量自身的独立统计或标志值、且不依赖它发布其他普通数据时可能足够。必须先说明它保护的不变量，不能以“单核”或“测试没出错”替代证明。
## 16
A: 死锁是互相等待导致无法前进，活锁是一直动作但没有业务进展，饥饿是某个参与者长期得不到资源，优先级反转是高优先级被低优先级持有的资源拖住。四者的解决办法不同。
E: 死锁条件如何用于设计|互斥、持有并等待、不可抢占、循环等待同时成立时可能死锁。规定所有线程按同一顺序拿 A、B 两把锁，可以破坏循环等待；把慢 I/O 移到锁外、先取得所需资源再进入临界区，也可减少持有并等待。超时只能让一次等待退出，如果退出后没归还已持资源或继续无休止重试，仍可能形成泄漏、活锁或严重抖动。
E: 经典三任务优先级反转|低优先级 L 持锁，高优先级 H 等锁，中优先级 M 不断抢占 L，H 就间接被不相关的 M 延迟。优先级继承使 L 暂时获得 H 的优先级，以便尽快释放锁；它不能让设备转换立即完成，也不自动解决多锁死锁。要得到时限，仍要约束最长持锁时间和更高紧急度中断。
F: 不用锁是否就没有死锁？|没有。两个线程可能互相 join，两个有界队列可能互相等待对方消费，协议双方也可能都等一个永远不会到来的消息。需要分析的是等待依赖图。
## 17
A: 通用 Linux 调度追求多任务响应与公平，实时调度强调优先级或期限约束；常见单核抢占式 FreeRTOS 选择最高优先级就绪任务。无论哪种调度器，“高优先级”都不等于已经证明最坏响应时间。
E: 固定优先级的干扰怎样计算|高优先级任务即使只执行 1 ms，若每 2 ms 就释放一次，也会消耗约一半 CPU。低优先级任务除自身执行时间外，还要承受所有高优先级任务和中断的干扰，以及资源阻塞。一个任务 taskYIELD 后只要自己仍是最高优先级就绪任务，就不保证低优先级运行；等待实际事件而阻塞才会从就绪竞争中退出。
E: 调度策略与系统前提|Linux 的 SCHED_FIFO、SCHED_RR 与普通策略不同，但仍受权限、实时带宽限制、内核可抢占性和驱动长临界区影响；目标内核使用 CFS 还是 EEVDF 应按版本确认。FreeRTOS 也要核对抢占、时间片、Tick 频率与移植层配置。同名优先级在 NVIC 和任务调度中的数值方向甚至可能相反。
F: CPU 平均利用率低，能证明任务不超时吗？|不能。短时间内的突发、长临界区、优先级反转和 I/O 等待都可能错过期限。实时性应看最坏响应和到达模式，而不只看一分钟平均值。
## 18
A: 中断前段负责必须及时处理的硬件状态，后续任务负责可以调度的解析和慢工作。拆分的目的是限制不可调度时间，并明确数据怎样从硬件上下文安全交给任务。
E: 延后处理为什么仍需要容量证明|ISR 只把数据放入缓冲然后唤醒任务，看似很短，但如果任务长时间拿不到 CPU，缓冲仍会满。必须计算中断到达速率、最长屏蔽时间、任务最坏调度延迟和消费速率；复制或 DMA 都只是改变搬运方式。一次 ISR 放入数据后立即退出，是把后续工作转移出去，而不是把工作消灭。
E: 不同平台的“下半部”不能混用|Linux 的 softirq、tasklet、工作队列和线程化中断有不同上下文限制，尤其能否睡眠不能统一回答。MCU 上常用 ISR 加任务通知/队列形成类似分工，但不是运行 Linux 的 softirq。描述机制时应先说平台，再说谁运行、何时可抢占、共享数据如何同步以及满缓冲怎么办。
F: 把所有工作都放入最高优先级任务会怎样？|它可迅速接手中断，却可能长期饿死其他任务；若任务内仍做无界等待，响应链依旧无界。需要短工作段、适当优先级和可阻塞的等待点。
## 113
A: fork 创建一个新的进程执行流，exec 用新程序替换当前进程映像，两者不是同一个操作。父子可通过继承的文件描述符通信，而普通私有内存修改不会自动同步。
E: 从返回值理解两条执行流|fork 成功后，父进程得到子 PID，子进程得到 0，两边从调用之后分别继续；exec 成功时不返回原程序，而从新映像入口执行。现代 Linux 的写时复制减少了 fork 立即复制全部内存的成本，但页表、任务状态和后续首次写页仍有开销。把 fork 称为“复制一个线程”会漏掉地址空间和资源语义。
E: 多线程 fork 的锁为什么危险|子进程只保留调用 fork 的线程，但地址空间中可能留下另一个已不存在于子进程的线程所持有的锁。子进程再调用依赖该锁的库函数可能卡住。POSIX 对多线程 fork 后、exec 前可调用的函数有严格限制；优先使用合适的 spawn/exec 流程，不把普通线程库操作任意塞进子分支。
F: 共享内存是不是最快就一定最好？|它可减少数据复制，但必须自己解决通知、同步、数据布局和崩溃恢复；管道/socket 自带消息传递所需的一部分生命周期边界。选择应结合数据量与故障隔离要求。
## 114
A: fd 是进程中的整数索引，open file description 是内核维护的一次打开状态。dup 或 fork 继承的 fd 可以共享该状态，因此“两个 fd”不必然对应两份独立文件偏移或状态标志。
E: dup 后谁的偏移会变|fd1 与 dup 得到的 fd2 通常指向同一 open file description，一边 read 推进的偏移会影响另一边；另一次独立 open 则通常有自己的打开状态。O_NONBLOCK 属于文件状态标志，相关描述符可共享；FD_CLOEXEC 是描述符标志。区分两层，才能解释子进程继承、关闭和 epoll 注册的行为。
E: fd 重用怎样制造误操作|连接 A 的 fd=7 被关闭后，新连接 B 可能立即拿到 7。一个迟到任务若只记着整数 7，再调用 write 或 close，可能操作 B。因此异步身份应带连接对象/代数并校验寿命；关闭一次失败后盲目再 close 同一数字，在 Linux 的某些失败情形下可能关闭已复用描述符，应按具体接口语义处理。
F: RAII 已经保证 close，为什么还要取消回调？|RAII 解决资源最终释放，无法自动删除外部队列里尚未执行的借用操作。回调的有效期必须早于资源释放，或能检测对象已失效。
## 115
A: Cache 改变访问成本，缓存一致性协调同一地址的多份缓存，内存序约束并发访问的先后关系。三者相关但不等价；“硬件缓存一致”不能替代语言同步。
E: 伪共享为什么没有逻辑共享仍会变慢|两个线程分别修改不同计数器，数据没有竞争，却恰好位于同一缓存行。每次写可能使该行的所有权在核心间转移，产生额外一致性流量。把热点写字段分散到不同缓存行可改善，但具体行大小需按目标确认；盲目填充所有结构体会增加工作集和内存占用。
E: DMA 与缓存是另一种所有权问题|非一致性 DMA 从内存读，CPU 最新数据可能仍在脏缓存中；DMA 写完内存，CPU 又可能读到旧缓存。需要按方向在规定时机 clean 或 invalidate，并遵守缓存行对齐和共享行边界。Cortex-M3 的 STM32F103 不应直接套用带 D-cache 的 M7 操作，但移植到后者时必须重新审计这条链。
F: 加 memory fence 能修复伪共享吗？|不能。屏障可能增加开销，它不改变两个字段处于同一缓存行的事实。伪共享是布局与访问模式问题；缺少同步则是另一个正确性问题。
## 19
A: select、poll 每次提交要检查的描述符集合；epoll 把关注集合长期保存在内核中，由事件把相关描述符加入就绪集合。它主要减少大量空闲连接下反复传递和扫描集合的工作，不代表整个服务器所有操作都是 O(1)。
E: 用 N 个连接、K 个就绪连接看成本|select/poll 的一次等待通常需要处理规模为 N 的集合，返回后用户也要找到哪些项就绪；epoll_wait 主要交付就绪项，应用仍至少处理 K 个结果。注册变更、内核回调、锁、复制和业务处理都有成本。若 N 很小或几乎所有连接都持续就绪，epoll 的优势未必明显；“10 万连接”也不代表 10 万个连接都能同时执行复杂业务。
E: 描述符数量之外还有什么限制|select 的常见 fd_set 有固定表示上限；poll 没有同样的位图接口限制，但集合仍需传递和扫描。epoll 关注表同样占内核内存，并受到资源限制。连接规模还受 socket 缓冲、用户对象、HTTP 输入上限、fd 限额和每连接处理成本影响，不能只调高 ulimit 就认为系统具备相同容量。
F: epoll 是零拷贝接口吗？|不是。它改变就绪事件的管理方式，事件数组仍要交付用户态，实际 read/write 也可能复制数据。I/O 多路复用与数据零拷贝是不同问题。
## 20
A: LT 在就绪条件持续满足时仍可报告，ET 主要报告就绪状态的变化。ET 要求应用记住尚未处理完的工作，通常以非阻塞 I/O 读写到 EAGAIN 才重新等待，否则可能把已经存在的数据留在内核里。
E: 半读为何可能永久等不到下一次通知|管道已有 2 KB，收到一次可读事件后只读走 1 KB。剩余 1 KB 仍可立即读取，但状态没有经历新的“从不可读到可读”的转换；如果对端等你的应答而不再写，你再 epoll_wait 就可能卡住。读到 EAGAIN 表示这一轮可取得的进展已耗尽，再等待才有依据。就绪只是提示，最终仍要按 read 的返回值判断。
E: 读到 EAGAIN 与公平性怎样兼容|持续高流量可能让一个连接长时间都读不到 EAGAIN，饿死其他连接。可为每轮处理设置预算，同时把该连接保存在用户态待处理集合，轮转后继续读；只有真正耗尽时才移除。不能达到预算就丢掉待处理标记、直接等下一条 ET 通知，否则又回到漏处理问题。写方向也应只在有待发数据时关心 EPOLLOUT。
F: EPOLLONESHOT 能自动解决并发安全吗？|它能让一次事件交付后暂停该项通知，便于由一个工作者处理后重新激活，但对象寿命、缓冲同步和 rearm 时机仍由应用负责。
## 21
A: 短写表示这次调用只接受了前一部分数据，EAGAIN 表示目前无法继续，EINTR 表示被信号中断。正确发送器保存未发送后缀及偏移，只在能够继续时推进，不能把它们统一当作整帧失败后从头重发。
E: 用 100 字节演示状态推进|初始 offset=0，write 返回 40，就把 offset 改为 40；下一次从 data+40 发送剩余 60。返回 EAGAIN 时偏移不变，保留数据并等待可写；返回正数即消费那部分进展。若所有 100 字节都被内核接受，才完成本地提交。若此时业务期限到了，已写出的前 40 字节不能从线路撤回，随意丢掉后缀再写新帧可能破坏对端分帧。
E: 错误处理为什么必须保留错误类别|真正的设备断开、无进展返回 0、暂时不可写和 EINTR 需要不同策略。回调还可能修改发送队列，所以完成当前项时应先取得回调、移除当前项，再调用外部代码，避免回调使正在引用的队首失效。fd 的发送完成只代表该接口约定的完成层级，不代表对端已经收到或执行。
F: 一个 write 返回整帧长度，RTO 就能忽略本地发送时间了吗？|不能，驱动或 UART 仍可能排队。RTO 起点可以选择“内核接纳完成”，但预算必须包含此后的本地发送、对端处理和返回延迟。
## 22
A: eventfd 是可纳入 epoll 的计数型唤醒通道，队列才保存命令或任务内容。通知可以合并，消费者以队列为真实状态，不能把读出的计数机械当作必须处理的命令数。
E: 两个生产者如何安全唤醒一个消费者|生产者先在同步保护下入队，再写 eventfd。消费者读取计数以清除通知状态，然后检查并消费队列；即使多个写被合并，队列中任务仍在。若先通知后入队，消费者可能醒来发现空队列并再次睡眠，生产者随后入队却没有新通知。入队顺序与唤醒协议必须成套考虑，eventfd 不会自动使一个不安全的容器变安全。
E: 限额消费后还有数据怎么办|一次只消费 32 项可以降低对其他事件的干扰，但队列还没空时必须保留“还有工作”的事实，例如自行再通知或进入本地待运行列表。若只是把 eventfd 读到零然后提前返回，剩余数据可能要等下一位生产者碰巧唤醒。计数满时非阻塞写 EAGAIN 一般说明已有唤醒待消费，但其他写错误仍应处理。
F: EFD_SEMAPHORE 改变什么？|普通读通常取走累计值并清零；信号量模式每次读返回 1 并递减计数。两者都不保存业务载荷，也不替代任务队列的容量与退出设计。
## 23
A: timerfd 把定时到期变成可读事件，便于与其他 fd 在同一事件循环处理。定时器决定何时到期，线程何时获得 CPU、何时运行回调是另一件事，因此超时回调可能晚于配置期限。
E: 相对期限为什么用单调时钟|墙上时间可能被校时向前或向后调整，用它计算“等待 500 ms”会产生误判；CLOCK_MONOTONIC 避免这类跳变，但不包含系统挂起时间，若业务要求把 suspend 算入期限，需考虑 CLOCK_BOOTTIME。绝对业务时间戳和相对超时应分别选时钟，不能用一个毫秒值隐去时钟域。
E: 扫描周期怎样带来额外延迟|若每 200 ms 扫一次请求表，某请求在 t=501 ms 到期而上一轮在 500 ms 扫过，通常要到 700 ms 左右才被发现，再叠加回调排队和调度延迟。读取 timerfd 得到累计到期次数，可以知道错过了多个周期，但业务应按当前单调时间判断 deadline，不应简单把超时判定次数当真实经过时间。
F: 把扫描周期改小一定更好吗？|它减少离散扫描误差，却增加唤醒和遍历成本。请求多时可用按截止时间排序的结构、时间轮或重设最近到期的一次性定时器；选型要结合数量和允许误差。
## 24
A: signalfd 把选定信号转换成普通读取事件，使退出和重载逻辑在正常线程上下文执行。前提是相关线程正确屏蔽这些信号，避免信号走传统处理路径。
E: 为什么必须在线程创建前准备|线程有自己的信号掩码，新线程通常继承创建者当时的掩码。若部分工作线程已经运行且没有屏蔽进程定向信号，内核可能把信号交给它们，而不是让指定事件线程通过 signalfd 消费。先设置掩码再创建线程，可以让继承关系成为设计的一部分；之后再创建 signalfd 仍不等同于自动修改所有线程掩码。
E: 普通信号处理函数的限制来自哪里|信号可打断任意执行位置，例如线程正持有 malloc 或日志内部锁。处理函数再调用非异步信号安全函数，可能重入受损状态或死锁。signalfd 回调则在事件循环中的普通调用路径，可安排资源重建与退出；但回调依旧不能无界阻塞所属事件循环。标准信号还可能合并，不能把它当可靠消息队列。
F: SIGKILL 能通过 signalfd 优雅处理吗？|不能，SIGKILL 和 SIGSTOP 不能被捕获、忽略或这样接管。强制终止后的恢复必须依赖外部持久状态与启动恢复机制。
## 25
A: 回调对象必须活到所有可能引用它的已排队操作结束。把 fd 从 epoll 注销只阻止后续注册产生事件，并不会抹掉已经返回到用户态事件数组中的指针。
E: 同一批事件如何触发释放后使用|epoll_wait 返回 A、B 两个指针，先处理 A 时关闭并删除 B；随后循环读到 B 的指针，它已经悬空。常见办法是把 B 标成失效，从活动集合移走，但暂存一份所有权，直到本轮事件批次处理完再释放。B 的条目被访问时先看失效标记；若读回调还能删除自身，写回调前也要再次确认。
E: 更广义的代数与取消规则|定时器、线程池和网络库队列可能比一个 epoll 批次活得更久，单轮延迟回收不够。可使用 shared_ptr/weak_ptr、连接代数或显式取消完成确认。取消请求只是提出意图，只有保证回调不再运行或运行时能安全识别失效，才允许释放被借用对象；否则“取消了”仍可能与已取出的回调竞争。
F: 用 shared_ptr 能否彻底避免所有错误？|它可以保活对象，但回调可能在逻辑关闭后继续修改新状态，也可能形成引用环。物理寿命和逻辑有效性都需要管理。
## 26
A: 串口配置同时决定物理帧格式和终端驱动怎样解释字节。二进制协议通常需要原始模式，关闭行编辑、回显及软件流控，并明确波特率、数据位、校验位和停止位。
E: 一个合法二进制字节为什么会被吃掉|终端行规程可能把换行转换、等待整行或把 XON/XOFF 控制字节用于软件流控。协议中的 0x11/0x13 如果被驱动解释成控制字符，上层看到的字节流就变了，CRC 会失败，却并非物理链路随机出错。调试应先确认 termios 与两端格式一致，再看解析器。
E: VMIN、VTIME 与非阻塞不能混讲|非规范模式中的 VMIN/VTIME 控制读等待条件，不同组合可表示等最少字节、首字节后超时等语义；O_NONBLOCK 又使调用在无进展时返回。跨系统细节需查实现，不能把“VMIN=帧长”当通用分帧方法。tcdrain 关心已提交输出的发送完成，而 write 返回更接近本地接纳，两者不能替代对端 ACK。
F: 改波特率之前要处理哪些旧状态？|需要考虑输出中残余帧、输入半帧、解析器状态和对端切换协议。只改寄存器或 termios 可能把一条帧的前后两段按不同速率发送。
## 27
A: HTTP/1.1 在 TCP 字节流上定义消息结构，解析器要跨多次读取保存状态，并按规范确定正文长度。一次 recv 可能半条请求，也可能包含多条，不能用读取次数划消息边界。
E: 正文长度为什么涉及安全|请求行与头部必须有大小上限；正文按有效的 Content-Length 或 Transfer-Encoding 等规则处理。冲突长度、非法重复头和不支持的分块编码不能各层自行猜测，否则前后代理对同一字节流的边界理解不一致，可造成请求走私。实现一个受限子集时应明确拒绝不支持的形式，不能悄悄忽略后继续复用连接。
E: 慢客户端如何耗尽资源|客户端每隔很久发一个字节，若每次收到字节就把整个超时重新计满，可能永久占用连接和缓冲。应区分头部总期限、正文期限、空闲期限与输出上限，并限制连接数量。处理完一条请求要保留剩余字节供下一条解析，出错或关闭时再一致清理连接状态。
F: 返回 200 是否意味着后台动作完成？|取决于接口契约。若只完成排队，响应应清楚表达接纳或提供结果查询；HTTP 状态码本身不能替底层业务建立完成保证。
## 28
A: 事件循环的可扩展性不仅来自多路复用，还来自每次回调的工作量可控。任何长计算、同步写盘或无界排空，都可能推迟其他连接、定时器和退出请求。
E: 用处理预算建立公平性|每轮限制读字节数、处理任务数或实际执行时间，把未完成工作记在本地待处理集合，然后轮转处理。预算不能破坏 ET 的继续处理责任；后台线程也要有有界队列，否则只是把拥塞移到看不见的地方。稳定运行要求长期消费能力覆盖到达率，短时预算解决公平性，容量和背压解决过载。
E: 停止标志为什么需要唤醒|一个线程把 running=false，主循环却正在无限期 epoll_wait；若没有新事件，它可能永远不再检查标志。正确退出通常既改变持久停止状态，也通过 eventfd、信号等唤醒等待点，然后停止接纳新任务、处理已有任务并退出。修改原子标志只保证可见性，不会凭空制造调度事件。
F: 回调中写一条日志也可能阻塞吗？|可能。即使平时很快，文件系统、锁或日志队列满时都可能改变行为。需要了解日志接口的最坏路径和满队列策略，而不是只看函数名称含 async。
## 39
A: 字节流没有天然帧边界。接收器要靠同步标志、长度、类型和完整性校验逐步识别消息，并在任意分包、连续多帧和损坏输入后恢复到可继续解析的状态。
E: 一个增量解析器需要记住什么|设帧为同步头、长度、正文、CRC。它必须记住目前在找头、收长度、收正文还是收校验，以及已收字节数。一次输入只有半个头时不能丢掉合法前缀；一次输入多帧时每完成一帧后还要继续处理余下字节。若正文也可能包含同步头，正常收正文阶段不能见头就重启，必须由当前长度和校验决定边界。
E: 恢复策略怎样避免越界和锁死|长度必须在写入正文缓冲前检查。校验失败后可重新搜索候选同步位置，但要考虑重叠前缀，例如 AA AA 55 中后一个 AA 仍可能是新头。错误长度可能吞掉后续帧，因此还应有最大帧长、必要的组帧超时和重同步策略。解析器接受外部字节时任何路径都必须有界，不能通过无限等待更多字节掩盖非法状态。
F: 用 IDLE 或 read 返回短数据来划帧可以吗？|只有协议明确把静默间隔作为定界条件且满足时序约束时才行。一般自定义长度协议应把这些当传输分块，最终边界由协议自身决定。
## 40
A: 累加和把字节作加法，CRC 把消息看作二进制多项式做模二除法。CRC 对特定差错模式有可证明的检测能力，但仍有漏检模式，也不提供防恶意篡改的认证。
E: 为什么调换字节可能骗过累加和|两字节 01、02 与 02、01 的加法和相同，但字节位置在 CRC 的多项式中对应不同次数，因此通常得到不同余数。生成多项式决定哪些错误模式是其倍数而无法检出；合适的 r 位 CRC 可检测长度不超过 r 的突发错误，但其他性质还要看多项式和消息长度。随机错误下常说的约 2^-r 漏检概率依赖分布假设，不是对所有输入的绝对保证。
E: 一套 CRC 参数必须完整给出|除了宽度和多项式，还要约定初值、输入/输出反射、最终异或、参与计算的字节及结果线上顺序。0x8005 与反射实现的 0xA001 是位方向相关的表示；看到同名 CRC16 仍不能确定双方兼容。用固定 check 向量确认基础算法，再用真实帧验证覆盖范围，才能把算法错误和协议拼帧错误区分开。
F: 攻击者改了数据后能重算 CRC 吗？|能。CRC 没有秘密密钥，不能证明来源或阻止重放。需要身份鉴别和防篡改时使用合适的 MAC、认证加密及新鲜度机制。
## 41
A: 停等用最少状态换取较低链路利用率；GBN 批量在途但通常从缺口起重传；SR 分别确认并缓存乱序数据。窗口大小受带宽时延积、缓存以及序号歧义共同限制，不能只追求更大。
E: 利用率可以怎样近似计算|设一帧发送耗时 T，最后一位发完到确认返回还需 D，忽略处理和 ACK 发送开销，停等利用率约为 T/(T+D)。允许 W 帧在途后，理想利用率上界可近似写成 min(1, W×T/(T+D))。这里 D 的定义已经排除本帧发送时间，避免把 RTT 和 T 重复相加；有丢包、半双工、有限接收处理能力时还会更低。
E: 半序号空间限制来自“旧帧像新帧”|对称 SR 窗口为 W、序号空间为 M，接收方交付一整窗后，新窗口不能与发送方仍可能重传的旧窗口发生无法区分的重叠，因此典型约束是 M≥2W。这个结论依赖循环序号模型及报文寿命等前提；若协议在序号用完前换会话，则还需证明新会话与旧迟到报文能被区分，不能仅引用公式就结束设计。
F: SR 为什么还会产生队头阻塞？|链路可先接收后续帧，但要求按序交付的业务仍要等前面的缺口。SR 减少无效重传，不自动取消业务顺序约束。
## 42
A: 接收确认表示对方已承担保存责任，按序交付表示数据可以进入业务，执行结果表示业务已经完成。这三个事件可能相隔很久，必须用不同状态与资源计数描述。
E: ACK 乱序时窗口为什么不能随便前移|发送 0、1、2，先收到 1 和 2 的接收确认，0 仍未确认。虽然已确认数量是 2，窗口左边界仍被 0 挡住；若简单按 ACK 数减在途数就继续无限发送，会超出接收端可接受范围。另一方面，0 已确认但执行仍很慢时，它可不再需要链路重传，却仍占业务结果表中的一个位置。
E: 结果先到的合法顺序|接收 ACK 可能丢失，而结果消息已经返回。只要结果身份、类型和长度有效，结果本身可证明该请求至少被接收并执行，状态机应允许直接进入完成。之后迟到的接收 ACK 不能把状态倒退，重复结果可以补发结果确认，但不能再次调用完成回调。这要求把状态转移设计成单向、幂等的规则。
F: 哪一刻可以复用请求对象内存？|只有相关输出、定时器、回调和重试引用都已结束或被安全隔离后。业务完成是必要条件之一，不代表所有异步借用立即消失。
## 43
A: 序号回答“本轮哪一条”，会话号回答“属于哪一轮”。组合键防止上一轮迟到的请求或确认命中新一轮相同序号，但仍需明确会话生成、接受规则与重启后的保存范围。
E: 随机标识与有序标识不能直接互换|随机足够宽的标识主要降低碰撞概率，不天然支持数值越大越新；单调递增会话可让接收方维护高水位，但要处理持久化、分配冲突和重启回退。基于墙上时间生成还要考虑时钟回拨。若接收方用“大于旧值”决定切换，发送方也必须遵守同一全序契约，而不是随便生成一个随机数。
E: 旧回调必须带哪一代身份|旧会话的写完成、定时器或网络结果可能在新会话建立后才执行。若回调只带 seq，它可能修改同号新请求；因此校验至少包含会话与请求身份，必要时再带发送尝试代数。会话重建不仅是清空哈希表，还要让外部队列中残留操作无法污染新状态。
F: 64 位会话为什么仍不能保证跨掉电不重复？|如果接收方丢失已执行记录，同一个业务可能以新会话身份再次到达。链路会话区分与长期业务去重是不同层次，后者需要稳定业务 ID 和相应持久状态。
## 44
A: RTO 控制一轮发送后多久重试，总截止时间限制请求整个生命期，重试预算限制额外尝试次数。三者分别解决暂时丢包、无限等待和资源占用，起点不能混用。
E: RTT 估计为何不能直接取最近一次测量|正常 RTT 会抖动，通常要结合平滑值和变化幅度留出裕量；TCP 的经典形式是 SRTT 加上与 RTTVAR 相关的裕量，并在超时后退避。重传后到达的 ACK 可能对应第一次发送，也可能对应重发，直接从最近发送时刻算样本会低估 RTT，因此需要处理重传歧义。自定义协议可采用固定有界 RTO，但也应解释选值覆盖哪些延迟。
E: 排队与发送期限要分开|假设请求在本地队列等了 300 ms、线上往返正常只需 50 ms。如果从入队立即启动 100 ms 单轮重传计时，就可能尚未发出便排入多份重试。可把排队纳入总期限，而在约定的本地发送完成点启动单轮计时。该完成点如果只是内核接纳，后续驱动排队也仍要计入 RTO 预算。
F: 超时后能向上层报告“没有执行”吗？|通常不能。请求可能已执行而结果丢失。应区分发送前拒绝、明确业务失败和结果未知，重试非幂等操作前先解决这种不确定性。
## 45
A: 有序协议遇到永久缺口时，必须让双方就“跳过还是重建”达成一致。发送方只删本地超时项，不会改变接收方等待的序号，也不能恢复后续业务的顺序执行。
E: 为什么整体重建有时更简单|接收端等 5，却缓存了 6、7。若要跳过 5，需一个本身可靠、可去重的跳过协议，并说明 6、7 在缺少 5 时是否仍有意义；重建会话可以直接结束旧顺序关系，让双方从新起点开始。但旧 5 可能已经执行、仅结果丢失，因此重建只是恢复传输能力，不是把现实世界回滚到未执行。
E: 恢复期间最容易漏掉的发送残留|本地可能已经写出半条旧帧，或者旧重试还排在发送队列。切换时要区分尚未开始的旧项与已经部分写出的帧：前者可因身份失效而取消，后者需按流完整性策略收尾或关闭流。新会话握手成功后再放行新命令，旧回调继续按代数过滤，不能仅清一个 active 标志。
F: 能否在新会话自动重发所有失败命令？|只有业务明确允许这种语义才行。绝对设置值可相对容易重建目标状态；增量动作需要稳定业务去重或查询实际结果，不能把链路重连当成重放授权。
## 46
A: 去重表不是普通缓存，它记录接收方已经承担的执行与结果责任。容量、TTL 起点、重复是否续期、确认后释放以及过期后的拒绝规则共同决定可靠性范围。
E: 满缓存时为什么不能先 ACK|若收到非幂等命令后先确认，再发现没有空间保存请求与结果，发送方可能停止重试，接收方却无法履约。应先预留记录，再接纳并确认；没有资源时不接纳、返回忙或用信用流控。随意 LRU 淘汰已接纳但未结束的项，会把重复执行风险重新引入系统。
E: “不再执行”与“还能回原结果”寿命不同|一个协议可能通过单调执行基序号记住 0..20 已经执行，而只保存最近若干条具体结果。21 之前的旧请求不会重做，但缓存被释放后也无法回答旧 3 的结果。相反，只保留短 TTL 哈希表而没有序号历史，过期后可能把同一请求当新请求执行。必须说明使用的是哪一套状态，而不是笼统说“做了去重”。
F: TTL 比发送方总期限短就一定错误吗？|需要连同完成时刻、结果重传、窗口推进和过期拒绝规则一起判断。短 TTL 会缩短结果可恢复期，但不必然破坏“旧请求不重执行”；保证的是哪一种性质必须分别写出。
## 47
A: 幂等是重复操作的效果属性，去重是识别重复请求的机制，恰好一次则涉及定义好的观察范围与失败模型。稳定请求 ID、结果记录和业务效果之间的原子关系决定保证能做到哪一层。
E: 数据库内的效果为什么较容易合并|如果业务只是更新同一数据库，可在事务中插入唯一请求键、修改业务数据并保存结果。并发重复请求由唯一约束仲裁，提交成功后可返回已保存结果；不能先在事务外查重再执行，因为两个线程可能都查到不存在。失败后要看事务是否真正提交，提交结果不确定时仍需按同一键查询，而非生成新键盲目重做。
E: 物理动作为什么留下空隙|先写“已完成”再让电机转，断电可能留下记录成功但动作未发生；先转电机再写记录，断电后又可能无法知道已转过。普通数据库事务不能自动覆盖电机。可改成设置绝对目标、记录动作 ID、读取位置反馈、设计恢复流程，但必须给出硬件可观察性与持久化假设，不能靠一个 done 位宣称任意动作恰好一次。
F: 设置同一个值就必然幂等吗？|只对选定业务效果可能幂等。若每次设置还触发计费、通知、脉冲或重置定时器，重复调用的总效果可能不同，应把这些副作用纳入定义。
## 48
A: 协议验证要检查状态与不变量，正常收发只是其中一条路径。应控制消息丢失、重复、乱序、迟到和时间推进，证明每次输入后资源与完成语义仍正确。
E: 怎样从不变量推导测试|先写出“同一请求最多执行业务一次”“窗口不越界”“完成回调至多一次”“总期限不被重试延长”等规则，再生成破坏条件的序列：结果先于接收 ACK、旧会话 ACK 到新会话、缓存刚过期、发送半帧时取消。测试不仅看返回值，还统计执行次数、保留槽数、发送内容与最终状态。
E: 虚拟时间为什么比等待真实超时好|把单调时钟作为依赖注入，可以直接检查 deadline 前一单位、等于和后一单位，不必每次睡几秒，也避免调度抖动让测试偶然通过。解析层再用任意切分点与噪声输入测试，与协议层的状态测试分开；最后用真实串口或 PTY 验证接口衔接。各层证据解决不同问题，不能彼此替代。
F: 随机压测很久没错，是否比边界测试更充分？|随机测试能发现未想到的组合，但不保证命中关键边界。应保存种子与失败序列，结合针对不变量的确定性测试和真实链路验证。
## 49
A: TCP 可靠传输的是有序字节流，不保存应用每次 send 的消息边界。接收端必须根据应用协议的长度、分隔符或其他明确规则恢复消息，即使每次发送都恰好是一条完整命令。
E: 合并与拆分为什么都是正常现象|应用连续 send 两条 20 字节消息，接收方可能一次读到 40 字节，也可能先读 7 字节再读 33 字节；网卡、TCP 分段、接收缓冲和线程调度都可影响读取分块。这里通常称为“粘包/半包”的现象并不是 TCP 把数据顺序弄错，而是应用错误地把接口调用边界当成消息边界。
E: 定界方法各有什么代价|固定长度解析简单但可能浪费空间；长度前缀能承载任意二进制数据，但必须验证上限并处理头部不完整；分隔符需要转义或保证正文不包含分隔符；关闭连接定界限制了复用和双向交互。无论哪种方法，接收缓冲都要保留未完成消息及多余后缀，不能每次 read 后清空。
F: 开 TCP_NODELAY 能解决粘包吗？|不能。它影响 Nagle 算法相关的小包发送行为，不改变 TCP 字节流语义。应用仍必须自行分帧。
## 50
A: 握手用于建立双方的序号与连接状态，关闭则分别结束两个方向的数据发送。TIME_WAIT 让主动关闭方在一段时间内处理迟到报文及最终 ACK 的重传问题，不是单纯的资源浪费。
E: 三次握手中分别确认了什么|A 发送 SYN 和初始序号 x；B 返回 SYN、自己的初始序号 y，并确认 x+1；A 再确认 y+1，双方才完成相互序号认知。SYN 占用序号空间，第三次确认使 B 知道自己的同步信息已被 A 收到。还必须结合旧重复报文和具体状态机解释，不能简化为“验证网络能不能双向通”就认为两次足够。
E: 四次挥手为什么也可能看到三段|一方 FIN 只表示它不再发送数据，对方仍可继续发送自己的剩余数据，因此 ACK 与另一个方向的 FIN 在逻辑上分开；若条件合适可合并到一个报文段。收到对端 FIN 后应用迟迟不关闭，可能停在 CLOSE_WAIT；主动关闭方完成最终确认后通常进入 TIME_WAIT。两种堆积的排查方向不同。
F: TIME_WAIT 能一律调短或删除吗？|不应先从参数下手。先看连接创建频率、主动关闭方、连接复用和资源是否真的耗尽；缩短保护时间可能改变迟到报文隔离与重传处理条件。
## 51
A: 流量控制防止接收端缓冲被压垮，拥塞控制防止网络路径被压垮。发送方能在途的数据同时受接收窗口 rwnd 和拥塞窗口 cwnd 约束，还要扣除已经在途的未确认字节。
E: 为什么接收缓冲很大仍可能很慢|即使 rwnd 很大，连接刚开始时 cwnd 可能较小，需要根据 ACK 逐步增长；发生丢包或拥塞信号后又可能收缩。反过来，路径空闲但接收应用读得慢，rwnd 可能变小甚至为零。慢启动不是“线性慢慢增大”，经典过程按 RTT 可近似指数增长；具体算法和实现版本会改变细节。
E: 带宽时延积与缓冲膨胀|若路径带宽为 B、往返时间为 R，要持续利用链路通常需要量级为 B×R 的在途数据；缓冲过小限制吞吐，过大且缺少控制又可能把排队时延推高。吞吐、时延和丢包需要一起看，不能只把 socket 缓冲调到最大。串口虽然不运行 TCP，同样要面对生产消费速率与排队增长，只是控制机制不同。
F: 超时重传说明一定发生拥塞了吗？|不一定，可能有链路错误、接收端停顿或 ACK 丢失；TCP 仍按其算法对信号做保守处理。应用排障应结合具体路径证据，不能把协议动作当成唯一根因。
## 52
A: MQTT QoS 0 不确认，QoS 1 用确认实现至少一次交付并允许重复，QoS 2 用分阶段状态避免同一次协议消息被重复交付。它们首先约束相邻 MQTT 通信端点之间的协议交付，不自动把外部业务动作纳入事务。
E: QoS 2 的四步在防什么重复|PUBLISH、PUBREC、PUBREL、PUBCOMP 使双方在不同阶段保留消息标识与处理状态。某一步丢失时可以重传对应控制报文，接收方依状态避免重复向后交付同一协议消息。它依赖会话状态及标识的正确保存；发布应用自己用一个新标识重新提交相同业务，仍可能成为另一条合法消息。
E: Broker 确认与设备执行隔了几层|发布方收到 PUBACK，说明当前 MQTT 交互完成了规定确认，不代表某个订阅应用已经处理，更不代表订阅应用控制的电机已经动作。Broker 到订阅者是另一段交付，订阅最大 QoS 也影响实际等级。需要业务闭环时，应让最终执行者返回稳定业务 ID 对应的结果，并定义掉线、重复与重启恢复。
F: QoS 1 重复时 DUP 必然为 1 吗？|不能把 DUP 当业务去重键。规范允许同一业务内容以不同 Packet Identifier 再次发送；业务重复与某次 PUBLISH 的重发是不同层次。
## 53
A: Clean Session 决定会话状态是否保留，Retain 保存主题最近一条保留消息供新订阅者获取，Keep Alive 检测连接活动，遗嘱用于异常断开后的通知。这四者不能互相替代。
E: 持久会话需要什么前提|MQTT 3.1.1 中要使用稳定 Client ID 并按 Clean Session 设置恢复会话，Broker 和客户端还要具备相应状态保存能力。订阅、未完成 QoS 交换及离线消息的处理受协议与服务端资源约束。只把 Clean Session 改成 false，并不会自动为应用生成跨重连业务 ID，更不会让未入库的本地命令在进程重启后恢复。
E: 为什么控制命令慎用 Retain|新订阅者建立订阅时会收到主题的保留值，适合“设备当前目标配置”这类状态表达；若内容是“再开一次阀门”这样的事件，重连订阅可能触发过期动作。命令应带有效期、身份和明确的状态/事件语义。Keep Alive 表示协议连接活动，遗嘱出现也不一定表示硬件损坏，可能只是网络分区。
F: 心跳业务消息与 MQTT PING 能互相替代吗？|PING 主要验证 MQTT 连接路径，业务心跳可带传感器状态、任务进展和数据新鲜度。两者观察层次不同，应按故障定位需求设计。
## 54
A: 断网恢复要解决两件事：消息有没有被持久保存，以及重复到达时能否识别为同一个业务。重连只是恢复传输通道，不能填补已经丢失的业务记录。
E: outbox 怎样关闭本地提交空隙|若先改数据库再发消息，进程可能在两步之间崩溃；若先发消息再改数据库，也可能产生相反不一致。可在同一数据库事务里写业务变化与待发送 outbox 记录，再由后台反复发送，确认后标记完成。发送与标记之间仍可能重复，所以接收方还需要稳定 ID 和 inbox/幂等处理；这是一组配合机制，不是单个发送队列。
E: 有限资源如何决定恢复策略|断网无限久而数据持续产生，有限磁盘不可能保证永久保存所有数据。应定义保留期、空间上限、优先级、合并或拒绝策略，并区分遥测与控制命令。恢复时也要限速，避免把全部积压瞬间灌入节点导致新一轮超时。可靠性承诺必须包含这些资源与故障持续时间条件。
F: 数据持久化成功后能立即告诉用户动作成功吗？|只能报告已可靠接纳或已记录，执行成功仍需要执行方结果。接纳、传输、执行和结果持久化是四个不同里程碑。
## 55
A: 心跳证明某条路径在某个时刻还能产生活动，不证明所有功能健康。健康检查应把任务存活、业务进展、外设有效性、数据新鲜度和通信双向能力分开观测。
E: “有心跳、命令没响应”如何成立|发送任务和采样任务仍运行，能周期性发心跳，但接收 DMA 已因错误停止；或者接收仍有数据，命令任务却卡在传感器锁上。此时连接看起来活着，控制链实际已失效。要区分这两类问题，需观察 RX 字节/错误计数、解析成功数、命令开始/结束、TX 进度，而不是仅增加心跳频率。
E: 有效进展要和任务职责绑定|周期采样任务可上报上次采样完成时间，命令任务可上报状态机推进或有界空闲循环，写库任务可上报队列消费位置与错误状态。空闲任务不应因为没有业务而被误判故障；持续积压时又不能仅凭循环转了一圈就视为健康。阈值要覆盖正常最长工作及调度延迟。
F: 节点在线时为什么仍要发送传感器无效标志？|在线只说明节点或部分任务存活。独立有效性可防止把上次成功读数当作当前新数据，也帮助区分设备离线与单个传感器故障。
## 56
A: 网络安全首先明确通信对象是谁、消息有没有被改、调用者允许做什么，以及外部输入最多消耗多少资源。TLS、权限控制、输入验证与业务去重各自解决不同问题。
E: TLS 完成了哪些验证才有意义|加密通道如果没有正确验证证书链、主机名或预共享密钥身份，仍可能连接到错误对端。服务端认证与客户端认证也不同；Broker 确认设备身份后，还要按主题或业务权限限制发布订阅。CRC 只能发现某些传输差错，不提供密钥身份鉴别，不能替代 TLS 或消息认证。
E: 合法连接也可能提交危险输入|已认证客户端仍可能发超长 JSON、越界周期、未知设备或无限命令。应在分配大块内存、排队和执行前验证大小、类型、范围、速率与权限，必要时给业务设置有效期和防重放标识。安全策略必须与有界队列和错误响应连接起来，否则“有认证”仍可能被合法流量拖垮。
F: 串口在本地，是否完全不需要输入校验？|不需要默认把它当公网攻击面，但物理噪声、驱动错误、测试工具和被替换节点都可能产生异常输入。长度、状态与范围校验本身就是基本正确性要求。
## 57
A: SQLite 可以有多个连接，但同一数据库文件的写入需要协调；WAL 改善读写并发，通常仍只有一个写者。让写连接归一个线程、读连接归相应读线程，可以把事务状态与线程所有权说清楚。
E: serialized 模式为什么不等于业务事务安全|SQLite 的 serialized 模式可在接口层对共享连接调用做串行化，但线程 A 的 BEGIN、线程 B 的 INSERT、线程 A 的 COMMIT 仍可能在业务上混用一个事务上下文。数据库内部互斥不理解“这些语句属于哪个请求”。因此连接使用权、预编译语句复用和事务范围仍需应用层管理，不能看到线程安全编译选项就随意共享连接。
E: WAL 的读快照怎么成立|写者把新页面版本追加到 WAL，读事务基于开始时可见的提交位置读取一致快照。读者不必因为每次追加而停止，但长读事务可能阻止检查点回收其仍需看到的历史版本，导致 WAL 增长。独立读连接缓解互相干扰，却不消除文件级锁、检查点和磁盘容量约束。
F: 多开几个写线程就能线性提升 SQLite 吞吐吗？|通常不能，文件级写者竞争仍存在，反而增加锁等待。先减少每行提交开销、复用语句并缩短事务，再用测量判断是否需要换存储架构。
## 58
A: 批量写入的收益主要来自把多条记录合进较少的事务，摊薄事务与同步开销。是否额外等待攒批，是另一个策略选择，直接影响低负载延迟。
E: 两种批处理的延迟不同|固定每 100 ms 刷一次，即使只有一条数据也可能多等近 100 ms；机会式批处理先阻塞等第一项，再立即取走此刻已有项，到数量上限或暂时无数据就提交。前者主动攒批提高合并机会，后者利用已有积压，空闲时延迟更低。两者都必须限制单次批量，避免大事务长期占写锁或拖住资源切换。
E: 上限单位必须一致|队列容量可能按任务数计，一个任务又包含多行记录；事务阈值可能按行数计，加入最后一个任务后实际行数可略超阈值。算内存和延迟时不能把“1024 项”直接当“1024 条传感数据”。还要考虑字符串、vector 容量与队列节点开销，不能只乘 payload 长度。
F: 合批时遇到“切换数据库”任务怎么办？|它应作为顺序屏障：先把屏障前的行写入旧连接，再切换，屏障后数据使用新连接。跨过控制任务继续合批会破坏提交顺序。
## 59
A: ACID 分别描述原子性、一致性、隔离性和持久性，WAL 是实现事务与并发的一种机制，不是“绝不丢数据”的开关。持久性还依赖同步配置、文件系统和存储设备兑现写入承诺。
E: COMMIT 与 checkpoint 各做什么|WAL 模式提交记录让这一批变化成为已提交事务，checkpoint 再把合适的 WAL 页面合并到主数据库。提交不要求每次都把全部变化写回主文件，所以能减少随机写与等待；恢复时依据 WAL 中的提交边界判断哪些变化有效。长读事务可能限制检查点推进，因此需要监测 WAL 大小与读事务时间。
E: NORMAL 与 FULL 的具体差别|WAL 配合 synchronous=NORMAL 在正常条件下保持事务原子性与一致性，但系统掉电或操作系统崩溃可能让已经返回成功的最近事务回退；FULL 在每次提交增加必要同步以提高该层持久保证。进程自身崩溃与整机断电不同，页缓存仍在时恢复条件更好。无论何种设置，硬件若谎报同步完成，软件也无法单独证明物理介质已保存。
F: 一个事务里单条 INSERT 失败，会自动整批回滚吗？|取决于错误类别、冲突策略和应用如何处理。应用若记录错误后继续执行并提交，可能形成部分业务成功；必须明确检查返回值并给出批次失败策略。
## 60
A: 索引减少定位和排序的工作，预编译语句减少重复解析并支持安全参数绑定，查询上限限制结果生成与传输成本。它们解决的瓶颈不同，应按真实查询模式组合。
E: 联合索引为什么看字段顺序|查询 WHERE device_id=? ORDER BY ts DESC LIMIT n 时，以 device_id、ts 排序的索引可先定位某设备范围，再按时间方向扫描少量记录。若只建相反顺序，可能需要遍历更多候选项。等值过滤、范围过滤、排序方向和覆盖列都会影响计划，最终用 EXPLAIN QUERY PLAN 核对，不能只凭“建了索引”判断有效。
E: 绑定值不等于拼 SQL 文本|预编译后用 bind 传递参数，使用户输入作为值解释，避免把引号或运算符拼进 SQL 结构。表名、列名等结构通常不能靠普通值参数代替，需要白名单。语句复用还要正确 reset、处理绑定数据寿命和错误码；数据库行指针一般只能在接口规定期间使用，返回给业务前应取得必要副本。
F: 索引越多越好吗？|每次写入还要维护索引，占用磁盘和缓存。应围绕高频查询建立必要索引，并衡量写放大与实际扫描量。
## 61
A: 异步日志把磁盘 I/O 从调用线程移到消费者线程，但生产者仍承担格式化、同步和排队开销。锁应只保护缓冲交接，慢写盘放在锁外；队列满时的策略必须显式定义。
E: 双缓冲怎么减少临界区时间|生产者向当前缓冲追加，缓冲满或需要刷新时，在短锁内把整块缓冲转交待写队列并换上空缓冲；消费者取得待写块后释放锁，再循环处理短写与错误。若消费者一直拿着同一把锁写文件，其他线程仍会被磁盘延迟阻塞，名义上的后台线程就失去主要价值。
E: 有限缓冲必然需要取舍|磁盘暂停期间到达日志总量超过队列容量，有限内存无法同时做到永不阻塞、永不丢失和无限接纳。可按级别丢弃、采样、阻塞关键日志或降级到另一通道，并累计丢失数。日志若用于业务审计，通常需要比调试日志更强的持久化与失败契约，不能只共用一个“尽力写”的接口。
F: write 成功后日志就能抗掉电吗？|通常只能说明数据被相应内核路径接纳；还要看 fsync/fdatasync、文件系统和介质。线程排空、内核接纳、介质持久化是不同完成层级。
## 62
A: 原子替换配置指针可以让读者看到完整的新快照，却不能让数据库、串口和网络客户端一起原子切换。内存发布与外部资源变更属于不同事务边界。
E: 一次重载为什么会出现混合版本|先发布新配置，再依次重建数据库和串口，如果数据库成功、串口失败，读取配置的线程看到新串口路径，实际 I/O 仍可能走旧端口。若允许这种降级，应暴露期望版本与实际生效状态；若要求全有或全无，就要预构造候选资源、验证后在受控点提交，并处理无法回滚的外部动作。
E: 不可变快照怎样减少读侧锁|加载新配置时先构造完整对象并校验；发布后不再原地修改，读者一次取得一份共享所有权，整次操作都用这份快照。这样避免读一半旧字段、一半新字段，旧读者也不会因替换而悬空。但同一操作若反复重新加载指针，仍可能跨越版本，应让快照范围与业务操作范围一致。
F: 为什么配置语法正确仍不能保证重载成功？|路径可能打不开、端口可能被占用、Broker 可能拒绝连接。语法校验与资源可用性验证是两步，生效结果必须按实际执行反馈。
## 63
A: 切换一个被后台消费的资源，最好让“切换”与普通数据经过同一条有序通道。这样顺序本身确定哪批数据属于旧资源、哪批属于新资源，避免读写侧各自切换而短暂错配。
E: 把控制任务放进数据队列的效果|队列为数据 A、数据 B、Swap、新数据 C。消费者先完成 A、B 对旧连接的写入，再替换连接，之后 C 使用新连接。切换完成时发布读侧新连接，才可保证读侧不会先看到一个还未被写侧接管的新库。Swap 入队成功只表示将来会执行，不等于切换已经完成。
E: 旧资源何时可以销毁|正在处理查询的读线程可能还持有旧连接，切换后新查询用新连接，旧查询允许完成并释放自己的引用。写连接的替换也必须等此前批次结束。共享所有权解决“何时最后一个使用者离开”，有序控制任务解决“什么时候逻辑切换”，两种机制各有职责。
F: 切换任务进不了满队列怎么办？|应返回明确失败或在有限期限内等待，保留旧资源继续运行；不能先把配置标成已生效，再默默丢掉切换任务。是否允许这种暂时不一致应由接口定义。
## 64
A: 优雅退出按照依赖顺序结束工作：先停止产生新任务，再关闭队列入口、唤醒消费者，按契约排空或取消，等待线程退出，最后释放被借用资源。这个顺序与构造顺序相反但并不总能只靠默认析构自动完成。
E: 为什么先销毁队列会产生悬空访问|网络回调可能还在运行并准备入队，如果主线程已经释放队列或 eventfd，回调会访问无效资源。先停网络生产者并等待其线程结束，再关闭队列，消费者才能在“不会再有新项”的前提下安全排空。对相互依赖线程还需避免一边持锁一边 join，防止被等待线程正需要同一把锁退出。
E: 排空也必须有业务边界|写数据库能否一直等、远端离线时是否继续重试、日志失败是否阻止进程退出，都需要明确。有限退出期限可能意味着最终取消部分任务，此时应给请求终态并保存必要恢复记录。队列空只说明这一层消费完，后面若还有内核缓冲、网络发送或持久化步骤，不能据此宣称业务全部完成。
F: 为什么 detached 线程不适合随意使用？|对象析构后无法自然 join 它，后台线程可能继续借用已经释放的成员。除非生命周期独立且清楚管理完成协议，否则显式所有者和可等待退出更易证明正确。
## 65
A: Cortex-M 复位后先从向量表取得初始主栈地址和复位入口，再由启动代码建立 C/C++ 运行环境，才进入 main。RTOS 调度器又在此之后建立任务运行环境，二者是不同阶段。
E: 为什么 main 前必须搬运和清零|有初值的可写全局变量，初始内容通常存在 Flash，启动时要复制到其 SRAM 运行地址；未显式初始化的静态存储对象所处 BSS 要清零。否则全局变量不满足语言规定的初始值。随后还可能调用 C++ 静态对象构造，再调用 main。SystemInit 与运行库初始化的具体次序以启动文件为准，早期代码不能假定后续才初始化的数据已经可用。
E: 任务怎样从一块栈开始运行|创建任务时内核为它构造初始上下文，栈中预先放入入口、参数、状态等内容；启动调度器后移植层通过异常返回机制开始第一个任务。任务函数不能像普通 main 子函数一样自然返回，结束时应显式删除或进入受控路径。调度器启动失败往往涉及内核任务创建、堆容量或中断配置，不能只看任务入口是否有断点。
F: Bootloader 跳应用为什么不能只调用一个函数指针？|还要处理向量表、MSP、残留中断、SysTick、外设和特权/栈选择状态，并校验入口地址。否则应用遇到第一次中断时可能仍跳到旧表或使用错误栈。
## 66
A: 链接脚本描述段在 Flash/SRAM 中的放置，启动代码把这种布局变成运行时状态。text、rodata、data、bss、C 库堆、RTOS 堆和各类栈有不同来源，不能只看某个数组大小估算 RAM。
E: LMA 与 VMA 为什么需要两个地址|带初值变量运行时可写，放在 SRAM 的 VMA；复位后 SRAM 内容不可靠，初值又要从 Flash 的 LMA 装载。链接器提供边界符号，启动代码按它们复制。BSS 通常不需要在 Flash 为每个零存一份镜像，而由启动循环清零。noinit 区若要跨复位保留，必须明确启动流程不覆盖它，并用校验/版本判断内容是否可信。
E: 一份 RAM 预算要把哪些项相加|静态变量占 data/bss，动态创建的 FreeRTOS 任务栈、TCB、队列通常来自内核堆，主栈/MSP 则还要承受异常处理与嵌套。C 库 malloc 可能又使用另一块堆。把内核堆数组算在 BSS 后再把其中任务栈重复加入总 RAM 会双计；反过来只统计应用任务又会漏掉 Idle 和 timer 任务。map 文件与运行期高水位应对应解释。
F: Flash 还剩很多空间，为什么创建任务失败？|创建任务主要需要 RAM 中的栈和控制块，Flash 富余不能直接替代可写 RAM。还要分清总剩余堆与最大连续可分配块。
## 67
A: 外设频率应沿时钟源、PLL、AHB、APB 和外设分频逐级推导。STM32F1 的定时器输入时钟在 APB 分频不为 1 时通常为对应 PCLK 的两倍，不能直接拿 CPU 主频代入所有公式。
E: 一个定时器周期怎样算|假设系统 72 MHz，APB1 分频为 2，则 PCLK1=36 MHz，相关定时器时钟为 72 MHz。向上计数模式下，更新频率通常为 fTIM/((PSC+1)(ARR+1))；PSC=71、ARR=999 时得到 1 kHz。公式中的加一来自计数包含零。高级定时器重复计数器、中心对齐模式等会改变事件频率，应注明模式再计算。
E: PWM 频率和分辨率如何权衡|边沿对齐 PWM 中，周期由 ARR 决定，占空比由 CCR 与计数周期关系决定；ARR 越大，可分的占空比步数越多，但在给定计数时钟下频率越低。更新 ARR/CCR 还要考虑预装载，避免在周期中途改变导致毛刺。系统提高主频时同时要满足电压、Flash 等待周期及 APB 最高频率等限制。
F: 改系统时钟后哪些软件常数会失效？|UART 波特率、I2C 时序、TIM 周期、SysTick 重装值以及按 CPU 周期计算的 DWT 延时都可能需要重新配置；不能只更新 SystemCoreClock 变量。
## 68
A: NVIC 中断优先级通常是数值越小紧急度越高，FreeRTOS 任务优先级则通常数值越大越高。抢占优先级决定能否打断当前异常，子优先级只在相应候选异常之间影响选择次序。
E: 逻辑优先级与寄存器编码怎样换算|若实现 4 个优先级位，逻辑值 0..15 存在 8 位优先级字段的高 4 位，逻辑 5 对应寄存器值 0x50。CMSIS/HAL 接口可能接收未移位逻辑值，底层 BASEPRI 配置则可能需要已移位编码。把 5 当成 0x05 直接写寄存器会丢失有效位，造成与预期完全不同的屏蔽范围。
E: 分组为什么会影响 RTOS 合法性|PRIGROUP 划分已实现的位为抢占位和子优先级位。依赖 BASEPRI 的内核希望中断屏蔽与调用 API 的范围可按其端口规则判断；某些不合适分组会使开发者给出的数字无法表达预期紧急度。调用 FromISR 的 IRQ 必须位于可被内核临界区屏蔽的范围，更紧急的 IRQ 可用于短硬实时处理，但不能直接进入内核对象操作。
F: 两个 IRQ 数值一样会相互嵌套吗？|同一抢占优先级通常不能彼此抢占；挂起后的执行次序还受子优先级和异常号等规则影响。不能仅凭“先到的中断”解释所有情况。
## 69
A: Cortex-M3 异常入口由硬件保存基础返回现场，软件或 RTOS 移植层保存其余任务现场。线程可使用 MSP 或 PSP，Handler 模式使用 MSP；进入异常前的那份基础帧可能保存在被打断线程的 PSP 上。
E: 一次任务被中断的栈变化|任务在 PSP 上运行，异常入口把 R0–R3、R12、LR、PC、xPSR 等基础帧压入该任务栈，然后处理函数在 MSP 上运行；若 Handler 再被嵌套，相关现场压入 MSP。基础帧常为 8 个字，必要时还有对齐填充。不能因为“中断函数用 MSP”就漏算任务栈上的异常入栈空间。
E: EXC_RETURN 为什么不是普通返回地址|异常处理期间 LR 中的特定 EXC_RETURN 值描述返回到 Thread/Handler、使用哪一个栈等信息。异常返回据此恢复栈中现场。FreeRTOS 的 PendSV 还保存 R4–R11、更新 TCB 栈顶，并加载下一任务栈，让异常返回继续另一个任务。把该值当普通函数地址跳转会破坏返回过程。
F: 切换上下文为什么不是硬件全包了？|硬件只保存定义好的基础帧，不知道哪个任务应运行，也不维护 TCB、延时队列和所有软件寄存器现场。调度选择与剩余保存由内核移植层完成。
## 70
A: PRIMASK 广泛屏蔽可配置优先级异常，BASEPRI 按阈值屏蔽一段紧急度范围；它们都不是把芯片所有硬件停止。临界区要说明防的是谁、屏蔽多久以及退出时如何恢复原状态。
E: 为什么内核保留更紧急中断|以 BASEPRI 建立临界区时，可调用内核 API 的中断被屏蔽，因而任务与这些 ISR 不会同时修改内核链表；更紧急中断仍能响应硬件，但必须不访问受保护内核结构。这是一份双方契约：若高紧急度 ISR 违规调用 FromISR，它就可能在内核数据结构更新到一半时进入，问题不一定立刻暴露。
E: 嵌套临界区为何要保存状态|外层已屏蔽中断，内层若退出时无条件全开，会提前破坏外层保护。任务临界区通常维护嵌套计数，ISR 专用屏蔽接口可能返回旧掩码供恢复；具体用法由端口规定。普通用户代码不要混用不配对的 enable/disable 与 RTOS 临界区，尤其不能在临界区里等待依赖被屏蔽中断的完成事件。
F: DMA 在关中断时会停吗？|通常不会。DMA 控制器仍可搬数据，只是 CPU 处理其完成或半满通知被延后；因此长临界区仍可能导致循环缓冲覆盖，甚至使多次硬件事件合并。
## 71
A: HardFault 首先是现场采集问题，再是根因分析问题。应保存异常栈帧和故障状态寄存器，区分非法地址、指令状态、除零、栈破坏或被升级的其他异常，而不是只停在死循环里猜测。
E: 现场如何指向出错指令|根据异常返回信息确认故障时使用 MSP 还是 PSP，定位堆栈中的 PC、LR 与参数寄存器；结合 CFSR、HFSR 及地址有效标志判断 MMFAR/BFAR 是否可解释。用对应 ELF 反汇编和源码映射检查指令，例如一次访问指针加偏移后的地址。若错误是非精确总线故障，堆栈 PC 未必就是最早出错指令，不能过度解读。
E: 为什么故障处理程序本身要克制|栈可能已经损坏，日志堆锁和外设状态也可能不可靠。在 Handler 中执行复杂 printf、动态分配或无限等待串口，可能再次故障或掩盖原现场。更稳妥的是用最小代码保存有限寄存器到预留区，附带校验和复位原因，下次启动再输出；同时确认看门狗是否允许保留足够取证时间。
F: 开栈溢出 Hook 就能抓住所有栈越界吗？|不能，它只在特定检测点与条件下发现部分问题；越界可能已经破坏调度结构，或发生在 MSP。还需静态栈预算、高水位、保护区与故障现场结合。
## 72
A: 寄存器不是普通内存变量，读写可能有硬件副作用。读改写会经过多个操作，既可能与中断竞争，也可能误处理写一清零、读清除等特殊位；应按寄存器契约使用专用置位/复位接口。
E: GPIO 的丢更新怎样发生|任务读 ODR 得到旧值，准备置位 bit0；中断先置位 bit1，任务随后把旧值加 bit0 写回，就可能把 bit1 清掉。使用 BSRR 可在单次写中表达某些位的置位或复位，避免为这些操作读取整个 ODR。它不自动使“先判断输入再切换输出”的多步业务原子化，复杂状态仍需协调。
E: GPIO 模式背后的电气行为|推挽可以主动驱动高低，开漏只主动拉低，释放后的高电平靠上拉；输入浮空可能被噪声影响，模拟模式可关闭部分数字输入路径以适应模拟信号。复用功能把引脚控制权交给外设，但仍需配置正确的电气模式、速度和上下拉。F1 的 MODE/CNF 与后续系列寄存器结构不同，不能跨系列照抄位域。
F: 对 W1C 状态寄存器做 reg |= flag 有什么风险？|读回的其他已置位状态也可能被写成 1，从而一起清除。应按手册要求只写需要清除的位，避免套用普通变量的读改写习惯。
## 73
A: HAL 提供状态机、超时和较统一接口，LL 更贴近单次外设操作，裸寄存器让控制最直接。选择应依据时序约束、代码体积、可维护性与对硬件的掌握，而不是预先把某层判为一定慢或一定可靠。
E: 高层驱动隐藏了哪些状态|一次 HAL 接收启动不仅设置地址和长度，还可能检查句柄状态、锁、DMA 回调和错误标志。如果应用直接改寄存器而不更新句柄状态，硬件与软件认知会分离，下一次 HAL 调用可能返回 BUSY 或执行错误清理。混用不同层时要明确哪个模块拥有外设，以及如何保持两层状态同步。
E: 优化要从具体路径开始|在微秒采样循环中，函数封装和 GPIO 读取路径可能影响判位；在等待 180 ms 传感器转换时，省几条配置指令却几乎没有收益。可把严格时序段写成经过测量的短操作，其余初始化和错误恢复保留可维护接口，并用逻辑分析仪验证真实波形。整体替换 HAL 前必须考虑版本、勘误和恢复路径。
F: HAL 返回 OK 是否代表业务正确？|只代表该接口定义的操作成功，不代表传感器数值合理、数据新鲜或上层命令已完成。驱动结果还要经过格式、范围与业务检查。
## 74
A: Bootloader/OTA 的核心是任何允许的掉电点之后仍有可运行、可验证的启动路径。下载完成、完整性检查、真实性验证、试运行确认和回滚应形成明确状态机。
E: 双镜像为何仍需提交标记|新固件写入备用区后，先校验长度、哈希及签名，再把它标为可试运行；首次启动若不能在限定条件下确认，Bootloader 回到旧镜像。状态标记本身也可能写到一半，需要原子写粒度、冗余或日志式更新。只保留两份二进制而没有可恢复元数据，仍可能不知道哪份完整、哪份已确认。
E: 安全与可用性是两组验证|CRC/哈希发现损坏，签名验证发布者身份；防回滚还需要受保护的版本策略。应用即便签名正确，也可能启动后卡死，因此需试运行与恢复入口。Flash 页擦除、写入对齐、同 Bank 执行限制、向量表和外设状态都要纳入平台设计；空间不足时应明确外部暂存或独立恢复协议，不能承诺凭空双备份。
F: 为什么升级不能沿用普通 RAM 队列的可靠性说法？|升级跨复位和掉电，RAM 中的进度会丢失，必须依赖可恢复的持久状态及受保护启动代码；传输成功只是其中一步。
## 75
A: UART 通过起始位让接收端对齐一帧，再按约定波特率采样数据与停止位。它没有随线传输的时钟，因此两端时钟误差、采样方式和电气质量都会影响可靠性。
E: 从波形推导有效吞吐|8N1 每个字节包含 1 个起始位、8 个数据位和 1 个停止位，共 10 bit。115200 bit/s 对应理想 11520 B/s，一个字节约 86.8 μs，69 字节约 5.99 ms；协议头、CRC、确认、空闲间隔再降低业务吞吐。若增加校验位或停止位，分母也要改变，不能始终用波特率除以 8。
E: 为什么不能背一个通用误差百分比|接收端检测起始沿后按自己的时钟取样，频差会在一帧内累积；允许误差取决于数据位数、过采样与判决方式、发送/接收时钟精度及边沿质量。具体器件的数据手册给出条件，不能把某个经验值外推到全部 UART。TTL UART、RS-232 和 RS-485 的电平与驱动也不同，名称带串口不代表能直接接线。
F: UART 全双工是否表示应用可以随意并发写同一个发送口？|硬件收发可以独立，但多个软件发送者的字节仍可能交错。帧发送应由同一个所有者串行化，或用明确互斥和整帧队列保证顺序。
## 76
A: DMA 由硬件在外设与内存之间搬运数据，减少 CPU 逐字节干预；CPU 仍负责配置、缓冲所有权、完成事件和错误恢复。DMA 提高搬运效率，不自动提供协议边界或无限容量。
E: 一次 DMA 传输有哪些参数|请求源决定何时搬，源/目的地址与是否递增决定搬到哪里，数据宽度和计数决定每次及总量，普通/循环模式决定结束后是否重装。地址宽度不匹配可能破坏相邻内存，外设请求映射也因系列而异。DMA 会占用总线，因此即使 CPU 指令数减少，也要考虑仲裁对访问延迟的影响。
E: TX 的两个完成点必须区分|DMA 传输完成通常表示最后一个数据已交给 UART 数据寄存器，不表示最后一个停止位已经离开引脚。UART TC 才对应更后面的线路发送完成条件。若要切换半双工方向或关闭外设，必须等正确事件；缓冲释放最早能在哪个事件发生，也应按驱动是否还会访问它来证明，不能仅靠变量名 complete。
F: 启用 DMA 后还能忽略中断吗？|只有明确采用轮询且轮询延迟有界时才可能；通常仍需要半传输、完成、IDLE 或错误通知来安排消费。搬运与消费是两条独立进度。
## 77
A: 循环 DMA 把内存当环持续写，IDLE、半传输和完成事件只报告接收进展。软件根据上次处理位置与本次位置取新增区间，再把字节交给协议解析器；IDLE 不是通用帧结束标记。
E: 回绕区间怎样算才不会漏一段|缓冲长度 N，上次位置 old=50，本次 pos=10，新增区间是 [50,N) 加 [0,10)；若 pos≥old，则是 [old,pos)。但 old==pos 有歧义：既可能没有新字节，也可能硬件已经绕过整圈。仅保留模 N 的位置无法知道发生过几圈，必须通过及时处理中断、累计代数或其他设计排除覆盖。
E: HAL 回调参数必须看接口契约|一些 Receive-to-idle HAL 回调的 Size 表示当前数据位置，可能等于 N，不是“本次新增长度”。把它直接当长度追加会重复旧数据；把 N 简单变成 0 又要防止相邻 TC/IDLE 通知对同一末尾产生重复处理。具体事件组合与回调次序需核对所用 HAL 版本，并测试半满、全满、回绕与紧邻 IDLE。
F: 能用“缓冲足够放一帧”证明安全接收吗？|不能。生产者可能连续发多帧，消费者也可能长时间得不到运行；容量证明要基于最坏消费停顿与到达速率，帧最大长度只是其中一个边界。
## 78
A: 缓冲能否不溢出，取决于到达数据减去已消费数据的最大积压。必须分别分析硬件 DMA 环和软件队列：前者可能被覆盖，后者可能拒绝或部分接收，扩大其中一个不自动修复另一个。
E: 把中断屏蔽时间换算成字节|115200、8N1 时约每 86.8 μs 来 1 字节。64 字节环一圈约 5.56 ms，半环 32 字节约 2.78 ms。若处理每半环一次，回调被延迟几毫秒就可能接近下一次覆盖；准确余量还取决于进入临界区时 DMA 已写到哪里。以上是理想满速输入的预算示例，不是测得的中断上限。
E: 软件缓冲还要覆盖慢消费者|即使 ISR 及时把数据复制进软件缓冲，命令任务在等待传感器转换期间仍可能不消费。容量需要覆盖这段等待中的最大输入，或者由窗口/信用限制发送方。若发送 API 只接收部分字节，必须记录实际返回长度并恢复分帧，不能更新读书签后假定全部交接成功。单纯增大缓冲只能吸收有限突发，长期输入快于消费仍会满。
F: 指针队列是不是自然的零拷贝优化？|不是。DMA 下一圈会重写原地址，指针仍有效但内容已变。需要可转移所有权的块池/双缓冲、回收协议与流控，先证明数据寿命，再比较复制收益。
## 79
A: ORE 表示接收数据未及时取走导致覆盖风险，FE 与帧格式/停止位有关，NE 与噪声检测有关。恢复不仅要清错误位，还要恢复 UART、DMA、驱动句柄和软件书签的一致状态。
E: 为什么“清了错误标志”仍收不到|驱动错误路径可能已关闭 DMA 请求、IDLE 中断并把接收状态退回 READY。应用只清一个寄存器位而不重新启动接收，链路就会保持静默。反过来，直接重启 DMA 但保留旧位置，也可能把重装后的新数据与旧半帧拼接。F1 的 SR/DR 清除顺序及 HAL 错误处理细节要按对应版本确认。
E: 有限恢复要保留可诊断结果|可计数错误、清理不可信的接收残段并尝试重启，记录重启是否成功；连续失败时交由任务以退避和期限处理。ISR 中无限恢复循环会阻塞整个系统。错误期间已经丢失的字节不能被重新开 DMA 找回来，只能靠协议重同步和上层重传弥补。
F: 看到 ORE 就能断定 CPU 太慢吗？|不能。还可能是长关中断、DMA 未启动或映射错误、优先级配置、重启窗口和驱动状态异常。应结合波形、DMA 计数器、错误发生时刻与消费者进度定位。
## 80
A: 常见 I2C 使用开漏/开集输出和上拉，实现多个设备只能拉低、释放后回高的线与行为。这支持 ACK、仲裁与时钟拉伸，也使上升沿由电阻和总线电容决定。
E: 上拉电阻为什么既不能太大也不能太小|电阻太大，RC 充电使上升沿变慢，采样时可能还未达到高电平门限；太小则低电平灌电流过大。常用估算 Rmax≈tr/(0.8473×Cb)，Rmin≈(VDD−VOLmax)/IOL，要使用器件允许的电流、总线模式上升时间和实际电容。布线、连接器及探头都会增加电容，不能只照抄一个 4.7 kΩ。
E: 数据什么时候允许变化|普通数据位在 SCL 高电平期间保持稳定，SCL 低时改变；SCL 高时 SDA 的下降/上升分别形成 START/STOP。每 8 位后还有第 9 个 ACK 时钟，由接收方决定应答。某些器件可把 SCL 拉低延长等待，因此主机释放 SCL 后还需按系统能力确认它真的变高，输出寄存器写高不等于线上已经高。
F: I2C 可以用推挽主动输出高吗？|普通共享 I2C 的这些信号阶段不应这样做，否则另一器件拉低时形成电气争用，破坏仲裁与拉伸。特殊模式须按专门规范设计，不能套进普通设备连接。
## 81
A: I2C 七位地址是设备身份，线上第一个地址字节通常由地址左移一位再附加读写位形成。驱动 API 可能要求七位值，也可能要求已移位值；正确性取决于接口契约，不取决于哪一种写法更像地址。
E: 用 0x23 检查线上字节|七位地址 0x23 的写地址字节为 0x46，读地址字节为 0x47。若 HAL 要求传入左移后的地址而应用传 0x23，或库已经左移而应用又左移一次，就会访问错误地址。抓波形时还要确认分析仪显示的是七位地址还是完整地址字节，避免把正常 0x46 误判为地址配置变了。
E: 数值读取前为何要等转换|命令发送成功只说明器件收到了配置，不表示新测量已完成。以默认测量时间寄存器的 BH1750 高分辨率模式为例，典型/最大转换时间和 raw 到 lux 系数都由手册规定；默认常用 raw/1.2，修改测量时间后换算也应调整。等待可以让任务阻塞释放 CPU，但若同时持有传感器锁，其他查询仍会被该转换时长挡住。
F: 连续测量模式下每次重发模式命令一定必要吗？|未必。要按器件行为判断是否重启测量或改变新鲜度；可设计缓存与定期更新，但不能把收到两个字节就等同于获得刚发生的测量。
## 82
A: SDA 卡低时发送最多九个 SCL 脉冲，是试图让停在一个字节中间的从机完成剩余位并释放总线。它是有前提的总线清理，不是能修复所有 I2C 故障的通用复位。
E: 为什么是九个而不是无限个|一个常见传输单元是 8 数据位加 1 ACK 位，主机复位可能让从机仍停留在其中某一位。释放 SDA、产生时钟并观察线路，可以推进残留状态，再构造 STOP 结束事务。前提是 SCL 能被拉高、从机仍按时钟工作；若短路、供电异常或器件永久拉低，继续打时钟并不能解决。
E: 硬件恢复与软件恢复要一起做|暂时停用外设、把引脚切到合适开漏模式、进行有界清理、恢复复用与外设配置，然后让应用知道本次事务失败并决定是否重试。不能保留旧接收数据并标成有效，也不能把恢复时的 GPIO 操作与另一个任务的正常 I2C 事务并发执行。涉及多个控制器时还要避免把合法传输误判为卡死。
F: SCL 本身一直低时怎么办？|先区分合法拉伸与超过期限的异常；若无法释放，应按器件能力使用硬件复位、断电恢复或报告故障。规范中的九时钟方案主要针对 SDA 卡低且 SCL 可控制的情形。
## 83
A: DHT11 用高电平持续时间区分 0 和 1，必须测量或采样微秒级波形。毫秒任务延时无法定位判位窗口；同时每段等边沿都要有界，防止断线把 CPU 永久困住。
E: 从两个时间区间推导采样点|所引奥松 DHT11 V1.3 手册中，0 的高电平为 23–27 μs、1 为 68–74 μs，选择上升沿后约 40 μs 采样，可在理想条件下区分二者。真正余量还要扣除边沿检测延迟、函数执行、中断抢占和时钟误差。若采样点被推到 70 μs，长脉冲也可能已回低，算法便失效。应以实物版本波形和手册确认，而不是只背“0 是 26、1 是 70”。
E: 校验成功仍不等于数据新鲜且可表示|五字节数据含温湿度字段与累加校验；V1.3 对读取间隔、上电稳定和上一轮测量值有说明，温度低字节还带负号约定。解析应检查版本、符号、小数格式及目标数值范围。一个无符号温度协议不能靠强转发送负温；应修改格式或显式报告不支持，不能悄悄变成很大的正数。
F: 关中断采样能否彻底消除时序问题？|只能屏蔽指定范围的抢占，还受更紧急异常、代码执行和电气波形影响，并把延迟转移给 UART、Tick 等路径。更高负载时可考虑定时器输入捕获等硬件计时方案。
## 84
A: 经典 CAN 是按标识符竞争访问的广播总线。控制器处理帧与仲裁，收发器负责差分物理信号；显性位覆盖隐性位，使优先级较低的发送者能退出而不破坏获胜帧。
E: 按位仲裁怎样保证非破坏|两个节点同时发，都会读回总线；发送隐性 1 却读到显性 0 的节点，在仲裁字段退出发送，剩余节点继续。相同帧格式下较小 ID 通常更优先，但标准帧与扩展帧混合时还涉及 IDE/SRR 等位，不能直接把两个不同长度的 ID 当普通整数比较。仲裁优先级也不保证低优先级帧不会长期等待，高负载下仍需总线调度预算。
E: ACK、重传与 bus-off 的关系|正常接收并验证帧的节点可在 ACK 槽给出显性确认，这不表示目标应用已消费。物理错误、位错误和缺少 ACK 等会影响错误计数，控制器可从 error-active 转到 error-passive，严重时进入 bus-off。恢复应检查终端电阻、波特率、采样点、时钟与接地；自动重传不停并不等于业务仍在有效运行。
F: 波特率一样为什么还可能通信失败？|位时间还包含不同时间段、采样点和重同步宽度，线长与传播延迟也参与容差。仅比较标称 bit/s，不足以证明两端时序兼容。
## 119
A: SPI 的 CPOL 定义时钟空闲电平，CPHA 定义在第一个还是第二个有效边沿采样。要从器件时序图确认数据建立/保持与片选范围，不能只记四个模式编号。
E: 用一对边沿解释模式|CPHA=0 时，接收方在第一个边沿采样，发送方必须在该边沿之前准备首位，之后在另一个边沿改变数据；CPHA=1 时通常在第一个边沿移出数据、第二个边沿采样。CPOL 决定这两个边沿分别是上升还是下降。双方错配时可能读到相邻位或边沿上的不稳定电平，低速偶尔可用也不是正确配置的证明。
E: 全双工移位为什么也要发 dummy|SPI 每个时钟同时推进发送与接收，即使业务只想读取，也常需发送占位字节产生时钟。命令、地址、dummy cycle 和结果之间的片选保持由器件协议规定。DMA 搬完不一定等价于 SPI 最后一位结束，拉高 CS 前还要按外设完成条件处理，尤其最后一次读写和 FIFO 排空。
F: SPI 有 ACK 和地址吗？|基础 SPI 没有统一的 I2C 式地址与 ACK，通常由片选和设备自身命令协议定义。错误检测、超时与多设备管理要由上层补充。
## 120
A: ADC 位数描述量化等级，精度还受参考电压、输入驱动、采样时间、噪声和校准影响。DMA 只搬运结果，不能让一个尚未稳定的采样电压变准确。
E: 为什么高源阻抗需要更长采样|采样开关闭合后，内部采样电容通过信号源阻抗和开关电阻充电，电压以 RC 规律接近真实输入。采样结束太早，剩余误差直接进入转换结果；高分辨率要求更小的剩余误差，通常更需要充分建立时间。可延长采样、降低源阻抗或加合适缓冲，但要同时考虑运放稳定性、输入范围与滤波器。
E: 用误差预算区分滤波与校准|N 位 ADC 理想量化步长约为 Vref/2^N，按端点做工程换算可能用 2^N−1，这不改变量化器本身的等级。多次平均可降低某些不相关噪声，不能修复偏置、增益误差、参考漂移或已混叠信号。模拟抗混叠必须发生在采样前；定时器触发减少采样时刻抖动，但多通道扫描仍可能是依次采样。
F: DMA 开了后采样率还受什么限制？|采样加转换的总周期、序列通道数、触发频率、ADC 时钟范围及消费者处理能力仍有限制。必须证明上一轮结束且缓冲未被覆盖，再谈吞吐提升。
## 85
A: 调度器只在就绪任务中选运行者，阻塞任务要等事件或时间条件满足后才回到 Ready。任务状态、优先级、等待对象和栈现场共同决定下一次何时能继续执行。
E: 从队列等待看内核链表|任务读空队列并允许等待时，需要记录它正在等哪个对象，以及最长等到什么时候。因此任务可同时参与事件等待结构与延时索引，但逻辑状态仍是 Blocked。数据先到时从相关等待结构移出并就绪；期限先到时解除等待并返回超时。两个来源竞争时，内核保护必须保证任务不会被重复插入或留在失效链表中。
E: Idle 不只是“什么都不做”|当没有更高优先级就绪任务时 Idle 获得 CPU，可处理自删除任务的资源回收并参与 Tickless。若高优先级任务持续 Ready，哪怕反复 yield，也可能让 Idle 饥饿，引起回收滞后或无法休眠。阻塞与删除都会改变调度状态，但释放应用锁、关闭驱动和取消回调并非由任务删除自动完成。
F: 用 suspend/resume 做一次事件通知为什么可能丢？|resume 发生时目标尚未 suspend，通常不会为将来保存一次唤醒；目标之后再 suspend 就可能一直等待。应使用有状态的任务通知、信号量或队列。
## 86
A: SysTick 推进内核时间，PendSV 执行延后的任务上下文切换，SVC 在典型 Cortex-M3 移植中启动首任务。这种分工把短异常处理与真正切换放到合适的异常优先级上。
E: 一次 ISR 唤醒高优先级任务的完整链|外设 ISR 把数据放入内核对象，使等待任务进入 Ready；如果新任务优先级高于被中断任务，FromISR 接口返回需要切换的标志，退出前请求 PendSV。更紧急 ISR 处理结束后，PendSV 保存原任务剩余寄存器与栈顶，选择并恢复新任务，异常返回后新任务继续。无需等下一个 SysTick 才有机会运行。
E: 为什么把 PendSV 放低紧急度|若在嵌套中断深处随意切换，难以把线程现场和当前 Handler 的调用现场正确分离；最低紧急度使它通常在其他异常处理完毕后统一切换。硬件尾链等机制可减少异常切换开销，但具体周期还受存储等待与实现影响，不应背一个固定纳秒数作为所有 MCU 的结果。
F: 每次 Tick 都发生一次任务切换吗？|不一定。可能没有更合适的就绪任务，同优先级时间片也受配置影响；反过来，任务阻塞、让出或 ISR 唤醒都可在 Tick 之外触发切换。
## 87
A: FromISR API 为中断上下文提供不进入任务阻塞等待的内核操作，并把是否应切换任务交给调用者处理。普通 API 的等待参数写 0，不会自动改变其合法调用上下文。
E: woken 为什么要累计|进入 ISR 时把标志初始化为 false，多次发送/通知中的任一次唤醒更高优先级任务，都应保留这个结果，最后统一请求切换。若每次调用前又清零，后一次没有唤醒新任务就可能覆盖前一次需要切换的事实。API 是否成功交付数据与是否需要立即调度是两种返回信息，都要按各自语义处理。
E: 名称包含 ISR 也不是任意优先级可用|BASEPRI 保护内核临界区时，只屏蔽配置范围内的中断。更紧急中断若调用 FromISR，就可能进入尚在更新的队列或链表，因此被禁止。逻辑优先级 5..15 可调用而 0..4 不可调用，是“4 位优先级、阈值为 5、分组符合要求”这一示例下的结果，不是所有芯片的固定表。
F: 软件缓冲满时 ISR 能不能循环等任务来取？|不能。被唤醒的任务一般要等中断返回才运行，在 ISR 中等待它可能形成自我阻塞。应记录失败、丢失或延期恢复，由任务和流控协议处理容量。
## 88
A: FreeRTOS Queue 按创建时指定的元素大小复制字节，因而适合明确的数据交接。若队列元素是指针，则只复制地址，底层对象的拥有、复用与释放责任必须另行设计。
E: 值队列为什么便于短帧发送|生产者在栈上组好长度和固定数组，发送成功后队列保有副本，生产者可以继续或返回；消费者取出后又拥有自己的副本。若改为栈数组指针，发送函数返回或再次组帧就可能让内容变化。对于大块数据，可从池取块并在成功入队时转移所有权，消费者完成后归还；失败时则由仍拥有它的生产者释放。
E: 队列深度与时延要一起算|若消费者每项最长需要 20 ms，前面已排 7 项，第 8 项可能仅排队就等约 140 ms，还未计算抢占。增大深度吸收更多突发，同时增加内存及可能等待。先查剩余空间再发送不构成原子预留，多生产者下仍以实际发送结果为准。固定元素复制也不能直接用于依赖 C++ 构造析构的非平凡对象。
F: 队列满时丢新项是否总比丢旧项安全？|看业务。遥测可能允许合并成最新值，命令和结果可能承担顺序与确认责任，不能随便淘汰。策略必须与上层接纳语义相符。
## 89
A: Queue 保留固定元素边界，StreamBuffer 是无消息边界的字节流，MessageBuffer 保存变长整条消息。后两者常规设计针对单写者单读者，不能把它们直接当任意多生产者队列。
E: SPSC 约束为什么能简化实现|写者推进写索引，读者推进读索引，不需要每次都在多个写者之间抢占同一个预留位置。多个任务或可互相嵌套的 ISR 同时写时，这个前提就被破坏；按文档加外部串行保护还必须遵守阻塞参数限制，不能简单围住一个可能睡眠的发送。一个 UART 的两个 IRQ 是否构成串行写者，要看它们的抢占优先级与所有调用入口。
E: trigger level 到底唤醒谁|它主要决定等待接收任务在积累多少字节时应被唤醒，不是每次返回的固定长度，也不识别业务帧。已有数据、等待到期等路径会影响实际返回数量。MessageBuffer 另有长度字段开销，并要求接收方能容纳完整消息；缓冲太小时不能假定像流缓冲一样自动取半条。
F: 同时用任务通知与 StreamBuffer 为什么要小心？|StreamBuffer 的阻塞实现可能使用任务通知槽。若应用复用同一个通知槽并采用不兼容语义，会干扰内部等待；应核对版本和可配置通知索引。
## 90
A: 任务通知直接把状态和值保存在目标任务 TCB 中，适合单一接收者。增量计数、置位事件、覆盖数值与不覆盖发送分别保留不同信息，选择前要说明是否允许合并或丢历史值。
E: 二值、计数和位图的区别|连续发生三次事件，二值通知可能只保留“至少一次”，计数方式可保留 3，按位置位只保留哪些种类曾发生。ulTaskNotifyTake 的退出清零与只减一又对应不同消费方式。把计数当业务数据本身时还要考虑溢出及处理失败；若需要每次事件的参数和顺序，队列通常更合适。
E: 通知为什么轻量又不通用|它省去独立队列对象并直接知道唤醒目标，通常开销小；但同一通知索引只有一个接收任务，不能直接替代多消费者队列或完整消息缓冲。多个独立用途应明确分配通知索引，避免库内部通知与应用状态互相覆盖。中断发送仍需 FromISR、正确优先级和切换请求。
F: DMA 完成用通知后，发送缓冲何时可复用？|在确认通知代表对应那一笔传输的正确完成点，并排除旧完成/超时恢复竞态后。通知只是传递事件，缓冲寿命仍由传输状态机管理。
## 91
A: 优先级继承让低优先级持锁者临时提高优先级，减少中间优先级任务对高优先级等待者的间接阻塞。它缩短的是可抢占干扰，不能消除临界区自身的工作时间。
E: 把反转时间拆开看|H 等待 L 的锁，L 还需执行 2 ms 才能释放；没有继承时，中优先级 M 可不断运行，把这 2 ms 拉得很长。继承后 L 可优先于 M 完成，但 H 仍至少等 L 剩余工作以及更高紧急度中断。如果 L 持锁等待外设 180 ms，继承并不能加快传感器，设计上应审视是否能缩短持锁范围或改用缓存/服务任务。
E: FreeRTOS 的继承为什么称为简化机制|其互斥量实现为了 RAM 与执行开销做取舍，持有多个互斥量时，优先级回落可能要等全部相关持锁释放，不能把完整的嵌套继承协议任意套入。二值信号量没有同样的所有者继承语义。讨论具体超时和多锁行为时，应核对所用内核的 queue/tasks 实现及文档，而不是只背“自动提高到最高”。
F: 优先级天花板与继承一样吗？|不是。天花板协议基于资源的预先优先级约束主动控制访问，继承通常在高优先级任务实际阻塞时生效；可证明性质与实现条件不同。
## 92
A: 互斥量适合任务之间保护可等待资源，临界区适合非常短的不可分割状态更新，挂起调度器只暂停任务切换而通常不停止中断。三者不能按“锁得更狠”排成替换关系。
E: 挂起调度器为什么保护不了 ISR 共享数据|任务暂停调度后仍可能被中断打断，ISR 可以修改共享索引；任务随后用旧值写回仍可能丢更新。只有相关访问者都被协议排除，才构成有效互斥。调度挂起期间内核还可能暂存待处理 Tick/就绪变化，在恢复时统一处理，不能在这段时间调用需要立即阻塞的操作。
E: 临界区为什么不能调用任意延时|进入临界区后若等待一个由被屏蔽 ISR 完成的标志，完成者根本没有机会运行。即使是循环执行固定次数，只要耗时很长也会增加所有相关中断延迟、缓冲覆盖风险和时钟失真。把持锁等待替换成关中断并没有解决等待本身，而是影响范围更大。
F: 一个 32 位变量在 32 位 MCU 上是否不用保护？|对齐单次访问可能具有硬件原子性，但复合更新、多个字段不变量、语言可见性以及 ISR/任务协议仍需分析。不能从访问宽度直接推导所有并发操作安全。
## 93
A: vTaskDelay 从调用时刻相对等待，周期会叠加本轮执行时间；vTaskDelayUntil 按保存的基准推进目标唤醒点，更适合保持周期相位。二者都只能让任务到时就绪，实际运行仍取决于调度。
E: 用 10 ms 周期比较漂移|一轮计算 3 ms 后调用 Delay(10)，下一轮约在 13 ms 后开始，执行时间变化会不断进入周期。DelayUntil 则把目标设置为原基准加 10 ms，正常只再等待约 7 ms，长期保持 0、10、20…的目标网格。若一次工作超过周期，目标可能已经在过去，函数可能不阻塞；应用需要决定补做、跳过还是报告错过期限。
E: 一个 Tick 延时不等于至少完整一个 Tick 时长|调用相对延时的时刻可能紧邻下一次 Tick，延时 1 Tick 的实际阻塞时间可能接近零到一个节拍，再加调度等待。若设备要求严格不小于某个物理等待时间，需考虑取整和相位，或用硬件时间判断。周期函数减少相位漂移，不会修复 Tick 丢失或中断长期屏蔽造成的时基错误。
F: 为什么周期计算不宜每轮只做 elapsed+=周期？|超期、补做和 Tick 失真时，累计逻辑次数未必等于真实经过时间。需要实际墙钟/单调时间语义的业务，应记录时间戳并计算差值。
## 94
A: FreeRTOS 的多种 heap 实现是在释放能力、碎片处理、多个内存区与可分析性之间取舍。选型关键是分配模式和最坏延迟，不是编号越大越先进。
E: 五种常见策略怎样区别|heap_1 只分配不释放，适合启动后不再释放的模式；heap_2 可释放但不合并相邻块，容易留下外部碎片；heap_3 包装 C 库分配器；heap_4 在释放时合并相邻空闲块；heap_5 可管理多个非连续内存区域并采用相关合并策略。各实现的可用配置与版本要核对，不能同时任意链接多个提供同名 pvPortMalloc 的实现。
E: 合并空闲块为什么仍不等于无碎片|如果两个空闲块之间夹着一个长期存活对象，就不能合并；总剩余堆大于一次申请仍可能失败。heap_4 的搜索与合并路径也随块分布变化，不能宣称固定 O(1) 或绝对实时。固定块池可减少尺寸搜索和外部碎片，但会有块内浪费及容量耗尽，需要明确失败策略。
F: heap_4 的空闲字节数够创建任务，为何还会失败？|还可能缺少足够大连续块、需要额外 TCB/对齐开销，或在同时创建 Idle/timer 任务时超出预算。应检查具体申请项与最大块，而不是只看一个总量。
## 95
A: 栈预算要沿最深调用链估算，再结合运行期高水位验证。任务栈、主栈/中断栈和堆是不同资源，FreeRTOS 栈深度接口的单位还可能是字而不是字节。
E: 栈空间怎样一步步累计|任务普通调用保存返回地址、寄存器和局部变量；最深路径还可能调用格式化、错误恢复与库函数。Cortex-M 任务被中断时，其基础异常帧可能压在任务栈上，Handler 的后续调用与嵌套再使用 MSP。必须把任务异常帧余量与 MSP 最大嵌套分别计算，不能只给三个应用任务分完 RAM 就认为没有其他栈消耗。
E: 高水位不是最坏情况证明|填充模式被覆盖到多深只能反映已经执行且实际写栈的路径；从未出现的错误、最大报文格式化或编译器变化可能用得更多。某些分配但未写入的栈区域也会影响解释。结合编译器栈使用报告、map、覆盖测试及保护机制，保留合理余量后再调整；不能把测得的最后 100 字节全部裁掉。
F: 大缓冲放 static 就一定更好吗？|可减少每任务栈压力，但变成共享长期对象，需要同步和寿命设计，也固定占 RAM。应看是否可重入、是否会被 DMA 或其他任务同时使用。
## 96
A: 软件定时器回调通常由公共定时器服务任务串行执行，事件组表达一组状态位而不保留每次事件次数。理解它们首先要回答“在哪个上下文执行、是否排队、是否允许阻塞”。
E: 定时器命令成功与回调执行之间隔了什么|start/stop 等 API 可把命令放入服务任务队列，服务任务取得 CPU 后才处理；回调若做长 I/O，会推迟其他所有软件定时器。回调向自己的命令队列无限等待，在队列满时可能等不到消费者，因为消费者就是自己。回调适合做短状态更新或通知工作任务，长业务放其他上下文。
E: 事件组的清除与广播行为|置位可能同时满足多个等待任务，重复置同一位会合并；等待任意位、所有位与退出清位组合要按实际需求选择。ISR 置事件位可能通过定时器服务任务延后处理，以避免在 ISR 唤醒数量不定的任务，因此还依赖该命令队列容量。用户可用位数受 Tick 宽度等配置影响，不能固定假定全部位都可用。
F: 先 GetBits 再 ClearBits 能保证只清除本轮已观察到的签到吗？|两个独立操作之间可能出现新签到，随后 ClearBits 把它一起清掉。若要求严格区分观察窗口，应采用能原子完成所需语义的等待/清除协议，或使用进度计数/时间戳。
## 97
A: HAL Tick 服务驱动的毫秒等待与超时，RTOS Tick 服务任务延时和调度。可以使用不同硬件时基，也可在满足启动、中断和低功耗约束后共享，关键是两套时间语义始终成立。
E: 调度器启动前为什么容易出问题|HAL 初始化和某些驱动已经需要超时，此时 RTOS 尚未开始，直接把 HAL_GetTick 改为任务 Tick 可能得到不推进的时间。反过来，调度启动后 SysTick 的处理权、频率与优先级要符合内核要求；如果 HAL 中断中的等待依赖一个无法抢占当前 ISR 的 Tick，超时可能永远不发生。时基统一不是简单改两个函数名。
E: 低功耗期间两套钟怎样保持一致|RTOS Tickless 可停止周期 Tick，并在唤醒后补偿内核时间；如果另一个 HAL 定时器被停掉，其 uwTick 不会自动获得相同补偿。于是两个“毫秒”可能逐渐不同。应决定 HAL 时间是否必须包含睡眠，对正在等待的超时有什么含义，再设计补偿或约束调用范围，不能只恢复中断就称为时钟恢复。
F: 保留两个 1 kHz 中断是否一定合理？|不一定，额外唤醒会影响功耗；但合并的收益要与启动和补偿复杂度比较。先明确哪一个周期中断可在 Idle 暂停，再证明醒来后的时间契约。
## 98
A: Tickless Idle 在没有可运行业务任务时，用一次较远的唤醒替代多个周期 Tick，并在醒来后补回实际经过的内核时间。它需要睡前重检、提前唤醒处理和计数边界，不能简化成关 SysTick 后执行 WFI。
E: 睡前为什么要再次确认|计算可睡 100 ms 后，可能有 ISR 把任务置为 Ready；若仍按旧估计入睡，会推迟本应立即运行的任务。端口在受控中断状态下重检是否允许睡眠，确定下次到期点，重装可用计时器，再进入等待。这个序列还要防止“检查后事件到达但睡下时错过唤醒”的竞态，因此应遵循架构与移植代码。
E: 提前唤醒怎样补偿|如果 UART 在计划的 100 ms 前、实际 30 ms 时唤醒，不能直接把 Tick 加 100。要根据保留下来的计数器值区分完整 Tick 和不足一个 Tick 的余量，恢复下一节拍相位，再处理到期任务。vTaskStepTick 不是允许随意跨越所有延时任务的万能加法接口，补偿必须与内核最早唤醒点及版本实现配合。
F: Tickless 开启后为何仍每毫秒醒？|可能还有 HAL 定时器或其他周期中断持续唤醒，也可能任务以短超时轮询导致 Idle 窗口很短。需要同时检查硬件唤醒源与任务阻塞期限。
## 99
A: 一次最长休眠由计时器范围、计时频率、最近任务期限和其他唤醒源共同决定。软件预计可空闲很久，不代表所用硬件计数器能一次计那么久。
E: 24 位计数器上限怎样算|SysTick 为 24 位递减计数器，最大一个周期约为 2^24/fCLK。若用 72 MHz 时钟，约为 0.233 s；按 1 ms Tick 切分时能抑制的完整节拍数还会因取整与端口补偿略有差异。如果改用另一种时钟源，必须重新代入频率，不应把 233 ms 记成 Cortex-M 的固定常数。
E: 最近任务期限常比硬件上限更小|一个任务每 100 ms 超时醒来检查状态，即使其他任务可睡数秒，内核也要在这个最早到期点附近恢复调度。硬件最大 233 ms、最近任务 100 ms，实际睡眠先被后者限制；更早的 UART/外部中断还能再次缩短。要延长空闲，应减少不必要轮询或使用更合适长计时源，同时保留看门狗和业务响应要求。
F: 换 RTC 作唤醒就能无限睡吗？|仍受任务最早期限、RTC 精度、可用唤醒模式、时钟恢复及看门狗限制。还需用 RTC 时间正确补偿 RTOS，不能只把唤醒来源换掉。
## 100
A: Sleep 通常保留较多外设与存储状态，只停止 CPU 等部分时钟；Stop 停止更多高速时钟但保留一定状态；Standby 通常需要按复位式流程重新启动。具体保留项和唤醒源必须按芯片系列核对。
E: 低功耗越深，恢复工作越多|Sleep 中外设可能继续工作并中断唤醒；Stop 退出后可能需要恢复 HSE/PLL、总线频率和受影响的外设时间参数；Standby 后普通 SRAM 内容可能不保留，应用不能从原任务栈直接续跑。为了接收 UART，不能只看 CPU 能否执行 WFI，还要看 UART 时钟和该模式的唤醒能力是否存在。
E: Tickless 与低功耗模式是正交选择|Tickless 减少周期唤醒，具体用 Sleep 还是更深模式由端口和睡眠钩子决定。设置 configUSE_TICKLESS_IDLE 不会自动打开所有芯片的深睡眠配置。实际功耗还受传感器、上拉、指示灯、调试器和电源芯片影响，降低 CPU 活跃率不等价于按同样比例降低整板电流。
F: 调试时测得功耗很低或很高都能直接作为产品值吗？|不能。调试连接和冻结选项会改变时钟、看门狗及睡眠行为；应在明确供电、外设状态和脱离调试条件下测量并记录模式。
## 101
A: 忙等适合很短且不能容忍调度粒度的等待，任务延时适合毫秒以上可让出 CPU 的间隔，硬件定时/捕获适合更稳定的边沿控制。选择要同时考虑精度、CPU 占用和对其他任务的影响。
E: HAL_Delay 为什么可能拖住低优先级任务|典型实现轮询 HAL Tick，函数本身不会主动把当前任务置为 Blocked。中断与更高优先级任务仍可能运行，但低优先级任务可能得不到机会。vTaskDelay 则退出就绪竞争，等待 Tick 到期后再竞争 CPU；代价是节拍取整与调度抖动，不能用于几十微秒的位采样。
E: DWT 周期计数的精度来自哪些前提|先启用计数器，再用差值比较经过周期，并按真实 CPU 频率换算时间。频率变化、调试冻结、某些睡眠行为及计数回绕都会影响解释；超时计时本身如果停止，循环即使写了 timeout 也可能永不退出。DWT 忙等让 CPU 持续工作，精细计时不等于低功耗。
F: 用长 NOP 循环延时为何不稳？|编译优化、指令取指等待、分支和主频变化都会改变耗时。需要明确硬件计时基准或经过约束的汇编，并用波形核对，不靠循环次数猜微秒。
## 102
A: 长时间屏蔽节拍中断时，硬件仍可能多次到期，但挂起状态通常不能记录每一次事件。恢复后只执行一次 Handler，就会少计真实时间；这与内核主动挂起调度器后累计已执行 Tick 的情况不同。
E: 三毫秒为什么未必补三个 Tick|假设每 1 ms 的 SysTick 在 3.5 ms 临界区内多次到零，NVIC 主要保留一个待处理状态而不是一个计数队列。临界区退出后进入一次 SysTick Handler，内核通常只增加一次节拍，之前多次事件可能合并。COUNTFLAG 也不是无限溢出计数器，不能事后仅凭一个标志重建所有圈数。
E: 主动 Tickless 为何能做补偿|Tickless 在关闭周期事件前保存当前相位并装载较长计数，在允许范围内根据硬件剩余值计算实际经过时间，属于受控协议。任意业务长关中断没有保存同样信息和边界，不能直接照搬补偿函数。更优先的办法是缩短屏蔽段，或让严格时序由硬件捕获承担。
F: RTOS Tick 少计只会影响显示时间吗？|还会影响任务延时、软件定时器、协议超时和基于 Tick 的健康判断。一个局部时序技巧可能改变整个系统的时间语义。
## 103
A: IWDG 使用独立低速时钟，适合在主时钟或软件失常时触发复位；WWDG 还检查喂狗是否过早，强调允许窗口。选择依据故障模型、时钟依赖与正常抖动，不是简单互相替代。
E: 超时公式与误差怎样一起算|IWDG 典型超时近似为分频值×(重装值+1)/LSI频率。分频 64、重装 1250、假定 LSI=40 kHz 时约 2.0016 s；真实 LSI 随器件、温度、电压变化，应以规定频率范围计算最短/最长超时。软件喂狗周期必须小于最短正常允许期限，并预留中断和任务阻塞余量。
E: WWDG 为什么可能发现另一类故障|窗口看门狗要求在计数器降到允许范围后、又未低到复位门限前刷新，过早和过晚都可能复位，可发现跑飞后疯狂喂狗等行为。但窗口受时钟与配置限制，也更容易受合法长阻塞影响。需要精确计算正常喂狗窗口和异常覆盖，不应仅因为名字多了 window 就认为更可靠。
F: 复位后怎样知道真的是看门狗？|读取并妥善清除复位原因标志，结合上次持久/保留故障信息和运行日志。调试冻结选项可能让断点期间看门狗暂停，必须把这种环境区别记录清楚。
## 104
A: 多任务看门狗不应让任意一个仍活着的循环独自喂狗，而应由监督者确认关键任务在允许窗口内完成了有意义的进展。监督条件与硬件超时必须覆盖真实最长合法工作。
E: 位图签到能做到与做不到什么|每任务置自己的位，监督者看到全部位后刷新并开始下一轮，能发现某任务长期没有到达签到点。但重复置位会合并，位图不记录次数和年龄；一个任务先签到再永久卡住，仍可能帮助完成当前一轮，直到下一轮才被发现。读位和清位之间出现新签到还可能被误清，需要原子窗口协议或计数/时间戳。
E: 有效进度应与故障模型一致|命令任务空闲时及时响应等待超时，可以说明任务尚可调度，却不能证明 RX DMA 还工作；发送任务循环签到也不能证明线路数据真的发出。可把调度存活与驱动健康分开监控，使用 RX 错误、队列消费和事务完成时间。监督者自身应避免被无限等待拖住，并且失败时留下尽可能轻量的诊断信息。
F: 监督周期 1 s、IWDG 约 2 s，能说故障一定 2 s 内复位吗？|不能只这样推断。从故障发生到最后一次允许喂狗之间可能还有观察窗口，硬件又有频率容差。应从最坏故障时刻、签到语义及最晚喂狗点推导总检测时间。
## 105
A: 性能排障先判断系统在计算、等待 CPU、等待锁还是等待 I/O，再针对瓶颈收集证据。CPU、内存和延迟不是孤立指标，队列积压可能把三者同时推高。
E: 高 CPU 和慢响应怎样分开|用线程级 CPU、调用栈采样和系统调用观察，区分计算热点、EAGAIN 忙循环、锁竞争和频繁唤醒。CPU 不高仍慢时，检查阻塞调用耗时、调度等待、磁盘与网络队列。不要先把所有锁换无锁：若根因是数据库每行提交或串口带宽，改锁可能无益还增加复杂度。
E: 内存增长先看对象生命周期|区分真正泄漏、队列增长、缓存保留、分配器未归还 OS 和碎片。结合活对象数量、队列深度、峰值输入及 RSS 曲线，判断是否随压力回落。记录吞吐与延迟分位数、最大值和超时率，比单个平均值更能反映突发问题；观测代码自身也应有开销预算。
F: 优化前后只看一组平均值够吗？|不够。需要相同输入、配置、环境和测量口径，并看尾延迟、资源峰值及错误率是否恶化。代码级推测不能直接写成已取得的性能提升。
## 106
A: 请求超时的排查应沿同一请求身份逐段找最后一个确定进展点：接纳、入队、本地写出、对端接收、执行、结果返回、上层交付。每一层都要区分明确失败与结果未知。
E: 为什么统一请求身份很重要|串口序号、会话、云端业务 ID 与一次发送尝试不是同一个编号。若日志只写“超时 seq=3”，重连后另一个 seq=3 可能混进分析。记录身份、单调时间戳与状态变化，才能看出是排队超时、重传计时过早、节点慢业务还是结果 ACK 丢失。墙上时间用于跨系统对齐时还要考虑时钟同步误差。
E: 定位最后一段已证实的事实|若线路上看见完整命令而节点 RX 计数不增长，优先查硬件/驱动；若解析成功但执行未开始，查窗口缺口和锁；若动作已完成而网关没结果，查结果队列、缓存和返回链。证据应逐层收窄，不要每轮同时改波特率、超时和优先级，否则即使恢复也无法知道原因。
F: 超时日志里最该避免哪种措辞？|把“没有收到结果”写成“设备没有执行”。前者是观察事实，后者需要额外证据；它会直接影响上层是否安全重试。
## 107
A: 逻辑分析仪看数字协议与时序，示波器看电压、边沿和模拟质量，GDB 看软件状态、调用栈和内存。要先确定问题发生在哪个层次，再选择能看到该现象的工具。
E: 同一 I2C 失败怎样交叉验证|逻辑分析仪可检查地址、ACK、START/STOP 和时序顺序；示波器判断上升沿是否过慢、低电平是否达标、是否有毛刺；调试器查看 HAL 状态和超时返回。数字解码器可能把边沿很差但勉强过阈值的波形解释成正确数据，因此解码成功不能证明模拟裕量充足。
E: 调试会改变被测系统|断点暂停 CPU 时，DMA、外设和看门狗是否暂停取决于配置；原本没有的缓冲覆盖可能因断点出现，原本应复位的问题又可能被调试冻结掩盖。微秒路径适合 GPIO 打点、捕获和轻量计数，复杂日志放到事后输出。硬件观察点可定位哪条指令改坏某地址，但数量与访问能力有限。
F: 量到一次最短中断响应就能宣称最大延迟吗？|不能。要构造竞争、中断嵌套、临界区和总线负载等最坏条件，测量结果还应与分析边界结合。
## 108
A: 单元测试验证局部逻辑，集成测试验证组件接口，端到端测试验证真实链路，板级测量验证硬件和时序。覆盖层次越清楚，面试时越不容易把一种证据夸大成另一种。
E: 怎么把测试从函数覆盖变成语义覆盖|协议应断言同一请求的执行次数、结果是否匹配、超时后资源是否释放，而不只断言某个函数被调用。并发应覆盖关闭时生产者仍在提交、回调删除自身、条件变量超时与入队竞争。错误注入应包括短写、EINTR、队列满和数据库失败，检查系统能否给出明确终态并继续处理后续工作。
E: 确定性与真实环境怎样互补|用虚拟时间和可控 I/O 缩短边界测试并复现失败；用 PTY、真实 Broker 或真实板验证系统调用、库回调及电气接口。模拟环境不会自动体现 DMA 覆盖、LSI 误差或 DHT 波形，真机测试也不容易穷举所有状态排列。分别记录做过什么、观察到什么和未验证什么，才有可评估的工程结论。
F: 仓库里有一套测试，能算个人贡献吗？|不能仅据存在就这样表述。应区分自己编写、维护或实际运行验证的内容，并明确其他成员或已有资产的来源。
## 109
A: systemd 负责进程生命周期、启动依赖、权限与失败重启；应用仍负责识别故障、释放资源和保存必要状态。自动重启可以恢复部分服务，却不能替代正确的业务恢复协议。
E: 启动顺序不等于外部服务已经可用|After 约束启动顺序，Wants/Requires 表达不同依赖关系，network-online 也不保证某个 Broker 已可连接。应用应对连接失败有明确启动或重试策略。Type=simple 通常以进程启动作为服务开始，不表示数据库和网络都已准备好；需要精确就绪通知时应选择相应协议和配置。
E: 最小权限如何影响部署正确性|串口访问需要合适设备权限，数据库与日志需要可写目录；ProtectSystem、DynamicUser 等限制必须与实际路径匹配。ExecReload 发送 SIGHUP 只是请求重载，是否成功生效仍需应用反馈。Restart=on-failure 加退避能避免快速重启风暴，但若每次重启都丢失未完成业务，服务“又起来了”不等于命令已可靠恢复。
F: 进程一直重启，第一步是什么？|先查退出码、服务日志、权限和配置路径，保留现场；不要把重启间隔调得更短来掩盖启动失败或资源依赖问题。
## 110
A: 可移植模块把纯逻辑与时间、I/O、存储等环境依赖分开，接口明确数据所有权、调用上下文与错误语义。可测试性来自可控制这些输入，而不仅仅是把代码拆成多个文件。
E: 协议内核如何脱离某个操作系统|把当前时间、发送帧和执行业务设计为回调或接口，状态机只处理有界字节与显式状态，不直接睡眠、访问 UART 或创建线程。主机测试可注入虚拟时间与记录发送结果，MCU 适配层则调用真实队列和驱动。接口需说明回调是同步还是异步、参数是否只在调用期间有效，否则移植后仍可能出现寿命错误。
E: 分层不能把责任一起丢掉|驱动层报告搬运或硬件错误，协议层处理定界、确认与重试，业务层决定参数合法性和执行结果。每层都应保留足够的错误信息，并明确谁负责恢复；若底层只返回 void、上层假定成功，分层反而隐藏失败。不要为每个小函数都造抽象，而应在真实变化点和测试控制点建立边界。
F: mock 全部通过就证明真驱动正确吗？|不能。mock 只能验证其建模的契约，真实中断次序、时钟、DMA 和电气行为仍需集成或板级验证；接口模型本身也可能错误。
## 118
A: SPSC 环形队列的优势来自只有一个生产者推进写位置、一个消费者推进读位置。正确性不仅是下标取模，还包括空满判定、数据发布顺序、回收顺序和计数回绕约束。
E: 发布与回收各需要一条同步链|生产者先确认有空间，再写槽内容，最后 release 发布新写位置；消费者 acquire 观察该位置后才能读对应槽。消费者读完再 release 发布读位置，生产者 acquire 观察后才可复用该槽。若先公布索引再写内容，消费者可能读取未准备好的数据；若先公布槽已空再读完，生产者可能覆盖仍在使用的数据。
E: 容量与算法模型要说清|一种设计留一个空槽区分空满，N 个槽只能存 N−1 项；另一种用单调计数及差值表示占用，可利用全部槽，但要证明计数回绕不会产生歧义。多生产者直接改成 CAS 增写位置还不够：预留顺序和实际写完顺序可能不同，需要额外发布协议。普通 volatile 下标不自动提供 C++ 跨线程同步。
F: 为什么不把 CPU 队列证明直接套在 DMA 环上？|DMA 不通过同一个 C++ 原子协议发布，也可能独立覆盖内存；若有非一致缓存还需维护。必须重新定义硬件生产进度、覆盖代数与 CPU 消费完成的交接机制。
