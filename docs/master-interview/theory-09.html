FreeRTOS 内核与任务通信

T084 原理问答

FreeRTOS 的任务状态和调度链路如何理解？

调度器只在就绪任务中选运行者，阻塞任务要等事件或时间条件满足后才回到 Ready。任务状态、优先级、等待对象和栈现场共同决定下一次何时能继续执行。

原理与成立条件

内核如何维护状态

TCB 保存栈顶、优先级和链表节点等信息。不同优先级有就绪结构，延时任务按唤醒时间组织，等待队列事件的任务还参与相应事件等待结构。事件到来或 Tick 到期使任务转回 Ready，再决定是否需要抢占。这里多个链表反映不同索引，不意味着任务同时在运行与阻塞。

阻塞为什么比轮询合适

等待队列或通知时任务退出就绪竞争，让低优先级任务及 Idle 获得运行。高优先级忙循环即使不断调用 taskYIELD，也通常只让同级就绪任务轮换，不保证低优先级得到 CPU。想等待数据应进入阻塞，而不是期待 yield 自动实现公平。

删除和挂起的陷阱

任务不应从入口函数普通返回；删除时要先归还应用资源、解除回调和锁依赖。自删除任务的内存回收还可能依赖 Idle，Idle 长期饥饿会影响回收。suspend/resume 也不是可靠事件计数器：先 resume 后 suspend 的竞争可能让事件丢失，通知或队列更适合事件同步。

推演与反例

从队列等待看内核链表

任务读空队列并允许等待时，需要记录它正在等哪个对象，以及最长等到什么时候。因此任务可同时参与事件等待结构与延时索引，但逻辑状态仍是 Blocked。数据先到时从相关等待结构移出并就绪；期限先到时解除等待并返回超时。两个来源竞争时，内核保护必须保证任务不会被重复插入或留在失效链表中。

Idle 不只是“什么都不做”

当没有更高优先级就绪任务时 Idle 获得 CPU，可处理自删除任务的资源回收并参与 Tickless。若高优先级任务持续 Ready，哪怕反复 yield，也可能让 Idle 饥饿，引起回收滞后或无法休眠。阻塞与删除都会改变调度状态，但释放应用锁、关闭驱动和取消回调并非由任务删除自动完成。

继续追问

高优先级任务延时 1 Tick 能保证低优先级充分运行吗？

只释放很短且相位相关的时间，低优先级是否满足期限仍需预算；更好的设计通常是按实际事件阻塞，并给 CPU 工作设明确负载上限。

用 suspend/resume 做一次事件通知为什么可能丢？

resume 发生时目标尚未 suspend，通常不会为将来保存一次唤醒；目标之后再 suspend 就可能一直等待。应使用有状态的任务通知、信号量或队列。

T085 原理问答

SysTick、PendSV、SVC 为什么分工？

SysTick 推进内核时间，PendSV 执行延后的任务上下文切换，SVC 在典型 Cortex-M3 移植中启动首任务。这种分工把短异常处理与真正切换放到合适的异常优先级上。

原理与成立条件

PendSV 为什么放最低紧急度

PendSV 是可挂起的系统异常，用来把切换延后到更紧急异常完成后。这样 ISR 先完成硬件处理，再统一切换任务，避免在任意中断深处执行完整上下文切换。最低紧急度是异常优先级配置，不是任务优先级 0 的含义。

一次切换的具体顺序

硬件异常入口保存基本帧；PendSV 读取当前 PSP，将 R4–R11 等软件现场压入任务栈，保存新栈顶到当前 TCB。在适当内核保护下选择下一任务，从其 TCB 取栈顶，恢复软件现场、PSP，最后按异常返回机制恢复基本帧并继续新任务。必须使用匹配该架构的移植层。

SVC 怎样启动第一任务

调度器为新任务预先构造类似异常返回的初始栈帧，含入口、参数和状态。该 ARM_CM3 移植通过 SVC 恢复首任务上下文，之后才进入普通调度生命周期。SVC 不是只在所有 RTOS 中用于同一用途，其他移植或带 MPU 的系统可能还用它完成特权服务。

推演与反例

一次 ISR 唤醒高优先级任务的完整链

外设 ISR 把数据放入内核对象，使等待任务进入 Ready；如果新任务优先级高于被中断任务，FromISR 接口返回需要切换的标志，退出前请求 PendSV。更紧急 ISR 处理结束后，PendSV 保存原任务剩余寄存器与栈顶，选择并恢复新任务，异常返回后新任务继续。无需等下一个 SysTick 才有机会运行。

为什么把 PendSV 放低紧急度

若在嵌套中断深处随意切换，难以把线程现场和当前 Handler 的调用现场正确分离；最低紧急度使它通常在其他异常处理完毕后统一切换。硬件尾链等机制可减少异常切换开销，但具体周期还受存储等待与实现影响，不应背一个固定纳秒数作为所有 MCU 的结果。

继续追问

ISR 把高优先级任务置就绪后，还需要等下一次 SysTick 吗？

正确调用 portYIELD_FROM_ISR 请求切换时，通常可在异常退出路径经 PendSV 切换，不必多等一整 Tick；未请求时则可能增加响应延迟。

每次 Tick 都发生一次任务切换吗？

不一定。可能没有更合适的就绪任务，同优先级时间片也受配置影响；反过来，任务阻塞、让出或 ISR 唤醒都可在 Tick 之外触发切换。

T086 原理问答

FromISR API 与普通 API 有什么本质差异？

FromISR API 为中断上下文提供不进入任务阻塞等待的内核操作，并把是否应切换任务交给调用者处理。普通 API 的等待参数写 0，不会自动改变其合法调用上下文。

原理与成立条件

woken 参数表达什么

调用前把 xHigherPriorityTaskWoken 初始化为 pdFALSE，API 若唤醒更高优先级任务可将其置真；同一 ISR 多次调用应累计这个结果，不要中途重置。最后通过 portYIELD_FROM_ISR 告知移植层需要尽快调度，真正切换通常由 PendSV 完成，避免在数据结构尚未处理完时随意换上下文。

FromISR 也有优先级限制

在采用 BASEPRI 保护的 Cortex-M3 移植中，调用者必须处于 configMAX_SYSCALL_INTERRUPT_PRIORITY 允许的紧急度范围。更紧急的中断不受内核临界区屏蔽，不能进入内核数据结构。函数名包含 FromISR 并不等于可从 NMI、HardFault 或任意高紧急度中断调用。

入队失败仍需应用处理

FromISR 不阻塞，缓冲满可能直接失败或只接收部分字节，具体看 API。保存返回值并计数，必要时通知任务执行恢复；不能在 ISR 无限重试等待消费者，因为被唤醒的任务尚未运行。中断前段只保存足够数据并交接，复杂重试应放任务上下文。

推演与反例

woken 为什么要累计

进入 ISR 时把标志初始化为 false，多次发送/通知中的任一次唤醒更高优先级任务，都应保留这个结果，最后统一请求切换。若每次调用前又清零，后一次没有唤醒新任务就可能覆盖前一次需要切换的事实。API 是否成功交付数据与是否需要立即调度是两种返回信息，都要按各自语义处理。

名称包含 ISR 也不是任意优先级可用

BASEPRI 保护内核临界区时，只屏蔽配置范围内的中断。更紧急中断若调用 FromISR，就可能进入尚在更新的队列或链表，因此被禁止。逻辑优先级 5..15 可调用而 0..4 不可调用，是“4 位优先级、阈值为 5、分组符合要求”这一示例下的结果，不是所有芯片的固定表。

继续追问

只调用 SendFromISR，不调用 YIELD 会不会完全无法工作？

数据可能仍成功进入队列，任务可在后续调度点运行，但立即响应更高优先级任务的机会会丢失；应遵循移植推荐模式，而不是以“偶尔能跑”判断正确。

软件缓冲满时 ISR 能不能循环等任务来取？

不能。被唤醒的任务一般要等中断返回才运行，在 ISR 中等待它可能形成自我阻塞。应记录失败、丢失或延期恢复，由任务和流控协议处理容量。

T087 原理问答

队列为什么复制数据，传指针又有什么代价？

FreeRTOS Queue 按创建时指定的元素大小复制字节，因而适合明确的数据交接。若队列元素是指针，则只复制地址，底层对象的拥有、复用与释放责任必须另行设计。

原理与成立条件

FreeRTOS 队列默认按值复制

创建时确定元素个数和单项字节数，发送时把这些字节复制进队列，接收再复制到调用者缓冲。因此发送局部结构体通常可以在入队成功后离开作用域；队列保存的是副本。但若元素本身是指针，只复制地址，被指数据不会自动被深拷贝或保活。

指针队列必须配所有权协议

生产者从池中取得块，填好数据并成功入队后交出所有权；消费者处理完成再归还。入队失败、消费者取消、任务退出和超时都要确定由谁释放。栈数组地址入队后函数返回、静态缓冲立即复用、DMA 下一轮覆盖，都属于指针仍非空却内容已无效的情形。

阻塞与唤醒如何发生

队列满时任务发送可在给定期限内阻塞，队列空时接收可阻塞；有进展时按内核规则唤醒等待者。ISR 只能用非阻塞专用 API。检查队列当前空闲再发送不是原子预留，多生产者下状态可能立刻变化，最终仍以发送返回值为准。

复制和实时预算

固定短帧按值传递便于证明寿命，代价是发送与接收复制及短临界区开销；大对象可用块池减少搬运，但增加管理复杂度。队列深度还带来等待时延，8 项不表示第 8 项一定及时处理。队列满的策略应在接口中体现，不能忽略失败却让上游以为已接纳。

推演与反例

值队列为什么便于短帧发送

生产者在栈上组好长度和固定数组，发送成功后队列保有副本，生产者可以继续或返回；消费者取出后又拥有自己的副本。若改为栈数组指针，发送函数返回或再次组帧就可能让内容变化。对于大块数据，可从池取块并在成功入队时转移所有权，消费者完成后归还；失败时则由仍拥有它的生产者释放。

队列深度与时延要一起算

若消费者每项最长需要 20 ms，前面已排 7 项，第 8 项可能仅排队就等约 140 ms，还未计算抢占。增大深度吸收更多突发，同时增加内存及可能等待。先查剩余空间再发送不构成原子预留，多生产者下仍以实际发送结果为准。固定元素复制也不能直接用于依赖 C++ 构造析构的非平凡对象。

继续追问

队列里放 shared_ptr 是否适合直接用 C 队列 memcpy？

需要尊重 C++ 对象构造/析构及复制语义，不能把非平凡对象当任意字节复制后当作合法独立对象。应使用适当包装或传可管理句柄。

队列满时丢新项是否总比丢旧项安全？

看业务。遥测可能允许合并成最新值，命令和结果可能承担顺序与确认责任，不能随便淘汰。策略必须与上层接纳语义相符。

T088 原理问答

StreamBuffer 与 Queue、MessageBuffer 有什么区别？

Queue 保留固定元素边界，StreamBuffer 是无消息边界的字节流，MessageBuffer 保存变长整条消息。后两者常规设计针对单写者单读者，不能把它们直接当任意多生产者队列。

原理与成立条件

三种容器保留什么边界

Queue 保存固定大小元素；StreamBuffer 只保存连续字节，不保留每次 send 的消息边界；MessageBuffer 在内部为变长消息保存长度，使接收按整条消息进行。选择应由数据模型决定：串口天然是字节流，固定事件适合队列，变长完整消息可用 MessageBuffer。

单生产者单消费者为何特殊

FreeRTOS StreamBuffer/MessageBuffer 的常规设计假设一个写者和一个读者，利用各自推进索引减少同步成本。多个写者或多个读者需按文档串行化并遵守阻塞限制，不能当作通用多生产者队列。两个 ISR 是否算一个串行写者，还要检查其能否嵌套及其他访问入口。

trigger level 不代表帧长

流缓冲的触发水位主要影响等待中的接收任务何时被唤醒，不负责协议定界，也不保证每次 receive 都返回同样数量。超时或已有数据等条件会影响返回数量；接收方必须按实际返回字节数处理。发送方也可能只写入部分字节，尤其在 ISR 无等待场景。

消息缓冲的容量陷阱

MessageBuffer 需要为每条消息存长度开销，接收缓冲不足时不能像字节流那样默认读半条后继续；应按 API 处理消息未取出。流缓冲适合一边输入一边解析，但仍需端到端容量与覆盖证明，省掉元素结构并不让溢出消失。

推演与反例

SPSC 约束为什么能简化实现

写者推进写索引，读者推进读索引，不需要每次都在多个写者之间抢占同一个预留位置。多个任务或可互相嵌套的 ISR 同时写时，这个前提就被破坏；按文档加外部串行保护还必须遵守阻塞参数限制，不能简单围住一个可能睡眠的发送。一个 UART 的两个 IRQ 是否构成串行写者，要看它们的抢占优先级与所有调用入口。

trigger level 到底唤醒谁

它主要决定等待接收任务在积累多少字节时应被唤醒，不是每次返回的固定长度，也不识别业务帧。已有数据、等待到期等路径会影响实际返回数量。MessageBuffer 另有长度字段开销，并要求接收方能容纳完整消息；缓冲太小时不能假定像流缓冲一样自动取半条。

继续追问

为什么不直接把 DMA 每次回调当一个 MessageBuffer 消息？

回调块由硬件进度决定，不是业务帧，可能半帧或多帧。人为保留这个边界往往没有业务价值，还增加长度开销。

同时用任务通知与 StreamBuffer 为什么要小心？

StreamBuffer 的阻塞实现可能使用任务通知槽。若应用复用同一个通知槽并采用不兼容语义，会干扰内部等待；应核对版本和可配置通知索引。

T089 原理问答

任务通知的计数、事件与数值语义如何选择？

任务通知直接把状态和值保存在目标任务 TCB 中，适合单一接收者。增量计数、置位事件、覆盖数值与不覆盖发送分别保留不同信息，选择前要说明是否允许合并或丢历史值。

原理与成立条件

任务通知为何轻量

通知值及待处理状态放在接收任务的 TCB 中，发送者直接指定目标任务，不必另建通用队列对象。支持的用法包括置位、计数、覆盖或不覆盖数值；较新内核支持通知数组，具体数量受配置控制。接收者是一个指定任务，不是可被任意消费者取走的公共队列。

通知不是数据存储容器

一个 32 位值不适合携带任意消息，也不负责外部缓冲生命周期。常见设计是 DMA/ISR 先把数据放在已约定的缓冲中，通知任务“有进度”，任务再消费。多块完成时需计数、生产索引或队列支持，不能每次只写同一个位还期待知道完成了几块。

什么时候选择其他机制

多个消费者竞争固定元素用 Queue；需要多任务等待组合条件用事件组；多个任意对象间资源计数可用信号量。通知还可能与库内部使用的通知槽冲突，例如流/消息缓冲相关等待，应核实版本及索引配置。轻量的前提是拓扑和语义恰好匹配，不是所有同步都替换为通知。

推演与反例

二值、计数和位图的区别

连续发生三次事件，二值通知可能只保留“至少一次”，计数方式可保留 3，按位置位只保留哪些种类曾发生。ulTaskNotifyTake 的退出清零与只减一又对应不同消费方式。把计数当业务数据本身时还要考虑溢出及处理失败；若需要每次事件的参数和顺序，队列通常更合适。

通知为什么轻量又不通用

它省去独立队列对象并直接知道唤醒目标，通常开销小；但同一通知索引只有一个接收任务，不能直接替代多消费者队列或完整消息缓冲。多个独立用途应明确分配通知索引，避免库内部通知与应用状态互相覆盖。中断发送仍需 FromISR、正确优先级和切换请求。

继续追问

DMA 超时后来了上一次完成通知，怎么避免误认下一次传输完成？

为传输建立轮次或状态，启动前清理/识别旧事件，取消时确认硬件不再继续回调；单独把通知值清零不能关闭晚到事件窗口。

DMA 完成用通知后，发送缓冲何时可复用？

在确认通知代表对应那一笔传输的正确完成点，并排除旧完成/超时恢复竞态后。通知只是传递事件，缓冲寿命仍由传输状态机管理。

T090 原理问答

优先级继承具体怎样工作，为什么仍不能保证快速响应？

优先级继承让低优先级持锁者临时提高优先级，减少中间优先级任务对高优先级等待者的间接阻塞。它缩短的是可抢占干扰，不能消除临界区自身的工作时间。

原理与成立条件

继承怎样改变调度

H 等锁时，内核把持有者 L 的有效优先级提升到足以降低这类干扰的水平，L 运行并解锁后再按实现规则恢复。它不改变硬件转换时间、不自动缩短临界业务、不修复死锁。若持锁者等一个永远不会到的外部事件，提升到最高优先级也不能建立有限等待上界。

为什么二值信号量通常不继承

信号量可由不同执行者发送与等待，没有必然的“拥有者必须归还”关系，内核无法简单确定该提升谁。互斥量把所有者纳入语义，适合保护共享资源；ISR 不应取得任务互斥量，因为它不是可阻塞、可提升任务优先级的普通持锁者。

推演与反例

把反转时间拆开看

H 等待 L 的锁，L 还需执行 2 ms 才能释放；没有继承时，中优先级 M 可不断运行，把这 2 ms 拉得很长。继承后 L 可优先于 M 完成，但 H 仍至少等 L 剩余工作以及更高紧急度中断。如果 L 持锁等待外设 180 ms，继承并不能加快传感器，设计上应审视是否能缩短持锁范围或改用缓存/服务任务。

FreeRTOS 的继承为什么称为简化机制

其互斥量实现为了 RAM 与执行开销做取舍，持有多个互斥量时，优先级回落可能要等全部相关持锁释放，不能把完整的嵌套继承协议任意套入。二值信号量没有同样的所有者继承语义。讨论具体超时和多锁行为时，应核对所用内核的 queue/tasks 实现及文档，而不是只背“自动提高到最高”。

继续追问

把 180 ms 传感器等待放进互斥区，有继承就没问题了吗？

仍会阻塞需要同一设备的高优先级任务。可以考虑启动转换后释放不需保护的状态、由设备服务任务管理事务，或读取缓存快照，但必须保持总线和测量状态一致。

优先级天花板与继承一样吗？

不是。天花板协议基于资源的预先优先级约束主动控制访问，继承通常在高优先级任务实际阻塞时生效；可证明性质与实现条件不同。

T091 原理问答

临界区、挂起调度器和互斥量分别适合什么？

互斥量适合任务之间保护可等待资源，临界区适合非常短的不可分割状态更新，挂起调度器只暂停任务切换而通常不停止中断。三者不能按“锁得更狠”排成替换关系。

原理与成立条件

临界区限制可打断者

在本类 Cortex-M3 移植中，taskENTER_CRITICAL 通过 BASEPRI 和嵌套计数保护内核允许范围，阻止相关 ISR 和任务切换干扰短更新。更高紧急度 ISR 仍可能运行，DMA 也继续工作；它不是对所有并发来源的万能锁。

互斥量允许任务等待

互斥量竞争时任务可以阻塞，其他任务得以运行；适合较长但有界、允许调度的资源操作。它不能在 ISR 中作为普通任务锁使用，并可能带来反转及死锁。选择机制时先问“谁会访问、允许等多久、等待期间谁能推进”，再问开销大小。

三者错误混用的后果

临界区中等待依赖 Tick 的超时可能永不到期；挂起调度器后等队列会妨碍使条件成立的任务运行；拿互斥量保护 ISR 直接访问的数据没有阻挡 ISR。对必须短时间跨任务和 ISR 共享的计数，可用合适原子/临界交接；对慢设备更适合请求队列和专属拥有者。

推演与反例

挂起调度器为什么保护不了 ISR 共享数据

任务暂停调度后仍可能被中断打断，ISR 可以修改共享索引；任务随后用旧值写回仍可能丢更新。只有相关访问者都被协议排除，才构成有效互斥。调度挂起期间内核还可能暂存待处理 Tick/就绪变化，在恢复时统一处理，不能在这段时间调用需要立即阻塞的操作。

临界区为什么不能调用任意延时

进入临界区后若等待一个由被屏蔽 ISR 完成的标志，完成者根本没有机会运行。即使是循环执行固定次数，只要耗时很长也会增加所有相关中断延迟、缓冲覆盖风险和时钟失真。把持锁等待替换成关中断并没有解决等待本身，而是影响范围更大。

继续追问

SuspendAll 后 Tick 没更新，与关中断漏 Tick 一样吗？

不同。ISR 若仍执行，内核可记录推迟的 Tick 并恢复处理；中断被长期屏蔽时硬件可能只保留一个待处理状态，未必知道过去了几次周期。

一个 32 位变量在 32 位 MCU 上是否不用保护？

对齐单次访问可能具有硬件原子性，但复合更新、多个字段不变量、语言可见性以及 ISR/任务协议仍需分析。不能从访问宽度直接推导所有并发操作安全。

T092 原理问答

vTaskDelay 与 vTaskDelayUntil 的周期误差有什么区别？

vTaskDelay 从调用时刻相对等待，周期会叠加本轮执行时间；vTaskDelayUntil 按保存的基准推进目标唤醒点，更适合保持周期相位。二者都只能让任务到时就绪，实际运行仍取决于调度。

原理与成立条件

相对延时为什么漂移

vTaskDelay(T) 从调用时刻起阻塞若干 Tick。若循环先执行 C，再延时 T，启动间隔约 C+T，还受调度影响；每轮执行时间变化会累积到相位。它适合“至少稍后再试”的相对等待，不适合单靠这种写法维持固定采样栅格。

DelayUntil 怎样保持相位

vTaskDelayUntil/xTaskDelayUntil 按保存的上次计划唤醒时刻加周期得到下一目标，执行耗时只占用周期内部预算。调用者正确初始化并保存 previousWakeTime；若目标尚未来到则阻塞，已错过则不等待或按接口返回信息报告，后续相位处理由设计决定。

Tick 量化和调度误差

延时单位是 Tick，应使用适当转换并检查转换为零或溢出；请求 1 Tick 的真实等待与调用相位有关，并不保证完整 1 ms。到期进入 Ready 后还需得到 CPU，所以 RTOS 延时不是高精度脉冲发生器，严格边沿用硬件定时器更合适。

超期后的追赶策略

若任务每轮耗时超过周期，DelayUntil 可能连续不阻塞以追赶旧目标，形成过载。业务需选择跳过过期周期、合并工作或更新基准，并记录超期；不能让无限补做把高优先级任务变成永久就绪。周期计时与工作完成计数也不能混用。

推演与反例

用 10 ms 周期比较漂移

一轮计算 3 ms 后调用 Delay(10)，下一轮约在 13 ms 后开始，执行时间变化会不断进入周期。DelayUntil 则把目标设置为原基准加 10 ms，正常只再等待约 7 ms，长期保持 0、10、20…的目标网格。若一次工作超过周期，目标可能已经在过去，函数可能不阻塞；应用需要决定补做、跳过还是报告错过期限。

一个 Tick 延时不等于至少完整一个 Tick 时长

调用相对延时的时刻可能紧邻下一次 Tick，延时 1 Tick 的实际阻塞时间可能接近零到一个节拍，再加调度等待。若设备要求严格不小于某个物理等待时间，需考虑取整和相位，或用硬件时间判断。周期函数减少相位漂移，不会修复 Tick 丢失或中断长期屏蔽造成的时基错误。

继续追问

调整周期变量后能否立刻改变已经开始的延时？

通常不会自动重排既有阻塞；若要求即时响应配置，需事件唤醒或重新计算目标，并规定从旧基准还是当前时刻开始新周期。

为什么周期计算不宜每轮只做 elapsed+=周期？

超期、补做和 Tick 失真时，累计逻辑次数未必等于真实经过时间。需要实际墙钟/单调时间语义的业务，应记录时间戳并计算差值。

T093 原理问答

FreeRTOS heap_1 到 heap_5 的分配策略与适用条件是什么？

FreeRTOS 的多种 heap 实现是在释放能力、碎片处理、多个内存区与可分析性之间取舍。选型关键是分配模式和最坏延迟，不是编号越大越先进。

原理与成立条件

heap_4 为什么仍可能失败

它维护空闲块并查找足够大的块，释放时尝试与地址相邻空闲块合并。被活对象隔开的空闲区不能合并，故总空闲量大于请求仍可能分配失败；分配耗时也与空闲链结构有关，不能宣称严格固定常数时间或永无碎片。

静态分配和内存池

静态创建接口由应用提供 TCB、栈、队列存储，便于预算并减少运行期分配失败；固定块池为特定对象提供简单的分配上界，代价是容量与块内浪费。选择时还要看对象是否会频繁创建删除、需要哪些尺寸、允许的最坏延迟，不是 heap 数字越大越先进。

监测与失败策略

总剩余堆、历史最低剩余和最大连续块回答不同问题。任务/队列创建失败应立即进入可诊断的安全路径；malloc 失败钩子只能帮助发现，不会凭空释放足够内存。ISR 中一般不应走普通堆分配，应使用预分配资源并设满时行为。

推演与反例

五种常见策略怎样区别

heap_1 只分配不释放，适合启动后不再释放的模式；heap_2 可释放但不合并相邻块，容易留下外部碎片；heap_3 包装 C 库分配器；heap_4 在释放时合并相邻空闲块；heap_5 可管理多个非连续内存区域并采用相关合并策略。各实现的可用配置与版本要核对，不能同时任意链接多个提供同名 pvPortMalloc 的实现。

合并空闲块为什么仍不等于无碎片

如果两个空闲块之间夹着一个长期存活对象，就不能合并；总剩余堆大于一次申请仍可能失败。heap_4 的搜索与合并路径也随块分布变化，不能宣称固定 O(1) 或绝对实时。固定块池可减少尺寸搜索和外部碎片，但会有块内浪费及容量耗尽，需要明确失败策略。

继续追问

同时用 malloc 和 pvPortMalloc 可以互相 free 吗？

除非实现明确约定同一个分配器且接口兼容，否则不能。heap_4 通常管理自己的数组，与 C 库堆是不同来源；必须成对归还。

heap_4 的空闲字节数够创建任务，为何还会失败？

还可能缺少足够大连续块、需要额外 TCB/对齐开销，或在同时创建 Idle/timer 任务时超出预算。应检查具体申请项与最大块，而不是只看一个总量。

T094 原理问答

如何估算任务栈，为什么中断栈要单独看？

栈预算要沿最深调用链估算，再结合运行期高水位验证。任务栈、主栈/中断栈和堆是不同资源，FreeRTOS 栈深度接口的单位还可能是字而不是字节。

原理与成立条件

栈深度单位先确认

FreeRTOS 原生任务创建常以 StackType_t 元素数表示深度，不是字节；在 32 位 ARM_CM3 上 384 个元素是 1536 B。CMSIS 等包装层接口可能使用字节，不能跨 API 套单位。每个任务都要保存自己的调用现场，任务越多并非只增加一个 TCB。

最坏调用链如何预算

沿最深同步调用路径累计局部变量、保存寄存器、库函数及递归空间，再加任务相关异常入栈与余量。格式化输出、大数组和错误恢复路径常比正常路径深；中断 Handler 使用的 MSP 也需独立考虑最大嵌套。平均函数栈耗没有证明意义。

高水位能证明什么

栈创建时填充已知模式，查询连续未被覆盖区域得到历史最小剩余。它只反映实际运行覆盖，未执行路径不会被测到；编译器保留但未写入的大区域也可能影响解释。测量要覆盖最大格式化、传感器失败、重试及嵌套场景，并与 map/编译器栈使用报告结合。

检测与预防

开启合适栈溢出检查、断言和失败钩子能更早暴露问题，但不是保护所有越界的硬件隔离。溢出可能先破坏邻近 TCB/链表，再在远处崩溃。避免无界递归和大局部数组，必要时使用静态/池化缓冲并明确所有权，同时保留主栈安全余量。

推演与反例

栈空间怎样一步步累计

任务普通调用保存返回地址、寄存器和局部变量；最深路径还可能调用格式化、错误恢复与库函数。Cortex-M 任务被中断时，其基础异常帧可能压在任务栈上，Handler 的后续调用与嵌套再使用 MSP。必须把任务异常帧余量与 MSP 最大嵌套分别计算，不能只给三个应用任务分完 RAM 就认为没有其他栈消耗。

高水位不是最坏情况证明

填充模式被覆盖到多深只能反映已经执行且实际写栈的路径；从未出现的错误、最大报文格式化或编译器变化可能用得更多。某些分配但未写入的栈区域也会影响解释。结合编译器栈使用报告、map、覆盖测试及保护机制，保留合理余量后再调整；不能把测得的最后 100 字节全部裁掉。

继续追问

高水位还剩 100 字节，能再缩 100 吗？

不应机械缩到零。观测未涵盖全部路径，未来编译器与库变化也会改变占用，应结合最坏分析和余量再调整。

大缓冲放 static 就一定更好吗？

可减少每任务栈压力，但变成共享长期对象，需要同步和寿命设计，也固定占 RAM。应看是否可重入、是否会被 DMA 或其他任务同时使用。

T095 原理问答

软件定时器和事件组有哪些容易忽略的上下文问题？

软件定时器回调通常由公共定时器服务任务串行执行，事件组表达一组状态位而不保留每次事件次数。理解它们首先要回答“在哪个上下文执行、是否排队、是否允许阻塞”。

原理与成立条件

软件定时器在哪执行

FreeRTOS 软件定时器回调由同一个定时器服务任务串行调用，不是每个定时器一个硬中断。到期精度受 Tick、服务任务优先级、命令队列和前面回调影响；一个回调很慢会拖延其他定时器。因此回调应短小、通常不阻塞，把慢工作交给专门任务。

事件组表示状态组合

每一位表示一个条件，任务可等任意位或全部位，并选择满足时清除。重复置同一位会合并，不保留事件次数；多个等待任务可能因同一置位同时解除阻塞。有效用户位数受 Tick 宽度和内核定义影响，不能固定认为整个 EventBits_t 都可供应用使用。

ISR 置事件的特殊路径

置位可能唤醒数量不定的等待任务，FreeRTOS 的 xEventGroupSetBitsFromISR 通常把操作延后到定时器服务任务，以保持 ISR 工作有界；因此依赖该命令队列空间，也不是硬中断里立刻完成所有唤醒。需要单接收者低开销通知时，可比较任务通知，但语义并不完全相同。

推演与反例

定时器命令成功与回调执行之间隔了什么

start/stop 等 API 可把命令放入服务任务队列，服务任务取得 CPU 后才处理；回调若做长 I/O，会推迟其他所有软件定时器。回调向自己的命令队列无限等待，在队列满时可能等不到消费者，因为消费者就是自己。回调适合做短状态更新或通知工作任务，长业务放其他上下文。

事件组的清除与广播行为

置位可能同时满足多个等待任务，重复置同一位会合并；等待任意位、所有位与退出清位组合要按实际需求选择。ISR 置事件位可能通过定时器服务任务延后处理，以避免在 ISR 唤醒数量不定的任务，因此还依赖该命令队列容量。用户可用位数受 Tick 宽度等配置影响，不能固定假定全部位都可用。

继续追问

事件组全部位曾经置一，是否代表各任务同一时刻健康？

只表示在该观察窗口内分别发生过签到；窗口、清除原子性与签到所代表的进展仍需设计，不能把位图当一致时间戳。

先 GetBits 再 ClearBits 能保证只清除本轮已观察到的签到吗？

两个独立操作之间可能出现新签到，随后 ClearBits 把它一起清掉。若要求严格区分观察窗口，应采用能原子完成所需语义的等待/清除协议，或使用进度计数/时间戳。
