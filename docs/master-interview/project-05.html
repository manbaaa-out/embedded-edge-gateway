P034 项目问答

节点从复位到业务任务运行经历什么过程？

面试时这样回答

复位后先按向量表进入启动代码，准备栈、复制初始化数据并清零未初始化数据区，再进入 C 运行环境与 main。main 完成 HAL、时钟和外设配置，初始化微秒计时资源，然后建立应用队列、流缓冲和任务，最后启动调度器。

这里必须区分调度器启动前后的等待。传感器初始化期间不能假定 RTOS 已能调度；依赖 DWT 周期计数器的延时，也必须先打开计数器。任务创建和通信对象创建失败要在启动阶段发现，否则后续任务可能拿空句柄继续运行。

P035 项目问答

三个任务的优先级为什么这样安排？中断优先级又怎么算？

面试时这样回答

命令任务优先级为 3，发送任务为 2，采样任务为 1。命令任务负责消费串口输入和推进协议状态，所以优先级最高；发送任务承接已经编码好的帧；周期采样的紧迫性相对较低。但高优先级任务如果等锁或同步等传感器，仍然可能错过及时处理后续输入的机会。

NVIC 是另一套优先级体系，数值越小中断紧迫性越高，不能和任务优先级直接比较。UART 与 RX DMA 中断使用逻辑优先级 6，RTOS 可调用 API 的最高逻辑紧迫级界限为 5，因此这些 ISR 可以使用适用的 FromISR 接口。

P036 项目问答

一段 UART 数据怎样从 DMA 到命令解析？

面试时这样回答

USART1 的 RX DMA 循环写入 64 字节缓冲。收到半满、满或空闲事件后，回调根据当前写入位置与上次位置计算新增区域，把新增字节复制到 StreamBuffer，再由命令任务取出并交给持续保留状态的帧解析器。

IDLE 表示线路暂时空闲，不表示业务帧完整。一个帧可以跨多个 DMA 事件，一个事件里也可以有多个帧，所以帧边界必须由长度、同步头和 CRC 判断。回调只搬运新增数据，完整协议处理在任务里进行。

P037 项目问答

64 字节接收缓冲为什么可能溢出？能算出时间预算吗？

面试时这样回答

115200、8N1 每字节在线路上占 10 bit，连续输入速率约为 11520 字节每秒，因此 64 字节大约 5.56 ms 就会被填满，半环只有约 2.78 ms。这个计算给出了连续流下的紧迫程度，不能等价为系统允许随意停顿 5.56 ms，因为已有占用和软件缓冲也要计入。

当前命令执行与解析在同一任务里，执行传感器命令可能让消费者停顿；DHT11 临界区还会推迟相关中断。若停顿期间持续有数据，DMA 可能绕回覆盖，或 StreamBuffer 无法接下全部新增字节。最高 69 字节的协议帧也大于单个 64 字节环，必须允许分段解析。

P038 项目问答

串口发生 ORE 等错误后，为什么可能再也收不到数据？

面试时这样回答

错误可能使 HAL 接收状态或 DMA 流程停止，光清一个错误标志不一定恢复整个接收链。当前错误回调会更新错误计数、复位接收位置并尝试重新启动 DMA 接收，但重启 API 的返回结果还没有形成完整的成功确认与失败重试闭环。

所以排查时要分别看 USART 是否仍收到字节、DMA 计数是否变化、RxEvent 是否继续触发、StreamBuffer 是否有新增，以及任务是否仍消费。任务能定期报心跳，只说明它在运行，不能证明接收驱动已恢复。

P039 项目问答

当前串口发送是 DMA 吗？若优化，核心难点是什么？

面试时这样回答

当前发送由独立任务处理，但任务内使用 HAL_UART_Transmit 和无限等待参数，属于阻塞发送。其他任务可以被调度，不代表发送任务自身没有轮询占用 CPU；它也没有缩短串口线路上发送这些 bit 所需的时间。

合理的改造是保留发送队列，由发送任务启动 TX DMA 后阻塞等待完成。但队列取出的帧必须一直有效，直到最终 UART TC 确认最后一位已离开移位寄存器；DMA 把最后一字节搬到数据寄存器，还不是线路发送结束。还要定义启动失败、超时和取消时谁收回缓冲。

P040 项目问答

为什么传感器已经加锁，命令响应还会慢？

面试时这样回答

锁解决的是两个任务同时访问传感器的问题，不保证持锁时间短。当前统一的传感器互斥锁覆盖完整读取过程，BH1750 的等待也在锁内，因此周期采样与主动查询会互相等待。

即使发生优先级继承，被提升的任务如果正在阻塞等待测量，也不能凭优先级让传感器提前完成。更合理的后续设计是把设备访问交给一个服务任务，按转换时间分阶段推进，再向其他任务提供带时间戳的缓存；若命令必须要新样本，则明确异步等待与超时语义。

P041 项目问答

BH1750 的地址、等待和总线恢复怎样解释？

面试时这样回答

传感器的 7 位地址是 0x23，而 STM32 HAL 这一接口接收的是左移后的地址形式，不能把两种表示混用。当前使用连续高分辨率模式，按默认测量时间设置把原始读数除以 1.2 转成照度，并在读取前等待测量时间。

失败后驱动尝试恢复总线并重试一次：输出时钟帮助被从设备拉住的数据线释放，再产生 STOP、重新初始化 I²C。这个方法针对部分协议中途被打断的情况；如果时钟线始终被拉低或器件供电异常，仅补几个时钟不一定有效。

P042 项目问答

DHT11 为什么使用 DWT 和临界区？代价在哪里？

面试时这样回答

DHT11 用脉冲宽度区分数据位，需要微秒级测量。当前先用毫秒等待拉低启动信号，再进入较短但仍可能持续数毫秒的临界区，使用 DWT 周期计数器判断响应和位宽；边沿等待设置了有限超时，避免正常计数器运行时永远卡住。

临界区降低了被部分中断打断而误判脉冲的机会，同时也推迟了 UART/DMA 等可屏蔽中断。这是在读数可靠性和系统响应之间的取舍。必须先启用 DWT，并让周期到时间的换算符合实际主频，否则有限超时本身也可能失效。

P043 项目问答

温湿度小数、无效值和采样时间怎样传给网关？

面试时这样回答

温湿度在线上按规定缩放成整数，避免直接传 C 结构体或依赖浮点布局；光照也按协议范围和舍入规则编码。读取失败时用有效性状态区分，不把一个看似正常的数值当作新样本继续上报。

当前温度编码采用无符号范围，因此驱动即使能识别某些 DHT11 版本的负号，也不能在不修改协议语义的情况下原样表示负温度。网关写入的时间主要表示接收时间，也不能直接当作传感器完成测量的精确时间。
