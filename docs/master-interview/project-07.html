FreeRTOS 移植与启动验收

P053 项目问答

这个节点具体怎样手动移植 FreeRTOS？

面试时这样回答

这个节点基于 STM32F103 的 CubeMX HAL 工程，手动接入 FreeRTOS 原生内核。编译时选 GCC/Cortex-M3 的 port.c、heap_4.c 和实际用到的任务、队列、定时器、事件组、流缓冲源码，把内核头、port 头和 FreeRTOSConfig.h 加入搜索路径；配置 72 MHz CPU、1 kHz Tick、10 KB RTOS 堆和任务优先级，然后由 app_start 创建对象与三个任务并启动调度器。

运行时关键是把启动向量表的 SVC、PendSV、SysTick 交给 FreeRTOS port，禁用 CubeMX 生成的同名空中断函数。USART1 与 RX DMA 的中断优先级设为 6，满足 FromISR 的门槛 5；HAL 继续用 TIM4 管自己的毫秒时基，RTOS 用 SysTick。源码能证明这些接线和参数，是否满足时序、栈余量及板上功耗还要分别验证。

实现依据与展开

芯片与构建选择

目标宏为 STM32F103xB，编译选项为 -mcpu=cortex-m3，链接脚本分配 64 KiB Flash、20 KiB SRAM。CMake 的 freertos.cmake 仅编入 tasks/list/queue/timers/event_groups/stream_buffer、GCC/ARM_CM3/port.c 与 heap_4.c；内核 include、port 目录和 Core/Inc 通过 freertos_if 传给应用层。根目录的 FreeRTOS-Kernel-main 不是当前固件的编译来源。

配置参数

configCPU_CLOCK_HZ=72000000，configTICK_RATE_HZ=1000，configMAX_PRIORITIES=7，configMINIMAL_STACK_SIZE=128 个 32 位栈元素；动态分配开启、静态分配关闭、configTOTAL_HEAP_SIZE=10 KiB。软件定时器任务优先级 2、栈深 256 元素、命令队列长 10。configUSE_TICKLESS_IDLE=1，睡眠钩子暂停和恢复 TIM4 更新中断。

异常接管

启动文件向量表使用 SVC_Handler、PendSV_Handler、SysTick_Handler；FreeRTOSConfig.h 将 port 的 vPortSVCHandler、xPortPendSVHandler、xPortSysTickHandler 映射到这些名字，并开启 configCHECK_HANDLER_INSTALLATION=1。stm32f1xx_it.c 中 CubeMX 的三个空桩被 #if 0 禁用。启动调度器后，SVC 恢复首任务，SysTick 推进 tick，PendSV 完成切换。

中断优先级

CMSIS 定义 4 个优先级位，NVIC 使用全抢占位分组。最低逻辑优先级 15 编码为 0xF0，调用内核的最高紧迫逻辑级 5 编码为 0x50；USART1 和 DMA1_Channel5 配为 6。串口接收回调调用 xStreamBufferSendFromISR，并用 portYIELD_FROM_ISR 请求必要的切换。

双时基与启动顺序

main 先 HAL_Init、配置 72 MHz 时钟，再初始化 GPIO、DMA、USART1、I2C1、IWDG；HAL_InitTick 被 TIM4 实现覆盖。app_start 先启用 DWT，再创建互斥量、发送队列、接收 StreamBuffer、看门狗事件组，最后创建 Cmd 3、Trans 2、Sample 1 三个任务并调用 vTaskStartScheduler。RX DMA 在 Cmd 任务实际运行后启动。

栈与版本

Cmd、Sample 各为 384 个栈元素即 1536 B，Trans 为 256 个即 1024 B；Idle 与软件定时器任务还要分别分配栈和 TCB。链接脚本的 _Min_Heap_Size 与 _Min_Stack_Size 不等于 FreeRTOS 的堆和任务栈。工程内核是开发分支快照，版本文件未给出精确提交，不能称为已核实的正式发行版。

继续追问

为什么 HAL 配置里的 USE_RTOS 仍是 0？

它是这版 STM32 HAL 自身的编译开关，不是 FreeRTOS 总开关。当前 HAL 头文件要求 USE_RTOS 为 0；FreeRTOS 是否接入由 CMake、FreeRTOSConfig.h、异常入口和 vTaskStartScheduler 决定。

重新用 CubeMX 生成代码，哪几处最可能坏？

重点检查 SVC/PendSV/SysTick 空桩是否被重新加入、TIM4 HAL timebase 是否仍保留、NVIC 分组与 USART/DMA 优先级是否变化，以及自定义 CMake 接线是否还在。

当前实现边界

这些是当前工作区代码和构建配置可核对的实现，不据此推断移植由某个人独立完成，也不把编译通过说成已做板上时序与功耗验证。

P054 项目问答

移植后若任务不运行或串口接收卡住，怎样逐层排查并验收？

面试时这样回答

我会按启动边界逐层排查：先看 ELF 是否链接了唯一的 SVC、PendSV、SysTick 实现，再看 app_start 是否因内核对象或任务创建失败进入 Error_Handler，之后确认首任务运行、SysTick 递增、PendSV 能切换。这样能把异常接线、10 KB 堆不足、任务栈和时钟参数不一致分开定位。

调度跑起来后，再检查 USART1、DMA1_Channel5 的逻辑优先级是否保持 6，接收回调的 FromISR 写入是否真正唤醒 Cmd 任务；最后单独验证 TIM4 HAL 超时、Tickless 的 WFI 唤醒以及睡眠后的时间语义。主机编译与符号检查只能证明前段，响应、栈余量和功耗需要在板上观察或测量。

实现依据与展开

构建与符号层

先检查 freertos.cmake 的 GCC/ARM_CM3/port.c 和 heap_4.c 是否各编一次，再用 nm 或 map 确认向量表的三个 Handler 来自 port.c；若仍落到启动文件的 Default_Handler 或 CubeMX 空桩，任务不会按预期调度。configCHECK_HANDLER_INSTALLATION=1 会帮助发现 SVC/PendSV 接线错误，但不能替代完整验证。

创建与调度层

app_start 对传感器互斥量、TX 队列、RX StreamBuffer、看门狗事件组及三个 xTaskCreate 逐项检查，失败进入 Error_Handler。启动后观察 Cmd、Trans、Sample 任务是否运行和阻塞唤醒，并用栈高水位、剩余堆及故障寄存器判断是否有任务栈或内存问题；当前 configCHECK_FOR_STACK_OVERFLOW=0，不能声称已开启溢出钩子。

中断与接收层

DMA1_Channel5 和 USART1 IRQ 均为逻辑优先级 6，大于等于系统调用阈值 5；HAL 回调把 DMA 新增字节写入 StreamBuffer，然后由 Cmd 任务消费。若任务还在打卡但没有命令输入，分别看 UART 错误计数、DMA 计数、RxEvent、StreamBuffer 短写和接收重启返回值，不能只凭任务存活判断接收链已恢复。

双时基与低功耗层

TIM4 的更新中断推进 HAL_IncTick，port 的 SysTick 推进任务 Tick。Tickless 睡前 HAL_SuspendTick、醒后 HAL_ResumeTick 只暂停和恢复 TIM4 更新中断；HAL 的 uwTick 没有在这段睡眠中按实时时间补偿。验收应记录唤醒源、实际驻留时间、HAL 超时与 RTOS 延时，若声称节能还需板上电流测量。

继续追问

看到 SysTick_Handler 符号就能证明 1 ms tick 正常吗？

不能。还要确认实际系统时钟与 configCPU_CLOCK_HZ 一致、port 设置的重装载值正确，以及 tick 与任务延时能在板上观察到。Tickless 开启时也不能预期每毫秒都有中断。

为什么串口无回应不一定是 FreeRTOS 调度故障？

可能是 RX DMA 已停、StreamBuffer 写不下、Cmd 任务忙于同步传感器读取、TX 队列满或发送任务阻塞。需要沿 ISR 到任务、队列到 UART 的链路定位，不能把所有超时归因于移植层。
