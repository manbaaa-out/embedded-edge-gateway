# 第一部分:纯面试(通用知识,最重要)

## 主题 A:线程安全队列(生产者-消费者)

### A1. 实现一个线程安全队列,需要哪几个同步原语?各管什么?

**答题要点**:一把互斥锁 `mutex` + 一个(或两个)条件变量 `condition_variable`。
- **mutex**:保护底层容器(`std::queue`)本身,任何 push/pop 对容器的访问都要先上锁,防止数据竞争。
- **condition_variable**:让消费者在队列空时**阻塞等待**而不是空转轮询;生产者 push 后 `notify` 唤醒。

**追问:为什么需要条件变量,光有锁不行吗?**
光有锁,消费者发现队列空时只能"解锁→再上锁→再看"忙等(busy-wait),浪费 CPU。条件变量让消费者 `wait` 时**原子地释放锁并休眠**,被唤醒时重新拿锁——CPU 让出去了。这是"锁管互斥、条件变量管等待/通知"的分工。

---

### A2. `cv.wait` 为什么必须配合 `while` 循环判断条件,而不是 `if`?

**答题要点**:防**虚假唤醒(spurious wakeup)** 和**唤醒后条件又被改变**。`wait` 可能在没有 notify 的情况下被操作系统唤醒(虚假唤醒);或者被唤醒后、抢到锁之前,条件又被别的线程改回去了。所以醒来必须**重新检查条件**,不满足就接着 `wait`——这只有 `while` 能做到,`if` 检查一次就往下走了。

标准写法:`cv.wait(lock, [this]{ return !queue_.empty() || shutdown_; });`(带谓词的 `wait` 内部就是 while 循环)。

**措辞陷阱**:别说"wait 醒了就一定有数据"。醒了**不保证**条件成立,必须复查。这是条件变量最经典的考点。

---

### A3. 队列要支持优雅停机(shutdown),怎么设计?

**答题要点**:加一个 `bool shutdown_` 标志。`shutdown()` 时置位 + `notify_all` 唤醒所有阻塞的消费者;消费者的 `wait` 谓词改成 `!queue_.empty() || shutdown_`,醒来后如果是因为 shutdown 且队列已空,就返回失败(让 worker 退出循环)。

**怎么答出深度**:关键是**"停机时不能丢掉已入队的数据"**——所以谓词是"队列非空**或**已停机",优先把剩余数据消费完,队列真空了才让 worker 退。如果只判 shutdown 就退,会丢数据。

**追问:有界队列的背压(back-pressure)怎么做?**
再加一个"未满"条件变量。队列满时**生产者**阻塞在 `notFull` 上,消费者 pop 后 notify 它。这样生产太快时生产者被反压住,防止队列无限膨胀吃光内存。这就是**双条件变量**(一个管"非空"给消费者、一个管"未满"给生产者)。

## 主题 B:线程池

### B1. 线程池解决什么问题?核心结构是什么?

**答题要点**:解决"频繁创建/销毁线程的开销"和"线程数量失控"。核心结构 = **固定数量的 worker 线程** + **一个任务队列**(就是上面的线程安全队列)。worker 们在队列上等任务,主线程把任务 push 进去,空闲 worker 抢到就执行。这本质就是生产者-消费者:提交任务的是生产者,worker 是消费者。

---

### B2. 怎么让 `submit` 既能接受任意任务、又能拿到返回值?

**答题要点**:用 `std::packaged_task` + `std::future`。`submit` 是个模板函数,接受任意可调用对象,内部包成 `packaged_task`,从中取出 `future` 返回给调用方;`packaged_task` 本身扔进任务队列让 worker 执行。worker 执行完,结果通过 `future.get()` 取回。

**怎么答出深度——为什么 packaged_task 要包进 shared_ptr**:`packaged_task` 只能移动不能拷贝,但任务队列里存的 `std::function` 要求可拷贝。矛盾。解法:把 `packaged_task` 放进 `shared_ptr`,lambda 捕获这个 shared_ptr(shared_ptr 可拷贝),队列里存的 lambda 就可拷贝了。这是个高频的实现细节考点。

**追问:worker 里任务抛异常了怎么办?**
`packaged_task` 会自动捕获任务抛出的异常,存进 future 的共享状态;调用方 `future.get()` 时异常会**重新抛出**到调用线程。所以异常能跨线程传播,worker 自己不会因为一个任务异常就崩。

---

### B3. 线程池析构时怎么保证不出问题?

**答题要点**:RAII——析构函数里先 `shutdown` 任务队列(置标志 + notify_all),再 `join` 所有 worker 线程,等它们干完手头的任务、退出循环。**绝不能 detach**,否则主程序退出时 worker 可能还在跑、访问已销毁的资源。

**措辞陷阱**:别说"析构就直接 join"。要先让 worker 有退出条件(shutdown 标志),否则 worker 永远阻塞在 `wait` 上,`join` 会永久卡死。**先 shutdown 唤醒、再 join** 这个顺序是关键。

# 第二部分:和项目挂钩(我具体怎么做的)

### P1. 你网关里的线程池是怎么用的?为什么需要它?

**答**:网关收到 MQTT 消息后,不在 I/O 线程里直接写 SQLite(写盘慢、会阻塞收消息),而是把"写库任务"`submit` 给线程池,I/O 线程立刻返回继续收。这就是"MQTT → 线程池 → SQLite 落库"链。线程池是固定 worker 数,任务队列就是我的 `ThreadSafeQueue`。

---

### P2. 你的 ThreadSafeQueue 有界吗?为什么这么选?

**答**:我做成了**可选有界**——构造时传容量,传了就启用双条件变量背压(非空给消费者、未满给生产者),不传就是无界。网关场景我评估 MQTT 消息速率不高,默认无界够用;但把背压能力留着,是因为"生产快于消费"在别的场景会撑爆内存,有界是更稳的工业默认。这是按场景选复杂度,但保留了扩展点。

---

**答**:这块我主要实测的是配套的异步日志前端(见日志卡),线程池本身我没单独压测吞吐——**这是我要诚实说明的**:我能讲清线程池的结构和正确性,但"它每秒能处理多少任务"我没测过具体数字,不会硬编一个。(这一条对应我之前 mock 暴露的"别把没测的当测过的"教训。)

---

### P4. 析构顺序在你 main 里踩过坑吗?

**答**:踩过——`main` 里对象的**声明顺序决定析构逆序**,我必须保证析构顺序是 client → pool → db。因为 worker 任务里会用到 db,如果 db 先于 pool 析构,worker 还在跑就会 UAF(Use-After-Free,释放后使用)。所以我把 db 声明在 pool 前面(后声明的 pool 先析构),client 放在 try 块内最先析构。这是 RAII 下"用声明顺序控制析构顺序"的实战。
