# 第一部分:纯面试(通用知识,最重要)

## 主题 A:守护进程与信号

### A1. 传统 daemon(守护进程)是怎么创建的?为什么要 fork 两次?

**答题要点**:经典步骤:`fork` → 父进程退出(让子进程被 init 收养、脱离控制终端的会话)→ 子进程 `setsid` 新建会话成为会话首进程 → **再 fork 一次** → 第一个子进程退出。
**为什么第二次 fork**:`setsid` 后进程是会话首进程,**可能重新获得控制终端**。再 fork 一次,孙进程不是会话首进程,**永远无法再获得控制终端**,彻底脱离终端。

**怎么答出深度**:`setsid` 要求**调用者不能是进程组组长**(否则失败)。第一次 fork 就是为了保证子进程不是组长(它有新 pid、旧 pgid),才能 setsid 成功。所以两次 fork 各有用途:第一次为了能 setsid,第二次为了防重获终端。

**追问:现在还需要手写 daemon 化吗?**
**通常不需要了。** 用 systemd 管理服务时,进程就以前台普通进程方式运行(`Type=simple`),后台化、脱离终端、重启、日志都交给 systemd。手写 double-fork 是 systemd 之前的做法。理解原理是为了面试和读老代码,实际部署交给 init 系统更好。

---

### A2. 进程怎么响应外部信号(如重新加载配置)?

**答题要点**:经典做法是注册信号处理函数(`signal`/`sigaction`),收到 SIGHUP 等信号时设个标志,主循环检查标志做相应处理。但**信号处理函数里能做的事极有限**(只能调异步信号安全的函数),直接在里面干活很危险。

**更好的做法——signalfd**:Linux 的 `signalfd` 把"信号"转成"**fd 可读事件**",于是信号能被 epoll 统一监听,在**普通代码上下文**(不是信号处理器的受限上下文)里处理。这和 timerfd 把定时器变 fd 是一个思路——**"一切皆 fd",把异步事件统一进事件循环**。

**追问:用 signalfd 要注意什么?**
要先 `sigprocmask` **阻塞**这些信号的默认处理,否则信号还会走默认路径(可能直接终止进程),signalfd 就收不到了。"先 block、再用 signalfd 收"是固定搭配。

## 主题 B:配置热加载

### B1. 什么是配置热加载?为什么要它?

**答题要点**:不重启进程就能让新配置生效。生产服务重启有代价(断连接、丢状态、服务中断),热加载让"改个日志级别、调个参数"不用重启。通常用 SIGHUP 信号触发重新读配置文件。

**怎么答出深度——不是所有配置都能热加载**:配置要**分类**:
- 有些改内存变量即可生效(如日志级别)。
- 有些要重建资源(如改了串口路径、数据库连接,得关旧的开新的)。
- 有些根本不能热改(如监听端口——已经 bind 了),只能重启。

成熟的热加载要明确"哪些能热改、哪些重建、哪些必须重启",而不是无脑全部重读。

---

### B2. 热加载时怎么保证"读配置的线程"不读到改了一半的配置?

**答题要点**:**load-then-swap(先加载,再原子替换)**。新配置先在一边完整构建好,构建成功后**用一个原子操作把"当前配置指针"指向新配置**;读配置的地方拿到的要么是完整的旧配置、要么是完整的新配置,绝不会是改了一半的。构建失败就保留旧配置(原子回滚)。

**实现手段**:`atomic<shared_ptr<const Config>>`——读端原子地拿到一个 shared_ptr 快照(无锁、读不阻塞),写端构建好新 Config 后原子替换指针。`const` 保证配置一旦发布就不可变(发布后不再有人改它,天然线程安全)。

**怎么答出深度**:这是**"不可变 + 原子替换"** 的无锁读模式——读多写极少的场景(配置就是),比读写锁更快(读端完全无锁)。

## 主题 C:调试工具链

### C1. GDB、AddressSanitizer、Valgrind 各擅长什么?怎么分工?

**答题要点**:
- **GDB**:**流程调试**——断点、单步、看调用栈、看变量。崩溃后用 core dump 看"崩在哪、调用栈是什么"。
- **AddressSanitizer(ASan)**:**内存错误**——越界、UAF、内存泄漏。编译期插桩(`-fsanitize=address`),运行时几乎实时报错且**定位精确**(直接指到出错行 + 分配/释放栈)。开销小(~2x),适合开发期常开。
- **Valgrind**:也查内存错误和泄漏,**无需重新编译**,但**慢很多**(10–50x),适合 ASan 没覆盖到、或不方便重编译的场景。

**怎么答出深度——排查链**:崩溃问题的流程是 **先看 core dump 用 GDB 判类型 → 怀疑内存错误就上 ASan(精确定位) → 偶发的、压力下才出的内存问题用压测逼出来再抓**。工具是分层的,不是只用一个。

## 主题 D:构建与部署

### D1. CMake 是干什么的?为什么不直接写 Makefile?

**答题要点**:CMake 是**跨平台构建系统生成器**——你写 `CMakeLists.txt` 描述"有哪些源文件、依赖什么库、生成什么目标",CMake 生成对应平台的构建文件(Linux 下生成 Makefile/Ninja,Windows 下生成 VS 工程)。好处:跨平台、能管理复杂依赖、子目录模块化(每个模块一个 CMakeLists)、find_package 找第三方库。手写 Makefile 不跨平台、大项目难维护。

**追问:增量构建有什么坑?**
改了 CMakeLists(比如加了新源文件)后,如果只 `cmake --build` 不重新 `cmake` 配置,新文件可能没被纳入构建,导致"明明加了 .cpp 却 undefined reference"。改了构建描述要重新配置。

---

### D2. systemd 怎么管理一个服务?关键配置有哪些?

**答题要点**:写一个 `.service` 单元文件,关键字段:
- `ExecStart`:启动命令。
- `Type`:`simple`(进程前台运行,不自己 fork——配合"不手写 daemon")最常用。
- `Restart=on-failure` + `RestartSec`:崩溃自动重启 + 重启间隔,这是服务高可用的关键。
- `ExecReload`:reload 时执行什么(通常发 SIGHUP 触发热加载)。

常用命令:`systemctl enable --now`(开机自启 + 立即启动)、`start/stop/restart/reload`、`status`,日志用 `journalctl`。

**怎么答出深度**:systemd 把"后台化、崩溃重启、开机自启、日志收集、依赖管理"这些以前要手写一大堆代码的事全接管了。所以现代服务**不手写 daemon、不自己搞重启逻辑**,写成前台进程交给 systemd——分工更清晰、更可靠。

### P2.(最重的模块)你的配置热加载具体怎么设计的?

**答**:这是项目一最重的模块。
- **触发**:SIGHUP 信号,但我没用传统信号处理器,而是用 **signalfd 接进 epoll**(Channel 抽象第 3 次复用),在普通上下文处理。前提是先 `sigprocmask` block SIGHUP。
- **原子性**:load-then-swap——新 Config 完整构建好,用 `atomic<shared_ptr<const Config>>` 原子替换;读端无锁拿快照。构建失败保留旧配置回滚。
- **三档分类**(我的核心设计):A 档改内存即生效(如日志级别);B 档需重建资源(用 shared_ptr 重建,diff 时基准用旧配置);C 档不能热改的(改了兜回启动值 + 告警忽略)。
- 配置解析我**手写 key=value parser**,零依赖(用 YAGNI 否决了引入 JSON/YAML 库——配置就十几个简单键值,不值得加依赖)。

**踩的坑**:真跑时发现行尾注释(`key=value  # 注释`)没处理,value 把注释也读进去了,加了 inline 注释剥离修掉。

### P3. 你 main 重构成 Reactor 后,热加载怎么和事件循环融合?

**答**:主线程 Reactor 化——串口 fd + signalfd 都做成 Channel 挂在同一个 EventLoop 上。SIGHUP 来了,signalfd 可读,在 loop 线程里处理热加载,和正常 I/O 事件统一调度,没有单独的信号处理线程。热加载里替换资源(如 MqttClient 不可移动)用**指针替换**绕过。

---

### P4. 你的调试排查实际用过这套工具吗?

**答**:用过。排查链是先看 core dump 用 GDB 判崩溃类型 → 内存错误上 ASan 精确定位 → 偶发的内存问题用压测逼出来再抓。项目里几个 UAF(Reactor 的 Channel 延迟销毁、task 持有 db 的析构顺序)就是这么定位的。

---

### P5. 你的 systemd 部署有什么细节?

**答**:`deploy/` 放在**项目根目录**(不是 src/ 里,因为它是部署产物不是源码)。`Type=simple`(配合不 fork 的 main)、`Restart=on-failure` + `RestartSec=3`、`ExecReload` 发 SIGHUP 接到 M2 的热加载闭环。**源(deploy/ 里的模板)和生效(/etc/ 下的实际配置)分离**——改 deploy/ 不影响运行,部署时才拷到 /etc/。已经 `enable --now` 实际跑通,日志走 journalctl。

**这能讲出的点**:source vs deployed 分离、配置文件不进 git 的运行位置、reload 不重启——这些是"代码"和"运维"的边界,体现我把项目当真服务在做,不只是跑通 demo。
