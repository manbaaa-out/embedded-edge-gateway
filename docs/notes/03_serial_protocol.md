# 第一部分:纯面试(通用知识,最重要)

## 主题 A:Linux 串口编程(termios)

### A1. Linux 下怎么配置一个串口?核心是什么结构?

**答题要点**:核心是 `struct termios`。流程:`open` 设备文件(如 `/dev/ttyUSB0`)拿到 fd → `tcgetattr` 读出当前配置 → 修改 termios 各字段 → `tcsetattr` 写回。termios 有四组 flag:
- **c_cflag**(控制):波特率、数据位、停止位、校验位。
- **c_iflag**(输入):输入处理(如是否转换 CR/LF、是否软件流控)。
- **c_oflag**(输出):输出处理。
- **c_lflag**(本地):**最关键的是 canonical(规范)模式 vs raw(原始)模式**。

**怎么答出深度**:配 flag 要用**读-改-写**(read-modify-write):先 `tcgetattr` 读出来,只改自己关心的位(用 `&= ~` 清、`|=` 置),再写回。不能整个结构体硬塞,否则会破坏其他没动的配置。

---

### A2. canonical 模式和 raw 模式区别?串口收二进制协议帧该用哪个?

**答题要点**:
- **canonical(规范/行模式)**:内核按"行"缓冲,遇到换行才把整行交给 read,还会处理特殊字符(退格、Ctrl-C 等)。适合终端交互。
- **raw(原始模式)**:内核不做任何加工,收到字节原样交给应用。

**收二进制协议帧必须用 raw**:因为协议帧里任何字节都可能出现(包括恰好等于换行 `0x0A`、退格的值),canonical 模式会错误地把它们当控制字符处理,破坏数据。raw 模式才能保证"收到什么字节就是什么字节"。

**追问:VMIN 和 VTIME 是干什么的?**
raw 模式下控制 read 的阻塞行为。`VMIN`=最少读够几个字节才返回,`VTIME`=超时(0.1 秒为单位)。`VMIN=1, VTIME=0` 表示"至少读到 1 字节就返回、无超时",是最常用的"有数据就拿"配置。

## 主题 B:协议分帧与状态机

### B1. 串口/TCP 是字节流,怎么从里面切出一个个完整的"帧"?

**答题要点**:设计一个**带定界的帧格式** + 一个**状态机(FSM)** 逐字节解析。典型帧格式:
**帧头(同步字)+ 长度域 + 类型 + payload + 校验(CRC)**。
状态机按字段推进:等帧头 → 读长度 → 读类型 → 读 payload → 读校验 → 校验通过则交付一帧。

**为什么需要这套**:字节流**没有天然的消息边界**(传输层怎么分批和协议怎么分帧无关,见 UART 卡 B1)。必须靠协议自己定界——帧头标识开始、长度域告诉还要读多少。

---

### B2. 解析时遇到半包、粘包、错帧怎么办?

**答题要点**:
- **半包**(一帧没收全):FSM 停在中间状态,`state` 保持不重置,等下一批字节续上。
- **粘包**(一次来了多帧):FSM 解析完一帧后自动回到"等帧头"状态,接着解下一帧。
- **错帧/垃圾字节**:这就是 **resync(重新同步)** ——如果在"等帧头"状态遇到的字节不是帧头,直接丢弃继续找;如果 CRC 校验失败,丢弃整帧、回到等帧头。

**怎么答出深度**:FSM 的健壮性全在 resync——线路有干扰、上电时收到半截帧、发送端出错,都靠"对不上就丢弃、重新找帧头"自愈。**容错不能砍**:三种现实场景(线路干扰、发送端出错、上电半截帧)都会产生垃圾字节,没有 resync 解析器会卡死。

**措辞陷阱**:长度域要做**范围校验**(如 1–64)。如果 `LEN==0`,下游算 `len-1` 时 `uint8_t` 下溢成 255,直接灾难。必须在读长度的状态就早检查,保证下游契约 `len>=1`。

---

### B3. CRC 校验是什么?为什么收发两端必须算法完全一致?

**答题要点**:CRC(Cyclic Redundancy Check,循环冗余校验)是把一段数据按多项式运算出一个固定长度校验值,附在帧尾;接收端用同样算法重算,对不上说明数据在传输中被损坏。

**为什么必须完全一致**:CRC 是收发两端的"合同"——多项式、初值、是否反射输入输出、字节序,任何一个参数不一致,两端算出的值就不同,所有帧都会被判为错帧。所以移植/重写 CRC 时必须逐字节照搬,不能"顺手优化"。

**追问:CRC 计算范围一般怎么定?**
典型不含帧头(固定同步字,损坏在帧头识别阶段就丢了)、不含 CRC 自身。范围差一字节是隐蔽的镜像 bug,必须用**标准测试向量**(已知输入→已知 CRC)交叉验证。

## 主题 C:RAII 资源管理(串口 fd 是典型例子)

### C1. 一个管理系统资源(如文件描述符)的 C++ 类,RAII 该怎么设计?

**答题要点**:**构造即获取、析构即释放**。对持有 fd 的类:
- **构造函数**:`open` 拿 fd,失败就抛异常(对象不会处于半残状态)。
- **析构函数**:`close` fd,标 `noexcept`(析构不该抛异常)。
- **禁拷贝**:`= delete` 拷贝构造和拷贝赋值——两个对象持有同一个 fd,析构会 double-close。
- **支持移动**:移动构造/移动赋值,把 fd 的所有权转移,源对象 fd 置为 -1(失效标记),这样源对象析构时不会误关。

**怎么答出深度**:这是 **Rule of Five** 的实战——一旦你自定义了析构(管理资源),就得考虑拷贝和移动。资源类的标准答案是"禁拷贝 + 允许移动",即**独占所有权可转移**,语义上像 `unique_ptr`。

**追问:移动赋值要注意什么?**
**自赋值保护**:`if (this == &other) return *this;`,以及移动前先释放自己已持有的资源(否则旧 fd 泄漏)。

# 第二部分:和项目挂钩(我具体怎么做的)

### P1. 你的 SerialPort 类完整设计?

**答**:`explicit` 构造(path+baud,explicit 防隐式转换)+ try-catch-throw 三件套 + noexcept 析构 + `=delete` 禁拷贝 + noexcept 移动构造(成员初始化列表)+ 移动赋值(含自赋值保护)+ const noexcept 的 getter + private `configure()` 做 4 个 flag 字段的 read-modify-write + `VMIN=1,VTIME=0` + 波特率参数化。我用 strace 验证过:禁拷贝是编译期拦截的、移动后只有 1 次 close(没 double-close)。后来方案 B 又给它加了非阻塞 write。

---

### P2. 你的协议帧格式具体是什么?

**答**:帧头 `0xAA55` / LEN 1 字节(1–64)/ TYPE 1 字节 / payload / CRC16-MODBUS(多项式 0xA001,初值 0xFFFF,反射输入输出,小端写)。8 状态 FSM:WAIT_HEADER1 / HEADER2 / LEN / TYPE / READ_PAYLOAD / CRC_LO / CRC_HI / DELIVER,switch-case 实现,所有错误路径 resync。CRC 用查表法 256 项,标准向量验证通过。

---

### P3. 这个模块踩过什么典型 bug?

**答**,几个都很典型:
1. **switch fall-through**:有个 case 漏写 `break`,fall-through 到下一个 case。后来开 `-Wimplicit-fallthrough -Werror` 让编译器拦截。
2. **FSM "先判断后消费" 写反**:应该是"先消费当前字节再判断状态",我写成先判断导致字节丢失、FSM 卡死。
3. **uint8_t 下溢**:LEN==0 时 `len-1=255`,靠 WAIT_LEN 状态早检查拦掉。
4. **集成测试抓出单测漏的 bug**:E2E 测试发现心跳路径上 `payload_buffer` 没重置——这印证了测试金字塔,单测覆盖不到的集成路径 E2E 能抓到。
