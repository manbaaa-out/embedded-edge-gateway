# 第一部分:纯面试(通用知识,最重要)

## 主题 A:应用层 Buffer

### A1. 为什么 TCP 网络编程需要一个应用层的 Buffer?内核不是有缓冲区吗?

**答题要点**:**TCP 是字节流,没有消息边界**。一次 `read` 读到的可能是半个 HTTP 请求(半包)、也可能是一个半请求(粘包)。应用层必须有个 Buffer 把读到的字节**攒起来**,等攒够一个完整的协议单元再解析。内核缓冲区只管"传输",不懂你的应用层协议边界,所以分帧/拆包必须应用层自己用 Buffer 做。

**怎么答出深度**:这和串口协议帧、UART 是同一个问题——**传输层分批和协议层分帧是两套独立边界**。Buffer 就是吸收这个不匹配的地方:read 进来多少先收着,解析器按协议边界从 Buffer 里切。

---

### A2. 一个高效的 Buffer 怎么设计?读写指针怎么管?

**答题要点**:**双游标**——`readIndex`(读位置)和 `writeIndex`(写位置)。
- 数据写入:从 writeIndex 往后写,writeIndex 前移。
- 数据读取:从 readIndex 往后读,readIndex 前移。
- `[readIndex, writeIndex)` 是可读数据,`[writeIndex, end)` 是可写空间。

空间不够时两步:先看**腾挪(compaction)**——把已读部分(readIndex 前面的)的空间回收,把未读数据搬到开头;腾挪后还不够才 **resize 扩容**。这样避免每次都扩容、复用前面已读空间。

**追问:为什么不直接每次扩容?**
频繁扩容要重新分配 + 拷贝,开销大。腾挪只在 buffer 内搬一次未读数据,把前面已消费的空间循环利用——大多数情况腾挪就够了,扩容是兜底。这是空间复用 vs 重新分配的权衡。

## 主题 B:HTTP 请求解析状态机

### B1. 一个 HTTP 请求的结构是什么?怎么用状态机解析?

**答题要点**:HTTP 请求 = **请求行**(`GET /path HTTP/1.1`)+ **请求头**(若干 `Key: Value`,空行结束)+ **请求体**(可选,长度由 Content-Length 或分块编码决定)。

四状态 FSM:**ExpectRequestLine → ExpectHeaders → ExpectBody → GotAll**。
- 请求行、头都是**面向行**的(以 `\r\n` 分隔),从 Buffer 里找 `\r\n` 切一行处理。
- 头解析完(遇到空行)后,看有没有 Content-Length 决定要不要进 ExpectBody。
- 收齐 body 后到 GotAll,交付一个完整请求。

---

### B2. 解析 HTTP 头有哪些细节坑?

**答题要点**:
1. **header key 大小写不敏感**:`Content-Length` 和 `content-length` 等价,要**归一化**(统一转小写)再比较/查找。
2. **Content-Length 解析要容错**:用 `std::stol` 转数字,但要 `try-catch`——字段是非法字符串(攻击或脏数据)时 stol 会抛异常,不能让它崩掉整个服务。
3. **半包**:一行 `\r\n` 还没收全时,FSM 停在当前状态、`state` 不重置,等下次 read 补上。

**措辞陷阱**:别说"按 `\n` 切行"。HTTP 行尾是 `\r\n`(CRLF),要按 `\r\n` 找,只按 `\n` 会在行尾留个 `\r`。

---

### B3. keep-alive 连接上一个请求处理完,解析器怎么复用?

**答题要点**:提供一个 `reset()` 把 FSM 状态清回 ExpectRequestLine、清空本次请求的临时数据,这样同一个连接上的下一个请求能接着解析。HTTP/1.1 默认 keep-alive(一个 TCP 连接发多个请求),不能解析完一个就把解析器扔了。

# 第二部分:和项目挂钩(我具体怎么做的)

### P1. 你的 Buffer 具体怎么实现的?

**答**:手写,双游标(readIndex/writeIndex),空间不够先 `makeSpace` 腾挪(把未读数据搬到开头、回收已读空间)、再 resize 扩容。支持半包拼接——一次没解析完的留在 Buffer 里,下次 read 追加。

---

### P2. 你的 HTTP 解析器和 Buffer 怎么接进事件循环的?

**答**:接在 M7 的 EventLoop 上。fd 是 **ET 模式**,所以读事件来时**循环 read 直到 EAGAIN**(把内核缓冲读干净);读到的字节进 Buffer;然后一个**内层 while** 循环:只要 Buffer 里还能解析出完整请求就接着解(处理 **pipelining**,一次 read 里可能有多个请求)。

**这里有个 UAF 坑**:处理完一个连接的请求后如果要关连接,我用的是"先 erase(从管理结构移除)再 return",避免在循环里继续访问已经准备销毁的连接对象——和 Reactor 卡的延迟销毁是同源问题。

---

### P3. 头解析的归一化和容错你都做了吗?

**答**:做了。header key 统一转小写归一化;Content-Length 用 `stol` + `catch` 容错(非法值不崩);行尾严格按 `\r\n` 切;keep-alive 用 `reset()` 复用解析器。写了 7 个单元测试覆盖这些路径,全绿;curl 实际请求也全部通过。

---

### P4. 你为什么没做 HTTP 路由和静态文件服务?

**答**:**主动砍的,不是没做完。** 我这是边缘网关,HTTP 接口只用于"暴露监控/状态查询"这种少量端点,不是个 Web 服务器。路由表、静态文件服务对网关主线没价值,做了是为凑功能而凑功能。所以我解析到"能拿到完整请求"就够了,直接进下一阶段(存储)。这是 YAGNI——避开了"WebServer 烂大街"的陷阱,把精力放在网关真正的主线(协议、Reactor、存储)上。

**这能讲出的点**:知道"什么不做"和知道"做什么"一样重要。面试官问"为什么不做 X"时,能答出"评估过、对主线无价值所以主动不做"比"没来得及"强得多。
